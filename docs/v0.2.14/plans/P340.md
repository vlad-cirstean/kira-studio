## Fix 1: Docker restore UI

### Root cause

`packages/docker-ui/src/components/RestoreBanner.vue` puts the Review button in `AlertAction`.
`AlertAction.vue` is `absolute top-2 right-2`. `alertVariants` (`packages/theme/src/components/ui/alert/index.ts`)
reserves only `has-data-[slot=alert-action]:pr-18` (72px) for it. The label "Review containers" with
`size="kira"` (`px-3`) is wider than 72px. In the narrow Docker side panel the banner body runs under
the button: text and button overlap. The `starting` status is an inline `<span>` glued to the body
with no separator, so it adds to the cramped wrap.

In `RestoreDialog.vue` the "Already running (n)" disclosure is a bare `variant="toolbar"` button with
no chevron: it does not read as an expandable section. Row labels have no `min-w-0`/truncate, so a long
container name pushes the waiting status off the row.

Declined: widening `pr-18` in the theme `alertVariants`. 15 other `AlertAction` callers would shift, and
a fixed reserve breaks again for any longer label. The fix keeps the action in normal flow instead.

### Changes

- One in-flow wrapper as the Alert's only content child (grid column 2):
  `<div class="flex flex-wrap items-center gap-x-3 gap-y-1.5">`.
- `AlertDescription class="min-w-0 flex-1 basis-48 flex flex-col gap-0.5"`. Body in a
  `<span>`; starting status in its own `<span class="text-kira-sm" data-testid="docker-restore-starting">`.

## Fix 2: Redis + S3 browse navigation disappears on double-click

### Root cause

`apps/kira-studio/frontend/src/views/browse/BrowseView.vue` `onRowOpen` (line 232):

```ts
if (node.hasChildren) { void browseViewStore.descend(props.tab.id, node.path); return; }
if (!props.tab.connectionId) return;
tabsStore.openKeyValueTab(props.tab.connectionId, node.path);
```

Row `@dblclick` and list Enter (`useListNavigation` `onOpen`) both call it. On a leaf (Redis key,
S3 object) `openKeyValueTab` -> `createTabsStore.openTab` inserts a new tab and calls
`setActiveTabId`. The browse tab, with its back button, breadcrumb and folder list, is replaced on
screen by a standalone KeyValue tab: the navigation vanishes. That predates P63's split. The split's
detail pane (`browse-detail-pane`, `KeyValuePane` on `${tabId}::preview`) already shows the selected
leaf in place, so the tab switch is redundant.

Folder rows (`descend`) and breadcrumb buttons (`@click` only, no dblclick handler) keep the browse
tab active. `setLevel` keeps the old `nodes` until the new level arrives, so the list does not blank.
Implementer: confirm first with the new spec (red before the fix). If a folder-row dblclick also loses
the nav, root-cause that before changing anything else.

### Changes

`apps/kira-studio/frontend/src/views/browse/BrowseView.vue`
- `onRowOpen`: leaf branch calls `onRowClick(node)` (select: preview pane shows it) instead of
  `tabsStore.openKeyValueTab`. Folder branch unchanged. Update the D12 comment above it in one line:
  a leaf previews in the split; context menu Open / Open in new tab opens a standalone tab.
- Context menus (`views/browse/menu.ts` `keyRowMenu`/`objectRowMenu` `openItems`) unchanged: they stay
  the explicit way to a standalone KeyValue tab.
- Project tree (`project/ProjectTree.vue` `onOpen`) unchanged: its dblclick opening a tab is the tree's
  own primary action, not the browse nav.
