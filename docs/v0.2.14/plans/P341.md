# P341 plan: remove sandbox keychain option and alternative token paths

Base: `6bf4af1`. One sequential Sonnet implementer; no stream split (Go policy, wire and frontend
changes form one dependency chain).

## Decision

Sandboxed agents always reach the macOS keychain. Every profile renders today's `keychain=true`
branch: no `keychain` mach-lookup deny section, `~/Library/Keychains` readable, no trailing
keychain read deny. `protectWrites` keeps denying file writes under `~/Library/Keychains` (unchanged;
`keychain_on` golden already has it). Policy guard keeps refusing `read`/`allow` entries that cover
the keychain dir (parser, `stepSandbox.ts`, `policy.go` guard unchanged): user paths never widen it.

"Alternative token injection" in this repo is advice only, no code: the
`claude setup-token` / `CLAUDE_CODE_OAUTH_TOKEN` hint in the auth-failure reason, the settings
description, site docs, `DEV_ENVIRONMENT.md` and a test comment. All go. The auth-failure mapping
(`AuthReason`, `IsAuthFailure`) exists only to explain a keychain denial, so it goes too; a sign-in
failure now surfaces as the agent's own error like any other failure.

`internal/harness/claude/structured.go:28` (`--bare` / `ANTHROPIC_API_KEY` comment) is about
unsandboxed structured calls: out of scope, untouched.
