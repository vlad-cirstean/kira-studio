| P294 | Test and CI speed. Goal: cut PR CI wall time and local test time sharply; planner decides every deferred point. Evidence (PR #2 run 22, `.github/workflows/pr.yml`): critical path is `wails-linux-cli` (1.5 min) then `checks (Linux)` (4 min, `typecheck` alone 1 min 50 s) then `ui` and `container-tests` in parallel (10 min and 9 min); `ui` and `container-tests` `needs` all three check jobs, so they idle until lint, typecheck and macOS finish. `test:ui:studio` took ~8 min before failing, and the `ipc-frontend` and `visual` steps run serially after it in the same job. `container-tests`: `docker load` of the cached image tar ~80 s, Go tests ~5.5 min, `test:unit` 12 s. Every Linux job repeats `apt-get install` of GTK4/WebKitGTK (~30 s), `setup-go` (~20 s) and `bun install`. Scope (1) CI: remove needless `needs` edges so test jobs start at once; split `ipc-frontend` and `visual` into own jobs; shard Playwright (`--shard`) across runners; cache the apt packages, the Go build and test cache and the Playwright browsers; avoid the `docker load` tar (pull in parallel, or smaller images); share one setup via a composite action instead of copy-pasted steps (workflow edits go through `docs/pending-workflows/`, see `docs/DEV_ENVIRONMENT.md`). (2) Tests: measure per-spec and per-package duration (Playwright JSON reporter, `go test -json`), list the slowest, then fix causes: fixed sleeps and long timeouts, `retries`, serial `workers: 1` projects, per-test app/DB/container setup that can be shared, duplicate coverage between flow tests and UI specs, `-count` or `-race` overuse, Testcontainers started per test not per package. Split a fast default tier from the slow tier where a test cannot be made fast. (3) This box: check why local runs are slow (4 cores, 15 GB; Playwright `workers: '100%'`, Docker, `build:test:studio` rebuilt on every run, cold Go and bun caches, hooks running the whole suite) and fix or document in `docs/DEV_ENVIRONMENT.md`. Record before and after timings in the plan result. Decline nothing silently: name each rejected option and its reason. | Done (CI half pending the pr.yml patch) |
| P295 | Release flow speed; publish, not draft. Goal: cut tag-to-release wall time and publish the release directly. Evidence (`.github/workflows/release.yml`, trigger `push` of tags `v*.*.*`): jobs `test-matrix` and `db-compat` (ubuntu, timeouts 30 and 60 min) run first, then `release` (macos-15, `needs` both, timeout 60 min) builds, signs and packages and ends in a `gh release create --draft` step (~line 213). Recent runs take ~15 to 31 min (run 10: 31 min; run 11 for tag `v0.2.6` was still running at 18 min). Scope (1) Speed: measure per-job and per-step times from the last successful release runs (GitHub Actions API); remove duplicate work against the PR workflow (the tagged commit already passed PR CI: decide whether `test-matrix` and `db-compat` must rerun on a tag at all, or can be replaced by a check that the commit's PR checks passed); start the macOS build in parallel with the tests and gate only the publish step on them; reuse the setup action and caches from P294 (`.github/actions/setup`, Go build cache, bun cache); avoid rebuilding what PR CI built. (2) Publish: the release is created already published, not draft, but only after the tests pass and the assets are uploaded and verified (create it as the last step, or upload to a draft and publish in a final step; planner decides). (3) Failure safety: a failed gate must not leave a published release; state how a bad tag is handled. Workflow edits go through `docs/pending-changes/` (see `docs/DEV_ENVIRONMENT.md`). Record before and after timings. Name each rejected option and its reason. | Done (pending the release.yml patch) |
