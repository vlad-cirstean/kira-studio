## P333: DB MCP: prominent target database and response preview

- The approval UI shows which database the query will run on as prominently as the query itself: connection name, kind, database, environment/read-only state, large and unmissable.
- New setting: show a response preview. When on, the approval step shows exactly what the AI will receive for the query, as a table, with table masking already applied.
- Scope: `DbMcpApprovalDialog.vue` and the MCP request path in `apps/kira-studio`. Planner decides whether this splits into Part 1 (target prominence) and Part 2 (preview setting); a split keeps the number per `CLAUDE.md`.
- Preview must run the same code path as the real answer, never a parallel reimplementation. Planner states how a preview can run without a double-execution side effect (read-only verdict only, or run once and hold the result for the approved send).

Result: Shipped in six commit groups, no split. Every approval request carries an `ApprovalTarget` (connection colour, read-only flag, host, effective database or file path, statement class); `ApprovalTarget.vue` renders it as a banner above the query for both stages. New setting `dbMcp.previewResponses` (default off, Settings > Database MCP). When on, `run_query` executes after the query-stage approval, then holds the exact result in a second response-stage request; Send returns the same result value untouched, so the preview is the real code path and runs once. Withhold, timeout, abandon and a full queue return an app-authored error with no row data. Execution comes before review because pre-running would defeat the query gate and a transaction held across a human wait keeps locks (and Redis, Kafka, SQS, S3 cannot roll back); a withheld write has already run and the dialog says so. Snapshots carry only `{isError, bytes}`; `DbMcpService.PendingResponse` serves the text. `ApprovalResponse.vue` parses the held bytes into a virtualised shadcn Table (masked columns marked) with an As sent tab; it never re-renders. Approve re-checks the mask set (`mask.Set.Equal`) and withholds if rules changed during review. The setting read fails closed. Go-sdk v1.8.0 assumption resolved: a plain handler error becomes an `IsError` text result carrying `err.Error()`, so the preview shows what the client gets. Only `run_query` is reviewed. Checks: `go test -race` for dbmcp, bridge, mask, dbmcpflow; all flow tests at `-count=2` and contracts stable; `bun run test:ui:studio` 596 passed; `bun run test:claude:studio` passed (preview off by default); full pre-commit hook on every commit. Out of scope: explain/describe/list review, per-connection setting, undo of a withheld write, editing the result, prompt registry changes. User still: checks the banner on a Mac in light and dark themes, compares the preview table to what Claude quotes, and raises `MCP_TOOL_TIMEOUT` if needed (two stages can hold a call up to 4 minutes).

## P334: Docker: restore running containers after an engine/VM restart

- Snapshot the running container set (ID, name, image, Compose project and service, Docker context) while the engine is healthy. Skip ephemeral origins (`testcontainers`, `buildx`, `kind`).
- Detect an engine/VM restart: the `internal/docker/events.go` stream drops (`unavailable`) then recovers (`ok`). Confirm it is a restart, not a socket blip or context switch, via engine boot identity (daemon ID, system time) and container `StartedAt`; planner picks the exact signals.
- Never let the post-restart empty state overwrite the snapshot. Keep "last known running" until the user restores or dismisses.
- After a restart, offer to start the containers the engine did not bring back itself (restart policy `always`/`unless-stopped` already does). Compose projects start together. Also compare snapshot with the running set at app launch for a restart that happened while Kira was closed.
- Deleted containers are listed as gone, not recreated. Boot-time restore (login item/helper) is out of scope.
- Planner decides the DB home of the snapshot, whether restore is click-only or automatic (default click-only unless told otherwise), and tests (`dockerflow` flow test plus UI spec).

Result: Shipped in nine commits, no split. Backend tracker (`internal/docker/restore*.go`) runs from app start without a window: 15 s tick while the engine answers, 30 s while it does not; remote (tcp/ssh) endpoints tick only while the events watcher has a window. Boot identity is (Info.ID, default bridge network ID): the bridge ID changes on every daemon start and survives live-restore. Snapshot rules: stopped container leaves after a 30 s grace, pending is frozen, an unreachable engine never writes, testcontainers/buildx/kind/kubernetes/swarm/`--rm` excluded. Stored in migration 0044 (`docker_restore_engines`, `docker_restore_containers`, pruned at 30 days) via `DockerRestoreRepo`. Bound calls `RestoreState`, `RestoreContainers`, `RestoreDismiss`; push channel `kira:docker:restore`. Restore is click-only: standalone containers first, then each Compose project in `depends_on` order, waiting up to 60 s on `service_healthy`. Banner shows only inside the Docker module; query key `['docker-restore']`. Deleted containers list as gone. Real callers: `events.go` kicks the tracker, `Manager.useContext` calls `contextChanged`, `appwire` calls `StartRestoreBound`/`StopRestoreBound`, `RestoreBanner.vue` uses `useRestoreState`, `RestoreDialog.vue` uses `useRestoreContainers`/`useDismissRestore`, `useDockerLiveSync` handles `onRestore`. Deviations: reconcile split into helpers after gocognit 37; tracker stops in appwire Teardown before the DB closes (else "database is closed" warnings); an all-gone snapshot clears pending, so that flow test was redesigned. Checks: `go test -race` dockerflow (7 restore tests) and `internal/docker`; `TestRestoreRealDaemonRestart` against the sandbox dockerd (`KIRA_FLOW_DOCKER_RESTART=1`) passed; contracts written; `bun run test:ui:studio` 595 passed, 3 failed under 12-worker load (list-keyboard:351, slick-grid:572, tooltips:459, all unrelated files) and all 3 pass on isolated rerun; full pre-commit hook on every commit. User still: on a Mac with Docker Desktop, Colima and OrbStack, restart the VM with Kira open in another module, then repeat with Kira quit during the restart, and confirm the bridge ID changes. Open limits (`ARCHITECTURE.md`): engines without a default bridge detect a restart only via an outage seen in-session; restart while Kira is closed followed by a CLI stop is not offered.

## P335: SQL grid: context-menu "Copy as" with multiple rows selected

Planner reproduces it first (UI spec, real clipboard read), finds why the menu path differs from the shortcut path, and fixes it so both share one code path. Backend-or-UI split per the new-feature test rule applies only if a bound call is involved.

Result: Root cause: console `onGridContextMenu` had no `row` case on a body hit. A gutter row selection plus right-click on a cell fell through to the single-cell menu, so every Copy item wrote one cell (NULL wrote ''). Keyboard and menu each decided "what does this selection copy" separately. New `views/shared/slick/selectionCopy.ts` (`selectionText`, `rowsText`) is the one path. Both grids' ⌘C go through `selectionText`; console menu builders take a `copy(format)` callback over it; data grid cell menu uses it and `rowMenu` uses `rowsText`. Console right-click acts on the selection when it covers the hit, else selects the hit first. Console `copy-column` copies every selected column; console cell copy now quotes through `tsvField`. Keyboard copy announces and reports a rejection in both grids. Data grid prints ⌘C on Copy rows ▸ TSV only for a row selection. New `tests/ui/grid-copy-menu.spec.ts` runs on Chromium (`ui-clipboard`, real clipboard) and WebKit (`ui`, pass-through `writeText` recorder). Proven on base: console fails at `menuCopy(cellAt(0, 0), 'copy-rows-tsv', 'copy-rows')` (no `menu-item-copy-rows` in the cell menu), data grid fails at `menu-item-copy-rows-tsv-shortcut` count 0 on a range; both pass after. Checks: pre-commit hooks clean on all commits; `lint:dead` clean; `grid-row-menu-lazy-snapshot.spec.ts` 4 pass unchanged; `bun run test:ui:studio` 606 passed on the clean rerun. First full run: 600 passed, 2 failed (`cell-editor.spec.ts:333` timeout, `http-history.spec.ts:28` "Page crashed", both WebKit under load, neither file touched); both pass in isolation and the full project passes on rerun with nothing else running.
