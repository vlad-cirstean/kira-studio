## 1. Engine facts measured for this plan

Measured on the sandbox `dockerd` 29.9.2 (API 1.56): containers plain, `--restart always`,
`--restart unless-stopped`, one stopped by hand; then graceful restart (SIGTERM), `--live-restore`
restart, and crash (SIGKILL dockerd, containerd, shims).

- `Info.ID` survives every restart (stored in `/var/lib/docker/engine-id`). It names the engine, not
  its boot.
- Default `bridge` network ID and `Created` change on every daemon start. `Created` equals daemon
  start time. With `--live-restore` and running containers, both stay the same, and containers keep
  running.
- Graceful shutdown emits `kill`, then `stop`/`die` for every running container about 11 s later
  (default stop timeout), about 3 s before the socket closes. Snapshot logic that trusts `die` events
  would empty itself right before every restart.
- After restart, `always` and `unless-stopped` containers are running again with a new `StartedAt`.
  Plain containers are `exited`: exit 137 after graceful shutdown, 255 after a crash. A container
  stopped by hand with `unless-stopped` stays stopped.
- Events since the restart hold only the new daemon's events (in-memory ring).

So: **boot identity = (`Info.ID`, default bridge network ID)**. `Info.ID` selects the snapshot;
a new bridge ID under the same `Info.ID` means the daemon restarted. Docker Desktop, Colima and
OrbStack run the same `dockerd` inside a VM, so a VM restart is a daemon start. Not verified on a
Mac (§8 Known open items).

## 2. Data model and persistence

### 2.1 Go (`internal/docker/restore.go`, new)

```go
type RestoreEntry struct {
    ID, Name, Image                 string
    ComposeProject, ComposeService  string
    ComposeDependsOn                string // raw com.docker.compose.depends_on label
    RestartPolicy                   string // no | always | unless-stopped | on-failure
    AddedAt                         int64  // ms
    StoppedSeenAt                   int64  // ms; 0 = running at last tick
}

type RestoreSnapshot struct {
    EngineID   string // Info.ID
    Context    string // Endpoint.Context at last update, display only
    Host       string // Endpoint.Host, display only
    BootID     string // default bridge network ID; "" = engine has none
    BootAt     int64  // bridge Created, ms
    State      string // "tracking" | "pending"
    DetectedAt int64  // ms, set when State becomes pending
    UpdatedAt  int64  // ms
    Entries    []RestoreEntry
}

// RestoreStore persists one snapshot per engine. Studio's repo implements it.
type RestoreStore interface {
    LoadRestore(engineID string) (RestoreSnapshot, bool, error)
    SaveRestore(s RestoreSnapshot) error // replaces the engine's row and entries in one tx
    PruneRestore(updatedBefore int64) error
}
```

Wire (bound result and push payload):

```go
type RestoreState struct {
    State      string        `json:"state"` // "none" | "pending"
    EngineID   string        `json:"engineId"`
    Context    string        `json:"context"`
    DetectedAt int64         `json:"detectedAt"`
    BootAt     int64         `json:"bootAt"`
    Items      []RestoreItem `json:"items"` // empty unless pending
}

type RestoreItem struct {
    ID, Name, Image                string
    ComposeProject, ComposeService string
    Status string `json:"status"` // restorable | waiting | back | gone
    Error  string `json:"error,omitempty"` // last Restore failure for this item
}
```

JSON tags camelCase like the rest of the package. `Items` sorted: compose project (natural), then
name; never nil.

## 3. Detection algorithm

### 3.1 Tracker lifecycle (`restoreTracker` in `restore.go`)

- Owned by `Manager` (`m.restore`), nil when no store is set. `docker.WithRestoreStore(store)`
  option. `docker.StartRestoreBound(b)` (package function, not a method: Wails binds methods) starts
  the loop; appwire calls it after building `dockerSvc`. `Manager.shutdown` stops it and waits.
- One goroutine. Ticks every 15 s while the engine answers, every 30 s while it does not.
- Remote endpoints (`Endpoint.Remote`, i.e. `tcp://`/`ssh://`): periodic ticks only while the events
  watcher has a window. A local socket costs nothing to poll; an ssh endpoint would hold an ssh
  session open all day.
- `kick()` (buffered chan of 1) runs a tick now. Callers: `eventsWatcher.run` on recovery (before the
  `ChannelChanged` emit); `eventsWatcher.stream` on a container `start`, `die` or `destroy` message
  (the tracker coalesces); `useContext`; `RestoreState` (synchronous, §4).
- Kira closed during the restart: the first tick at launch loads the stored snapshot and runs the
  same comparison. That is the "compare at app launch" path; no special case.

### 3.2 One tick

1. `Ping` + `Info`. Fail: record `unreachableSince` (memory only), return. **No write, no change.**
   An unreachable or empty engine never touches the snapshot.
2. `engineID = Info.ID`. `boot = NetworkInspect("bridge")` → `(ID, Created)`. Not found → `BootID ""`
   (§3.4).
3. `ContainerList(All: true)` → by ID and by name.
4. Load the snapshot for `engineID` (memory cache, DB on first sight). None → build a `tracking`
   snapshot from the running set (step 6 rules), save, done.
5. `State == "pending"`: frozen. Do not add or prune entries. Update `BootID/BootAt` if they moved
   (a second restart while pending). Recompute item statuses (§3.3). Every item `back` → clear
   (rebuild `tracking` from the running set). Emit `ChannelRestore` when the computed state differs
   from the last one emitted. Done.
6. `tracking`, `BootID` differs from stored and both are non-empty → **restart detected**. Compute
   item statuses over every entry, including those with `StoppedSeenAt != 0` (shutdown casualties).
   Any `restorable` or `waiting` → `State = pending`, `DetectedAt = now`, save, emit. Otherwise
   (all back, or only gone) → adopt the new boot and continue with step 7.
7. `tracking`, same boot → normal update:
   - Each running container not excluded (§3.5) and not in the snapshot → inspect once (restart
     policy, `AutoRemove`); `AutoRemove` → exclude; else add.
   - Each entry seen running → `StoppedSeenAt = 0`.
   - Each entry not running, or missing → set `StoppedSeenAt = now` if 0; remove when
     `now - StoppedSeenAt ≥ grace` (30 s). Removal needs at least two reachable ticks on the same
     boot, so a deliberate stop drops out and a shutdown casualty does not.
   - Save when anything changed. Update `Context/Host` on save.

### 3.3 Item status (pending)

Per entry, against the live list:

- ID present and running → `back`.
- ID missing, a container with the same name running → `back` (compose recreated it).
- ID missing otherwise → `gone`. Listed, never recreated.
- ID present, not running, restart policy `always` or `unless-stopped`, `now - BootAt < 60 s` →
  `waiting` (the daemon starts these itself, slightly after the socket opens).
- ID present, not running otherwise → `restorable`.

### 3.4 Engines without a default bridge

Windows engines, `--bridge=none`, some Podman sockets. `BootID ""` on both sides → fall back to an
observed outage. If this session saw the engine unreachable (`unreachableSince`) and it now answers,
treat it as a restart for entries whose container `FinishedAt` ≥ `unreachableSince - grace`.
`FinishedAt` comes from `ContainerInspect` on the not-running entries only. No launch-time detection
for these engines; documented as a Known open item.

### 3.5 Excluded containers

Never snapshotted: origin `testcontainers`, `buildx`, `kind` (SPEC), plus `kubernetes` and `swarm`
(their orchestrator restarts them; Restore would fight it), plus `AutoRemove` (`--rm`) containers
(the engine deletes them on stop; every restart would list them as gone). Devcontainers and Compose
stay in.

### 3.6 Edge cases

| Case | Outcome |
|---|---|
| Socket blip, no restart | Boot unchanged. Nothing offered. Stops during the blip prune after grace. |
| Flapping (down/up several times) | Pending is sticky. Each restart updates `BootID/BootAt` only. Items stay the snapshot taken before the first restart. |
| Docker Desktop / Colima / OrbStack restart | Same `Info.ID`, new bridge → pending. |
| Graceful shutdown `die` events | Entries get `StoppedSeenAt`. Socket closes within grace. Restart detection then includes them. |
| Daemon restart with `--live-restore` | Bridge unchanged, containers running. Nothing offered (correct). |
| Restart policy brought it back | `back` (or `waiting` during the first 60 s). Not offered. |
| User stopped containers via CLI while Kira was closed, no restart | Same boot. Pruned after grace. Not offered. |
| Restart while Kira closed, then CLI stops after restart | Indistinguishable. Offered. Click-only, so harmless. Documented. |
| Context switch | Different `Info.ID` → that engine's own snapshot. The other engine's stays untouched. Same engine via two contexts → same `Info.ID`, same snapshot. |
| Engine reset / reinstall | New `Info.ID`. Old snapshot orphaned, pruned after 30 days. |
| Engine down at launch | No tick succeeds. Snapshot untouched until it answers. |
| Container removed while engine healthy | Pruned after grace (deliberate). |
| Two Kira Studio instances | Single-instance app; not handled. |

## 4. Bridge API

On `BoundService` (bindings regenerate; `DockerService` embeds it, no new service, the
`TestHarnessBootsWithDefaultSettings` count does not change):

- `RestoreState() (RestoreState, error)` runs one tick synchronously, then returns the current
  engine's state. Engine unreachable → `{state: "none"}` from memory, no error. The UI calls it on
  module mount; flow tests call it instead of waiting for the timer.
- `RestoreContainers(args RestoreArgs{EngineID string; IDs []string}) (RestoreResult, error)`.
  `EngineID` ≠ current `Info.ID` → `E_CONFLICT`. Not pending → `E_CONFLICT`. An ID not a
  `restorable`/`waiting` item → `ipcerr.BadRequest`. Order: standalone containers in name order;
  each compose project in `depends_on` topological order (parse `service:condition[:required]`
  comma list; a cycle or unknown service falls back to name order). For a `service_healthy`
  dependency with a healthcheck, wait up to 60 s for `healthy` before its dependents; on timeout
  the dependents fail with "dependency <name> did not become healthy". Starts reuse `m.start`.
  Result: `{items: [{id, name, ok, error}]}`. Then recompute: no `restorable`/`waiting` left → clear
  to `tracking` (new boot). Failures keep `Error` on their item. Emit.
- `RestoreDismiss(args {EngineID string}) error` clears pending, rebuilds `tracking` from the
  running set on the current boot, emits. Same `E_CONFLICT` check.
- Push channel `ChannelRestore = "kira:docker:restore"` (`channels.go`), payload `RestoreState`,
  `Emit` to every window.

Compose "start together" means one selection unit and one call, in dependency order. No
`docker compose up`: no CLI dependency, and up would recreate changed services.

Restore is click-only. No auto-restore setting this phase (§10).

## 10. Open questions (recommended default in bold)

1. Auto-restore setting? **No. Click-only, no setting.** SPEC default; add later on request.
2. Notify outside the Docker module (mode-tab dot or toast) when a restart is detected? **No.** The
   banner shows on opening the module. A cross-module badge needs mode-tab infrastructure this phase
   does not own.
3. Track remote (`tcp://`, `ssh://`) engines in the background? **No, only while a window watches.**
4. Restore a stopped container whose ID is gone but a same-name container exists stopped?
   **No: `gone`.** Only a running same-name container counts as `back`.
5. Offer when only `gone` items remain? **No.** Gone items show only alongside something
   restorable.
6. Compose `depends_on` label (`com.docker.compose.depends_on`, Compose 2.17+) absent on older
   projects? **Name order.** Implementer confirms the label format against a real
   `docker compose up` if the CLI is in the sandbox; otherwise the flow test sets the label by hand.

## 11. Out of scope

Boot-time restore (login item, helper). Recreating deleted containers. Restoring paused state,
images, volumes or networks. `docker compose up`. Swarm, Kubernetes, Kind, Testcontainers, buildx and
`--rm` containers. Kira Space (no Docker module).
