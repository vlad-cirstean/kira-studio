### Summary

No release ever failed in `build` or `publish`. Every failure was a gate: `ci-gate` (v0.2.7, v0.2.8,
v0.2.11) or a container test (v0.2.1, v0.2.7, v0.2.8). Container causes were fixed in test code
(`d7efbe03f`, `5d2c3d482`, PR #5). P330's patch removes `ci-gate`. No failure cause remains in
`release.yml` itself.

## 1. Remaining fixes (release.yml only)

Reviewing P330's patched `release.yml` against these failure modes leaves three gaps. All live in
the `tag` job and `publish`.

- **F1 Off-main tag ships unchecked.** `ci-gate` was the only check that a tagged commit passed PR
  CI. P330 relies on the `main` ruleset instead (PACKAGING §7 step 2). A manual tag push on any
  commit (a chapter branch head, an unmerged commit) now builds and publishes with no CI at all.
  Fix: `tag` refuses a non-prerelease tag whose commit is not on `main` (compare API, one call, no
  polling). Prerelease tags (`vX.Y.Z-…`) stay allowed anywhere, as today.
- **F2 Already-published tag burns all runners before failing.** `publish` refuses a published
  release only after `build` (macOS, about 7 min) and the Linux jobs finish. A duplicate run (manual
  dispatch of a released tag, or push plus dispatch of the same tag) shows red after about 10 min.
  Fix: `tag` checks first and fails in seconds. `publish` keeps its own check (race between two
  queued runs).
- **F3 Rerun after a tag move publishes the old build.** On "Re-run failed jobs", the green `tag`
  job is not rerun; its `sha` output is reused. If the tag moved in between (v0.2.8 precedent),
  `build` rebuilds the old commit, and `gh release create --verify-tag` attaches those images to the
  moved tag. A push no longer triggers anything once releases come from dispatch. Fix: `publish`
  re-resolves the tag first and refuses when it no longer points at `needs.tag.outputs.sha`, naming
  the dispatch command for a fresh run.

Declined:

- Automatic retry of `test-matrix`/`db-compat`. Both flake causes were test bugs, now fixed, and
  green for 5 straight runs. A blind retry would hide the next real flake. "Re-run failed jobs" stays
  the manual path, and F3 keeps it safe.
- Pinning `ubuntu-24.04` instead of `ubuntu-latest`. The kernel 6.19 move happened inside the 24.04
  image, so a pin would not have stopped it.
- Waiting on PR CI in any form. Removed by P330 at the user's request.

## 2. Exact edits (on top of P330's patched file)

Graph comment: append two lines after P330's comment block, before `jobs:`:

```yaml
# P331: `tag` refuses an already-published release and a non-prerelease tag off main before any
# runner starts; publish refuses a tag that moved after `tag` resolved it.
```

`tag` job, `resolve` step: insert between the `printf … grep -Eq '^[0-9a-f]{40}$'` line and
`echo "tag=$TAG" >> "$GITHUB_OUTPUT"`:

```yaml
          if gh api "repos/$GH_REPO/releases/tags/$TAG" --jq .draft 2>/dev/null | grep -qx false; then
            echo "release $TAG is already published; not overwriting" >&2
            exit 1
          fi
          # Replaces the dropped ci-gate: main takes only PR merges, so a main commit passed PR CI.
          case "$TAG" in
            *-*) echo "prerelease $TAG: main ancestry not required" ;;
            *)
              STATUS="$(gh api "repos/$GH_REPO/compare/$SHA...main" --jq .status)"
              case "$STATUS" in
                ahead | identical) ;;
                *) echo "tag $TAG at $SHA is not on main (compare: $STATUS); only a merged commit ships" >&2; exit 1 ;;
              esac
              ;;
          esac
```

`compare/{base}...{head}` reports `ahead` when base is an ancestor of head, `identical` when equal;
`behind`/`diverged` mean the commit is not on `main`. The job keeps workflow-level
`contents: read`, which covers releases, refs and compare.

`publish` job: new first step, before "Download the disk images and check their hashes":

```yaml
      # A rerun of failed jobs reuses `tag`'s outputs; a tag moved since then would get the old build.
      - name: Refuse a tag that moved after this run resolved it
        env:
          SHA: ${{ needs.tag.outputs.sha }}
        run: |
          set -eu
          read -r TYPE NOW <<EOF
          $(gh api "repos/$GH_REPO/git/ref/tags/$TAG" --jq '.object.type + " " + .object.sha')
          EOF
          if [ "$TYPE" = tag ]; then NOW="$(gh api "repos/$GH_REPO/git/tags/$NOW" --jq .object.sha)"; fi
          if [ "$NOW" != "$SHA" ]; then
            echo "tag $TAG moved from $SHA to $NOW after this run started; start a new run: gh workflow run release.yml -f tag=$TAG" >&2
            exit 1
          fi
```

`publish` already has `GH_TOKEN`, `GH_REPO` and `TAG` (= `needs.tag.outputs.tag`) in job `env`.
The peel logic duplicates `tag`'s three lines on purpose: neither job checks out the repo, and a
checkout only to share three lines costs more than it saves.

Nothing else changes. `publish`'s "Refuse an existing release, clear a leftover draft" step stays.
