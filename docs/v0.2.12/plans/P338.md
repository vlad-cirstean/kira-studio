# P338: DB MCP: focus the Kira DB window when an approval appears

Planner: Opus. Implementer: one Sonnet subagent, sequential. Base: `be2c902f3`.

No split. Four small commit groups (§7), each depends on the one before. Diff stays small: one
router policy, one shell helper, Studio wiring, one setting, tests, docs.

"Kira DB" in the ask is the Studio app (`apps/kira-studio`, window title "Kira Studio").

## 0. What exists (CodeGraph findings)

Approval path:

- `dbmcp.ApprovalBroker.Request` (`apps/kira-studio/internal/dbmcp/approval.go:204`) enqueues one
  `ApprovalRequest` per stage. P333's response stage is a second `Request` with
  `Stage: ApprovalStageResponse`. Heavy-read prompts use the same broker.
- `Request` calls `openPrompt` under `b.mu`. `openPrompt` calls `prompts.Sink.Open` with kind
  `dbmcp`, `Ref` = request id, `CreatedAt` = `EnqueuedAt`. `resolve` and `AbandonAll` call
  `closePrompt`, so approve, deny, timeout, abandon and server stop all go through `Router.Close`.
- `prompts.Router` (`internal/prompts/router.go`) is the P246 popup router, shared by both apps.
  - `Open` sends one OS notification per kind when the target window is not `Focused`.
  - `RevealKind(k)` handles a notification click. It finds the oldest prompt of kind `k`, calls
    `Deps.Reopen` when no window is registered, then `Windows.Focus(target)`, then
    `Deps.Reveal(target, id)` (push `kira:prompts:reveal`).
  - `Deps.Windows` is `Windows{MainKey, Has, Focused, Focus}`. Studio passes
    `*shell.WindowRegistry` (`apps/kira-studio/internal/appwire/wire.go:267` `newPromptRouter`).
- `shell.WindowRegistry.Focus` (`internal/shell/registry.go:148`) runs `Show`, `UnMinimise`,
  `Focus` on the Wails window. Each wraps `InvokeSync`, so any goroutine may call it. Kira Space
  `FocusSession` uses the same method.
- Closing Studio's last real window hides it (`closeDecision`, `closeflush.go:156`). Its registry
  entry stays, so `Focus` → `Show` brings it back. `Reopen` only runs when no window is registered.
- `PromptHost.vue` shows the revealed prompt, else the oldest one targeted at its window.
  `DbMcpApprovalDialog.vue` renders only when `pending.requestId === entry.ref` (broker head). The
  broker is FIFO and `CreatedAt` is `EnqueuedAt`, so the kind's oldest prompt is the head. Revealing
  a non-head `dbmcp` id would render nothing; `RevealKind` reveals the oldest, which is correct.
- The dialog focuses Deny on mount; Escape denies. A keystroke the user meant for another app, landing
  after a focus steal, can only deny, never approve.

Wails v3 (`v3.0.0-beta.28`, `pkg/application`):

- darwin `windowFocus`: if `![NSApp isActive]` → `[NSApp activateIgnoringOtherApps:YES]`, then
  `makeKeyAndOrderFront:` and `makeKeyWindow`. `windowShow` = `makeKeyAndOrderFront:`;
  `windowUnminimise` = `deminiaturize:`.
- Activating the app makes macOS switch to the Space holding the window. That needs System Settings >
  Desktop & Dock > "When switching to an application, switch to a Space with open windows for the
  application", which is on by default. A full-screen window is its own Space; same rule.
- `App.Show()` darwin = `[NSApp unhide:nil]` (undoes Cmd+H). On Windows it re-shows windows that
  `App.Hide` hid, then `SetForegroundWindow` on a saved hwnd. On Linux it shows all windows. So it is
  safe only on darwin. `application.Get()` returns the global app (nil before `application.New`).
- Windows `focus` = `SetForegroundWindow`, then un-minimise. Linux `focus` = `gtk_window_present`.
- `MacWindowCollectionBehaviorMoveToActiveSpace` moves the window to the user's Space. Declined: the
  ask is to move the user to the window's Space, not to rearrange windows.
- `SetAlwaysOnTop(true/false)` toggling: declined. It raises without key focus, does not switch
  Spaces, and flickers.
- `Flash` darwin = `requestUserAttention:NSInformationalRequest` (one dock bounce). Not used; see §8 Q2.

## 1. Decision: where the call lives

Backend, in `prompts.Router.Open`, gated by a per-kind policy. Not frontend on event.

- The renderer cannot activate a hidden or minimised app reliably: a hidden or background webview
  may throttle timers and events, and a closed window has no renderer at all.
- The router already knows the target window, its focus state, `Reopen`, and `RevealKind`.
- One place covers both stages, heavy prompts, and the queue, because all of them call `Open`.
- `dbmcp` stays untouched. Space passes no policy, so Space behaviour is unchanged.

## 2. Router change (`internal/prompts/router.go`)

New `Deps` field:

```go
// RaiseOnOpen reports whether opening a prompt of kind k brings its window to the front; nil means never.
RaiseOnOpen func(k Kind) bool
```

New constant `raiseQuiet = 2 * time.Second` and a field `raised map[Kind]time.Time` (init in `New`).

In `Open`, after the entry is stored and before `commit`:

1. `tgt := r.target(e)`; `focused := r.d.Windows.Focused(tgt)`. Reuse both for the notification
   check that is already there (one `Focused` call, not two).
2. `raise := r.d.RaiseOnOpen != nil && !focused && r.d.RaiseOnOpen(p.Kind)`, then
   `now.Sub(r.raised[p.Kind]) >= raiseQuiet`. When true, set `r.raised[p.Kind] = now`.
   `now` is `r.d.Now()`.
3. After `r.commit(n)` returns (mu released): `if raise { go r.RevealKind(p.Kind) }`.

Rules this gives:

- Async. `Open` runs under the broker's `b.mu` and the router's `mu`; `Focus` blocks on the main
  thread through `InvokeSync`. The goroutine holds neither lock.
- Burst debounce: at most one raise per kind per 2 s. Prompts inside that window still route, and
  still notify when unfocused. 2 s covers the macOS Space-switch animation, during which
  `IsFocused` may still read false.
- No raise when the target window already has focus (`isKeyWindow` is false while the app is
  inactive, so a background app reads unfocused).
- Never on close. `Close`, `Claim`, `Reroute` do not raise. A request answered, timed out or
  abandoned before the goroutine runs makes `RevealKind` find no prompt, so it is a no-op.
- A queue advance (A answered, B becomes head) does not raise: B's `Open` already happened, and the
  user just clicked in the window.
- `RevealKind` reveals the kind's oldest prompt, which is the broker head (§0). When no window is
  registered it calls `Reopen`.
- Calling `RaiseOnOpen` under `mu` is fine: Studio's implementation reads settings from SQLite and
  takes no router lock.

## 3. Shell change: unhide on darwin

`WindowRegistry.Focus` gains one call before `Show`: `unhideApp()`.

- `internal/shell/unhide_darwin.go` (`//go:build darwin`): `if a := application.Get(); a != nil { a.Show() }`.
- `internal/shell/unhide_other.go` (`//go:build !darwin`): empty `unhideApp()`.
- Pure Go, no cgo. Comment states why darwin only (Windows/Linux `App.Show` re-shows hidden windows).
- Effect on Space: `FocusSession` and notification clicks also unhide a Cmd+H-hidden app. That is
  what both want; no Space test changes.

Activation after Cmd+H may unhide on its own; the explicit unhide costs nothing and removes the doubt.

## 5. Setting `dbMcp.focusOnApproval` (default on)

Justified. Focus stealing across Spaces is the most intrusive thing a desktop app does. Without a
setting, the only way to stop it is switching connections from prompt to allow or deny, which
weakens the approval gate. Default on, because the user asked for the behaviour.

- Go: `model.DbMcpSettings.FocusOnApproval bool` (`json:"focusOnApproval"`), default `true` in the
  defaults; `DbMcpPatch.FocusOnApproval *bool`; `repos/settings.go` `Leaf` + `UpsertOptional` for
  `dbMcp.focusOnApproval`. Copy `previewResponses` exactly.
- Frontend: `settingsDomain.ts` schema `focusOnApproval: z.boolean().default(true)` and both default
  objects. `DatabaseMcpPane.vue`: a second instant `Switch` below the preview switch, same
  mutation pattern as `onTogglePreviewResponses`, `data-testid="settings-db-mcp-focus"`.
- i18n: `studio.settings.dbMcp.focus.label` "Bring Kira Studio forward for approvals",
  `.description` "When a query or result waits for approval, show the window and switch to its
  desktop." Run the copy checker.
- No migration: settings are key/value leaves with code defaults.

   `kira:prompts:reveal` event to `w1` with id `dbmcp:<requestId>` (`Events.Wait`).

4. `setPreview(on)`. New write (reads are `allow` in the fixture) → focus count 2. `Blur()`,

5. Set `focusOnApproval` off (record `args:SettingsService.Set` in contract `dbmcp-focus`). `Blur()`,

## 8. Open questions (recommended default in bold)

1. macOS 14+ deprecates `activateIgnoringOtherApps:` for cooperative activation. It still activates
   a regular app in practice, but Apple may tighten it. **Ship Wails' call; the Mac check decides.**
   If activation fails, the existing notification still fires (target unfocused); a follow-up row
   would add a dock bounce.
2. Dock bounce (`Flash`) when focus did not take. **No** in this phase; adds a second signal the
   notification already gives.
3. Quiet window length. **2 s.**
4. Raise on a stolen keystroke: Deny is focused on mount, so a stray Space/Enter denies. **Accept**:
   deny is the safe direction and the AI can retry. A key-guard delay is a separate row if the user
   hits it.
5. Space prompts (git credential, pairing) could use the same policy. **Out of scope.**

## 9. Docs (`docs/ARCHITECTURE.md`)

- Prompt routing (P246) section: bullet for `RaiseOnOpen` (per kind, async `RevealKind`, 2 s quiet
  window, never on close, skipped when the target is focused) and the darwin unhide in
  `WindowRegistry.Focus`.
- DB MCP "The approval flow": bullet: both stages and heavy prompts raise the window, gated by
  `dbMcp.focusOnApproval` (default on); a stray key can only deny.
- DB MCP UI surfaces: settings section lists the new switch.
- Platform behaviour, stated plainly:
  - macOS: un-hide, un-minimise, show, activate; macOS switches to the window's Space (default
    Mission Control setting). A hidden last window reappears.
  - Windows: best effort. Foreground lock usually refuses `SetForegroundWindow` from a background
    app; the taskbar button flashes. A window on another virtual desktop is not switched to.
  - Linux: best effort. `gtk_window_present`; Wayland compositors usually show "is ready" instead
    of focusing; workspace switch depends on the window manager.
- Known open items: "Approval focus is unverified on macOS (P338)", with the checks below; delete
  once checked.

## 10. User checks on a Mac (signed build)

Set a connection's write mode to prompt, then from Claude Code run a write. Each case: dialog visible,
window key, typing goes to the dialog.

1. Kira Studio on Space 2, terminal on Space 1 → switches to Space 2.
2. Kira Studio full-screen → switches to its full-screen Space.
3. Another app full-screen, Kira Studio on a desktop Space → leaves that full-screen Space.
4. Kira Studio minimised → restores and focuses.
5. Kira Studio hidden (Cmd+H) → unhides and focuses.
6. Last window closed (hidden by Studio) → window reappears with the dialog.
7. Preview on → query stage raises; switch away during execution; response stage raises again.
8. Five requests at once → one switch, not five; queue count reads 5.
9. Deny, then let one time out → focus stays where you are afterwards.
10. Setting off → no raise; notification still appears.
11. Mission Control "switch to a Space with open windows" off → note what happens (record only).
12. macOS version used (14 or 15+), for §8 Q1.
