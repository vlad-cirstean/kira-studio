# P311: Docker container list scrolls sluggishly

SPEC row: "Docker container list in the left panel scrolls sluggishly. Find the cause, fix (likely
virtualization or per-row cost)." User: "The docker containers in the left panel seem to be quite
sluggish when scrolling."

Runs as Stream C, parallel to Stream B (P307) and Stream D (P312). Ownership table in section 6.

## 1. Findings (CodeGraph discovery, read of installed library source)

The list is already virtualized. `ContainerList.vue` renders through docker-ui's own
`VirtualList.vue`, which calls `useVirtualRows` (`packages/workbench/src/behaviour/virtualRows.ts`,
on `@tanstack/vue-virtual` 3.13.39, overscan 8). Missing virtualization is not the cause.
Image, Volume and Network lists use the same `VirtualList` and are not reported slow. Only
container rows carry reka tooltips and per-row components. So the cost is per row.

The cause is per-row cost multiplied by a full re-render of every mounted row on each range change:

1. **Range change re-renders every mounted row.** virtual-core's `maybeNotify` fires on each
   `startIndex`/`endIndex` change and on `isScrolling` toggles
   (`virtual-core/dist/esm/index.js:381`). vue-virtual then calls `triggerRef`, so `VirtualList`
   re-renders. Container rows are 44 px (comfortable density), so this happens about every 44 px
   of scroll, which is most frames during a flick. About 30 rows are mounted (viewport plus 8
   overscan on each side).
2. **Each re-render cascades into every row's child components.** The slot passes
   `rowNav(rows[vi.index])` (`VirtualList.vue:100`). `rowNav` returns fresh `onFocus` and
   `onContextmenu` closures on every call (`VirtualList.vue:72`, `listNavigation.ts:321`). The row
   template's handlers reference slot props (`@click.stop="act(row.container, 'start')"`,
   `@click="groupAction(row, 'start')"`). Vue's compiler does not cache a handler that references
   a slot or `v-for` scope variable. So every `TooltipIconButton` gets a new `onClick` attr on every
   pass, `shouldUpdateComponent` sees a changed attr, and the whole subtree re-renders:
   `Tooltip` > reka `TooltipRoot` > `TooltipTrigger` > `Button` > `CodiconIcon`, plus
   `TooltipContent` > `TooltipPortal`.
3. **Mounting is heavy.** Each entering row mounts one or two full reka tooltip trees. A container
   row has a `TooltipIconButton` (start/stop) and an `OriginIcon` (its own `Tooltip`). A group row
   has two `TooltipIconButton`s plus an `OriginIcon`. Each row also runs `cn(rowVariants(...))`
   inline on every pass.

Precedent: P161 measured this exact pattern in the Documents list (`docs/PERF.md`, "P161 Documents
list"). Two reka `Tooltip`s per row cost about 51 ms of a 142 ms frame. One shared tooltip fixed
it. The repo's shared mechanism is `packages/theme/src/components/AttributeTooltip.vue`: one hoisted
reka tooltip driven by `data-kira-tip` attributes. git-ui's virtualized lists already use it
(`FileTree.vue:432`, `StashRows.vue`, `WorktreeList.vue`).

Ruled out:

- Live stats. `useStatsSubscription` writes `useDockerStatsStore`. Nothing in `ContainerList` or
  `DockerPanel` reads that store.
- Refetch churn. `useDockerLiveSync` filters `exec_*`/attach/detach as noisy
  (`internal/docker/events.go:27`). TanStack Query's structural sharing keeps `data` identity when
  nothing changed.
- `ContainerSize`. `useContainerSize` is `enabled: false` and used only in
  `ContainerSizeSection.vue`, not in the list.
- Non-passive listeners. Scroll events are not cancelable. virtual-core's own listener is passive.
  `VirtualList`'s `@scroll` only writes an unread ref.

No measurement is needed to choose the fix: the cascade is visible in the code, and P161 already
measured the tooltip cost. Measurement is still needed to confirm the fix works, because "less
sluggish" cannot be checked by reading the code. Section 4 covers it.

## 2. Fix

### 2.1 Stable per-row identity in `VirtualList.vue`

- Key the row wrapper by row key, not virtual index: `:key="rows[vi.index]!.key"`. When rows
  shift (collapse or filter), a row's component instance then stays with its row. Every current
  caller's keys are unique (container id or `g:<project>`, image id, volume name, network id).
- Cache nav handlers per key so the slot's `nav` values stay identical between renders:

  ```ts
  type RowHandlers = { onFocus: () => void; onContextmenu: (e: MouseEvent) => void };
  const handlers = new Map<string, RowHandlers>();
  watch(() => props.rows, () => handlers.clear());

  function rowNav(row: T) {
    let h = handlers.get(row.key);
    if (!h) {
      h = {
        onFocus: nav.rowProps(row.key).onFocus,
        onContextmenu: (e) => { /* current body, closing over this row */ },
      };
      handlers.set(row.key, h);
    }
    return { 'data-nav-key': row.key, tabindex: nav.tabindexFor(row.key), ...h };
  }
  ```

  The `watch` runs with default `pre` flush, before the re-render, so a new `rows` array never
  reuses a stale closure. The slot's type is unchanged, and Image, Volume and Network lists need no
  edit.

### 2.2 Row components in docker-ui

Extract the two row bodies of `ContainerList.vue`'s `#row` slot into components. Use
`<script setup lang="ts">` and keep the markup and classes unchanged.

- `packages/docker-ui/src/components/ContainerRow.vue`
  - Props: `container: DockerContainer`, `grouped: boolean`, `selected: boolean`, `busy: boolean`.
  - Emits: `select: [DockerContainer]`, `open: [DockerContainer]`,
    `act: [DockerContainer, ContainerAction]`.
  - Root `div` keeps every `data-*`, `role="option"`, `aria-selected` and the
    `@click`/`@dblclick` behaviour, now done through emits.
  - Row class goes in a `computed` (`cn(rowVariants({ layout: 'double', selected }), ...)`).
  - `portLabel` moves here as a `computed`.
- `packages/docker-ui/src/components/ContainerGroupRow.vue`
  - Props: `name: string`, `running: number`, `total: number`, `open: boolean`.
  - Emits: `toggle: [string]`, `groupAction: [string, 'start' | 'stop']`.
  - Keeps `data-testid="docker-group"`, `data-project`, `TreeTwisty`, the name button and its
    `aria-expanded`.

Wiring in `ContainerList.vue`:

- In the slot, do `<ContainerRow v-bind="nav" :container ... @act="act" @select="select"
  @open="openContainer" />`. `nav` falls through as attrs onto the row's root, so `data-nav-key`,
  `tabindex`, `onFocus` and `onContextmenu` behave exactly as today.
- Every event handler passed is a setup-scope function identifier, never an inline arrow over
  `row`. With these handlers, plus 2.1's stable nav values and primitive props, a range change
  re-renders only entering rows.
- `act` and the single `useContainerAction()` stay in `ContainerList`, because its `busy` set is
  per instance. The parent passes `busy: actions.isBusy(id)`.
- `groupAction` takes the project name and resolves its members from the current `rows` or
  `visible` data.
- `runningCount(row)` becomes the `running` prop.

### 2.3 One shared tooltip instead of per-row reka tooltips

- Row action buttons become plain shadcn `Button` with `CodiconIcon` inside:
  `variant="toolbar"`, `size="kira-icon"`, `:aria-label="label"`, `:data-kira-tip="label"`,
  `:data-tone="tone"`. These are `TooltipIconButton`'s defaults, so its look is reproduced exactly.
  `data-tone` keeps the green/red styling that `docker-module.spec.ts:452` asserts. Keep every
  `data-testid`.
- `OriginIcon.vue` gains prop `tip?: 'tooltip' | 'attribute'` (default `'tooltip'`). With
  `'attribute'`, it renders the same `span` with `:data-kira-tip="label"` and no `Tooltip` wrapper.
  `ContainerEditView.vue` keeps the default. Both row components pass `tip="attribute"`.
- `ContainerList.vue` wraps `VirtualList` in
  `<div ref="listEl" class="flex min-h-0 flex-1 flex-col">`. Next to it, mount
  `<AttributeTooltip :container="listEl" />`. `QueryState` renders its default slot with no
  wrapper, and `VirtualList` relies on `flex-1 min-h-0`, so the wrapper must keep that flex chain.
- `AttributeTooltip` already opens on `focusin`, so keyboard focus on a row button still shows its
  tip. Rows themselves carry no `data-kira-tip`.

Library check: this adds no new dependency. `@tanstack/vue-virtual`, reka (through shadcn-vue) and
`AttributeTooltip` stay the mechanisms. No hand-rolled virtualizer or tooltip.

Comments: one line on the handler cache, explaining that stable values let rows skip re-render on
range change. Nothing else.
