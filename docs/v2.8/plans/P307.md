# P307 plan: preconnect scripts in Operations panel, timer, connect race

Row: "Operations panel shows a DB's preconnect scripts. Preconnect script run has a visible timer.
Fix the race between "connecting" and the script itself."

User ask: "I should see in operation panel the preconnect scripts for a db. The preconnect script
should have a timer. Now connecting and script itself races."

User refinement (relayed): "The issue is that the preconnect script might take a little bit to
start running. So if it tries to connect to the db immediately of course it will fail. If it can be
mitigated somehow, sure, otherwise just add a setting for adding a delay."

- Running rows show `—` for duration (`OpLogPanel.vue:263`, `durationMs` null until `op:end`). No
  live timer anywhere in the op log.
- `preconnectSidecar` flag only decides whether the script is `Arm`ed (exit drops the connection).
  It does not change readiness.

## 2. Root cause of the race

`settleWindow` is a guess. A tunnel script (`kubectl port-forward`, `ssh -L`, `aws ssm
start-session`) that is still alive at 2s is declared ready, and `Backend.Connect` dials at once.
If the tunnel needs longer than 2s to start listening (auth plugin, SSO token fetch, slow API
server), the dial hits a closed port and fails (`connection refused`). Then `attemptConnect` calls
`Preconnect.Stop`, killing the script that was about to work. Retry = same race. Not a lock or
ordering bug in Go: it is a wrong readiness signal. Matches the user's refinement exactly.

## 3. Decision: readiness probe, not a delay setting

Options weighed:

1. **Fixed per-DB delay setting** (user's fallback). Still a guess: too short = same race, too long
   = every connect pays the full wait. Needs migration, Go model, zod, form field, validation.
2. **Retry `Backend.Connect` with backoff while the script runs.** Rejected: a full adapter connect
   per attempt (TLS, auth) spams the server, can trip auth-failure lockouts, multiplies `connect`
   op rows, and conflates "tunnel not up" with "wrong password".
3. **Probe the DB's host:port until it accepts TCP, while the script is alive.** Chosen. It
   observes the actual condition the connect needs (something listening) at near-zero cost (one
   TCP dial per 100ms, closed at once). No new setting, no migration, no user tuning.

Probe applies only when the target is **loopback** (`localhost`, any `127.0.0.0/8`, `::1`) with an
explicit port: that is where a port-forward/tunnel listens. A remote host being reachable says
nothing about the script (e.g. a credentials-refresh script against a public endpoint would probe
ready at once and reintroduce the race), so non-loopback targets keep today's settle-window rule.
That residual case is recorded in `docs/ARCHITECTURE.md` "Known open items" with the delay setting
named as the follow-up if it ever bites. Not built now: the user's ask makes the setting
conditional on no mitigation, and the probe mitigates the described case.

### New `Supervisor.Start` readiness rule

Signature: `Start(ctx, connectionID, command string, ready ReadyCheck) (Start, error)` where
`type ReadyCheck func(context.Context) error`; nil = no probe.

First event wins:

1. Script exits 0 -> one-shot (unchanged, incl. tracking a surviving group).
2. Script exits non-zero or on a signal -> error (unchanged message).
3. `ready != nil` and a probe succeeds while the script is alive -> tracked sidecar entry,
   `go awaitExit`, return `KindSidecar` (same as the timer branch today).
4. `ready == nil` and `settleWindow` elapses -> sidecar (unchanged fallback).
5. `ready != nil` and `readyTimeout` (new package var, 60s) elapses -> drain stderr, `killEntry`,
   error `Pre-connect script not ready after 60s: nothing accepting connections on <addr>` plus
   stderr tail via `exitDetail`-style tail. Message carries the addr; build it from the probe
   (make `ReadyCheck` a small struct `{Addr string; Check func(ctx) error}` or pass addr
   alongside; implementer's choice, keep one type).
6. ctx cancelled -> `killEntry`, return `fmt.Errorf("Pre-connect script cancelled: %w", ctx.Err())`
   (wrapped so `errors.Is(err, context.Canceled)` still holds; message is readable in the error
   state when the user cancels from the Operations panel).

Probe loop: own goroutine on a child ctx cancelled when `Start` returns; dial, on success send on
a 1-buffered channel; else wait `probeInterval` (package var, 100ms). When the ready branch fires,
do a non-blocking read of `outcomeCh` first: if the script already exited, handle it as cases 1/2
(never leave `awaitExit` blocked on a consumed channel).

Production probe: `preconnect.DialReady(addr)` -> `net.Dialer{Timeout: 300ms}.DialContext("tcp",
addr)`, close conn on success.

Known edge, documented not fixed: a port already listening before the script starts (stale tunnel,
local DB) probes ready at once. Connect then targets what is there, which is what a manual connect
would do too.

### Target derivation

New `readyAddr(cfg model.ResolvedConnectionConfig) string` in
`apps/kira-studio/internal/connections/resolve.go`; `resolved` gains `readyAddr string`, filled by
both `resolve` and `resolveFromInput`. Rules:

- file kinds (`fileKinds`) -> "".
- fields mode: `Host` and `Port` both set, host loopback -> `net.JoinHostPort(host, port)`.
- URI mode: `url.Parse(*cfg.URI)`; host list with `,` (mongo multi-host) -> ""; `u.Hostname()`
  loopback and `u.Port() != ""` -> join. Parse failure -> "". Never log the URI (holds password).
- Loopback: `strings.EqualFold(h, "localhost")` or `net.ParseIP(h)` non-nil and `IsLoopback()`.

Small table test in `resolve_test.go` (mode x host form x port presence x multi-host interact;
qualifies as a multi-rule parser under `CLAUDE.md`'s test bar).

## 4. Preconnect as an Operations panel op, with timer

### Backend

- New op kind `preconnect`: add to `model.opKinds` (`internal/storage/model/ops.go`) and
  `opKindSchema` (`packages/shared/domain/ops.ts`). Go/TS parity spec
  (`tests/unit/go-ts-vocabulary-parity.spec.ts`) then passes unchanged. `op_log.kind` has no CHECK
  constraint, so no migration. Not added to `throttledKinds`.
- `connections.Backend` gains
  `RunPreconnect(ctx context.Context, connectionID *string, command string, run func(context.Context) error) error`.
  `adapterhost.Router` implements it: `r.host.RunOp(ctx, OpSpec{ConnectionID: connectionID,
  Kind: "preconnect"}, func(ctx, op) { op.SetCommand(command); return nil, run(ctx) })`. Command =
  the script text so the row's Command column and detail show it. Same plaintext exposure as the
  `connections.preconnect` column already in the same DB.
- `attemptConnect`: replace the bare `Preconnect.Start` call with
  `s.deps.Backend.RunPreconnect(ctx, &id, script, func(opCtx) error { _, err := s.deps.Preconnect.Start(opCtx, id, script, check); return err })`.
  `started` stays true only on success. Error handling: `ctx.Err() != nil` (attempt aborted by
  Disconnect/Remove/Shutdown) -> `finalizeAbortedAttempt` as today; otherwise the op error
  (incl. user Cancel from the panel, which cancels only the op's derived ctx) becomes the
  connection's error state. Op ends before `Backend.Connect` starts: preconnect row finishes,
  then the `connect` row begins. That ordering is the visible proof of the race fix.
- `Service.Test`: same wrap with `connectionID nil` (matches the `test` op's own nil id) so a
  dialog Test also shows the script and gets the probe. Keep its `defer Preconnect.Stop`.
- Op status mapping comes free from `Host.RunOp`: ok / error / cancelled, `durationMs` = wait until
  ready (not the sidecar's lifetime; the op is the startup, the process may live on).
- `fakeBackend` in `connections/service_test.go`: passthrough `RunPreconnect` that just calls
  `run(ctx)`. No other `Backend` implementers (grep `) SetThrottle(` found only Router, Host, fake).

### Frontend timer (shared panel)

  `now` ref ticked by VueUse `useIntervalFn(..., TIMING.clockTick)` for the whole list (not per

## 7. Docs

`docs/ARCHITECTURE.md`:

- Preconnect readiness: loopback host:port probe every 100ms, 60s timeout, settle window 2s only
  for non-probeable targets; op kind `preconnect` wraps the startup wait, command = script,
  cancellable from the panel; op ends before `connect` starts.
- Op log: running rows show a live elapsed clock (shared `OpLogPanel`).
- Known open items: "A pre-connect script whose DB target is not loopback (or has no explicit
  port) is judged ready by the 2s settle window, so a slow tunnel to a non-loopback address can
  still race the connect. Follow-up if needed: a per-connection start delay."
