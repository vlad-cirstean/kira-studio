## Root cause

Both tests use a CPU- or broker-speed-dependent workload as a clock. Production code is correct in both. A fast runner, or a faster server build, finishes the workload before the timing the test assumes.

### Redis (`apps/kira-studio/internal/adapters/redis/redis_test.go:855-880`)

- Test sets console read timeout to 1s (`SetConsoleReadTimeout`, `export_test.go:6`). It then runs a Lua loop of 250 000 000 iterations, assumed "~2.5s", and expects `E_TIMEOUT` from `runConsoleCommand` (`console.go:423`).
- Loop duration is pure interpreter speed: runner CPU, plus the image's own Lua build flags. Test total of 0.75s, including connect, proves the script returned in under 1s, so `cc.Do` got a reply before its read deadline. `err = nil` follows.
- `TIME` cannot bound the loop (frozen inside a script, as the test's comment notes).
- Rejected: `CLIENT PAUSE WRITE`. go-redis closes the connection on read timeout. Redis then frees the postponed client and drops its pending EVAL, so the INCR never runs. The test would see 0 runs, losing its "exactly once" proof.
- Rejected: `DEBUG SLEEP`. Disabled by default from Redis 7.0 (`enable-debug-command no`), and it cannot carry the INCR resend probe.
- Rejected: shorter read timeout alone. Still assumes CPU speed, only with a wider margin.

### Kafka (`apps/kira-studio/internal/adapters/kafka/kafka_test.go:770-821`)

- Test seeds 20 000 records, starts `Read`, sleeps 50ms, cancels. It expects `E_CANCELLED`. Its own comment says it was tuned empirically so that "an uncancelled full read" takes "three-digit milliseconds".
- A 0.14s total, including the ProduceSync of 20 000 records, proves `Read` returned with `err = nil` before the 50ms cancel. The ~1.5 MB payload arrives in one or two fetches (1 MiB partition fetch cap). A faster broker (cp-kafka 8.3.0, i.e. Kafka 4.x) or runner finishes it in well under 50ms.
- `readTopic` (`read.go:490`) is correct. A cancel landing after its last `CheckCancelled` (`read.go:561`) truthfully yields a completed page.

### ci-gate / PR CI

- `release-ci-gate.sh` exits 1 when no green pr.yml run exists for the SHA. That is correct behaviour.
- pr.yml job `go-containers (Linux)` runs `scripts/go-test-split.sh containers`. That job includes both packages above, on default images (`redis:8.10`, `cp-kafka:8.0.7`), on the same `ubuntu-latest` runner class. Same timing assumptions apply, so the same two tests are the likely cause.
- Not provable without run logs (no GitHub API in this session). If PR CI on the fix commit is still red for another reason, that becomes a follow-up. Do not guess at it here.

## Fixes

### F1: Redis test calibrates its busy loop (`redis_test.go`)

Make the script's duration a measured quantity, not an assumed one.

1. Add a local helper in `redis_test.go`, next to the test:
   `func calibratedLoopIterations(t *testing.T, root *goredis.Client, target time.Duration) int64`
   - Run `local x = 0; for i = 1, tonumber(ARGV[1]) do x = x + i end; return 0` via `root.Eval` with `ARGV[1] = 50_000_000`. Time it client-side.
   - Return `int64(float64(calib) * target.Seconds() / elapsed.Seconds())`.
   - `t.Fatalf` if the calibration EVAL errors. Floor elapsed at 1ms to avoid division by ~0.
   - Root client's default 3s read timeout covers the calibration: 50M iterations ran ~0.5s on the slowest observed CPU.
2. In the test (`:855-880`):
   - Before the console run: `iters := calibratedLoopIterations(t, root, 3*time.Second)`.
   - Script becomes `local x = 0; for i = 1, tonumber(ARGV[1]) do x = x + i end; return redis.call('INCR', KEYS[1])`.
   - Statement becomes `fmt.Sprintf("EVAL %q 1 %s %d", script, key, iters)`.
   - Target 3s: 3x the 1s read timeout, and under Redis's 5s `busy-reply-threshold`, so root's EXISTS polling never meets BUSY even with ±30% calibration drift.
   - Replace the fixed trailing `time.Sleep(3 * time.Second)` with `time.Sleep(target + time.Second)`. A resend would go out at ~1s and queue behind the first script, so it finishes ~2×target after start. The check runs at ≥ target + target + 1s. This keeps the original margin while scaling with the measured duration.
   - Replace the "~2.5s of Lua busy work" comment with one line: loop length is calibrated to this server's speed, since TIME is frozen inside a script.
3. Keep both assertions unchanged (`E_TIMEOUT`, exactly one INCR).

### F2: Kafka test throttles the adapter's fetches broker-side (`kafka_test.go`)

Make the browse slow by a broker-enforced rate, not by record count. The adapter's clients use `kgo.ClientID("kira-studio")` (`client.go:112`). The fixture's side client uses kgo's default id, so a client-id quota scopes to the adapter alone. Kafka tests run serially (no `t.Parallel` in the package).

1. Add a local helper in `kafka_test.go`:
   `func throttleAdapterFetches(t *testing.T, f *testsupport.KafkaFixture, bytesPerSec float64)`
   - `f.Admin.AlterClientQuotas` with entity `{Type: "client-id", Name: "kira-studio"}` and op `{Key: "consumer_byte_rate", Value: bytesPerSec}`. Check both the call error and each `AlteredClientQuota.Err`.
   - Wait until the quota is visible: poll `f.Admin.DescribeClientQuotas(ctx, true, [{Type: "client-id", MatchName: "kira-studio", MatchType: kadm.QuotasMatchTypeExact}])` until it lists `consumer_byte_rate`. Use `kafkaReadyPollInterval`-style 100ms spacing, 10s bound, then `t.Fatal`. This is a condition wait, not a timing guess: quota apply goes through the KRaft metadata log asynchronously.
   - `t.Cleanup`: same `AlterClientQuotas` with `Remove: true`, then poll until `DescribeClientQuotas` lists no entry. This stops later tests in the binary from being throttled. `resetKafka` does not reset quotas.
   - Name the client-id once as a test const with a comment pointing at `client.go`'s `kgo.ClientID`. If the adapter's client id ever changes, the quota silently stops applying, and the test fails visibly with "want an error" rather than passing falsely.
2. In the test (`:783-821`):
   - Call `throttleAdapterFetches(t, f, 64*1024)` after seeding, before `Read`. At 64 KiB/s the ~1.5 MB browse needs ≥ ~20s. The broker mutes the channel for up to its quota window (11s by default) after the first ≤1 MiB fetch. kgo also honours `throttle_time_ms`.
   - Raise the pre-cancel sleep from 50ms to 500ms. The cancel then lands inside the throttled browse, after `prepareWindows`/`openBrowseClient` setup (a few ms of admin calls, not consumer-throttled). It cannot land before the browse starts, which would only exercise `CheckCancelled` before the loop. The sleep stays only as "cancel after start". Its pass condition no longer races: the browse lasts seconds, not milliseconds.
   - Keep the 20 000-record seed (~1.5 MB). One fetch carries ≤1 MiB per partition, so at least one further fetch must wait out the throttle. A smaller seed could fit in the first, unthrottled response.
   - Keep every assertion: an error, code `E_CANCELLED`, elapsed < 5s, return within 10s.
   - Rewrite the M9.2 comment block (`:770-782`) to 3-4 lines. A record count alone is a speed race. A broker-side consumer quota on the adapter's client id makes the browse last seconds, so the cancel always lands mid-flight.
3. If elapsed < 5s fails because `browse.Close()` (`read.go:518`) blocks on a muted connection, that is a real production finding: Stop must return promptly. Root-cause it in `read.go`; do not loosen the bound.
