# P5.5 — Query console

> Plan for SPEC.md §8.14, the phase between P5 and P6 per the phasing table. Deliverable: *A
> `console` tab bound to a connection (and optionally a default database/schema); CodeMirror with
> SQL highlighting; run-statement/run-all; result grids reusing §8.5's infrastructure; errors
> surfaced verbatim; console contents saved to `saved_queries`.* Scoped to postgres/mariadb —
> independent of every adapter still to come (P8–P10).

This document is written after the implementation, not before it (a departure from P4/P5's own
practice of a plan doc preceding or alongside the work) — it records the decisions actually made,
in the same D-table format, so the phase leaves the same paper trail as every other one.

## 0. Ground rules for this phase

- Build only what §8.14 lists. No query history (unlike §8.5's filter box, the console has no
  "Recent" concept — `saved_queries` is the only persistence, exactly as the deliverable says).
- `execute()` is **call-level** all-or-nothing, not a database transaction: one op-log row, one
  success/failure outcome per call, via a single `ctx.setCommand()` call joining every statement
  with `;\n` — P5 D9's precedent, reused verbatim. A statement that already committed before a
  later statement in the same batch fails **stays committed**; `execute()` does not wrap the batch
  in `BEGIN`/`COMMIT` the way `mutate()` does (P5 D10), because an arbitrary console script may
  itself contain transaction-control statements, DDL that can't run inside one, or deliberately
  mix statements the operator wants to survive a later failure. This is a documented, tested
  property (DB-spec "earlier statements already landed" scenarios), not an oversight.
- One `Page` per statement, in order — including statements with no rows (`INSERT`/`UPDATE`/DDL),
  which get a synthetic single-cell status page rather than being skipped.
- No new `AdapterErrorCode`. A failing statement rejects with the existing `E_QUERY`; an
  already-cancelled signal rejects with `E_CANCELLED` before anything runs.
- `execute` is gated by the new `caps.sql` flag (`shared/caps.ts`), already reserved for this
  phase with the comment "gates §8.14's query console menu item" — true for postgres/mariadb,
  false for every adapter not yet built.
- Console tab state persists only the editor's own text (`ConsoleTabState.text`); the last run's
  result pages are runtime-only (`views/console/state.ts`'s `runtime` map), never round-tripped
  through `tabs.save`, mirroring `views/ddl/state.ts`'s own runtime/state split.
- Run `bun run lint`, `bun run typecheck` and `bun run build` throughout; `bun run test:db` from
  the adapter step on, `xvfb-run -a bun run test:ui` from the renderer step on.

### P0–P5 realities this phase works with

1. **The `Adapter` roadmap comment already named this phase**: `execute(req: ConsoleRequest, ctx:
   OpCtx): Promise<Page[]>`, gated by `caps.sql` (`src/engine/adapters/adapter.ts:113-120`). P5.5
   is the last item on that roadmap comment — "all above, nothing pending".
2. **P5's `mutate()`/`preview()` batching precedent carries over directly**: one op-log row per
   call, `ctx.setCommand()` called once with the full joined statement text before anything runs
   (D9 of P5's plan). `execute()` reuses this exactly, but without P5's transaction wrapper (see
   ground rules above) and without P5's fresh-catalog re-validation (a console statement is not a
   structured `MutationPlan` — there is nothing catalog-shaped to validate against).
3. **`savedQuerySchema` (`shared/domain/queries.ts`) already needed to grow** to hold a second
   kind of saved thing. Converting it to a `z.discriminatedUnion('kind', ['filter', 'console'])`
   (rather than adding a second parallel table) keeps one `saved_queries` store, one
   `queriesList`/`queriesSave`/`queriesUpdate`/`queriesDelete` IPC surface, and one pin/rename/
   delete UI pattern for both — `FilterHistoryMenu.vue`'s pattern is reused, not reinvented.
4. **`views/grid/page.ts`'s page cache was built assuming one page per tab** (`drop(tabId)`
   deletes exactly one key). A console tab can produce N result pages per run (one per statement),
   so the cache needed a second entry point that frees a whole prefix at once — see D-table below.
5. **`CodeMirrorHost.vue` had no way to report cursor position** — every existing caller (DDL's
   read-only viewer, the filter box) only ever needed `update:doc`. "Run statement" needs to know
   which statement the cursor is currently inside, so the host needed a second, narrowly-scoped
   emit.
6. **`VirtualList.vue` had no header slot** — every existing caller (`OperationsPanel.vue`,
   `ProjectTree.vue`) renders rows only, no sticky header row. A console result grid needs a
   column-header row that stays visible while scrolling, the same as `DataGrid.vue`'s (which is
   not itself virtualized through `VirtualList.vue` — it rolls its own).
7. **`sql-split.ts` did not exist before this phase.** "Run statement" (the one under the cursor)
   and "Run all" both reduce to "send N statements to one `execute()` call" — both need the same
   quote/comment/dollar-quote-aware `;`-splitter, so it is a single shared module, not duplicated
   logic in each command handler.

## 1. `ConsoleRequest` shape (D1)

```ts
// src/shared/domain/console.ts
export interface ConsoleRequest {
  path: NodePath; // binds the batch to a connection and, optionally, a default database/schema
  statements: string[]; // pre-split by sql-split.ts — one element for "Run statement"
}
```

## 2. Decisions made in this plan

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | `ConsoleRequest` carries `path` (for connection + optional default database/schema scoping) and a pre-split `statements: string[]`. Splitting happens renderer-side (`sql-split.ts`), not engine-side. | The renderer already needs the split for "Run statement" (find the statement under the cursor) before it ever calls the engine; splitting twice (once to find the target statement, once again engine-side) would be redundant and could disagree with itself on edge cases (dollar-quoting, string-embedded semicolons). |
| D2 | `execute()` is call-level all-or-nothing but explicitly **not** a database transaction — no `BEGIN`/`COMMIT` wrapper, unlike `mutate()` (P5 D10). Verified by a DB-spec scenario per adapter: a statement that inserts a row, then a later statement in the same batch that fails, leaves the inserted row committed. | A console script is arbitrary SQL, potentially including its own transaction control or DDL that can't run inside an implicit transaction; wrapping it would silently change what the operator's own script does. The one-op-log-row guarantee is about the *op log*, not about atomicity of the underlying statements. |
| D3 | One `Page` per statement, always, including non-row-returning statements (`INSERT`/`UPDATE`/DDL/…), rendered as a synthetic single-cell "status" page (Postgres: the command tag `"<COMMAND> <rowCount>"`; MariaDB: `"<affectedRows> row(s) affected"`, since node-mariadb's OkPacket doesn't expose a command tag). | §8.14 requires visible feedback for every statement run, not just `SELECT`s — a `Run all` batch mixing a `SELECT` with an `UPDATE` needs both to produce something in the results list, in order. |
| D4 | `caps.sql` gates the "Open query console" menu item, spliced into `connectionMenu`/`containerMenu`/`relationMenu` only — deliberately **not** added to `simpleObjectMenu` (sequence/function) or `columnMenu`. | §8.10's own row-kind menu list has no console entry for those kinds; a console is a connection/database/table-scoped surface, not a per-object one. |
| D5 | `openConsoleTab(connectionId, path)` **always creates a new tab**, never reuses an existing one for the same `(connectionId, path)` — unlike `openDataTab`/`openDdlTab`, which reuse. | Unlike data/ddl, a console is a scratch work surface (like a SQL client's "New Query"), so the same target routinely wants several independent consoles open at once. |
| D6 | `ConsoleTabState` persists only `{ text: string }`. The last run's result pages live in a separate runtime-only map (`views/console/state.ts`'s `runtime`), keyed by tab id, never written to `tabs.state_json`. | Mirrors `views/ddl/state.ts`'s existing runtime/state split; results are large, regenerable, and stale the moment the underlying data changes — not worth persisting or restoring across a relaunch. |
| D7 | `views/grid/page.ts` grows `dropForTab(tabId)` alongside the existing `drop(tabId)`: it deletes every cache entry keyed `tabId` itself *or* `${tabId}:...`. `state/tabs.ts`'s four close paths (`closeTab`/`closeOthers`/`closeToTheRight`/`closeAll`) all switch from `drop()` to `dropForTab()`. | A console tab can hold N result pages (one per statement of its last run), keyed `${tabId}:result:${i}` (`resultPageKey`) — a single-key `drop()` would leak every page but the first. Switching every close path (not just console's) keeps one cache-cleanup entry point rather than two call sites to keep in sync. |
| D8 | `CodeMirrorHost.vue` grows a second emit, `update:cursor: [pos: number]`, fired from the same `updateListener` on `update.docChanged \|\| update.selectionSet`, carrying `update.state.selection.main.head`. | "Run statement" must know which statement the cursor is in even on a bare click or arrow-key move with no text change — `docChanged` alone would miss that. |
| D9 | `ConsoleResultGrid.vue` is a new, lightweight component — explicitly not a retrofit of `DataGrid.vue`. It reuses only `views/grid/page.ts`'s page cache and `columns.ts`'s width/alignment helpers, plus `VirtualList.vue` for row virtualization. No pager, no sort, no pending-changes, no persisted column widths/order. | A console result has none of the state DataGrid's other features exist to serve (server-side pagination, staged edits, saved column layout per target) — reusing DataGrid wholesale would mean stripping most of it back out for a component that only needs to virtualize rows and show cells. |
| D10 | `VirtualList.vue` grows an optional `#header` slot, rendered `position: sticky; top: 0` inside the same scrolling container (its CSS changes from split `overflow-y`/`overflow-x` to plain `overflow: auto` to allow this). The header's own height is **not** subtracted from the scrollTop→startIndex virtualization math — accepted as a sub-row-height offset absorbed by the existing overscan, rather than adding height-tracking complexity for a cosmetic edge case. | `ConsoleResultGrid.vue` needs a column-header row that stays visible while scrolling a large result set; verified safe for the two pre-existing callers (`OperationsPanel.vue`, `ProjectTree.vue`/`TreeRow.vue`) since their row content already clips via `overflow: hidden`, so no horizontal scrollbar can newly appear from the container-level CSS change. |
| D11 | `savedQuerySchema` becomes `z.discriminatedUnion('kind', ['filter', 'console'])`; a new `consoleBodySchema` (`{ text: string }`) sits beside the existing `filterBodySchema`. New IPC ops `queriesListConsole`/`queriesSaveConsole`, sharing `queriesUpdate`/`queriesDelete`/`queriesTouch` with the filter kind. | One `saved_queries` table serves both purposes (§8.14 says console content is "saved to `saved_queries`" — the same store, not a new one); a discriminated union keeps `pin`/`rename`/`delete`/`touch` generic across both kinds without duplicating that plumbing. |
| D12 | `ConsoleSavedMenu.vue` is a lean sibling of `grid/FilterHistoryMenu.vue`: saved-only (no "Recent" section — §8.14 gives the console no run-history concept), and applies an entry by calling `setText()` directly rather than emitting an `apply` event. Saving a query does **not** close the menu (only applying an entry, or the backdrop, does) — matches `FilterHistoryMenu.vue`'s own `saveCurrent()`, which likewise leaves the menu open so the freshly-saved entry is visible in the reloaded list. | State-module-direct-call is the pattern already used elsewhere for a tab-scoped mutation (e.g. `DdlView.vue`'s `load()`); consistency with `FilterHistoryMenu.vue`'s save-then-stay-open behavior avoids two different saved-query menus disagreeing on what "Save" does to the menu. |
| D13 | Execution order for `run()` (`views/console/state.ts`): a fresh `run()` call always replaces the previous run's result set wholesale (`dropResults()` then rebuild), never appends. "Run statement" after "Run all" therefore shows only the one statement's result, not both. | Matches a SQL client's conventional "each Run replaces the results pane" behavior; an accumulating results list would grow unbounded across a long console session with no way to clear it. |
| D14 | DB-spec scenarios for the console start at **27** in `tests/db/mariadb.spec.ts` (previously ending at 26) and **28** in `tests/db/postgres.spec.ts` (previously ending at 27, after P5's mutation scenarios). | Continues each file's existing numbered-scenario convention without renumbering anything already there. |
