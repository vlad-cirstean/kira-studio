## 2. Decisions

### 2.1 Layout

- A config folder is a direct child of an app home: `<home>/<module>/`. Workflows stay `<home>/workflows/`.
- A module's folder lives in the home of the app whose DB holds the module's state. So Space modules
  (git repos P461, Agents) in `~/.kira-space/`, Studio modules (API P460, connections P462) in
  `~/.kira-studio/`, Runs (both apps) one folder per app (P459 confirms). This is the Studio/Space DB split
  rule: a process only ever projects files into its own DB.
- A definition shared by both apps (P452 context, P453 settings) has exactly one folder. Default (Q1):
  `~/.kira-space/agent/`, the spec's "Kira Space app folder, alongside workflows". Studio resolves it with
  `kirapaths.Home("KIRA_SPACE_HOME", ".kira-space")`; both apps read, write and watch it; each projects
  what it needs into its own DB. The resolver lands with P452 (its first user), not here.
- Reserved names inside a config folder: `AGENTS.md` (generated, §2.7) and hidden files (temp files,
  editor swap files). The store never reads either as config.
- Folder mode follows the home (0700 home, 0755 folder as workflows today); files 0644. Files never hold a
  secret value, so 0644 under a 0700 home is enough.
- Per-machine values (paths, ports): convention fixed now, code lands with the first module that has one
  (P461 repo paths): `<name>.local.yaml` beside `<name>.yaml`, merged over it key by key, never written by
  the app except for those keys, and `AGENTS.md` tells users to keep `*.local.yaml` out of sync and git.

### 2.2 Formats

- Structured config: YAML, extension `.yaml` (workflows precedent; comments survive, agents write it
  well). Parsed through `yaml.Node` for lines. Anchors, aliases and merge keys (`<<`) are refused with a
  line (no alias bombs, no hidden indirection an agent cannot follow).
- Prose (agent context): Markdown text, `.md`, no schema beyond size cap and UTF-8.
- JSON files: none. YAML flow syntax accepts JSON text anyway; no module needs a JSON file. A module that
  must keep a native JSON shape (P454 import/export) renders it, never stores it.
- Collections are one item per file, `<id>.yaml`, and the file stem is the id. New modules put no `id:`
  key inside (workflows keep theirs: removing it is a P451/workflow-format change, not this phase).
  Singletons are one fixed file name (`settings.yaml`).
- Cap: 1 MiB per file (workflows' cap), refused on read and write.

### 2.3 Validation

- Schema language: JSON Schema draft 2020-12, one embedded `.schema.json` per kind. Validator:
  `github.com/santhosh-tekuri/jsonschema/v6` v6.0.3 (Apache-2.0, deps `golang.org/x/text` already in
  `go.mod`, `dlclark/regexp2` test-only; all features open source). Declined `google/jsonschema-go`
  (already in go.mod) for the validator: it reports one flat error against the schema path with no
  instance location, so it cannot give the line the spec requires. Hand-rolling a schema validator is the
  alternative the library rule forbids.
- Pipeline per file: `yaml.Node` parse (syntax error: line from the yaml error text, as `adeflow.Parse`
  does) → own node-to-JSON-value walk (tags to JSON types; `!!timestamp`/`!!binary` stay strings;
  non-string keys refused) → schema validate → map the first leaf error's `InstanceLocation` back through
  the node tree to `Line`/`Col` → JSON round-trip into the module's Go type (`DisallowUnknownFields`) →
  module rules.
- Messages: configfs formats its own message per error kind (required, type, enum, range, pattern,
  additional property) from the kind's fields, and never echoes the offending value. A pasted token in a
  wrong field must not reach the UI, logs or the projection. Messages are English (backend text is
  English-only by user decision, P265); configfs' own fixed strings go through `i18n.T` with new
  `backend.core.config.*` keys.
- Module rules (cross-field, id references): `Rule[T]{Doc string; Check func(v T, at Locator) *Problem}`.
  `Doc` is mandatory and renders into `AGENTS.md`, so a rule cannot exist without its doc line.
- Schema keywords configfs reads itself (ignored by the validator as unknown keywords):
  `x-kira-ref: true` on a string field means it may contain references (§2.5); `x-kira-secret: true` means
  the whole value must be one reference, never a literal.
- Workflows keep `adeflow.Parse` (hand-written, many interacting rules). Folder accepts any decode
  function, so workflows use the store without a schema. P451 decides generated versus checked docs.

### 2.4 DB sync (one mechanism, every module)

- Direction: files to DB only. Files are the source of truth for config. No DB-to-file path exists except
  the one-time migration below.
- Projection: each module keeps a projection of its config in SQLite: the last valid parsed content per
  file, written only by the sync. It serves three needs: last good survives restart while a file is
  broken, state rows (run history, response history, op log) keep a local key to join and cascade on, and
  hot paths read rows instead of files when a module wants. Workflows' projection is
  `ade_workflow_last_valid`. The foundation defines the interface; each module implements it on its own
  table(s), so P450 adds no migration (none to collide with P447's).
- App writes never touch the projection. A UI edit writes the file (atomic, `baseHash` check), then the
  same load path projects it. App edits and external edits share one code path.
- Load: `Folder.List` at start before the module serves (as `Recover` before `Start`), then on every
  debounced watch event (200 ms). Per file: hash; unchanged JSON is skipped (current `record` compare);
  valid → `Projection.Record`; invalid → no DB change, `Problem` returned with the last good value, Warn
  log once per new hash (file name and line, never content); file gone → `Projection.Forget`.
- Identity: state references config only by the stable id (file stem). A rename is a delete plus a create.
  Whether a deleted item cascades or orphans its state is each module plan's call, stated per module.
- Migration of existing rows (P459 to P462): one-shot at first start of the new build. If the module's
  marker is unset, export every legacy row to `<id>.yaml` through the store, then set the marker (a
  settings row: app-produced, so state). Marker set means never export again, even if the folder is
  emptied by the user. Legacy secret values are never exported: they move into the P447 store and the file
  gets a reference. The helper lands with P459, its first user; the contract is fixed here.
- Studio/Space split: per §2.1, each process projects only into its own DB. The shared agent folder is
  watched and projected by both processes independently. Two processes writing one file are serialized
  by `baseHash` plus atomic rename: the later writer gets `ErrConflict`, never a silent overwrite.
- Config versus state for P450's own surface: workflow files config; `ade_workflow_last_valid` derived
  projection (SQLite); task workflow snapshots state (unchanged); `AGENTS.md` derived (regenerated, not
  config, not in SQLite).

### 2.5 Interpolation

- Syntax, one for every module: `${NAME}` reads an environment variable (`[A-Za-z_][A-Za-z0-9_]*`);
  `${secret:name}` reads an app secret (`[a-z0-9][a-z0-9_.-]{0,63}`); `$${` is a literal `${`. Anything
  else inside `${…}` is a load-time `Problem`. `${NAME}` matches Claude's native `${VAR}` in MCP config,
  so P454 can export env references unchanged. `{{name}}` stays the API module's own variable syntax
  (P460 keeps `apivars`); config files never use it, so the two never collide.
- Only fields marked `x-kira-ref` are interpolated. Shell command fields (hook commands, script steps) are
  never marked: the shell expands its own `$VAR`.
- Stage 1 (load): syntax checked, references kept verbatim in the decoded value and the projection.
  Stage 2 (use, at launch): `Resolver.Resolve(ctx, text)` returns the resolved text plus `[]Used{Name,
  Value, Placeholder}` for secret references only (apivars `UsedSecret` shape). Callers feed `Value`s to
  P447's masker and write the result only to a 0600 per-run file or env (P453). Env values are not masked:
  they are the user's environment, not app secrets.
- A missing env var or secret fails the resolve with an error naming the reference, never empty-string
  substitution. Resolver never logs values.
- Env source is injected (`Env func(string) (string, bool)`). The GUI process env on macOS lacks the login
  shell's variables; P453 picks the source (login-shell probe as in Studio's kubernetes `Env`, or process
  env).

### 2.6 Secret seam (P447 independence)

P450 defines, in `internal/configfs`:

```go
// SecretSource returns the plaintext of one app secret. Errors wrap ErrSecretMissing when absent.
type SecretSource interface {
	Secret(ctx context.Context, namespace, name string) (string, error)
}
type SecretSourceFunc func(ctx context.Context, namespace, name string) (string, error)
var ErrSecretMissing = errors.New("configfs: secret not set")
```

`Resolver{Env, Secrets SecretSource, Namespace string}`: the namespace is the owning module's (P447's
"one namespace per owner"), fixed by the module, never written in the file. P450 imports nothing from
P447 and wires no production `SecretSource`: no P450 surface resolves secrets in production. Integration
happens in P453 (first module with secret references), after P447 and P450 have both landed:
`appwire` builds `configfs.SecretSourceFunc` over P447's store, mapping its not-found error to
`ErrSecretMissing` and passing keychain-unavailable errors through. P447 needs no change for this.

### 2.7 AGENTS.md

- Generated, not hand-written. Source: a neutral `DocModel` (title, intro, file naming, options, rules,
  reference syntax). `DocFromSchema(schema, rules)` builds the options list from the schema (every property
  path, type, required, default, enum, range, description, `x-kira-ref`/`x-kira-secret`), so the reference
  part cannot drift from the validator. The intro is one embedded Markdown template per module with purpose
  and workflow prose only, no option facts. P451 builds its `DocModel` from `adeflow`'s key tables (no
  schema there).
- Fixed sections: header line "Generated by Kira <app>. Edits here are overwritten at start.", intro,
  Files (pattern, format, cap, one item per file, stem is id), Options, Rules, References (§2.5, listed only
  when a field is marked), How changes apply (watch, last good, where errors show, `baseHash` conflicts).
- Written by `Folder.WriteDocs` at app start when bytes differ (atomic). Creates the folder if missing.
  The watcher and `List` skip `AGENTS.md`.

### 2.8 Minimal UI contract

- Plain file edit in the user's own editor is the default. A module may add small edit actions; each writes
  the whole file through `Folder.Save` with `baseHash` and surfaces `E_CONFLICT` as workflows do. No new
  rich editor anywhere.
- Shared component `packages/workbench/src/config/ConfigFileBar.vue` (shadcn-vue `Button`, Tailwind,
  VueUse `useClipboard` through the existing `useCopy`): file path (truncated, full path tooltip), status
  (valid, or "Line N: message" through `FieldError`), Open (OS default app), Reveal (file manager), Copy
  path, and an "About these files" link that opens the folder's `AGENTS.md` when it exists. Props in, emits
  none; no Pinia store (no shared client state). Open and Reveal are plain bound calls, not TanStack Query
  (no server state).
- Bound service `ConfigFilesService` (repo-root `internal/configfs/configsvc`, embedded by each app like
  `windowsvc`): `Open({folder, file})`, `Reveal({folder, file})`. It accepts only a registered folder name
  plus a visible file in it (or `AGENTS.md`): no path from the renderer ever reaches the OS. Space binds it
  in P450 (workflows); Studio binds it with its first config module.
- "View": the module shows the file text read-only or its parsed form (workflows already do both). A
  `Status(folder)` list method and a `kira:config:changed` push land with the first module that has no list
  of its own (P452); workflows have `kira:adetask:workflows`.

## 3. API (repo-root `internal/configfs`)

```go
type Problem struct { // wire: line/col 1-based, 0 = not line-specific; path = JSON pointer
	Line, Col int; Path, Message string
}
type DecodeFunc[T any] func(file string, src []byte) (T, *Problem)
type Projection interface {
	Snapshot() (map[string]string, error)          // file -> last good JSON
	Record(file, valueJSON string, now int64) error
	Forget(file string) error
}
type Folder[T any] struct {
	Dir string; Ext string; Name *regexp.Regexp; Decode DecodeFunc[T]; Projection Projection
	Now func() time.Time
}
type Entry[T any] struct { File, Path, Hash string; Value *T; Problem *Problem } // Value: current or last good
func (f *Folder[T]) List() []Entry[T]
func (f *Folder[T]) Get(file string) (Entry[T], bool)
func (f *Folder[T]) Read(file string) (src []byte, hash string, err error)
func (f *Folder[T]) Save(file, baseHash string, src []byte) (Entry[T], error) // ErrConflict, ErrInvalid
func (f *Folder[T]) Watch(onChange func()) (stop func(), err error)
func (f *Folder[T]) WriteDocs(m DocModel) error
func WriteAtomic(path string, data []byte, perm os.FileMode) error // renameio
func ReadCapped(path string, max int) ([]byte, error)
func TextHash(src []byte) string
var ErrConflict, ErrInvalid error
func YAMLSchema[T any](schemaJSON []byte, rules ...Rule[T]) (DecodeFunc[T], DocModel, error)
func Text(max int) DecodeFunc[string]
type Rule[T any] struct { Doc string; Check func(v T, at Locator) *Problem }
type Locator func(pointer string) (line, col int)
type DocModel struct { /* §2.7 */ }
func DocFromSchema(schemaJSON []byte, rules []string) (DocModel, error)
func RenderAgentsMD(m DocModel) []byte
type Ref struct { Kind string; Name string; Start, End int } // "env" | "secret"
func Refs(text string) ([]Ref, *Problem)
type Used struct { Name, Value, Placeholder string }
type Resolver struct { Env func(string) (string, bool); Secrets SecretSource; Namespace string }
func (r *Resolver) Resolve(ctx context.Context, text string) (string, []Used, error)
// + SecretSource, SecretSourceFunc, ErrSecretMissing (§2.6)
```

Fit against consumers: P451 `DocModel` + `RenderAgentsMD` + `WriteDocs` over `adeflow`'s tables. P452
`Folder[string]` + `Text`, shared root, `Status`/push. P453 `YAMLSchema`, `x-kira-ref`/`x-kira-secret`,
`Resolver`, `SecretSource` adapter. P454 `Folder.Save` (import writes files), `Refs` (export keeps
references). P455 none directly. P459 to P462: `Folder`, `YAMLSchema`, `Projection` on their tables,
migration helper (§2.4), `.local.yaml` (P461). Nothing in the list has no named consumer.

## 7. Spec issues

- "Config lives … in the Kira Space app folder" conflicts with the DB split and with Studio-only modules:
  API (P460) and connections (P462) keep state in Studio's `kira.db`, so their files belong in Studio's
  home. The plan applies "own app's home" to modules and reads the Space-folder sentence as the location
  of shared definitions only (Q1).
- "Studio's shared definition rule for agent config" exists in no doc or code. P452/P453 say "Kira Studio
  owns it, Kira Space consumes it", while the Space Agents module edits it. With files, ownership is only
  a location; the plan picks the Space home (Q1).
- "Keychain secret": the keychain holds one key, not the values. Values are ciphertext in each app's DB.
  A config reference names a value in P447's store. Two apps with two DBs do not share secret values
  unless P447 makes them; P453 "Keychain secrets are shared" depends on that (Q3).
- The foundation has no module of its own. Store, watch, atomic write, last good, projection and the file
  bar get a production consumer here (workflows). Schema validation, references, the resolver and
  `AGENTS.md` generation have their first production callers in P451 to P453; in P450 the flow test drives
  them through a test kind. This follows the spec's order, but it is the "unused scaffolding" shape
  CLAUDE.md warns about for one to three phases (Q2).
- "Format per thing (yml, json or text)": JSON is dropped (§2.2).
- "DB follows" is unclear for a prose file (P452 context). Last good across restart still needs a
  projection, so every module has one. P452 states its table.
