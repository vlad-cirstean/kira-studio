### Runs at quit today

- Every live run ends recorded at quit: terminal runs through `Service.Exited` with `terminal.CauseQuit`
  (`EndQuit`), smart and headless runs through `Service.Close` (`endQuit`). Both write outcome source `restart`,
  reason "Kira <app> quit while it ran". A crash leaves rows `running`; boot `Recover` ends them with `EndRestart`
  ("interrupted: Kira <app> closed while it ran") through `Repo.FailRunning`, then skips waiting runs.
- `resume_id` already keeps a smart run's Claude session when a restart ended it (`resumeExpr`, keyed on source
  `restart`); `Service.Resume` continues it as a new run. `resumeArgs` rebuilds args from the run's stored params and
  names secret params (never stored).
- Nothing records "this run should be offered again". Outcome source `restart` alone cannot tell the last session
  from older ones.
- Re-running from the UI: `useRerun` -> `useRunScript`: a plain script without params opens a terminal at once (no
  confirm); others open the run dialog (preview + hash). `Start(args, hash)` refuses a second live run of the same
  key and returns a terminal token or a run id.
- `scriptruns.Bound` is embedded by each app's `bridge.ScriptRunsService` shim, so new Bound methods bind with no app
  Go change. Each app's frontend bridge (`frontend/src/bridge/index.ts`) wraps every binding; `automationsModule.ts`
  maps them onto `ScriptRunsSeam`.

## Decisions

### D1 One offer at start, one dialog, banners for later

- At start, the first window to claim the offer opens the shared dialog when any source has something to restore.
  Studio: Docker group + Runs group. Space: Runs group only.
- Claim: `ScriptRunsService.RestoreClaim({windowKey})` answers true once per process (first caller). Both apps have
  `scriptruns`, and the offer belongs to the app restart it owns. No prompt-router kind: that needs root
  `internal/prompts` plus both appwires and buys OS notifications nobody asked for.
- The host waits for sources for up to 15 s after mount. A Docker engine still booting answers `none` first; if it
  turns pending inside the window the dialog opens (or gains the group live, if already open). Later detections keep
  today's path: the Docker banner.
- Each module keeps a banner that reopens the dialog filtered to its own group: Docker `RestoreBanner` (existing),
  Runs a matching banner at the top of `AutomationsPanel`.
- Buttons: primary "Restore N" starts the checked items. "Don't restore" forgets every shown group. Escape/X means
  "later": nothing changes, banners stay.
- After a confirm where every chosen item started, the dialog dismisses the rest of each group (deselected means "do
  not restart", per the request). Any failure keeps the dialog open with inline errors; nothing is dismissed for that
  group.

### D2 "Was running" for scripts: a column marked when a quit or crash ends a run

- Migration in each app: `ALTER TABLE script_runs ADD COLUMN restore_pending INTEGER NOT NULL DEFAULT 0`.
- `Repo.finish` and `Repo.FailRunning` set it in the same UPDATE that ends the run:
  `restore_pending = CASE WHEN ? = 'restart' THEN 1 ELSE restore_pending END`, keyed on the outcome source exactly
  like `resumeExpr`. Covers quit (terminal, smart, headless) and crash (boot `FailRunning`). A user stop, window close,
  exit or timeout never marks.
- Boot `Recover` (after `FailRunning`, before `skipWaiting`): `UPDATE script_runs SET restore_pending = 0 WHERE
  restore_pending = 1 RETURNING id` in one statement; the ids become the in-memory offer (`Service.restore`). So the
  offer lives for one app session: answered, or replaced by the next quit's set. Nothing accumulates.
- Declined alternatives: deriving the set from outcome source and timestamps (cannot separate sessions); a key in the
  `settings` table (user preferences only, owned by each app's settings repo); a JSON file (state outside the DB).
- Purge (`keepFinished = 500`) can drop a marked row before boot only after 500 newer runs; the offer then omits it.
  Acceptable.

### D3 What a restore does per run

New `internal/scriptruns/restore.go`; Bound methods in `bound.go`.

- `RestoreState() (RestoreState, error)`: for each offered run id, newest first, deduped by run key
  (`scriptId`, `taskId`, `branchId`; keep newest): load the run and its script, rebuild args with `resumeArgs`, plan
  with `s.plan` (current definition), and report an item:
  - `ready`: plan has no blocker and no missing param.
  - `running`: `Runs.Running` finds a live run of that key now (user or schedule started it).
  - `needsInput`: a secret param (`resumeArgs` names) or a required param is missing. Not selectable; the row says to
    start it from Runs ("secret values are never stored").
  - `gone`: script deleted (or ADE task/branch gone: plan error `CodeNotFound`).
  - `blocked`: plan blocker (folder) or other plan error; `reason` carries the text.
  - Fields: `runId`, `scriptId`, `scriptName`, `color`, `kind`, `trigger`, `taskTitle`, `branchLabel`, `cwd` and
    `command` from the new plan (what will run, not what ran), `model`, `resume` (smart run with `resumable`),
    `params` (masked as stored), `endedAt`, `hash` (`hashOf` of the plan), `status`, `reason`.
- `Restore(RestoreArgs{Items []{RunID, Hash}}) (RestoreResult, error)`: refuses an id not in the offer
  (`backend.core.scriptRun.restoreNotOffered.body`). Per item, in order, under `startMu` like `Start`:
  - smart and resumable: the `Resume` path, with the plan hash checked first;
  - otherwise `Start(StartArgs{RunArgs: args, Hash: hash})`: a terminal script returns its token, a smart or
    headless one its run id; a changed script answers the existing `E_CONFLICT`.
  - Result per item `{runId, started *Started, error string}`. A started item leaves the offer; a failed one stays.
  - Trigger of the new run: `manual` (the user confirmed). No new trigger value.
- `RestoreDismiss() error`: clears the offer. `RestoreClaim(ClaimArgs{WindowKey}) (bool, error)`: true once.
- No push channel: the Service has no emitter for it, and adding one means both appwires. The Runs restore query
  refetches on window focus and on dialog open; a stale banner in another window resolves on its first click.
- Frontend, per started item: a terminal token opens a terminal tab exactly as `RunScriptDialog` `onSuccess` does
  (`ctx.openTerminalTab` with `launchToken`, `replace: scriptTabs.replaceTarget(key)`, so a stale tab of the same
  script is replaced). Smart and headless runs open no tab (they show in Runs and Operations); no tab spam.

### D7 Safety

- Nothing starts without the confirm. Each row shows what will run now: command or prompt kind, folder, params as
  stored (secrets masked), task. The plan hash guards edits between view and confirm (`E_CONFLICT` -> row error, the
  host refetches).
- Secrets are never replayed (`needsInput`). A live run of the same key is never doubled (`running`, and `Start`
  refuses anyway). Smart runs in worktree mode claim the worktree through the existing `Start`/`Resume` paths.
