### 1.2 Cmd+Enter

xterm 6.0.0 `src/common/input/Keyboard.ts:100-103`:

```ts
case 13:
  // return/enter
  result.key = ev.altKey ? C0.ESC + C0.CR : C0.CR;
```

`metaKey` is ignored, so Cmd+Enter sends plain `\r`. Claude Code submits on `\r`. Alt+Enter already
produces `ESC CR`, which is meta-Enter: Claude Code's newline key and zsh's default
`^[^M` (`self-insert-unmeta`, inserts a literal newline into the line buffer). Fix: send `ESC CR`
for Cmd+Enter, same bytes as xterm's own Alt+Enter. VS Code reaches the same result only through a
user keybinding (`workbench.action.terminal.sendSequence`); xterm has no option for it, so a custom
key handler is the only seam.

xterm `CoreBrowserTerminal._keyDown` (`:1021-1027`) calls the custom key handler first; `false`
returns before `evaluateKeyboardEvent`. `_keyPress` (`:1149`, `:1166`) also consults it and already
drops any meta-modified keypress. Public API (typings `xterm.d.ts`): `attachCustomKeyEventHandler`
(`:1072`), `input(data, wasUserInput)` (`:1025`).

Kira Studio has a native menu accelerator on Cmd+Return (`view.run`,
`apps/kira-studio/internal/appshell/menu.go:47`). Kira Space has none. Studio's `view.run` handler is
a no-op without a mounted request/console view (`studioCommands.ts:46`), so a terminal tab is safe
either way. Whether WKWebView still forwards the key to the menu after the page calls
`preventDefault` is macOS-only behaviour (§5).

### 1.3 Why Claude Code TUI scroll is slow

Claude Code 2.1.310 (sandbox `/opt/claude-code/bin/claude`) has a fullscreen renderer: alt screen
plus mouse tracking (bundle carries `?1049h`, `?1000h`, `?1006h`, `?1007h`, and env flags
`CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN`, `CLAUDE_CODE_DISABLE_MOUSE`, `CLAUDE_CODE_SCROLL_SPEED`). It
does its own scrolling from wheel reports.

xterm side, 6.0.0 `CoreBrowserTerminal.ts`: with wheel tracking on, `sendEvent` sends exactly one
wheel report per DOM wheel event (`:641-659`), no matter how many lines the delta is worth. With alt
buffer and no tracking it sends one arrow per event (`:820-844`, comment: "simplified to simply send
a single up or down sequence"). `CoreMouseService.consumeWheelEvent` (`:241-269`) also damps a
likely-trackpad event (`|deltaY| < 50`) by `0.3` and floors to whole lines. The 6.1 beta
(`MouseService.ts:146-155`, `:276-292`) is identical, so upgrading changes nothing.

VS Code (`microsoft/vscode` main, `xtermTerminal.ts:270-275`, package.json `@xterm/xterm
^6.1.0-beta.304`) passes `scrollSensitivity: mouseWheelScrollSensitivity` (default 1),
`fastScrollSensitivity` (default 5), `smoothScrollDuration` 0 unless `smoothScrolling` plus a
physical wheel (`:641`), and `scrollOnEraseInDisplay: true`. So VS Code's xterm sends the same one
report per event. The difference is on Claude Code's side.

Claude Code's wheel config (decompiled from bundle, readable strings):

```js
gy()  = TERM_PROGRAM==="vscode" || xtversionName.startsWith("xterm.js")   // xtermJs
uro() = cursor || (TERM_PROGRAM==="vscode" && 1.92<=ver<1.105) || xtversion "xterm.js"  // wheelFlood
useDecayCurve = !wheelFlood && (xtermJs || win32 || WT_SESSION)
base = jediTerm ? 2 : (CLAUDE_CODE_SCROLL_SPEED ?? (!wheelFlood && (xtermJs || WT_SESSION) ? 3 : 1))  // max 20
```

`fAt` turns each wheel report into rows: decay curve (VS Code) gives `base`-scaled rows with
acceleration up to 36 rows per report; "window (native)" mode gives `base` rows, rising by 0.3 per
report under 40 ms apart, capped at `max(6, base*2)`.

In Kira: `TERM_PROGRAM=Kira Space`, and xterm 6.0.0 does not answer XTVERSION (`CSI > q` has no
handler in `InputHandler.ts`; the beta adds `sendXtVersion`). So Claude Code picks window mode,
`base = 1`: one row per report. Under trackpad damping that is about 0.3 rows per line of finger
travel. In VS Code ≥1.105 it picks decay curve, `base = 3`. That is the "very slow" gap.

Main buffer (non-fullscreen Claude Code, shells, `less` without alt screen): xterm 6.0.0's `Viewport`
is VS Code's own `SmoothScrollableElement` (`Viewport.ts:42-63`) fed `scrollSensitivity`/
`fastScrollSensitivity`. Kira's values equal VS Code's defaults, so native scrollback already
matches. Only `scrollOnEraseInDisplay` differs: VS Code pushes an `ED2` clear into scrollback, Kira
erases it, so scrolled-back history loses whole screens.

## 2. Design

### 2.1 Cmd+Enter (`terminalRenderer.ts`)

After `new Terminal(...)`, before `open`:

```ts
// Cmd+Enter is meta-Enter (ESC CR), xterm's own Alt+Enter bytes: a newline in Claude Code and zsh.
term.attachCustomKeyEventHandler((ev) => {
  if (ev.key !== 'Enter' || !ev.metaKey || ev.ctrlKey || ev.altKey || ev.shiftKey) return true;
  if (ev.type === 'keydown' && !ev.isComposing) {
    ev.preventDefault();
    term.input('\x1b\r', true);
  }
  return false;
});
```

- `term.input` goes through xterm's own `onData`, so it reaches `writeTerminal` like typed text and
  honours `scrollOnUserInput`.
- `false` for every event type of the chord, so keypress/keyup never add a stray `\r`.
- `preventDefault` stops `useShortcut` listeners (they skip `defaultPrevented`) and asks WKWebView
  not to hand the key to Studio's `view.run` menu item.
- Cmd+Shift+Enter is untouched (Studio's `view.runAll`). Shift+Enter is not in this row's ask; it
  stays `\r`.
- Phone `TerminalScreen.vue` inherits it (iPad hardware keyboard Cmd+Enter); bytes go through its
  own `fromTerminal`, length 2, so the sticky-Ctrl branch is not hit.

### 2.2 Scroll

Two changes, both VS Code parity:

1. `terminalRenderer.ts` options: add `scrollOnEraseInDisplay: true` (VS Code's value). One-line
   comment: VS Code parity, keeps `ED2`-cleared screens in scrollback.
2. `internal/terminal/shell.go` `sessionEnv()`: add `CLAUDE_CODE_SCROLL_SPEED=3` only when the app's
   own environment does not already set it (`os.LookupEnv`), so a user's explicit value wins (env
   is appended after `os.Environ()`, last value wins in `os/exec`). A shell rc can still override.
   Comment: Claude Code picks 3 for VS Code's xterm.js; it cannot tell Kira's xterm.js apart from a
   native terminal (no XTVERSION in xterm 6.0.0), so it would fall back to 1.

   Result: window mode at `base 3`. One report gives 3 rows, rising to 6 for fast reports. With
   trackpad damping (one report per about 3.3 lines of travel) that is close to 1:1 with finger
   travel. VS Code's decay curve still accelerates harder on a fast flick (up to 36 rows per report).
   This is the one known gap (§5).

Declined:

- `TERM_PROGRAM=vscode`. That is the only way to get Claude Code's decay curve. It breaks P103's
  `TERM_PROGRAM` identity and tells every tool it runs inside VS Code; Claude Code alone branches
  on `TERM_PROGRAM==="vscode"` at 6 sites in 2.1.310's bundle.
- Answering XTVERSION as `xterm.js(...)` via `term.parser.registerCsiHandler`. Claude Code then sets
  `wheelFlood` (the `uro()` fallback), which forces `base 1` and no decay. That is slower, not faster.
- Repeating each xterm wheel report N times per event, or a custom wheel encoder via
  `attachCustomWheelEventHandler`. VS Code sends one report per event too, so this would diverge
  from the parity the user asked for. It would also re-implement xterm's private mouse encoding
  (X10/SGR/URXVT, cell coordinates) that the public 6.0.0 API does not expose.
- Raising `scrollSensitivity`. It changes native scrollback too (already VS Code parity) and still
  yields one report per event in mouse mode.
- Upgrading to 6.1 beta. Wheel code identical (§1.3), and it is a prerelease.
