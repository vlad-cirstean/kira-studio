## 2. Design

### 2.1 Selection store

New `api/state/collectionSelection.ts`, `useCollectionSelectionStore` — one concern: which tree
rows are selected. Owns:

- `focusKey: string | null` — today's `collectionsStore.selected` (roving stop, single-target
  actions, palette Variables…). Moves here; `collectionsStore.selected` is removed and its writes
  (`createCollection`, `createItem`, `createGrpcItem`, `moveRow*`, `deleteRow`, `beginRename`,
  `importPostman`) call the selection store. Keep the field name `selected` out; one term:
  "focus key".
- `keys: ShallowRef<ReadonlySet<string>>` — selected set, always contains `focusKey` when non-null.
- `anchorKey: string | null` — range anchor.
- Actions: `selectOnly(key)`, `toggle(key)` (Cmd/Ctrl-click; removing the focus key moves focus
  to the clicked row anyway, anchor = clicked row), `extendTo(key, order, additive)` (Shift; range
  anchor..key in `order`; `additive` keeps prior keys, for Cmd/Ctrl+Shift), `selectAll(order)`,
  `selectMany(keys, focus)` (after a move), `collapseToFocus()` (Escape), `prune(order)`, `isSelected(key)`, `count`.
- `prune`: CollectionsTree watches `visibleRows` keys and prunes any selected key no longer
  visible (collapse, search, delete, remote change). Reason: a bulk action must never hit a row the
  user cannot see. Focus falls back to the anchor or first remaining key, else null.

Store stays order-free; callers pass the visible key order. Selected rows in tree order come from
`visibleRows.filter(isSelected)` (a computed in CollectionsTree, `selectedRows`).

### 2.2 Pointer and keyboard

`CollectionRow.vue`: `select` emit carries the `MouseEvent` (`select: [row, event?]`). Tree's
`onSelect(row, event)`:

- `isPrimaryModifier(event)` and Shift: `extendTo(key, order, true)`.
- Shift: `extendTo(key, order, false)`.
- `isPrimaryModifier(event)`: `toggle(key)`.
- else `selectOnly(key)`.

`isPrimaryModifier` from `@workbench/shortcuts/keys` (Cmd on mac, Ctrl elsewhere). Row's
`onFocus` select only fires when the row is not already selected (unchanged guard, now
`isSelected`), so Tab-focusing a multi-selected row keeps the set.

Row visuals: every selected row gets `rowVariants({ selected: true })` and `aria-selected`; the
tree gets `aria-multiselectable="true"`. Tabindex 0 only on the focus key's row (roving stop).

Keyboard — extend `useListNavigation` (`packages/workbench/src/behaviour/listNavigation.ts`) with
one opt-in option, other callers unaffected:

```ts
/** Shift+Up/Down/Home/End: move the roving stop and extend a selection to it. */
onExtend?: (item: T) => void;
```

In `onKeydown`, before the `if (e.shiftKey) return;` line: when `opts.onExtend` and `e.shiftKey`
and key in Up/Down/Home/End, compute `navigate(...)` as today, focus the target, call
`onExtend(item)`. Tree passes `onExtend: (row) => selection.extendTo(row.key, order, false)`.
Plain arrows keep `activeKey` setter -> `selectOnly` (unchanged behaviour).

New shortcut `tree.selectAll` in `packages/shared/domain/shortcuts.ts`
(`{ key: 'A', cmdOrCtrl: true }`, scope `tree`), added to `TREE_IDS` in `treeShortcuts.ts`.
`useShortcut` with `ignoreTextFields: true` already leaves the rename input and search field alone.
Escape on the tree (no drag, no rename): `collapseToFocus()`; bind via VueUse `useEventListener`
on the scroll container, skipped when `defaultPrevented`.

Mac risk: Edit menu SelectAll role is a key equivalent. WKWebView should receive the keydown first, and a
`preventDefault` should consume it (not verified in this repo). Implementer checks in the webkit UI

### 2.4 Drag and drop

**Library decision: pointer-based drag on VueUse, no new dependency.** Options weighed:

- vue-draggable-plus (Sortable, MIT; already used): list reorder of mounted DOM siblings only. Cannot
  serve a virtualized tree whose rows unmount on scroll, nor nest-into (ARCHITECTURE.md:887).
- Native HTML5 DnD: `dragend` fires on the source element, which the virtualizer unmounts during
  auto-scroll; no auto-scroll control; OS drag image of one row, not a selection count. Real requirement it fails: a drag that survives its source row
  unmounting.
- @atlaskit/pragmatic-drag-and-drop (Apache-2.0, open source) with its tree-item hitbox: built on
  HTML5 DnD, so the same unmount and auto-scroll gaps; second drag stack beside the in-repo one.
- In-repo `connectionReorder.ts` pattern (VueUse `useMouse`/`useElementByPoint`/`useRafFn`): already
  solves the virtualized-tree case and is tested by `connection-order.spec.ts`.

**Shared core.** Extract the generic half of `connectionReorder.ts` into
`packages/workbench/src/behaviour/treePointerDrag.ts`:

```ts
export function useTreePointerDrag<D>(opts: {
  container: Ref<HTMLElement | null>;
  /** Row under a press that may start a drag, or null. */
  pressable: (target: HTMLElement) => HTMLElement | null;
  disabled: () => boolean;
  rowHeight: () => number;
  /** Drop under the pointer for the hovered element and client y, or null. */
  resolve: (hit: HTMLElement | null, y: number) => D | null;
  onDrop: (pressed: HTMLElement, drop: D) => void;
}): { dragging: Readonly<Ref<HTMLElement | null>>; drop: Readonly<Ref<D | null>> };
```

Holds press tolerance, `useElementByPoint` hit loop, edge auto-scroll, Escape/pointercancel,
click swallow. `connectionReorder.ts` becomes a thin caller (`resolve` = top/bottom edge of a
connection row, `onDrop` = `orderAfterDrop`); its behaviour is unchanged and
`connection-order.spec.ts` stays green. `http/**` may not import `project/**` (biome), hence
workbench as the home.

Note `dragging` exposes the pressed row; the api caller stores the dragged keys itself at drag
start (press on a selected row drags the whole selection; press on an unselected row first
`selectOnly`s it on drag start, Finder/VS Code behaviour).

**API drop model** — new `api/collectionDrop.ts` (pure, no Vue):

```ts
export type DropZone = 'before' | 'into' | 'after';
export interface DropTarget { key: string; zone: DropZone }
/** Where the moved items land. beforeId null = append. */
export interface Placement { collectionId: string; parentId: string | null; beforeId: string | null }

export function zoneFor(row: CollectionRowVm, fraction: number, searching: boolean): DropZone | null;
export function topmost(rows: readonly CollectionRowVm[], items: readonly CollectionItemSummary[]): CollectionRowVm[];
export function placementFor(target: DropTarget, moved: ReadonlySet<string>, items: readonly CollectionItemSummary[]): Placement | null;
```

Rules:

- `zoneFor`: collection row -> `into` (whole row). Folder row -> top quarter `before`, bottom
  quarter `after`, middle `into`; an expanded folder with children turns its bottom quarter into
  `into` (the next row is its first child, so "after" would draw in the wrong place). Request row ->
  top half `before`, bottom half `after`. While search is active only `into` is allowed (`before`/
  `after` return null) — reorder against a filtered list hides siblings, same refusal P140 made
  for environments.
- `topmost`: drop rows whose ancestor is also selected (moving the ancestor carries them). Order =
  tree order.
- `placementFor`: resolves `into` -> (row's collection, row id or null for a collection row,
  `beforeId: null`); `before`/`after` -> target's own parent; `beforeId` = target id (`before`) or
  next sibling (`after`), then skipped forward past any moved sibling (a selection dropped next to
  one of its own members). Returns null when: target row is moved or a descendant of a moved row
  (no drop into self/descendant); every moved item would land where it already is in the same
  order (no-op drop, no IPC).
- Drag is refused when the selection holds a collection row (collections never nest; reordering
  collections has no API and is out, see 4).

`CollectionsTree.vue` wires `useTreePointerDrag` with `pressable` = closest
`[role="treeitem"][data-kind="folder"|"request"]` not in the sticky band, `resolve` = row under
pointer -> `zoneFor` + `placementFor` (null = no-drop, cursor `not-allowed` on the tree), `onDrop` =
`collectionsStore.moveRows(keys, placement)`. Hovering a collapsed folder in `into` zone does not
auto-expand (keep out; no requirement).

Visuals (Tailwind, in `CollectionRow.vue` props `dragging`, `dropZone`): dragged rows
`SORTABLE_GHOST_CLASS`; `into` target `ring-1 ring-inset ring-focus bg-accent/40`; `before`/
`after` the same `h-0.5 bg-focus` line `TreeRow.vue` draws (`data-testid="tree-drop-indicator"`,
`data-zone`). Count badge near pointer when `keys.length > 1`: small fixed `Badge` following
`useMouse` (`data-testid="collection-drag-count"`), `pointer-events-none`. Tree gets
`select-none` while dragging.

### 2.5 Backend batch calls

Batch: yes, mirroring P358's `review.markMany`. Per-item `MoveItem` calls are non-atomic (a
mid-batch failure leaves a half-moved selection) and each emits its own `treeChange`, so every
window refetches the tree N times; a reorder across N items also needs one shared target order,
which per-item appends cannot express.

`CollectionsService` (bridge), replacing `MoveItem` and `Delete` (no other caller of either bridge
method; frontend single-row paths route through the batch with one id):

```go
type CollectionsMoveItemsArgs struct {
	ItemIDs      []string `json:"itemIds"`
	CollectionID string   `json:"collectionId"`
	ParentID     *string  `json:"parentId"`
	BeforeID     *string  `json:"beforeId"`
}
func (s *CollectionsService) MoveItems(args CollectionsMoveItemsArgs) error

type CollectionsDeleteManyArgs struct {
	CollectionIDs []string `json:"collectionIds"`
	ItemIDs       []string `json:"itemIds"`
}
func (s *CollectionsService) DeleteMany(args CollectionsDeleteManyArgs) error
```

Bridge guards: `ipcerr.Required` for empty `itemIds`/`collectionId`, and for both delete lists
empty. Repo sentinel `repos.ErrInvalidMove` (into self/descendant, parent not a folder of the
target collection, `beforeId` not a child of the target parent or itself moved) maps to
`ipcerr.T(CodeBadRequest, "backend.studio.collections.invalidMove.body", nil)`; a missing id maps
to `ipcerr.NotFound`; anything else `InternalErr`. One `emitApiData` per call: `treeChange()`
plus `variablesChange(collection, id)` per deleted collection.

Repo (`internal/storage/repos/collections.go`):

- `MoveItems(ids []string, collectionID string, parentID, beforeID *string) error` replaces
  `MoveItem`. One tx: load `id, collection_id, parent_id, kind` for all items (local table, same
  size `List` already returns whole); dedupe ids first-seen; validate target collection, parent,
  `beforeId`; drop non-topmost ids; reject when the target parent is a moved id or under one (walk
  parent chain). Per moved item whose collection changes: the existing recursive CTE rewrites the
  subtree `collection_id`. Set `parent_id`. Target order = target parent's children minus moved,
  moved inserted (argument order) before `beforeId` or appended; write `sort_order` 0..n-1. Then
  `reindexSiblings` for each distinct old (collection, parent) pair other than the target. Commit.
  `updated_at` on moved rows.
- `DeleteMany(collectionIDs, itemIDs []string) error`. One tx: dedupe; skip item ids inside a
  deleted collection or under another deleted item (cascade covers them); missing id -> not-found
  sentinel, rollback (no partial delete); delete collections, then items; reindex each surviving
  distinct old parent. Repo `Delete` stays (import rollback) and shares the per-row delete helper.

Frontend: `apiControl.ts` `collectionsMoveItems(args)`, `collectionsDeleteMany(args)`; drop
`collectionsMoveItem`, `collectionsDelete`. Regenerate bindings with
`wails3 task common:generate:bindings` (DEV_ENVIRONMENT.md), never by hand.

### 2.6 Store mutations (`state/collections.ts`)

- `moveRows(rows, placement)`: one `useMutation` (`mutationKey ['apiCollectionsTree','moveItems']`,
  `onSuccess: afterTreeListChange`), `revealItem(placement.collectionId, placement.parentId)`,
  selection keeps the moved keys (`selection.selectMany(keys, focus)`), `state.error` on failure.
  `moveRow`/`moveRowToNewCollection` become one-row callers (`placement` = target root, append —
  today's semantics).
- `deleteRows(rows)`: `topmost` rows; orphan set = union of `subtreeItemIds` per row (already
  correct per kind) computed before the call; one `deleteManyMutation`; purge caches as today;
  `closeVariableSetTabsForOwner` per deleted collection; `selection.prune` runs off `visibleRows`.
  `deleteRow` removed (callers use `deleteRows([row])`).
- Request tabs of deleted requests stay open (existing orphan rule, deliberate: closing would lose
  unsaved edits). Not changed here; the bulk dialog says it (2.7).

TanStack Query: both mutations end in `afterTreeListChange` (tree key refresh + `reconcileTree`).
Other windows refetch from the one `treeChange` event.
