## 1. What the code does today

Importer is Go only. No TS parser exists (grep of `frontend/src`, `packages/` finds none).

- `internal/postman/environment.go` `ParseFile`: an `info` member means collection; `_postman_variable_scope: "globals"` is refused; a `values` array means environment. Anything else fails with "not a Postman collection or environment".
- `parseEnvironment`: per `values[]` entry reads `key` and `value` via `decodeScalarString` (string, number, bool), `type`, `enabled`. `enabled: false` skips the entry and counts `Disabled`. `type == "secret"` sets `Secret`.
- `internal/postman/parse.go` `decodeVariables`: same for collection `variable[]`, plus `description`. Ignores `disabled`.
- `internal/storage/repos/variables.go` `ImportVariables` / `ImportEnvironment` insert every parsed value; secrets go through `encryptFor` (`kira:v3` envelope in `secret_value`). `promoteIfNeeded` (legacy pre-P5 rows) has its own copy of the scalar decode (`scalarString`).
- `frontend/src/api/VariableRow.vue` renders `row.value`; a secret shows `••••••••` until revealed.
- Fixtures `internal/postman/testdata/environment.json` and `internal/flows/apiflow/testdata/{collection,environment}.json` are hand-written. Every entry has a `value`.

The pipeline carries any string, number or bool `value` end to end. No zod schema or dedup step sits in the path.

## 2. Root cause

Primary, outside this app: since Postman's September 2025 variables model, a variable's value is **local by default**. Local values never go into an exported file. Only a value the user explicitly *shared* (the old "initial value") is written to `value`. Postman staff state this on the Postman forum (thread 86088, "Exporting environment to share as file gives strange results"). Postman's docs say collection variables follow the same share model. So a real export carries the key with `"value": ""` for every unshared variable. That matches the report exactly: keys present, values empty; "some" values missing in environments, meaning the unshared ones.

This app cannot import a value the file does not contain. No real Postman export format writes local values (`currentValue`/`initialValue` members exist only in Postman's internal model, not in exports). So "import every value" splits into:

1. Import every value the file does carry, in every real shape (section 3 gaps).
2. Say clearly, at import time, when entries arrived without a value, and what to do in Postman (section 4).

Not verified: no real export of the user's is in the repo. Orchestrator: ask the user for one redacted export. If it does have non-empty `value`s that fail to import, that is a different bug, and this plan's tests will localise it.

Secondary, in this app:

- G1. Non-scalar `value` (object, array) imports as `""`. Postman's schema leaves `value` untyped, and `pm.environment.set(k, obj)` from older versions persists objects. Silent loss.
- G2. Postman API wrappers are refused. `GET /collections/{id}` returns `{"collection": {...}}`; `GET /environments/{id}` returns `{"environment": {...}}`. Users save these via the API, the Postman CLI or scripts. Today: "not a Postman collection or environment".
- G3. Collection `variable[]` ignores `disabled: true`. The entry imports as active, while Postman resolves nothing for it. Environments already skip and count.
- G4. `promoteIfNeeded`'s `scalarString` duplicates `decodeScalarString`. G1's fix must not diverge between them.

## 4. Empty-value warning

New kind `postman.WarnEmptyValues = "empty_values"`. Counts imported entries whose value is `""` after decode (V6), in collection `variable[]` (collection level only) and environment `values[]`. Disabled entries never count; they are not imported. Secret entries count too (empty secret is still empty).

- Postman package: `Environment.Empty int` beside `Disabled`; the collection side uses `Report.warnN(WarnEmptyValues, n)`.
- Bridge (`internal/bridge/collections.go`): add the kind to `importWarningKinds` right after `WarnVariablesImported`; add a `case` in `importWarningDetail`; `importEnvironment` appends it after the disabled warning. G3's collection-level disabled count also goes through `Report.warnN(WarnDisabledVariables, n)`; add `WarnDisabledVariables` to `importWarningKinds` (it is missing there today, because only environments used it).
- i18n (`packages/theme/src/i18n/en.json`, under `backend.studio.collection.import`): `emptyValues.body`: "{count} variables arrived without a value. Postman exports only shared values; share them in Postman, then export again." Run the copy catalog check (`scripts/copy/`) the repo already wires.
- No value text in any log line or warning. Counts only.

## 5. Changes, by file

1. `internal/postman/parse.go`
   - New exported `VariableValue(raw json.RawMessage) string`: `decodeScalarString` result when ok; for an object or array, the compact form (`json.Compact` into a buffer; on error `""`); `null`/absent gives `""`. Exported because `repos` already imports `postman` (G4).

4. `internal/storage/repos/variables.go`: delete `scalarString`; `promoteIfNeeded` calls `postman.VariableValue(entry.Value)`. Legacy promotion also skips `disabled:true` entries: add `Disabled bool` to `promotedVariableRow`. No warning there (no import report on that path).

7. Export side: no change. `write.go` already emits `value` from `Variable.Value`; a V5 object now round-trips as a JSON string, not an object. Accepted: the app stores text; Postman reads a string value fine.
