# P325: Keep fetched data when a connection drops

Base commit `79a7ace72` (branch `v0.2.10`). One sequential Sonnet implementer. Frontend only. No
stream split: every change hangs off one new predicate (`isStale`), so the files depend on each
other in order.

## Scope

- **In: SQL data view** (`DataView.vue`, tab kind `data`). It is the only view with a staged
  edit/commit path (`pendingChanges.ts`), which is what the row's "cannot be edited or committed"
  guards.
- **Out: Documents, KeyValue (Redis/S3), Stream (Kafka/SQS), Browse, Definition, Console.**
  Each has its own page store, its own write path (immediate writes, no staging, per
  `docs/ARCHITECTURE.md` "MongoDB/Redis/Kafka/SQS/S3 write immediately") and its own lockout
  predicates. Keeping their data needs a separate lockout audit per view. They keep today's
  behaviour: drop the page and show the reconnect panel. If the user wants them too, that is a
  new SPEC row, not part of this phase.

## Current state

- **What clears data on drop:** `state/tabs.ts:192-199`. On a `disconnected`/`error` connection
  state, every tab of that connection is unhydrated (`unmarkHydrated`) and its page bytes are
  freed (`actions.dropPageStoresForTab`, which blind-calls every kind's `dropResources`;
  `createTabsStore.ts:173`). The grid runtime record and the pending-change set survive.
- **Second drop signal:** a read failing with `E_ENGINE_DOWN`/`E_CONNECT`
  (`viewOp.ts:23` `DISCONNECTED_CODES`) runs `applyLoadFailure` (`viewOp.ts:143-153`), which
  unhydrates the tab. The page is kept (`runPagedLoad` never drops on failure), but the backend
  state can still say `connected`.
- **What hides data:** `DataView.vue:326-341`. `v-if="needsReconnect"` swaps the whole grid for
  the `EmptyState` reconnect panel. `needsReconnect` is
  `!isHydrated(tab.id) || status !== 'connected'` (`useConnectionGate.ts:30-32`).
- **Edit gates today:**
  - `SlickGridHost.vue:255` `isWritable()` feeds `canEditTable()` (`:284`) and `canDeleteRows()`
    (`:293`). Those gate the grid `editable` option (`canEditTableReactive` watch, `:2387`),
    paste (`:1820`), cell/row menus (`ctx.canEdit`/`ctx.canDelete`: Paste, Set NULL, Duplicate
    row, Delete row), and the dock's `onEdit`/`onRevert` (publication watch, `:2455-2540`).
  - Insert-row `<input>`s are plain DOM, made read-only only while committing (`:211`, `:2391`).
  - `DataToolbar.vue:63` `isWritable` gates Add row, Delete rows, Generate (with
    `canGenerateData`, `:166`).
  - `DataView.vue:83` `isWritable` gates Preview command, Discard, Commit (`:279-300`).
    `onGenerateData` (`:153`) is the palette path.
  - `caps` comes from `connectionsStore.states[id].caps`. A `disconnected`/`error` state carries
    `caps: null` (`service.go:976`, `:1000`), so most write controls already go disabled once the
    state flips, but with the wrong tooltip ("connection read-only"). When the tab is unhydrated
    by a failed read while the state still says `connected`, caps stay set and nothing blocks
    editing.
- **Session change without a drop in this tab:** Disconnect then Connect from the tree. The
  `disconnected` event unhydrates the tab, so it is covered by `needsReconnect`. A failed connect
  (`error`) is covered the same way. The one gap: `ConnectionState.since` is set once per
  successful connect (`service.go:954-956`), and nothing records which session a shown page came
  from. After a reconnect from outside the tab (tree, MCP `connectForQuery`), `onOpened` re-open
  can re-hydrate the tab (`tabs.ts:145-150`) while it still shows the old session's page.
- **Backend:** `adapterhost/data.go:154` `Dispatcher.Mutate` opens with `requireLiveAdapter`, which
  refuses with `E_ENGINE_DOWN` when no adapter is live. `data.preview` builds statements
  server-side too. No other guard.
- **Dock read-only reason:** `views/shared/celleditor/state.ts:49` `readOnlyReasonFor` plus
  `readOnlyChip.ts`. With `onEdit` undefined and no reason, the dock is read-only with an empty chip.

## Design decisions

- **Definition of stale.** A data tab's shown page is stale when either holds:
  1. `needsReconnect` (unhydrated, or status is not `connected`), or
  2. the page was read under a different connection session: `rt.loadedSince !== null` and
     `rt.loadedSince !== states[connectionId]?.since`.
  Rule 2 closes the outside-reconnect gap at no protocol cost: `since` already exists on the
  wire and changes only on a new connect. A fresh load re-stamps it, so any successful read
  (Refresh, paging, filter) clears staleness.
- **One predicate, one owner.** Extract the body of `needsReconnect` into a plain exported function
  `tabNeedsReconnect(tabId, connectionId)` in `useConnectionGate.ts`. It reads reactive stores,
  so it is reactive inside any `computed`/`watch` and still callable from event handlers.
  `useGridViewStore` gets `isStale(tabId)`, combining both rules. Every grid gate calls
  `isStale`. No second copy of the logic.
- **Keep the page for `data` tabs only.** `tabs.ts` skips `dropPageStoresForTab` for
  `t.kind === 'data'`. It still unhydrates. Other kinds keep dropping (scope above).
- **UI: existing components only.** The reconnect `EmptyState` stays for a tab with no page
  (restored session, never loaded). A tab with a page keeps the grid and gains a top strip:
  `Alert strip variant="warn" icon="plug"` with `AlertDescription` plus `AlertAction` holding
  `Button variant="toolbar-primary" size="kira" :pending="reconnecting"`, reusing
  `studio.common.reconnectAndLoad.label`. Same composition as `KeyValuePane.vue:236-260`, same
  strip slot as `mask-preview-strip`. No new variant, size, or component.
- **Selectable, copyable, searchable.** Selection, copy, find, column resize/reorder, and FK
  navigation are reads and stay on. Only write paths lock.
- **Reads while stale stay as they are.** Pager, page size, Σ count, filter and sort issue a read.
  Against a dead connection that read fails as disconnected: the page stays, the pager reverts
  (`revertPageIndexOnFailure`), and the strip keeps explaining. Refresh already routes to
  reconnect (`refreshOrReconnect`). No new gating there, since a read never updates data.
- **Write lockout while stale:** grid inline edit, paste, Set NULL, Duplicate row, Delete row,
  insert-row inputs, dock edit/revert, Add row, Delete rows, Generate data (toolbar, palette and
  the dialog's own submit), Preview command, Commit.
- **Discard and Revert row stay available.** They only drop local staged changes, never reach
  the database. Discard's gate becomes `committing || (!isWritable && !stale)`. Revert row is
  already gated on `isCommitting` only (`menu.ts:416`), unchanged.
- **Staged changes survive the drop.** Nothing clears `pendingChanges` on drop (today too).
  Edits are keyed by primary key, so they still apply after the reconnect reload; Commit
  re-enables once the fresh page lands.
- **Inline edit open at the drop is staged, then locked.** `grid.setOptions({ editable: false })`
  (the `canEditTableReactive` watch) runs SlickGrid's `prepareForOptionsChange`, which calls
  `commitCurrentEdit()` (`slick.grid.ts:1380-1386`, slickgrid 5.20.0). That reaches
  `editorCtx.commit` and then `stageEdit`, which is local only. No extra code; the UI spec covers it.
- **No backend guard.** `Mutate` already refuses with `E_ENGINE_DOWN` when the connection is down.
  The remaining case is a page from an older session over a live adapter. The frontend closes it
  synchronously: `onCommit` checks `isStale` in the same tick that `commitPending` sends
  `data.mutate` (no await between). A server-side session check would need the router's adapter
  epoch exposed to the frontend and a new wire field on `MutateRequestWire`. That costs a
  protocol change for a race the single-threaded click path already rules out. Ops are
  primary-key addressed either way.
- **Writable badge** reads Read-only while stale (`effectivelyWritable` adds `!stale`), reusing
  `common.state.readOnly.status`.
- **Library rules.** No new dependency. Pinia store owns the predicate (grid store, its own
  concern: grid runtime). Tailwind only, no `<style>`. shadcn-vue `Alert`/`AlertAction`/`Button`.
  No VueUse or TanStack Query fit: no DOM wiring, no new bridge fetch.

### 1. `apps/kira-studio/frontend/src/views/shared/useConnectionGate.ts`

- Add and export `tabNeedsReconnect(tabId: string, connectionId: string | null): boolean`:

### 2. `apps/kira-studio/frontend/src/views/grid/state.ts`

  (`ConnectionState.since`) the shown page was read under. `defaultRuntime()` sets `null`.
- `load()` `apply`: after `setPage`, set
  `rt.loadedSince = useConnectionsStore().states[tab.connectionId]?.since ?? null`. Import
  `useConnectionsStore` from `../../state/connections` (it imports only `control`, so no cycle).
- New `isStale(tabId: string): boolean`:
  - Find the tab with `findDataTab`. Return false with no tab or no `connectionId`.

  - Export it from the store's return object.

  has frontend behaviour only.

  tree menu `menu-item-disconnect` as in `tree.spec.ts:622`. One test:
  1. Open the table and stage one cell edit (`pending-count-chip` shows 1). Open a second
     inline editor and type, without committing.
  2. Disconnect from the tree menu. Expect `grid-stale-strip` visible and no `reconnect-panel`.
     Grid cells still show the fetched values (`gridCell`). The open edit is now staged
     (pending count 2).
  3. Click a cell: it selects, and the dock shows the value with chip "Connection lost".
     Double-click opens no editor. `toolbar-commit-changes`, `toolbar-preview-command`, add row
     and delete rows are disabled. `toolbar-discard-changes` is enabled.
     `grid-writable-badge` reads Read-only.
  4. Click `grid-stale-reconnect`: connect snapshot plus one read. Strip gone, commit enabled,
     pending count still 2.
  5. Assert the port log holds no `DATA_OP.mutate` op before step 4.
  Copy-coverage specs pick up the new keys through the existing pseudo-locale run.
