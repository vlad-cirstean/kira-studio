## 1. What exists

### 1.1 How the app talks to GitHub

- `internal/githost` is the neutral contract (P318). `Provider` = `Remotes` + `Auth` + `ChangeRequests` + `URLs` + `ID`/`Terms`. Optional roles are found by type assertion. `ChangeRequestSync` (P352) is the only one today; `gitsession/crsync.go:828` gates on `p.(githost.ChangeRequestSync)`.
- Hosts: GitHub only in production (`githost/providers/providers.go`). `flowharness/fakehost` is the test-only second host (`forge.test`, merge requests, account `forger`).
- `githost/github` drives the user's own `gh` CLI. No token is held. `Runner` (`runner.go`) is the spawn seam, fake in every unit test. `Client.get` (`api.go`) gates on `discovery.Status` (auth), runs `gh api --method GET` with the pinned API version headers, and maps the outcome through `classify` (`errors.go`). Every call reports failure in a `Status`, never a Go error. `Client.graphql` (`graphql.go`) is the GraphQL sibling used by `sync.go`.
- `classify`: 401 is `unauthenticated` ("run `gh auth login`"). 403 is `forbidden` (rate limit, SSO, scope). 404 is `gone`. Anything else is `forbidden` with the body's `message`. There is no 422 arm: GitHub's validation errors (`{"message":"Unprocessable Entity","errors":["Can not approve your own pull request"]}`) reach the user as "Unprocessable Entity".
- `Provider.Account(ctx, host)` is the `gh auth status` login (the viewer).
- `gitsession.RepoEntry`: `hostRepo(ctx)` resolves `(Provider, Repo, ok)` under the repo's `kiraSpace.gitHost.provider` setting. `ResolveBranchChangeRequest(ctx, branch)` answers `ChangeRequestLookup{Kind: ok|disabled|unavailable}` (index, snapshot, cache, then `ForBranch`; newest first, closed included, same-owner heads only). `e.host.breakerStatus()` / `armBreaker` are the per-repo rate-limit breaker. `branchTip(ctx, branch)` (`incremental.go:151`) is the local tip, `ErrBranchNotFound` when absent. `SyncChangeRequests(ctx, nil, false)` triggers an async index run (non-blocking when `wait` is false).
- `gitrpc` (`changerequests.go`) projects those onto the git-ipc wire via `handleRepoCall`. Host failure is a result kind, never an RPC error. Only shape validation returns `ipcerr`.

### 1.5 GitHub VS Code extension behaviour (target)

The extension's PR page has a comment box. Its button group offers Comment, Approve and Request changes. Approve and Request changes submit a pull request review with that event and the box text as body. Comment with no pending review posts a conversation (issue) comment. GitHub refuses Approve and Request changes on your own PR, and needs a body for Request changes and for a Comment review.

REST equivalents (one call each, no pending-review dance):
- Review: `POST /repos/{owner}/{repo}/pulls/{n}/reviews` with `event` (`APPROVE|COMMENT|REQUEST_CHANGES`), `body`, `commit_id`. It creates and submits in one step.
- Conversation comment: `POST /repos/{owner}/{repo}/issues/{n}/comments` with `body`.
- Review facts: `GET /repos/{owner}/{repo}/pulls/{n}` gives `state`, `draft`, `merged_at`, `head.sha` and `user.login`.

## 2. Scope decisions

1. **Two features, two controls.** A "Review" dropdown (Comment, Approve, Request changes) submits a pull request review with that event. A separate "Comment on {short}" button posts a conversation comment. Both open one dialog with a body box. The "Comment" review event and the conversation comment stay distinct, as on GitHub: the first shows as a review, the second as a plain comment.
2. **Local inline comments are not included in a submitted review.** They are agent instructions (kind, state, agent reply). They are anchored to local commits that may not be pushed. GitHub refuses the whole review when one line is outside the PR diff (422 "could not be resolved"). Mapping them onto PR diff positions is its own feature. The review body is the only content. Listed as assumption A1.
3. **REST, not GraphQL.** One POST per action, with no node id lookup and no pending-review create/submit pair. `Client.graphql` stays for `sync.go`, untouched.
4. **Own change request.** The server computes `own` (author equals viewer, case-insensitive). The UI disables Approve and Request changes with a reason line. Comment stays enabled. The host still has the final word: a refusal comes back as `unavailable` with GitHub's message.
5. **Merged or closed.** All three review events are disabled with a reason ("This {short} is merged." or "…closed."). The conversation comment stays enabled (GitHub allows comments on closed PRs; a locked conversation comes back as a host refusal). Draft is treated as open.
6. **No change request.** Kind `none` hides the actions group. Host off or no matching provider, or a provider without the role: kind `disabled`, group hidden.
7. **Host failure (auth, rate limit, gone, gh missing).** The review state query returns `unavailable` with the host status. The header shows the Review button disabled, with the status reason in a tooltip. A failed submit keeps the dialog open with the reason in an `Alert` and an "Open {short}" button.
8. **Head staleness.** The dialog refetches the review state on open. The review is sent with `commit_id` set to the PR head the server just read (`headSha`), so GitHub records it against what the PR showed. When the local branch tip differs from that head, the dialog shows a warn `Alert` naming both short shas. Submit stays allowed. A head force-pushed away after the read comes back as a 422 host refusal.
9. **Double submit.** The submit button is disabled while the mutation is pending, and the dialog closes on success. There is no server-side dedupe: GitHub reviews and comments are not idempotent, and a client-held token would add state for one double-click case the pending guard already covers. A timeout ("gh api did not respond within 10s") may still have posted. The error `Alert` offers "Open {short}" so the user checks before retrying.
10. **Body rules (server).** Normalize with `normalizeCommentBody` (CRLF to LF, trim). Required for `comment`, `requestChanges` and the conversation comment, optional for `approve`. Cap 64 KiB (`githost.MaxHostCommentBytes`); GitHub caps a body at 65,536 characters, and a byte cap never exceeds that.
11. **Body transport.** Every field goes through `gh api -f key=value`, never `-F`. `-F` reads a value starting with `@` from a local file. A body often starts with an @mention, so `-F` would read and post an arbitrary local file. One argv test guards this.
12. **After success,** the server triggers a non-waiting `SyncChangeRequests(ctx, nil, false)`, so board badges pick up the new review decision within the sync gates. The client does not refetch the review state (approving changes neither author nor head).

## 3. Design

### 3.1 githost role (`internal/githost/githost.go`)

Add after `ChangeRequestSync`:

```go
// Review events.
const (
	ReviewApprove        = "approve"
	ReviewComment        = "comment"
	ReviewRequestChanges = "requestChanges"
)

// MaxHostCommentBytes bounds a review or change request comment body. GitHub caps one at 65,536
// characters; a byte cap never exceeds that.
const MaxHostCommentBytes = 64 << 10

// Review is one submitted review. CommitSHA is the head it applies to.
type Review struct {
	Event     string
	Body      string // "" only for ReviewApprove
	CommitSHA string
}

// ReviewTarget is one change request's current review facts, read fresh.
type ReviewTarget struct {
	State   string // "open" | "draft" | "merged" | "closed"
	HeadSha string
	Author  string // host login; "" when the host has none (a deleted account)
}

// ChangeRequestReviews is optional: a provider that reviews change requests and comments on their
// conversation. Every call reports failure in Status, never an error.
type ChangeRequestReviews interface {
	ReviewTarget(ctx context.Context, r Repo, number int) (ReviewTarget, Status)
	SubmitReview(ctx context.Context, r Repo, number int, rv Review) Status
	Comment(ctx context.Context, r Repo, number int, body string) Status
}
```

`Info` gets no field. The role is found by type assertion only (P369 removed the last role flag from `Info`).

### 3.4 gitsession (`internal/gitsession/crreview.go`, new)

```go
// ChangeRequestReviewState is changeRequest.reviewState's result. Kind is "ok" | "disabled" |
// "none" | "unavailable".
type ChangeRequestReviewState struct {
	Kind   string
	Status *githost.Status
	Host   githost.Info
	Number int
	Title, State, HeadSha, LocalHeadSha, Author, Viewer string
	Own    bool
}

// ChangeRequestPost is the result of a review or comment post. Kind is "ok" | "disabled" | "unavailable".
type ChangeRequestPost struct {
	Kind   string
	Status *githost.Status
}
```

- `reviewHost(ctx) (githost.Provider, githost.ChangeRequestReviews, githost.Repo, bool)`: `hostRepo`, then type assertion.
- `ChangeRequestReviewState(ctx, branch) (ChangeRequestReviewState, error)`:
  1. No host or no role: `disabled`.
  2. `ResolveBranchChangeRequest(ctx, branch)`: `disabled` passes through as `disabled`, `unavailable` passes its status through, and an empty ok is `none`. Take `ChangeRequests[0]` (number, title).
  3. Breaker armed: `unavailable` with the breaker status.
  4. `rv.ReviewTarget(ctx, repo, number)`. Not ok: arm on `RateLimited`, return `unavailable`.
  5. `branchTip(ctx, branch)`: `ErrBranchNotFound` gives `LocalHeadSha ""`. Any other error is returned (the handler maps it with `mapDetailError`).
  6. `Viewer = p.Account(ctx, repo.Host)`. `Own = t.Author != "" && strings.EqualFold(t.Author, Viewer)`. `Host = githost.Describe(p)`.
- `SubmitChangeRequestReview(ctx, number int, rv githost.Review) ChangeRequestPost` and `CommentOnChangeRequest(ctx, number int, body string) ChangeRequestPost` share `post(ctx, fn func(githost.ChangeRequestReviews, githost.Repo) githost.Status)`: no host or role gives `disabled`; an armed breaker gives `unavailable`; call; arm on `RateLimited`; on ok call `e.SyncChangeRequests(ctx, nil, false)`; map to the result.

## 7. Assumptions for the user to check

- A1: Local inline review comments stay agent-only. A submitted review carries only the dialog's message, not the window's comments. Sending them as GitHub review threads would need each comment mapped onto the PR diff; GitHub refuses the whole review when one line is outside it.
- A2: The "Comment" review event and "Comment on PR" are two separate actions, as on GitHub: the first records a review, the second a plain conversation comment.
- A3: On a merged or closed PR, all three review events are disabled and the conversation comment stays available.
- A4: Errors show inline in the dialog (the repo has no toast primitive), and success shows a short status line in the title bar with an "Open PR" link.
- A5: The review is recorded against the PR's current head on GitHub, not the local branch tip. A differing local tip only warns.
- A6: A pending review the user started on github.com makes GitHub refuse a new one (422). That refusal is shown as is; the app does not submit or discard the pending review.
