## 1. Hunk mark shift

### 1.1 Where the marks live

`frontend/src/views/repo/reviewDecorations.ts` paints the review layer on the diff's modified editor (`attachReviewDecorations`, mounted by `views/repo/RepoDiffView.vue`).

- Hunk mark: `hunkCollection`, one decoration per hunk at `block.start`. Class `codicon codicon-circle-large-outline … kira-review-glyph-actionable` (unreviewed) or `codicon codicon-pass-filled … kira-review-glyph-reviewed` (the checkmark). Lane `GlyphMarginLane.Right`.
- Add-comment mark: `addGlyphCollection`, painted by `paintAddGlyph()` on the hovered line (`onMouseMove`). Class `codicon codicon-add … kira-review-glyph-add`. Lane `GlyphMarginLane.Left`.
- Comment mark: `commentCollection`, lane `Left`.
- Colours only: `packages/theme/src/review-decorations.css`. No sizing there, so CSS is not the cause.

### 1.2 Root cause

Monaco lays glyph lanes out per line, not per editor. Read from `node_modules/.bun/monaco-editor@0.56.0/.../esm/vs/editor/`:

- `common/viewModel/glyphLanesModel.js`: `getLanesAtLine(line)` lists only the lanes that have a decoration on that line. `requiredLanes` is the max lane count on any single line.
- `browser/viewParts/glyphMargin/glyphMargin.js:211`: a glyph's column is `getLanesAtLine(line).indexOf(lane)`, not its lane number.
- `common/config/editorOptions.js:1233`: `glyphMarginWidth = lineHeight * glyphMarginDecorationLaneCount`, with the count from `requiredLanes` (`browser/view.js:464`).

So on a hunk line with no comment, lanes are `[Right]` and the mark renders in column 0. Hovering that line adds the Left add-comment glyph: lanes become `[Left, Right]`, the mark jumps to column 1, and `requiredLanes` goes 1 to 2. The whole glyph margin widens by one line height, which shifts line numbers and code too. Leaving the line reverses it.

Same defect, no hover: a comment on line 12 and a hunk on line 100 both render in column 0 (one lane each), so the two lanes never form columns. The "two lanes never collide" note in `docs/ARCHITECTURE.md:1893` only holds for one line.

### 1.3 Fix

Monaco's own escape hatch: `IModelDecorationGlyphMarginOptions.persistLane` ("render the lane even outside this decoration's range", `editor.api.d.ts:1648`). With both Left and Right persisted, every line reports `[Left, Right]`, `requiredLanes` is 2 from the first paint, and nothing moves on hover.

In `reviewDecorations.ts`:

1. Add `glyphMargin: { position: …, persistLane: true }` to the hunk, comment and add-comment decorations.
2. Add a fourth collection, `laneCollection`, set inside `paint()` (so a model swap re-applies it like the others) to one decoration at `Range(1, 1, 1, 1)`: `glyphMarginClassName: 'kira-review-lane'`, `glyphMargin: { position: Left, persistLane: true }`. It reserves the Left lane before any hover or comment exists. Monaco drops a decoration whose `glyphMarginClassName` is empty (`textModel.js:1944`), so the class must be a non-empty name. It needs no CSS and has no `::before`, so it paints nothing. Clear it in `dispose()`.
3. Fix the module doc comment (lines 13-15) and `docs/ARCHITECTURE.md:1893`: both lanes persist, so the glyph margin is always two lanes wide and a hover never shifts a glyph.

Click routing needs no change: `mouseTarget.js:550` reads `getLanesAtLine(line)[floor(offset / lineHeight)]`, which now always maps the left column to Left and the right one to Right.

Not chosen:
- Reserving space with CSS (`.kira-review-glyph-*` width or margin): Monaco positions each glyph node inline (`left`, `width`) every render, so a class cannot pin a column.
- One shared lane (draw the add glyph over the hunk mark): hides the checkmark exactly when the user points at it.
- Glyph margin widgets instead of decorations: same lane model, more code.

## 2. Review comment dialog

### 2.1 What exists

`frontend/src/ade/v2/review/AdeReviewSubmitDialog.vue` (P370) is the only `Dialog` in the review window. It serves Comment, Approve, Request changes and Comment on PR (opened from `AdeReviewActions.vue`, `v-if="mode && ok"`, so it unmounts on close).

- `DialogContent size="md"`: `packages/theme/src/components/ui/dialog/index.ts` gives `w-120 max-w-[90vw] max-h-4/5 overflow-hidden flex flex-col`. Centred with `top-1/2 left-1/2 -translate-x-1/2 -translate-y-1/2` (`DialogContent.vue`).
- `DialogBody`: `flex min-h-0 flex-1 flex-col gap-3 overflow-auto p-3`.
- `Textarea rows="6"`, theme variant `field-sizing-content min-h-16`: it grows with the text, not with the dialog. At a short window the body scrolls and the textarea keeps its height, so the footer and the box compete for 80vh.
- No dialog in the repo is resizable. Pane resizing has one primitive: `packages/theme/src/components/ui/resizable/ResizeHandle.vue` (ARIA separator, pointer drag via `usePaneResize` over VueUse `useDraggable`, keyboard steps, `kira-resizing-*` cursor from `base.css`).

### 2.2 Design

Add an opt-in `resizable` prop to the theme `DialogContent`, and use it from the submit dialog. Default `false`: every other dialog renders exactly as today.

`packages/theme/src/components/ui/dialog/DialogContent.vue`, when `resizable`:

- Track the rendered border box: VueUse `useElementSize(contentRef, undefined, { box: 'border-box' })`. Template ref on reka's `DialogContent`; `useElementSize` unwraps a component to its `$el`.
- Bounds: VueUse `useWindowSize()`. Max is `0.9 * width` by `0.8 * height`, the same bounds as the size variant's `max-w-[90vw] max-h-4/5`. Min is 320 by 240 px (theme constants in the file).
- Two `ResizeHandle`s rendered after the `<slot />`: `axis="x"` on the right edge (`class="absolute inset-y-0 right-0"`), `axis="y"` on the bottom edge (`class="absolute inset-x-0 bottom-0"`). `cn()` in `ResizeHandle` replaces its own `relative` with `absolute`. Test ids `dialog-resize-x`, `dialog-resize-y`. Labels: new keys `common.dialog.resizeWidth.label` ("Resize dialog width") and `common.dialog.resizeHeight.label` ("Resize dialog height") in `packages/theme/src/i18n/en.json`.
- Live size: `width`/`height` refs, `null` until the first drag or key step, bound as inline `style` on reka's `DialogContent`. Inline width overrides `w-120`; the class `max-w`/`max-h` still clamp it, so a window that shrinks after a resize still fits with no extra code.
- Centring: the dialog grows from its centre, so an edge moves half the size change. Pass `ResizeHandle` half sizes (`size`, `min`, `max` all divided by 2) and set `width = 2 * live`. The dragged edge then tracks the pointer exactly, with no new math in `paneResizeMath`. One comment states this.
- `live` and `commit` both set the ref; `cancel` keeps the last committed value. Nothing is persisted: the dialog unmounts on close, so each open starts at the variant size.

`AdeReviewSubmitDialog.vue`:

- `<DialogContent size="md" resizable …>`.
- Textarea fills the body: `class="min-h-24 flex-auto resize-none field-sizing-fixed"`. `flex-auto` keeps the six-row basis at the default size and grows into a taller dialog. `min-h-24` keeps it usable when the window is short; the body scrolls only below that. `field-sizing-fixed` stops content growth fighting the user's size (precedent: `packages/workbench/src/automations/run/RunScriptDialog.vue:180`). `resize-none`: the dialog is the one resize affordance.

Not chosen:
- CSS `resize: both` on `DialogContent`: the native grip lags the pointer at half speed on a centred box and has no keyboard path.
- Bare VueUse `useDraggable` in the dialog: `ResizeHandle`/`usePaneResize` already wraps it with a11y, cursor and blur abort. U45 also forbids `useDraggable` outside `/behaviour/` in app code.
- Persisting the size (`usePersistedState`): spec asks for resize, not memory. Easy to add later.

## 6. Assumptions to check with the user

- A1: "Review comment dialog" is `AdeReviewSubmitDialog` (Review dropdown and Comment on PR), the only dialog in the review window. The inline compose box in the diff (`ReviewThread.vue`, a Monaco view zone) is not a dialog and stays out. Its `resize-y` textarea grows inside a zone whose height is measured once at mount, so it scrolls instead of growing. If the user meant that box, it is a separate fix (re-lay the zone on a `useResizeObserver` callback, capped at the editor height).
- A2: "Fits the available space" means: never larger than the window (90% by 80%, the existing variant bounds), the textarea fills whatever height the dialog has, and the footer stays visible at small windows. The default open size stays `md` (480 px); it does not open full-window.
- A3: Resize is by the right and bottom edges, mouse and keyboard, growing from the centre. No corner grip and no left or top edge.
- A4: Size is not remembered between opens.
- A5: The review diff's glyph margin is now always two lanes wide (about one line height wider than a hunk-only file today). That is the cost of marks that never move, and it also gives comment and hunk marks their own columns.
