# P1 — Git driver

Plan for the P1 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** one `GitDriver` through which every git invocation in this product will ever pass,
with the discipline of §4.3 built into it rather than remembered at each call site, plus the
read-side query and parse layer of §4.4 that P2 turns into a graph.

**Platform:** macOS only (D27) — only the macOS `PlatformGitLocator` is implemented, the other
two are named cases that throw. No CI (D28) — every check here is a command someone runs, and
running them is an exit criterion.

**Not a goal:** anything a user can see. No graph, no store, no UI, no host, no IPC changes.
P1 produces a library with tests and no consumer; P2 is its first caller. Also explicitly not
a goal: the mutating operation surface of §7 (fetch/push/pull/branch/stash/tag/checkout/
reset/revert). Reasoning below.

The one thing P1 must get right that no later phase can fix cheaply: **the invocation
discipline is structural, not conventional.** If `run(['log', ...])` is reachable without the
env hygiene, the quoting flags, the read/write classification and the cancellation plumbing,
then by P7 half the call sites will have skipped some of it, and the resulting bugs (a locale
that breaks error classification, a `color.ui=always` user whose porcelain arrives with ANSI
escapes, a superseded query that keeps a `git log` alive) are the kind that reproduce on one
machine in ten. Every one of those is closed by making the disciplined path the only path.

## Scope boundary

The phasing row names: discovery, the 2.38 block state, the capability probe, spawn
discipline, the streaming NUL parser, cancellation, the write queue, `cat-file --batch`, and
typed error classification. That list is **driver infrastructure plus the read path** — it
names no feature of §7. The exit bar agrees: "unit tests over recorded porcelain fixtures"
describes the `parse/` layer, "integration tests against generated repos" describes the §4.4
queries.

So P1 draws the line there, deliberately:

| In P1 | Deferred to | Why |
|---|---|---|
| `driver.ts`, `discovery.ts`, `capabilities.ts`, `catFile.ts`, `errors.ts` | — | named by the phasing row |
| `parse/{log,refs,status,diffTree,stash,mergeTree}.ts` | — | one coherent deliverable: everything turning porcelain bytes into model types, which is exactly what the recorded-fixture exit bar tests |
| §4.4 read commands (identity, history walk, refs, status, commit detail, merge-tree prediction) | — | the parsers need something to parse; a parser with no invocation is untested against real git |
| `ops/*.ts` (fetch, pull, push, stash, branch, tag, checkout, reset, revert, cherryPick, conflict) | P6–P9 | each maps one-to-one to a feature phase that owns its pre-flight, confirmation copy, undo slot and typed errors. An `ops/push.ts` written now would be a bare argv builder with no lease check, no protected-branch confirmation and no askpass — precisely the half-implemented scope `AGENTS.md` forbids. The *write queue* is still P1 and is proven against real mutating commands issued through the driver directly (below). |
| `logSession.ts` (paused long-lived paging, §5.1.1) | P2 | the phasing table puts 5.1.1 in P2 by name. P1 delivers the streaming read and the incremental parser it will be built on. |
| `watcher.ts` (§4.5) | P3 | it needs the `FileWatcher` port, whose only implementations are host-owned, and it produces signals that nothing consumes until there is a graph to invalidate and a `repo.changed` event to carry it. Building it now means a watcher tested only against a fake, wired to nothing. The part of §4.5 that is genuinely driver-shaped — invalidation on write completion — *is* in P1 (W7). |
| `core/store/`, `core/graph/`, `core/search/`, `core/preflight/` | P2, P2, P10, P6–P9 | phasing table |
| Worktree *enumeration* (`git worktree list --porcelain`, other worktrees' HEADs as badges) | P6 | D12 says detection is free at P1, and detection is the `--git-common-dir` comparison P1 already makes in its identity probe. Enumerating the others is a second command feeding a P6 badge. |
| `packages/ipc` contract changes | P3 | P0's findings anticipated revision here. Shaping the wire contract against a driver whose consumers (P2's store, P4's UI) do not exist repeats the speculative design P0 avoided. P1's obligation is that its output types live in `core/model` so P3 can reference them instead of redeclaring them. `packages/git` must not import `@kira-version/ipc` in P1 at all. |

## W1 — `core` model types, the `ProcessRunner` port, `nulSplit`

`packages/core` has no I/O (§3.1), so what P1 adds there is exactly two things: the shapes the
parsers produce, and the interface the driver spawns through.

**Model.** Create only what a P1 parser or query actually returns:

- `model/repo.ts` — `RepoIdentity`: `root`, `gitDir`, `commonDir`, `isBare`,
  `isLinkedWorktree` (D12: `gitDir !== commonDir`), `head` (`{ kind: 'branch', name } |
  { kind: 'detached', sha } | { kind: 'unborn', name }`). The unborn case is not an edge case
  to add later — a freshly `git init`ed repo is the first thing someone points this at.
- `model/commit.ts` — `CommitRecord`, the one row the history walk yields: sha, parents,
  author/committer name+email+unix time, subject, decoration. Strings here, not table indices;
  §5.5's typed-array store is P2's job and it will consume these records, not replace them.
- `model/ref.ts` — `RefRecord` from `for-each-ref`: full refname, object id, object type, the
  peeled target for annotated tags, upstream and ahead/behind track, committer date, whether
  it is HEAD. Refs, remotes and tags are one record type discriminated on the refname prefix,
  because that is how `for-each-ref` returns them and inventing three types means three
  parsers.
- `model/status.ts` — porcelain v2's five record kinds (`#` headers, `1` ordinary, `2`
  rename/copy, `u` unmerged, `?` untracked, `!` ignored) as a discriminated union, plus the
  branch header (oid, head, upstream, ahead/behind).
- `model/stash.ts` — `StashEntry`: index, ref, message, base sha, timestamp.
- `model/conflict.ts` — `UnmergedEntry` (from the `u` records, carrying the stage 1/2/3 oids
  and modes) and `MergePrediction` (`{ kind: 'clean', tree } | { kind: 'conflicts', paths,
  messages }`), the typed result of `merge-tree --write-tree`.

**Not created:** `model/tag.ts`. Annotated-tag *detail* (tagger, tag message, signature) is
read from the tag object, and nothing in P1 reads one — `for-each-ref` gives the peeled target,
which is all the read path needs. P6 owns §7.9 and creates it then.

**`ports/processRunner.ts`.** The whole port, byte-oriented:

```ts
export interface SpawnRequest {
  readonly argv: readonly string[]        // git's own argv, without the executable
  readonly cwd: string
  readonly env: Readonly<Record<string, string>>  // replaces, never merges (see W7)
  readonly stdin?: Uint8Array | AsyncIterable<Uint8Array>
  readonly signal?: AbortSignal
}
export interface SpawnedProcess {
  readonly stdout: AsyncIterable<Uint8Array>
  readonly stderr: Promise<Uint8Array>        // always collected; small, and errors need it
  readonly exit: Promise<{ code: number | null; signal: NodeJS.Signals | null }>
  write(chunk: Uint8Array): Promise<void>     // for cat-file's persistent stdin
  kill(signal?: NodeJS.Signals): void
}
export interface ProcessRunner { spawn(exe: string, req: SpawnRequest): SpawnedProcess }
```

**Bytes, not strings, is the load-bearing decision here.** Node will happily hand back decoded
strings, and every one of this project's parsers would then be splitting a string that has
already had invalid UTF-8 replaced with U+FFFD — irreversibly, before we ever see it. Paths are
bytes on macOS, `core.quotepath=false` means we asked git *not* to escape them, and
`cat-file --batch` returns blob content that is frequently not text at all. So `stdout` is a
stream of `Uint8Array`, the NUL splitter works on bytes, and decoding happens once per field at
the point a byte range becomes a model string. Retrofitting this after three parsers assume
strings is a rewrite of all of them.

`util/nulSplit.ts` is the incremental splitter: fed chunks, yields complete records, holds the
remainder across chunk boundaries, and is parameterised on the delimiter byte so the same code
serves `-z` NUL records and `%x1f` fields. It carries a remainder cap (default 8 MiB) that
throws rather than growing without bound — a malformed or unexpected output format must fail
loudly (§3.5), not consume the machine's memory quietly.

`util/assert.ts` for the invariant checks the parsers make. **Not** `util/result.ts`: the
driver signals failure by throwing typed `GitError`s (W6) and returns discriminated unions only
where failure is an expected outcome (`merge-tree` exit 1, `cat-file` missing object). Two
error idioms in one codebase is worse than either one.

**Done when:** `nulSplit` has unit tests covering a record split across three chunks, an empty
trailing record, a delimiter as the first byte, and the remainder-cap throw; the model types
compile under `exactOptionalPropertyTypes` with no `any`.

## W2 — `nodeProcessRunner.ts`

§3.3 lists `ProcessRunner`'s implementation as `child_process` for both hosts. They are
identical — the extension host and Electron main are both Node — so writing it twice at P3 is
a copy-paste bug factory. It lives once, at `packages/git/src/nodeProcessRunner.ts`, and P3's
`host-*/src/ports/processRunner.ts` wrap it with host-owned policy (which git path, which cwd,
logging) rather than reimplementing the spawn. Add the file to §3.1's tree in the same commit
per `AGENTS.md`.

`packages/git` may import `node:*` (the Bun ban of §8.1/B2 is about `bun:` and the `Bun`
global, not Node builtins); `packages/core` still may not, which is why the port interface and
its implementation are in different packages.

Details that are easy to get wrong and expensive to debug later:

- `stdout` must be consumed as an async iterable with **backpressure preserved** — pausing the
  consumer must pause the pipe, because that is the mechanism §5.1.1's paged log session is
  built on at P2. Do not attach a `data` handler and buffer into an array.
- `kill()` sends SIGTERM and escalates to SIGKILL after a 2 s grace. Record whether the escalation
  fired; a git that ignores SIGTERM is worth knowing about.
- `stderr` is always collected (bounded, 1 MiB, truncated with a marker beyond that) because
  every typed error needs it and it is never large in practice.
- `spawn` never uses a shell. `shell: true` with a repo path containing a space or a quote is a
  command-injection hole and there is no reason to want it.
- ENOENT on the executable surfaces as a typed error, not an unhandled `error` event.

**Done when:** unit tests (against `/bin/echo`, `/bin/cat` and a script that ignores SIGTERM)
cover streaming, stdin writes, backpressure, abort mid-stream, the SIGKILL escalation, and
ENOENT.

## W3 — Test corpus: recorded porcelain and the fake git

Two fixture kinds, for two different jobs.

**`tests/fixtures/porcelain/`** — recorded bytes for parser unit tests, and P1 populates it
(P0 left it a `.gitkeep`). Stored as **raw byte files**, never as string literals in a `.ts`
file: escaping NUL and 0x1f into TypeScript source is exactly where a fixture silently stops
representing what git actually emits, and the resulting parser passes its tests and fails on a
real repo. `tests/fixtures/recordPorcelain.ts` regenerates the recorded set from P0's
`generateRepo.ts` shapes, so the corpus is reproducible (P0's deterministic shas make the
recorded bytes stable) and a git-version-driven format change shows up as a reviewable diff
rather than as a mystery.

Recorded from generated repos: `log` over `linear`, `branchy`, `octopus`, `criss-cross`,
`withStash`; `for-each-ref` over `withRemote` (upstream and track fields populated) and over a
repo with an annotated tag; `status --porcelain=v2` clean, dirty, untracked, staged+unstaged,
renamed, and unmerged (from `conflicting`); `diff-tree --numstat` and `--name-status -M -C`
including a rename, a copy, a binary file and a merge commit with `-m`; `stash list`;
`merge-tree` clean and conflicting.

Hand-authored alongside them, because a generated repo cannot easily produce them and they are
where parsers break: a path with non-UTF-8 bytes, a path with a newline in it, a subject
containing a literal 0x1f, a CRLF subject, an empty subject, an unborn-HEAD `status`, a
`for-each-ref` line with an empty upstream, and a `%D` decoration listing HEAD plus a tag plus
three remotes.

**`tests/fixtures/fakeGit.ts`** — `makeFakeGit({ version, behaviour })` writes a temp directory
containing an executable script named `git` and returns its path, for tests that need a git
binary the machine does not have. Behaviours: report an arbitrary version string, exit non-zero
on `version`, print garbage on `version`, hang until killed. This is what makes the sub-2.38
block state testable end-to-end through the real resolution order rather than by injecting a
version number past the code being tested. Add both files to §3.1's tree.

**Done when:** `recordPorcelain.ts` regenerates the corpus byte-identically on two consecutive
runs, and `makeFakeGit({ version: '2.30.2' })` produces a binary that `discovery.ts` (W5)
resolves and rejects.

## W4 — `parse/*`

Six files, each owning **both the argv format string and the parser that reads it**. Keeping
them in one file is the point: the single most likely parser bug in this codebase is a
`--format` edited without its parser, and a field added in one place and not the other should
be a type error in the same file rather than a runtime shift of every field after it.

- `parse/log.ts` — the §4.4 walk. Records are NUL-separated, fields 0x1f-separated. **Split
  fields with a limit, not a plain split**: `%s` is deliberately last in the spec's format, so a
  subject containing a stray 0x1f can only corrupt itself, and a limited split makes that
  guarantee real instead of theoretical. `%P` is space-separated and may be empty (root commit)
  or hold 3+ entries (octopus). `%D` may be empty and its `HEAD -> main` arrow form must be
  parsed, not stored raw.
- `parse/refs.ts` — `for-each-ref` with 0x1f fields. `%(upstream:track)` is `[ahead 3, behind 1]`,
  `[gone]`, or empty; parse to `{ ahead, behind } | 'gone' | undefined`.
- `parse/status.ts` — porcelain v2 `-z`. The hard part is that `2` (rename/copy) records carry
  **two** NUL-separated paths in one record, so the record splitter cannot be uniform — the
  parser must consume a second path when it sees a `2`. This is the single most common
  porcelain-v2 parsing bug and it gets its own test.
- `parse/diffTree.ts` — `--numstat -z` (with `-` for binary, which must map to a binary flag
  rather than to zero) and `--name-status -M -C -z` (where `R100`/`C75` records carry two
  paths, same shape hazard as above).
- `parse/stash.ts` — `stash list -z` with an explicit format.
- `parse/mergeTree.ts` — the `--write-tree --messages --name-only` output: tree oid on the
  first line, then conflicted paths, then the informational messages block. Exit 0 clean, 1
  conflicts, >1 error — the exit code is part of the parse contract, so the parser takes it.

Every parser takes bytes and a `TextDecoder`-based field decoder; every parser is total (no
throwing on unexpected input except through `assert` for genuine invariant violations, which
are bugs, not user data).

**Done when:** each parser has unit tests over the W3 corpus, including every hand-authored
pathological case; each parser's field count is asserted against its own format string.

## W5 — `discovery.ts`

§4.2's resolution order, plus the version probe, plus repo identity.

**Resolution order.** Steps 1 and 2 (`kiraVersion.git.path`, VS Code's `git.path`) are host
settings that do not exist until P3, so `locateGit()` takes an ordered
`configuredCandidates: readonly string[]` parameter. P1 implements the mechanism and passes an
empty list; P3 fills it. This is a real parameter with real behaviour, not a stub — the
candidate loop, the "configured path is invalid" error, and the precedence are all exercised by
tests that pass fake-git paths in.

Step 3 is `PATH`. Step 4 is `PlatformGitLocator`, a strategy selected on `process.platform`,
with `darwin` implemented (`/opt/homebrew/bin/git`, `/usr/local/bin/git`, then `/usr/bin/git`)
and `win32`/`linux` as named cases that throw a clear "platform not supported yet" error (D27,
and P0's established pattern). The macOS trap is explicit in §4.2 and must be honoured:
`/usr/bin/git` is the Command Line Tools shim and **running it without CLT installed pops a
system install dialog**, so gate it behind `xcode-select -p` succeeding and never spawn the shim
blind. That is not a nicety — it is a modal dialog appearing on a user's screen because a panel
was opened.

**The version probe and the block state.** `git version` output is parsed by taking the leading
numeric triple, because the real forms in the wild are `2.39.5 (Apple Git-154)`,
`2.38.0.windows.1`, `2.38.0-rc1` and `2.38.GIT`. Each of those is a test case.

The result is a discriminated union, and this is where "never a half-working app" is enforced:

```ts
export type GitResolution =
  | { kind: 'ok'; git: ResolvedGit }
  | { kind: 'notFound'; probed: readonly string[] }
  | { kind: 'tooOld'; path: string; detected: GitVersion; required: GitVersion }
  | { kind: 'unusable'; path: string; reason: string; stderr: string }
```

`ResolvedGit` is opaque — its constructor is not exported — and `GitDriver.open()` requires
one. So a sub-2.38 git cannot produce a driver, and no amount of forgetting to check a boolean
at a call site can route around the floor. **The block state is a type-level guarantee, not a
runtime check someone might skip.** The `tooOld` payload carries everything §4.2 says the
blocking UI must show — detected version, required version, the platform upgrade command, and
the `kiraVersion.git.path` setting id — so P3's UI renders a value rather than composing prose
from parts.

`unusable` covers a `git` that exists but does not behave (non-zero exit on `version`,
unparsable output). Treating it as "probably fine" is how a half-working app happens.

**Repo identity.** One `rev-parse --show-toplevel --git-dir --git-common-dir
--is-bare-repository` call, plus HEAD resolution (`symbolic-ref --quiet HEAD`, falling back to
`rev-parse HEAD`, with the unborn case detected by both failing on a repo that exists).
`gitDir !== commonDir` is the linked-worktree flag — D12's "detection is free at P1" is
precisely this comparison, and it costs one already-needed command. Not-a-repository is a typed
result, not an exception, because "the user picked a folder that isn't a repo" is an expected
outcome.

Discovery results are cached per resolved path + mtime; identity is cached per repo root and
invalidated by the driver's generation counter (W7).

**Done when:** the version parser handles all four real-world forms; a fake git at 2.30 yields
`tooOld`; an absent git yields `notFound` naming everything probed; identity is correct on a
normal repo, a bare repo, a linked worktree (`git worktree add` on a generated repo), and a
freshly `git init`ed repo with no commits.

## W6 — `errors.ts`

The §4.3 union — `AuthFailed`, `NonFastForward`, `Conflict`, `DirtyWorktree`, `LockHeld`,
`NotFound`, `HookRejected`, `Unknown` — as a `GitError` class carrying a `kind`, the argv (with
no credentials in it, which the discipline of §7.4 will keep true), the exit code, and **the
raw stderr, always, unmodified**. §4.3 requires it preserved and surfacable; a classifier that
discards the text it did not understand makes every `Unknown` unactionable.

Two additions to the union, both driver-level rather than git-level, and both kept out of the
domain union deliberately:

- `GitCancelled` — raised when an `AbortSignal` kills a read. It is not a failure, it must never
  reach a user-facing error surface, and callers superseding their own query must not have to
  pattern-match a domain error to know that.
- `GitSpawnFailed` — the binary could not be executed at all. Distinct from any git-reported
  failure.

Classification is exit code plus stderr pattern matching, and the patterns are only sound if
git's messages are in a known language — which motivates `LC_ALL=C` in W7's env.

**Done when:** each `kind` has at least one test asserting classification from a recorded real
stderr (captured in W11 from an actually-failed operation, not invented), and an unmatched
stderr yields `Unknown` with the text intact.

## W7 — `driver.ts`

The single spawn path. §4.3's rules, made structural.

**Env, replaced not merged.** The child's environment is built from the parent's, minus the
variables that would break us, plus ours. It is passed as a complete map so nothing leaks in by
accident:

| Setting | Why |
|---|---|
| `GIT_TERMINAL_PROMPT=0` | §4.3. Git must never block on an invisible TTY prompt. |
| `GIT_OPTIONAL_LOCKS=0` | §4.3. Safe env-wide: it suppresses only *optional* locking, so mutating commands still take the locks they need. |
| `GIT_PAGER=cat`, `--no-pager` | belt and braces; a `core.pager` with side effects on a non-TTY is not worth discovering later. |
| `LC_ALL=C` | error classification (W6) pattern-matches stderr. A user with a translated git otherwise gets every error classified `Unknown`. Porcelain and plumbing formats are untranslated by contract, so this should not perturb parsed output — verified in V1, because "should" is not good enough for a change this broad. |
| `GIT_ASKPASS`/`SSH_ASKPASS` | **not set in P1** — §7.4's askpass path is P7's. P1 leaves them as inherited and relies on `GIT_TERMINAL_PROMPT=0` to fail fast. |

And the flags on every invocation: `-c core.quotepath=false` (§4.3), `-c color.ui=false` (a user
with `color.ui=always` gets ANSI escapes in porcelain output — a parser bug that reproduces on
their machine only), `-c log.showSignature=false` (a user with `log.showSignature=true` gets
signature blocks injected into `git log` output, which destroys the record framing), and
`-c i18n.logOutputEncoding=UTF-8` (so `%s` comes back in a known encoding regardless of config).
Reads additionally get `--no-optional-locks`; writes do not.

**What we must *not* do:** suppress the user's git config. P0's fixture generator sets
`GIT_CONFIG_NOSYSTEM=1` and null global/system config, and that is right *there* and wrong
here — §4.1's entire rationale for shelling out to system git is config and credential
fidelity. A driver that ignores `includeIf`, `core.autocrlf` or a credential helper shows the
user something different from their terminal, which is the one outcome this design refuses.
The `-c` overrides above are the narrow, enumerated exceptions, each because it corrupts a
machine-readable format.

**Surface.**

```ts
export interface GitDriver {
  read(argv: readonly string[], opts?: ReadOptions): GitRead
  write(argv: readonly string[], opts?: WriteOptions): Promise<GitWriteResult>
  readonly catFile: CatFileSession
  readonly generation: number
  onInvalidated(fn: () => void): Disposable
  dispose(): void
}
export interface GitRead {
  readonly bytes: AsyncIterable<Uint8Array>
  records(delimiter: number): AsyncIterable<Uint8Array>  // via util/nulSplit
  readonly done: Promise<void>                            // rejects with a typed GitError
  cancel(): void
}
```

Reads stream; nothing waits for exit (§4.3). `read()` returning a lazy handle rather than a
promise is what makes that non-optional — there is no `readToEnd` convenience, because the one
call site that wants all the bytes (small outputs like `rev-parse`) can collect them in two
lines, whereas a convenience method is what every hot path would reach for.

**Concurrency.** A per-repo serial queue for writes; reads run concurrently up to a bounded
pool (default 4 — enough to overlap a status, a refs query and a detail fetch, low enough not
to thrash a laptop's disk during a graph walk; configurable, not a magic number buried in a
closure). Queue depth and pool saturation are observable, because "why is this slow" is
otherwise unanswerable.

**Cancellation applies to reads and to queued-but-unstarted writes only.** A started write is
never killed. Killing `git commit` or `git stash push` mid-flight is how a user ends up with a
stale `index.lock` and a repository in a state we then have to explain. This is a rule worth
stating loudly because the obvious implementation (`AbortSignal` on everything) is wrong here.

**Invalidation.** A completed write bumps `generation` and fires `onInvalidated` (§4.3's "a
mutating op invalidates the graph cache on completion"). In-flight reads started at an older
generation are *marked stale, not cancelled* — the consumer decides whether to discard, and
throwing away a nearly-complete 100k walk because a tag was created is worse than serving it
and re-querying. This is the whole of §4.5 that belongs in P1; the fs watcher is P3's.

**Done when:** unit tests with a fake `ProcessRunner` assert the exact argv and env of a read
and of a write; the write queue serializes under a burst of ten concurrent writes; the read
pool never exceeds its bound; an aborted read kills its process and rejects with `GitCancelled`;
an abort on an in-flight write is a no-op and the write completes.

## W8 — `capabilities.ts`

Two caches with different keys, because they answer different questions (§4.2).

**Per binary**, keyed by resolved path + version: `mergeTreeWriteTree` (≥2.38),
`commitGraph` (≥2.24), `sparseCheckout` (≥2.25). All three are implied true by the floor today.
They exist anyway because §4.2 says so and the reason is sound — the floor moves, and a
capability that is a version comparison today is one that is a probe tomorrow. Derived from the
version, not probed by spawning: spawning `merge-tree` to find out whether `merge-tree` exists
is a process per repo open for information we already have.

**Per repo**, keyed by repo root + generation: is a commit-graph file present
(`$GIT_COMMON_DIR/objects/info/commit-graph` or a `commit-graphs/` chain — check the common dir,
not the git dir, or every linked worktree reports "no graph"); is the worktree sparse
(`core.sparseCheckout` true, and whether the sparse index is in use); is this a linked worktree
(from W5's identity).

**D21 is a hard rule in this file:** P1 reads whether a commit-graph exists and never writes
one. No `commit-graph write`, not opportunistically, not behind a default-off flag. The
`kiraVersion.git.maintainCommitGraph` setting and its one-time prompt are P3's settings schema
and a later phase's UI. Writing into someone's `.git` unasked is not ours to do, and the
cheapest way to guarantee it does not happen by accident is for the string
`commit-graph write` not to appear in this phase's diff.

**Done when:** capabilities are computed once per binary and once per repo (asserted by
counting spawns through a fake runner); a repo with a written commit-graph reports present and

## W9 — `catFile.ts`

One persistent `git cat-file --batch` per repo (§4.3, §3.2), plus `--batch-check` for size
probing.

The protocol is simple and the failure modes are not. A request is an oid plus newline on
stdin; the response is `<oid> SP <type> SP <size> LF`, then exactly `size` bytes, then LF — or
`<oid> missing LF`. So:

- The reader is a **byte-exact state machine**, not a line reader. Blob content contains
  newlines and NULs and is frequently not text; reading "until the next newline" corrupts every
  binary blob and most source files.
- Requests are queued and matched to responses **in order**, since the protocol has no request
  ids. One outstanding request at a time is simplest and fast enough — the process spawn was the
  cost we were removing, not the round trip.
- The process can die (OOM killer, a repo that disappears, a git upgrade mid-session). Detect
  exit, fail the outstanding request with a typed error, and restart lazily on the next request
  with a bounded retry so a permanently broken repo does not spawn in a loop.
- `--batch-check` first for anything that might be large: reading a 2 GB blob into a
  `Uint8Array` because a user opened a diff on it is an avoidable out-of-memory. The size gate's
  threshold and the "too large to display" typed result belong here; the UI copy is P5's.
- `dispose()` closes stdin and waits for exit. A leaked `cat-file` per repo open is a process
  leak the user sees in Activity Monitor.

LFS pointer detection (D22) is *not* here — `catFile` returns bytes; recognising a pointer file
and labelling it is P5's presentation concern.

**Done when:** integration tests read a text blob, a binary blob containing NUL and LF bytes,
and a blob whose size is exactly at a chunk boundary, all byte-identical to `git cat-file -p`;
a missing oid returns the typed missing result; killing the process mid-session causes the next
request to restart it and succeed; `dispose()` leaves no child process.

## W10 — `queries.ts` — the read surface

The thin façade binding driver + argv + parser into the typed API P2 will call. One new file,
added to §3.1's tree. It holds no formats (those live with their parsers, W4) and no spawn
policy (that lives in the driver, W7) — what it owns is which query is a stream and which is a
one-shot, and what each one's cancellation semantics are.

| Query | Command (§4.4) | Shape |
|---|---|---|
| `identity()` | `rev-parse` + HEAD resolution | one-shot (W5 owns it; re-exported here) |
| `log(opts)` | the history walk, `--all --glob=refs/stash --topo-order -z` | **streaming** `AsyncIterable<CommitRecord>`, cancellable, `--max-count` paged |
| `refs()` | `for-each-ref` over heads/remotes/tags | one-shot |
| `status()` | `status --porcelain=v2 --branch -z` | one-shot |
| `commitDetail(sha)` | `show -s --format=<full>` + two `diff-tree` runs | one-shot; merges take `-m` and a parent index |
| `countCommits(scope)` | `rev-list --count` | one-shot; §5.1.1's remaining count, cheap and needed by P2 |
| `predictMerge(base, other)` | `merge-tree --write-tree --messages --name-only` | one-shot, exit code carried into the parse (W4) |

`log()` is the hot path and the only streaming query in P1. It yields records as they arrive,
its consumer can stop early, and stopping kills the process. P2 replaces its paging with the
long-lived paused session of §5.1.1; the record-yielding interface it exposes is the one P2
keeps, which is why it is worth getting right now.

`predictMerge` is raw prediction only — invocation, exit-code semantics, parsed paths. The
policy that turns a prediction into "stash-and-carry will conflict in these files, here are your
three options" is §7.5/§7.6's pre-flight engine and belongs to P6 and P8. P1 delivering the
exact mechanism that the 2.38 floor was adopted for, and no policy on top of it, is the right
seam.

`--show-signature` appears nowhere: D20 says selected-commit only, and the selected commit is
P5's detail pane. `%G?` comes free in `commitDetail`'s format, which is the whole of what D20
needs from this phase.

**Done when:** every query returns typed model values from a real repo, and `log()` on a
cancelled iteration kills its process within the SIGTERM grace.

Coverage: identity across normal/bare/linked-worktree/unborn repos; the walk over `linear`,

how a broken driver ships.

**Done when:** `bun test` runs unit and integration suites green on a machine with git ≥2.38,

## W12 — Parser throughput in the perf harness

## Findings

_Recorded during implementation. V1–V3 outcomes, and any decision made at the keyboard that
this plan did not anticipate — later phases read this section as part of the context they
inherit._

**V1 — `LC_ALL=C` is parse-safe. Confirmed, zero diffs.** Every §4.4 command (`log --all`,
`for-each-ref`, `status --porcelain=v2`, `stash list`, `show -s` metadata, `diff-tree
--numstat`, `diff-tree --name-status -M -C`, `merge-tree --write-tree`) was run twice —
through `buildGitEnv()` as-is, and again with `LC_ALL` deleted from that same env — over every
generated shape (`linear`, `branchy`, `octopus`, `crissCross`, `conflicting`, `withRemote`,
`withStash`), and the raw stdout bytes byte-diffed. 41 checks, 0 diffs. One caveat this
sandbox cannot close: the only locales installed here are `C`/`C.utf8`/`POSIX`, and the
system git (2.43.0) has no gettext/NLS support compiled in (no `.mo` catalogs, no `libintl`
linkage) — so this run cannot exercise git's actual translated-message codepath at all, only
confirm the env-manipulation mechanism itself is inert when there is nothing to translate.
The porcelain/plumbing formats checked are contractually untranslated regardless, which is
the basis for the "should be zero diff" expectation this verifies; a machine with a real
translated git remains the only way to close the loop completely.

**V2 — the macOS CLT shim gate. Not verifiable here, inherited open thread.** This sandbox is
Linux-only; `xcode-select -p` and `/usr/bin/git`'s CLT-shim behavior do not exist to probe.
Per P0's own owed-macOS-verification thread, this stays open pending real macOS hardware (D27).
discovery.ts's macOS branch is written to check `xcode-select -p` before ever touching
`/usr/bin/git` (`locateGit()`'s candidate ordering — read the macOS branch to confirm the gate
precedes the shim path in source, which this sandbox *can* check even without running it), but
the actual failure-mode behavior on a CLT-absent machine is unconfirmed.

**V3 — record framing against pathological commit messages. Confirmed, contained as designed.**
Two things tested directly against real git (2.43.0) via `git commit-tree -F` with crafted
message bytes, never `git commit -m` which the shell would mangle first:

- A literal NUL (0x00) byte in a commit message is categorically impossible: `git commit-tree`
  refuses outright — `error: a NUL byte in commit log message not allowed`, exit 1. The `-z`
  record terminator can therefore never collide with in-message content; this hazard does not
  exist at the object-store level, regardless of what any parser does.
- A literal 0x1f (unit separator) byte *is* accepted in a commit message and comes through
  raw and unescaped in `%s`'s output — confirmed both in git's raw byte stream and by running
  `parse/log.ts`'s actual `parseLogRecord()` over it end-to-end: every field before `subject`
  (sha, parents, author/committer identity and timestamps, decoration) parsed correctly and
  the embedded 0x1f landed intact inside `subject`, exactly as W4's "subject last" ordering and
  `splitLimitedFields`'s last-field-absorbs-remainder design intend. The damage a pathological
  message can do is contained to corrupting only its own field, never shifting an earlier one.

**Unplanned: a Bun-runtime child_process reaping bug, not a driver bug.** `driver.ts`'s
`read()` originally had `done` await `spawned.exit` independently, concurrently with a
caller's own `stdout` consumption — the natural reading of the two as separate concerns. Under
this sandbox's Bun runtime (not real Node.js — confirmed absent across 150+ clean Node runs),
that concurrent-consumer pattern reproducibly left a genuine unreaped zombie process, which
then hung `tests/integration/errors.test.ts` intermittently. Root-caused via ~13 minimal
reproduction scripts to the precise trigger: two independent consumers of one spawned
process's exit state, racing. Fixed by restructuring `read()` so the exit outcome is captured
inside the same async generator that drains `stdout`, in a `finally` block after its own
`yield*` completes, signaling a dedicated promise that `done` only ever awaits — never a second
independent consumer. This changed `GitRead`'s contract: `done` now only settles once `bytes`
has been driven to completion by *someone*, true of every real call site in `queries.ts` but
not of several of `driver.test.ts`'s original fake-runner tests, which were updated to drain
`bytes` before checking `done` to match. `nodeProcessRunner.ts`'s `waitForExit()` also listens
for both `exit` and `close` (not just `close`) as a second, independent defense against the
same runtime quirk. Production never runs under Bun (§8.1), so this is a test-environment
concern the fix closes rather than a correctness bug in shipped code — but it was real enough
to hang CI-equivalent runs, so it is recorded here rather than silently patched over.

**Two environmental caveats found at the exit-criteria pass, neither from this phase's diff.**
A truly bare, argument-less `bun test` (as opposed to `bun run test`, the project's actual test
command) also picks up `tests/e2e/harness/shell.spec.ts` and fails — Playwright's
`test.describe()` rejects being invoked outside its own runner. This is P0's test-harness
config, predates this phase, and this phase's diff never touches `tests/e2e` or
`playwright.config.ts`; flagged rather than fixed, since a git-driver phase touching test
harness wiring would itself be scope creep. Separately, `tests/perf/run.ts`'s pre-existing
P0 browser-timing budget (`kira:page-parsed` etc.) reports a large, noisy regression in this
sandbox (163%–415% across repeated runs against the same committed baseline) — this phase's
diff touches neither `packages/ui` nor `apps/harness`, so this reads as this particular
container's browser being slower/noisier than whichever machine captured the committed
baseline, not a regression this phase introduced. `tests/perf/parserThroughput.ts` (W12's own
metric, added by this phase) passes cleanly on the same runs.
