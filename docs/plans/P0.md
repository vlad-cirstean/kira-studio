# P0 — Foundation

Plan for the P0 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** a repository where every later phase can be implemented without stopping to decide
tooling, and where the architectural constraints from the spec are enforced by machinery
rather than by discipline.

**Platform:** macOS only (D27), and there is no CI (D28) — every check in this plan is a
command someone runs. Both are reflected throughout rather than noted once and forgotten.

**Not a goal:** any product behaviour. No git driver, no graph, no real UI. If a P0 deliverable
looks like a feature, it is scaffolding for testing that feature later.

The one thing P0 must get right that no later phase can fix cheaply: **the boundaries**
(§3.1's dependency rule, §8.1's Bun runtime ban, §6.1's token-only colour rule). Retrofitting
those onto a codebase that has already violated them is a refactor. Landing them in P0 costs
an afternoon.

---

## Ordering

Work items are ordered by dependency. W1–W3 unblock everything; W4–W6 are independent of each
other and can be done in any order; W7–W9 need W4 and W5.

| # | Item | Depends on |
|---|---|---|
| W1 | Workspace skeleton and the normative tree | — |
| W2 | TypeScript configuration | W1 |
| W3 | Biome, and the three boundary checks | W1 |
| W4 | `packages/ipc` contract skeleton | W2 |
| W5 | `packages/ui` placeholder shell + theme token layer | W2, W3 |
| W6 | Fixture repository generator | W2 |
| W7 | `apps/harness` + mock bridge | W4, W5 |
| W8 | Playwright wired to the harness | W7 |
| W9 | Performance budget harness | W7, W8 |
| W10 | Verification tasks (toolchain reality checks) | W1–W3 |

There is no CI work item. Per D28 there is no pipeline; every check runs locally on macOS
(D27) and running them is part of this phase's exit criteria. Scripts are still written to be
CI-callable — a single command, a non-zero exit on failure, no interactive prompts — so adding
a pipeline later is configuration rather than rework.

## W1 — Workspace skeleton

Create the tree exactly as §3.1 defines it. Directories that a later phase fills get a
`.gitkeep`; do **not** pre-create empty stub files, which read as "implemented" in a diff.

Root `package.json`:

- `"private": true`, `"workspaces": ["packages/*", "apps/*"]`.
- `"engines": { "node": ">=20" }` — the extension host and Electron both run Node; this
  documents the floor for anyone running scripts outside Bun.
- **Every dependency pinned exactly.** No `^`, no `~`. This project's toolchain has three
  moving parts with known in-flight churn (Biome's Vue support, the TS 7 transition, Bun's
  vsce interaction); a float range turns any of them into a surprise mid-phase.

`bunfig.toml`: `[install] exact = true` so `bun add` cannot reintroduce ranges.

**Package resolution decision.** Workspace packages export TypeScript source directly —
`"exports": { ".": "./src/index.ts" }` — with no per-package build step. This is safe here
because every consumer is a bundler (Vite for the UI and harness, `bun build`/esbuild for the
hosts) and `tsc` runs `--noEmit` as a checker only. It removes a build graph, stale-artifact
bugs, and watch-mode complexity from every later phase. The cost is that these packages are
not independently consumable outside this repo, which we do not need.

**Done when:** `bun install` succeeds, `bun run --filter '*' typecheck` resolves every
workspace package, and the tree matches §3.1 — which no longer contains `.github/`.

## W2 — TypeScript configuration

`tsconfig.base.json`, extended by each package. The options are chosen to be **TS7-clean**
(D4) so the eventual switch is a dependency bump rather than a migration:

```jsonc
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2023"],                    // DOM added only in ui/harness tsconfigs
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,     // typed-array indexing is everywhere in this codebase
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "noEmit": true,
    "skipLibCheck": true
  }
}
```

Deliberately **not** enabled: `noUnusedLocals` / `noUnusedParameters`. Biome reports unused
symbols already, and duplicate diagnostics from two tools train people to ignore both.

`noUncheckedIndexedAccess` deserves a note because it will be felt: §5.5's commit store is
built on typed arrays, and this option makes every read `T | undefined`. That is correct — an
out-of-range row read is a real bug class in a virtualized list — and the store's accessors
are the right place to do the bounds check once and return a non-optional type.

Root `tsconfig.json` is a solution file with `"references"` to every package, so `tsc --build`
checks the whole workspace in one invocation.

**Banned constructs** (TS7-clean, enforced in W3): legacy/experimental decorators, `namespace`,
`enum` (use unions or `as const` objects), `import =`/`export =`, and implicit `any` via
untyped catch clauses (`useUnknownInCatchVariables` is on via `strict`).

**Done when:** `bun run check:types` (`tsc --build --force`) passes on the empty tree, and a
file using a banned construct fails.

## W3 — Biome and the three boundary checks

`biome.json`: formatter and linter for TS/JS/JSON/CSS/Vue. Line width 100. Recommended rules
on, plus the project-specific restrictions below.

Biome's Vue support is experimental (§8.2), so pin the exact version and expect cross-block
false positives — a `<script setup>` binding used only in the template may be reported as
unused. **Do not disable the rule globally to silence it.** If it fires, disable that one rule
under an `overrides` entry scoped to `*.vue` and record why in `biome.json` as a comment.

Three boundaries must be machine-enforced. Two fit Biome's `noRestrictedImports` under
per-glob `overrides`; the third does not and gets a script.

**B1 — Host isolation (§3.1, C1).** The specifier `vscode` may be imported only under
`packages/host-vscode/**`. Anywhere else it is an error. Same treatment for `electron` outside
`packages/host-electron/**`.

**B2 — Bun runtime ban (§8.1, D-none-but-hard).** The `bun:` specifier prefix and the `Bun`
global are banned everywhere except `scripts/**` and `*.test.ts`. This is what keeps the
extension host and Electron builds honest, since neither runs Bun.

**B3 — Package dependency direction (§3.1).** `core` and `ipc` import nothing from siblings;
`git` and `ui` may import `core` and `ipc`; only hosts import everything; nothing imports a
host. Expressible as a set of `noRestrictedImports` overrides, one per package.

**B4 — No hardcoded colour in the UI (§6.1).** Biome has no rule for this, so
`scripts/check-tokens.ts` greps `packages/ui/**` for hex literals, `rgb(`/`hsl(` calls, and
named CSS colours outside `theme/*.css`, and fails with file:line. Crude and completely
effective — the failure mode it prevents (a stray `#1e1e1e` that looks right in dark and wrong
in every other theme) is invisible in review and obvious in a grep.

Exact Biome rule ids are confirmed against the pinned version during implementation rather
than taken from this plan; the intent above is what must hold.

**Done when:** `bun run check` runs format check + lint + types + `check-tokens`, and a
deliberate violation of each of B1–B4 fails it. Add those four violations as a throwaway
commit, confirm four failures, revert.

## W4 — `packages/ipc` contract skeleton

Real structure, minimal surface. P3 fills it in; P0 proves the shape works and gives the
harness something to implement.

`contract.ts` defines one type map with three sections, so a transport implementation and a
mock implementation are checked against the same source of truth:

```ts
export type Contract = {
  requests: { 'repo.open': { params: …; result: … }; 'graph.query': { … } }
  events:   { 'repo.changed': { … } }
  streams:  { 'graph.stream': { chunk: … } }
}
```

with helper types (`RequestKey`, `ParamsOf<K>`, `ResultOf<K>`) so call sites are inferred
rather than annotated.

Seed it with exactly four entries — `repo.open`, `graph.query` (request), `repo.changed`
(event), `graph.stream` (stream). Four is enough to exercise all three mechanisms; more is
speculative design against a driver that does not exist yet.

`transport.ts` — the `Transport` interface both hosts and the mock implement.
`codec.ts` — encode/decode, including collecting `ArrayBuffer`s into a transfer list, since
§5.3 depends on transferring layout buffers rather than cloning them. Get the transfer path in
now: retrofitting it after the UI assumes structured clone is a rewrite of the stream layer.
`validate.ts` — boundary validation and a `CONTRACT_VERSION` constant. A mismatch **throws**;
per §3.5 it must fail loudly rather than half-work.

**Done when:** a unit test round-trips each of the four entries through the codec, including
one carrying an `ArrayBuffer`, and asserts the buffer was transferred (detached) rather than
copied.

## W5 — `packages/ui` placeholder shell and the theme token layer

The UI is a placeholder in P0, but the **theme token layer is not** — it is the foundation
every component built in P4–P10 sits on, and it is cheap now.

- `theme/vscode-tokens.css` — the `--kv-*` token layer from §3.4, each token a
  `var(--vscode-…, var(--fallback, <literal>))` chain. Roughly 40 tokens. This is the only
  file in `packages/ui` permitted to contain a colour literal (W3/B4 exempts `theme/*.css`).
- `theme/density.css` — the spacing and row-height scale from §6.1 (22px default row).
- `theme/readTokens.ts` — the `getComputedStyle` bridge plus the `MutationObserver` on
  `<body>` that re-reads on theme change. Implement it fully in P0 even though nothing paints
  to canvas yet: it is small, it is easy to get subtly wrong, and P4 will otherwise implement
  it in a hurry while also writing a renderer.
- `App.vue` — a placeholder that renders the app shell regions (toolbar strip, list area,
  detail pane) as empty boxes styled from the token layer, and displays the connection state
  from the bridge. Enough for W8's Playwright test to assert something real and for the
  visual-regression baseline to exist from day one.
- `icons/` — wire `@vscode/codicons` and render two icons in the placeholder toolbar, proving
  the font loads under the webview CSP that P3 will impose.

**Done when:** the harness shows the shell, switching theme kind in the harness restyles it,
and `readTokens` reports changed values after the switch (asserted in W8).

## W6 — Fixture repository generator

`tests/fixtures/generateRepo.ts` builds **real** repositories with real `git`. Recorded
porcelain fixtures (`tests/fixtures/porcelain/`) are for parser unit tests; anything that
exercises behaviour uses a generated repo.

**Determinism is the whole job here**, and it is easy to get wrong in ways that produce tests
that pass on the author's machine only. Every invocation runs with:

- `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_SYSTEM=/dev/null`, plus `GIT_CONFIG_NOSYSTEM=1`
  — otherwise the developer's own `~/.gitconfig` (aliases, `init.defaultBranch`, `core.autocrlf`,
  a `commit.gpgsign`) leaks into fixtures and two developers get different shas. With no CI to
  catch the divergence (D28), this hygiene is the only thing standing between us and tests that
  pass on one machine only.
- Fixed `GIT_AUTHOR_NAME`/`EMAIL`/`DATE` and `GIT_COMMITTER_*`, with dates advancing by a fixed
  step per commit, so shas are **reproducible**. Reproducible shas mean a test can assert on a
  sha and a perf baseline can be trusted across runs.
- `--no-gpg-sign` on every commit.
- An explicit initial branch name rather than relying on the default.

Shapes to provide, each a named export:

| Shape | For |
|---|---|
| `linear(n)` | trivial baseline, parser tests |
| `branchy(opts)` | lane layout: parallel branches, merges, re-merges |
| `octopus()` | 3+ parent merge, the case layout algorithms get wrong |
| `criss-cross()` | two branches merging each other, the other layout trap |
| `withStash(opts)` | stash entries including `-u` |
| `conflicting(opts)` | a pair of branches guaranteed to conflict on a known file |
| `withRemote(opts)` | a local bare "remote" for P7's fetch/push/non-ff/lease tests |
| `large(n)` | perf; must generate 100k commits in reasonable time (see below) |

`large(n)` cannot be n invocations of `git commit` — that is minutes to hours at 100k. Build it
with `git fast-import`, which takes a stream on stdin and writes packed objects directly.
Expect single-digit seconds for 100k. Cache the generated repo under a gitignored directory
keyed by a hash of the generator inputs, so it is built once per machine.

**Done when:** each shape builds; `linear(5)` produces identical shas on two consecutive runs
and on a second machine; `large(100_000)` builds in under ~30s and is cached thereafter.

## W7 — `apps/harness` and the mock bridge

A Vite app that mounts `packages/ui` unchanged and supplies a `Transport` implementation
backed by fixtures. This is the fast Playwright target and, per §8.4, the reason the UI is
host-agnostic in the first place.

- `mockBridge.ts` implements the `Transport` interface from W4 against fixture data,
  including the stream mechanism with realistic chunking so the UI's streaming path is
  exercised rather than bypassed.
- `scenarios/` — named states selectable via a query parameter so a Playwright test can deep
  link: `clean`, `dirty`, `conflicted`, `hugeRepo`, `authFailure`. P0 implements `clean` and
  `hugeRepo` (the two W8/W9 need); the rest are stubs that later phases fill as they gain
  behaviour to show.
- `themeSwitcher.ts` — forces `vscode-light` / `vscode-dark` / `vscode-high-contrast` /
  `vscode-high-contrast-light` on `<body>` and injects a **small hand-written dev palette** for
  the tokens the placeholder uses. The generated-from-VS-Code palettes
  (`scripts/gen-theme-palettes.ts`) are a P3 deliverable; P0 does not need fidelity, it needs
  four switchable kinds.

**Done when:** `bun run dev` serves the harness, `?scenario=clean` renders the shell, and the
theme switcher visibly changes it.

## W8 — Playwright

`playwright.config.ts` with three projects declared, only the first runnable in P0:

| Project | Target | Runs |
|---|---|---|
| `harness` | the Vite dev server | the default suite; runs on demand |
| `electron` | `_electron.launch` on the Electron host | from P3 |
| `vscode` | the downloaded VS Code build with the extension installed | from P3 |

Declaring all three now means P3 wires a host into an existing slot rather than inventing test
infrastructure while also writing a host.

P0's tests, deliberately few and load-bearing:

1. The shell renders its regions.
2. Switching theme kind changes the computed value of a `--kv-*` token **and** what
   `readTokens` reports — this is the §3.4 canvas-desync bug caught at the earliest possible
   moment.
3. A visual-regression screenshot of the shell in all four theme kinds, establishing the
   baseline the P4 suite grows from.

Screenshot comparison needs a stable environment or it produces false failures that erode
trust in the suite — and with no CI runner to standardise on (D28), the environment is
whatever macOS machine runs it. So: pin the Playwright version (implied by W1's exact
pinning), pin the browser Playwright downloads, fix the viewport, disable animations, and set
a `maxDiffPixelRatio` tolerant enough to absorb font rasterisation differences between
machines rather than demanding byte equality. If baselines still prove machine-specific,
generate them in a container rather than loosening the tolerance until it catches nothing.

**Done when:** `bun run test:e2e` passes locally with baselines committed, and passes on a
second macOS machine without regenerating them.

## W9 — Performance budget harness

`tests/perf/` measures the §5.1 budgets and fails on a >20% regression. Building it in P0 —
before there is anything slow — is the point: a budget adopted after the code exists gets set
to whatever the code currently does.

With no CI (D28), nothing runs this for us. That makes it more important, not less: running
`bun run test:perf` is an explicit exit criterion of every phase from P2 onward, and the
budget file is committed so a regression shows up as a diff someone has to justify.

- **Time** — `performance.mark`/`measure` inside the app at named points
  (`first-paint`, `page-parsed`, `layout-complete`), read out through Playwright.
- **Heap** — the browser measurement to prefer here is a Chrome DevTools Protocol session from
  Playwright: `Performance.getMetrics` reports `JSHeapUsedSize`. Force a collection before
  sampling and take the median of several samples; JS heap readings are noisy and a single
  sample will flap. `performance.measureUserAgentSpecificMemory()` is the more accurate API but
  requires cross-origin isolation, which is friction the harness does not need in P0 —
  reconsider if CDP numbers prove too noisy.
- Baselines in a committed JSON file, per metric, with the tolerance in the runner not the
  baseline. A regression prints the metric, baseline, actual, and delta.

P0 measures the placeholder shell, so the numbers are near zero. That is fine and expected —
what P0 must prove is that the plumbing reports a number, compares it, and fails on a
deliberately introduced regression. Test that by adding a temporary 200ms delay and confirming
red.

**Done when:** `bun run test:perf` reports each §5.1 metric, and an injected regression fails it.

## W10 — Verification tasks

Three things this plan assumes that must be confirmed against reality, not against this
document. Each gets a recorded answer appended to this file under "Findings" as it is resolved.

**V1 — TS 7 / `vue-tsc` state (D4, §8.3).** Re-check whether `vue-tsc` has shipped TS 7 support
since the spec was written; if it has, D4's condition is already met and P0 should adopt tsgo
as the single checker instead of TS 5.x. If it has not, install `@typescript/native-preview`,
confirm `tsgo --noEmit` passes on the non-UI packages, and wire it as `check:fast` only.
Record the versions checked and the date.

**V2 — Bun and `vsce` packaging (§8.1).** Confirm the mitigation: no `vscode:prepublish`
script, explicit build, `bunx @vscode/vsce package --no-dependencies`. Do this on a throwaway
minimal extension **in P0**, not at P11. If it fails, we need to know while the packaging story
is cheap to change.

**V3 — Playwright driving Electron and VS Code (§8.4).** Smoke-test `_electron.launch` against
a trivial Electron app, and launching a downloaded VS Code build with an extension installed.
P3 depends on both working; discovering otherwise at P3 would strand the phase.

None of the three blocks W1–W9. Run them in parallel with the build-out and fold the findings
back before closing the phase.

## Exit criteria

The phase is complete when all of the following hold, verified by running them, not by
inspection:

- [ ] `bun install && bun run check && bun test` is green on macOS.
- [ ] The tree matches §3.1; no stub files pretending to be implementations.
- [ ] Each of B1–B4 fails the build when deliberately violated (demonstrated, then reverted).
- [ ] The ipc codec round-trips all four seeded contract entries, with `ArrayBuffer` transfer
      asserted.
- [ ] The harness renders the placeholder shell and switches between all four theme kinds.
- [ ] At least one Playwright test passes against the harness, plus visual baselines for the
      four theme kinds.
- [ ] The perf harness reports time and heap, and fails on an injected regression.
- [ ] The fixture generator produces reproducible shas, and `large(100_000)` builds and caches.
- [ ] V1–V3 resolved, versions pinned exactly, findings recorded below.
- [ ] Every check is a single non-interactive command with a meaningful exit code, so a
      pipeline can be added later without touching the packages (D28).
- [ ] Nothing from P1+ has been implemented. If the diff contains a git command outside
      `tests/fixtures/`, the phase overran.
