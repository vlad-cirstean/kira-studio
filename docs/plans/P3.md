# P3 — Host bridge

Plan for the P3 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** the two real hosts, and the one typed pipe between them and the UI. A VS Code panel
webview view and an Electron `BrowserWindow` that boot the *same* UI bundle over the *same*
`packages/ipc` contract, served by one host-side `RepoService` composing P1's driver and P2's
paged walk and store; §5.4's cache and rehydration, so hiding and revealing the panel repaints
from memory rather than re-running git; one settings schema in `core` driving both hosts (D25);
and the theme layer completed at its one genuinely missing end — Electron's palette, generated
from VS Code's own theme JSON.

**Platform and runtime constraints.** macOS only (D27), inherited unchanged. What is new in
this phase is that **two of the packages P3 writes are production runtimes rather than
libraries**: `packages/host-vscode` runs inside the VS Code extension host and
`packages/host-electron/src/main` runs in Electron main. Both are Node (§8.1), so the `bun:`
and `Bun` bans bite for the first time on code that has a real deployment target, and B1
confines the specifiers `vscode` and `electron` to their own package. Neither API can be loaded
by `bun test`: there is no `vscode` module outside a running VS Code, and `electron` resolves
to a launcher whose binary this sandbox has not downloaded (`packages/host-electron/
node_modules/electron` has no `path.txt`). **That is a design constraint, not just a testing
inconvenience:** every host file that touches `vscode`/`electron` must be thin enough that the
logic it wraps lives somewhere a unit test can reach — the ports (§3.3), the RPC endpoint, the
`RepoService`, the settings schema — and the host file itself must be adapter code with no
branching worth testing.

No CI (D28) — every check here is a command someone runs, and running them is an exit criterion.

**On verification in this sandbox, stated up front so the phase does not stall on it.** This is
a headless Linux container. `xvfb-run` is present and P0's V3 confirmed `_electron.launch`
works under it, but the Electron *binary* is not currently installed; `update.code.
visualstudio.com` is blocked, so `downloadAndUnzipVSCode()` — and therefore the `vscode`
Playwright project — may remain unrunnable here, exactly as P0 recorded. The posture, matching
P1's V2 and P2's V1/V2 precedent: **verify everything that can be verified headlessly (the
integration suite over a real repo, the harness e2e suite, the transport over an in-memory
channel pair, the RepoService cache with spawn counting), and record the display- and
hardware-dependent halves as inherited-open in Findings with the exact command a macOS machine
must run.** A plan that only closes on hardware this repository has never had is a plan that
does not close.

**Not a goal:** anything that renders history. No canvas, no virtualized list, no row
components, no ref badges, no columns, no keyboard navigation, no responsive breakpoints — that
is P4, and P3's UI surface is deliberately a plain-text strip (W9). No commit detail, no diff
(P5). No mutating operations, no pre-flight, no conflict banner (P6+). No search (P10). No
packaging, no `.vsix`, no notarization, no marketplace metadata, no status bar item, no SCM
title button (P11). No `contributes.colors`, since the lane palette it exposes is P4's to
generate and contrast-check.

The one thing P3 must get right that no later phase can fix cheaply: **the boundary is one
mechanism, not two.** There are two transports (§3.5: `webview.postMessage` in VS Code,
`ipcRenderer.invoke` + `MessagePort` in Electron) and there will be a third consumer of the same
contract (the harness's mock). If request correlation, stream lifecycle, backpressure and
version validation are written per host, then by P7 the two hosts have diverged in their
cancellation semantics and every stream bug has to be diagnosed twice. Everything above the
literal `postMessage` call is written once, in `packages/ipc`, and each host contributes about
ten lines of channel adapter. The same argument applies to the wire *format*: §5.5's "transfers,
not clones" only survives if there is one packing routine, and the one place it can live is
beside the store that produced the buffers.

### The watcher.ts thread, resolved

P1's scope table deferred `watcher.ts` to P3 with a two-part reason: "it needs the `FileWatcher`
port, whose only implementations are host-owned, and it produces signals that nothing consumes
until there is a graph to invalidate and a `repo.changed` event to carry it."

**Both halves are discharged in this phase, so `watcher.ts` is in P3** — but only its refs half.

- The port is P3's to define either way (§3.3), and its implementation turns out **not** to be
  host-owned for the part we need: watching `.git/HEAD`, `.git/refs/**`, `.git/packed-refs`,
  `.git/FETCH_HEAD` and the in-progress state files is `node:fs.watch` in both hosts, exactly
  as `ProcessRunner` was `child_process` in both. So it is written once, in `packages/git`,
  following P1's `nodeProcessRunner.ts` precedent (W6). The genuinely host-specific
  implementations §3.3 names (`workspace.createFileSystemWatcher`, a `chokidar`-class watcher)
  are for the **worktree**, whose only signal is `worktreeChanged`, whose only consumer is the
  `status` re-query behind P6's conflict banner and P4's decorations. That half is deferred with
  its consumer, and no `chokidar`-class dependency is added now.
- The consumer half is no longer hypothetical. P3 is the phase that creates the host-side cache
  (§5.4) whose correctness depends on knowing that refs moved, and it is the phase that
  finalizes `repo.changed` — an event P0 put in the contract and that P3 must either wire to a
  producer or delete. Shipping a contract entry no host ever emits is a lie in a type map, and
  a lie in a type map is what the harness's mock will faithfully reproduce.

What P3 does with the signal is bounded and is the part worth stating: on `refsChanged` the
`RepoService` marks the repo's cached set stale and emits `repo.changed`; the UI displays it
(one testid, W9). **P3 does not re-walk, does not auto-refresh, does not read `.git` state files
for §7.11's in-progress detection, and does not build the Refresh action** — those are P4's and
P6's, and the debounce/coalesce logic they will call is exactly what W6 delivers and tests.

### "Shows live data", scoped so a test can assert it

The exit bar is *"Panel opens in VS Code and shows live data; Electron app shows the same."*
Before P4 there is no list and no canvas, so this needs an explicit reading rather than a
hopeful one.

**P3's reading: a real repository, opened by a real host, walked by P1's driver and P2's
`logSession`, parsed into a host-side `CommitStore`, packed, streamed over the real transport,
unpacked into a UI-side `CommitStore`, and rendered as plain text.** Concretely, the shell grows
a status strip with these and nothing more: repository root, HEAD, git version or block state,
loaded row count, remaining count, the first row's short sha and subject, the chunk's `source`
(`git` or `cache`), and the last `repo.changed` kind. Every one is a `data-testid` a Playwright
test can read, and every one is a value that could only have come from the pipeline actually
running end to end. There is no styling work in it beyond the token layer it inherits.

Two things this deliberately is not. It is not the graph — asserting "the graph renders" would
be asserting P4's deliverable a phase early, and the honest way to keep P3 from drifting into
P4 is to make its UI incapable of drawing a lane. And it is not a debug backdoor: `source` is a
real field of the stream chunk that P4 keeps (the UI genuinely wants to know whether it is being
served from cache, and §5.4's whole promise is that it sometimes is), not a test-only hook that
gets deleted later.

### Which ports P3 implements, and where each lives

| Port | P3 implementation | Consumer in P3 |
|---|---|---|

| `FileWatcher` | `git/nodeFileWatcher.ts`, shared (`node:fs.watch`) — worktree impls deferred | `git/watcher.ts` |
| `WorkspaceRoots` | separate: `workspace.workspaceFolders` + change event / recent-repos store + folder pick | `repo.list`, first-repo auto-open |

Ports are narrow interfaces that grow with their callers: `Dialogs` having exactly one method in
P3 is the point, not an omission to apologise for.

### The `ipc` → `core` boundary, which P3 is the first phase to hit

§3.1's dependency rule says "`core` and `ipc` depend on nothing", and `biome.json` enforces it:
`packages/ipc` importing `@kira-version/core` is a lint error today. But P1 and P2 both wrote
that their output types live in `core` "so P3 can reference them instead of redeclaring them",
which cannot be done literally.

**Resolution: the boundary rule wins, and the drift it risks is closed by a type test rather
than by an import.** `ipc/src/contract.ts` declares its own wire shapes — structural, plain
data, no classes — and `tests/unit/ipc/wireConformance.test.ts` asserts assignability in both
directions against `core`'s types (`HeadState`, `DecorationRef`, the settings snapshot, the
packed chunk). `tests/` may import both packages (its tsconfig already references all three), so
the check runs inside `bun run check` and a field added to one side and not the other is a type
error with a name on it. Amending B3 to allow type-only `ipc → core` imports was the
alternative; it was rejected because §3.1's rule is normative, because "type-only" is not a
distinction `noRestrictedImports` draws, and because a one-file type test is cheaper than an
architectural exception that later phases will read as permission.

## W1 — `packages/ipc/src/contract.ts`, finalized

P0 seeded four entries and said so in the file's own comment ("P3 grows this; P0 only proves the
shape"). This item replaces them with the surface §3.5 describes, restricted to what P3 or an
immediately following phase actually calls. Every entry below has a producer and a consumer in
this phase; nothing is added on speculation, because a contract entry with no producer is what
the harness mock will then have to fake convincingly.

**Requests** (UI → host, one response):

```ts
"app.init":      { params: Record<string, never>;
                   result: { host: HostKind; contractVersion: number;
                             settings: SettingsSnapshot; git: GitStatus } }
"repo.list":     { params: Record<string, never>;
                   result: { candidates: readonly RepoCandidate[]; activeRepoId: string | null } }
"repo.pick":     { params: Record<string, never>; result: { path: string | null } }
"repo.open":     { params: { path: string };      result: RepoOpenResult }
"repo.close":    { params: { repoId: string };    result: Record<string, never> }
"graph.status":  { params: { repoId: string };
                   result: { loaded: number; remaining: number; exhausted: boolean } }
"graph.loadMore":{ params: { repoId: string; pages?: number }; result: { started: boolean } }
```

**Events** (host → UI): `repo.changed` (`{ repoId, kind: "refsChanged" | "worktreeChanged" }`,
kept from P0 and now given a producer in W6) and `settings.changed`
(`{ settings: SettingsSnapshot }`).

**Streams** (host → UI, chunked with backpressure): `graph.stream`, params
`{ repoId: string; resumeThroughRow?: number }`, chunk:

```ts
interface GraphChunk {
  readonly repoId: string;
  readonly seq: number;
  readonly from: number;             // absolute row indices, not chunk-relative
  readonly to: number;
  readonly source: "git" | "cache";  // §5.4 made observable; W9 renders it, P4 keeps it
  readonly remaining: number;
  readonly exhausted: boolean;
  readonly commits: PackedCommitChunk;   // W3's shape; the ArrayBuffers live here
}
```

Three discriminated unions carry the states the UI must be able to render rather than infer:

```ts
type GitStatus =
  | { kind: "ok"; path: string; version: string }
  | { kind: "notFound"; probed: readonly string[] }
  | { kind: "tooOld"; path: string; detected: string; required: string; settingId: string }
  | { kind: "unusable"; path: string; reason: string };

type RepoOpenResult =
  | { kind: "ok"; repo: RepoSummary }
  | { kind: "notARepository"; path: string }
  | { kind: "gitUnavailable"; git: GitStatus };
```

`GitStatus.tooOld` is the §4.2 block state crossing the boundary at last. P1's `GitResolution`
carries `path`/`detected`/`required` and not the upgrade hint or the setting id its plan
promised, so W1 adds `settingId: "kiraVersion.git.path"` here (the UI needs a value to render,
not prose to assemble) and the upgrade command stays a UI string, since it is platform copy and
`core` should not hold it. **P3 renders this state as text in the strip (W9); the designed
blocking surface is P4's**, and that is the honest split — the phase that owns the shell owns
what a blocked shell looks like.

`log` from §3.5's event list is **not** added. It is host → UI, and P3's Logger writes host-side
only; the UI has a devtools console in both hosts. It lands when something reads it.

`validate.ts` grows `assertContractShape(method, payload)` — a per-key structural check on
arrival, not a schema library: the wire is trusted-but-versioned between two halves of one
build, and §3.5's requirement is that a *mismatch* fails loudly, which a version check plus a
shape check on the discriminants delivers. `CONTRACT_VERSION` goes to `2`.

`codec.ts` keeps `encode`'s transferable collection and gains `dedupeTransferList` — the same
buffer appearing twice throws at `postMessage`, and W3's packed chunk deliberately shares no
buffers, so this is an assertion that catches a future mistake rather than a workaround for a
current one.

**Done when:** the type map compiles with no `any`; `tests/unit/ipc/wireConformance.test.ts`
asserts each wire type against its `core` counterpart in both directions; a deliberate field
rename in `core` fails `bun run check`.

## W2 — `packages/ipc/src/rpc.ts`, the generic endpoint

New file, added to §3.1's tree. Everything above the literal `postMessage` lives here, once, so
the two hosts and the mock cannot diverge on semantics.

```ts
export interface MessageChannelLike {
  post(message: unknown, transfer?: readonly ArrayBuffer[]): void;
  onMessage(handler: (message: unknown) => void): () => void;
  close(): void;
}

export function createRpcClient(channel: MessageChannelLike): Transport;
export function createRpcServer(channel: MessageChannelLike, handlers: ServerHandlers): RpcServer;
```

`Transport` (P0's interface, unchanged in shape) is now *implemented once*; `host-vscode/src/
transport.ts` and the Electron preload each supply a `MessageChannelLike` of about ten lines.
The frame union, every member wrapped by P0's `wrapVersioned`:

```
{ t:"req", id, method, params } | { t:"res", id, ok:true, result } | { t:"res", id, ok:false, error }
{ t:"evt", method, payload }
{ t:"open", id, method, params } | { t:"chunk", id, seq, chunk } | { t:"end", id, error? }
{ t:"credit", id, n } | { t:"cancel", id }
```

Decisions inside it that are worth fixing now:

- **Backpressure is credit-based** (§3.5 says streams are "chunked with backpressure", and
  neither transport gives us a delivery signal to infer it from). The client opens a stream with
  an initial credit of 2 and returns one credit per chunk consumed; the server emits at most its
  outstanding credits. This is the mechanism that keeps a 100k walk from queueing twenty pages
  of buffers into a webview that is busy painting the first one.
- **Cancellation is a frame, not a dropped listener.** `AbortSignal` on the client side sends
  `cancel`; the server maps it to the `AbortSignal` it passes into `RepoService`, which P1's
  driver already honours. A client that disappears without cancelling (webview disposed) is
  handled by the server's channel-closed path, which aborts every in-flight stream for that
  channel — not by a timeout.
- **Errors cross as data**, `{ code, message, kind? }`, where `kind` is P1's `GitErrorKind` when
  the failure was a `GitError`. Raw stderr is deliberately not forwarded by default: it is
  unbounded and sometimes contains a remote URL with a username in it. The Logger has it
  host-side; a later phase that needs it in the UI adds an explicit request for it.
- **One in-flight `graph.stream` per repo per channel.** Opening a second supersedes the first
  (the server cancels it), which is the same "superseded query is killed" rule §4.3 states for
  reads.

**Done when:** a full-duplex test over an in-memory `MessageChannelLike` pair covers request/
response, a rejected request, an event, a stream of ten chunks with credits (asserting the
server never runs ahead of its credit), cancel mid-stream, a superseded stream, a version
mismatch throwing on receipt, and channel close aborting in-flight work.
(`packages/ipc/src/rpc.test.ts` — colocated; it needs no fixtures.)

## W3 — Packed commit chunks

Two methods on P2's `CommitStore`, in `commitStore.ts` rather than a new file, because packing
needs the interner and the CSR columns that are private to it:

```ts
packSlice(from: number, to: number, dictionaryBase: number): PackedCommitChunk;
appendPacked(chunk: PackedCommitChunk): AppendResult;
```

```ts
export interface PackedCommitChunk {
  readonly from: number; readonly to: number;
  readonly shaWidthBytes: number;
  readonly shas: ArrayBuffer;           // (to-from) × width, binary (§5.5)
  readonly parentOffsets: ArrayBuffer;  // Uint32Array, (to-from)+1, chunk-relative
  readonly parentShas: ArrayBuffer;     // binary, CSR order — shas, not row indices
  readonly identityIds: ArrayBuffer;    // Uint32Array, 4 per row, into the dictionary
  readonly times: ArrayBuffer;          // Uint32Array, 2 per row
  readonly subjectBytes: ArrayBuffer; readonly subjectOffsets: ArrayBuffer;
  readonly dictionaryBase: number;      // first id this chunk's dictionary defines
  readonly dictionary: readonly string[];  // only strings interned since dictionaryBase
  readonly decorations: readonly (readonly [row: number, refs: readonly DecorationRef[]])[];
}
```

**Parents travel as shas, not as row indices.** Row indices would in fact match — both sides
append in the same order — but sending shas means the receiving store resolves them through the
pending-parent machinery P2 already built and tested (`AppendResult.resolvedParentSlots`), so a
chunk is independent of what the receiver has loaded and a page boundary behaves identically on
both sides of the wire. The alternative saves ~26 bytes a row and buys a whole class of
off-by-one that only appears after a Load more.

**The dictionary is a delta.** Author names and emails repeat (§5.5); chunk *n* carries only the
strings interned since chunk *n−1*, and `dictionaryBase` is the assertion that the receiver's
interner is in the same state. A mismatch throws — it means chunks arrived out of order or a
chunk was dropped, and silently re-interning would produce a store whose author column points at
the wrong names.

`packedTransferList(chunk): ArrayBuffer[]` returns each buffer exactly once, mirroring P2's
`layoutTransferList` and reusing its lesson: a buffer listed twice throws at `postMessage` and a
buffer omitted is silently cloned, which shows up later as a memory regression with no obvious
cause.

**Done when:** a store built from `topology()` packs and re-appends into a second store whose
every accessor (`shaAt`, `subjectAt`, `authorAt`, `parentsOf`, `decorationAt`, `commitAt`)
matches the source for every row of every W1-of-P2 shape; page-by-page packing equals one-shot
packing; `structuredClone(chunk, { transfer: packedTransferList(chunk) })` round-trips and
detaches every source buffer; a chunk applied out of order throws; a sha-256 store round-trips.
(`tests/unit/store/wire.test.ts` — it needs `tests/fixtures/topology.ts`, so it lives under
`tests/unit/` per P2's finding.)

## W4 — The settings schema (D25) and its generator

```ts
export const SETTINGS = { /* … */ } as const;

```

`coerceSettings` never throws and never returns a partly-valid object: a wrong type, an
out-of-range number or an unknown enum member falls back to the default and is reported in
`CoerceResult.problems`, which the host logs. A user with `"pageSize": "lots"` in their
settings.json gets a working panel and a log line, not a dead one.

**The keys P3 defines are exactly the keys P3 consumes.** Each later phase adds its own with its
own consumer; the schema's value is being the one place, not being complete on day one.

| Key | Type | Default | Consumer |
|---|---|---|---|
| `kiraVersion.git.path` | string | `""` | `locateGit`'s `configuredCandidates[0]` (§4.2 step 1); VS Code's own `git.path` is appended as step 2 by the host, not by the schema |
| `kiraVersion.graph.pageSize` | number (100–50000) | `5000` | `openLogSession` (§5.1.1) |
| `kiraVersion.graph.scope` | enum `all` \| `head` | `all` | `openLogSession` (D10's toggle) |

**Done when:** `bun run check` fails when the manifest is edited by hand or a setting is added

## W6 — `git/nodeFileWatcher.ts` and `git/watcher.ts`

**`nodeFileWatcher.ts`** — the one real `FileWatcher` for the `.git` directory, `node:fs.watch`
based, shared by both hosts for the reason `nodeProcessRunner.ts` is shared: the extension host
and Electron main are the same runtime doing the same thing, and writing it twice at W10/W11 is
a copy-paste bug factory. Details that matter on macOS: `fs.watch` with `recursive: true` is
supported (FSEvents-backed) and coalesces aggressively, so the watcher must re-read state rather
than trust the event; a watch on a file that is atomically replaced (git writes `refs/heads/x`
via rename) can stop firing, so directories are watched, not individual ref files, and
`packed-refs`/`HEAD` are watched through their parent directory too. Errors (EMFILE, a `.git`
that disappears) surface as a typed failure and a log line, never an unhandled `error` event.

**`watcher.ts`** — §4.5's coalescing, and the only thing in this phase with real timing logic:

```ts
export interface RepoWatcher extends Disposable {
  onSignal(fn: (s: "refsChanged" | "worktreeChanged") => void): Disposable;
  pause(): void; resume(): void;
}
export function watchRepo(watcher: FileWatcher, identity: RepoIdentity,
                          opts?: { debounceMs?: number; now?: () => number }): RepoWatcher;
```

Watched, per §4.5, under `--git-common-dir` (not the git dir — a linked worktree's refs live in
the common dir, D12): `HEAD`, `refs/**`, `packed-refs`, `FETCH_HEAD`, `MERGE_HEAD`,
`rebase-merge/`, `rebase-apply/`; plus `index` in the git dir. Events are debounced 200 ms and
coalesced into the two signals — ref-ish paths to `refsChanged`, `index` to `worktreeChanged`.
`pause()` exists because §4.5 says "we never poll on a timer while the window is hidden" and the
same logic applies to a burst of events nobody is listening to; the host pauses on hide.

The worktree source is not wired (see the scope boundary), so `worktreeChanged` in P3 has
exactly one producer: `.git/index`. That is honest — an index write *is* a worktree state change
— and it means the signal exists with a real, if partial, source rather than as a dead branch.

**Done when:** unit tests over a fake `FileWatcher` with injected time assert that ten events in
50 ms produce one signal; that a ref event and an index event in the same window produce both
signals once each; that `pause()` drops and `resume()` does not replay; that dispose stops
everything. Integration test over a real generated repo: `git tag`, `git branch`, and a
`packed-refs` rewrite (`git pack-refs --all`) each produce exactly one `refsChanged` within
~500 ms; `git add` produces `worktreeChanged`. (`tests/integration/watcher.test.ts`.)

## W7 — `git/repoService.ts`

§3.2's host-side object, and the first thing in this project to compose P1 and P2 into something
with a lifetime. New file, added to §3.1's tree.

```ts
export interface RepoServiceDeps {
  readonly runner: ProcessRunner; readonly fileWatcher: FileWatcher;
  readonly logger: Logger; readonly settings: Settings;
  readonly configuredGitCandidates: readonly string[];
}
export class RepoService {
  static create(deps: RepoServiceDeps): Promise<RepoService>;   // runs locateGit once
  readonly git: GitStatus;
  open(path: string): Promise<RepoOpenOutcome>;
  close(repoId: string): void;
  status(repoId: string): { loaded: number; remaining: number; exhausted: boolean };
  streamGraph(repoId: string, opts: {
    resumeThroughRow?: number;
    onChunk: (chunk: GraphChunkPayload) => Promise<void>;   // awaited: this is the backpressure
    signal?: AbortSignal;
  }): Promise<void>;
  loadMore(repoId: string, pages?: number): Promise<void>;
  onChanged(fn: (e: { repoId: string; kind: "refsChanged" | "worktreeChanged" }) => void): Disposable;
  setUiVisible(visible: boolean): void;
  dispose(): void;
}
```

**Per open repo it holds** exactly what §5.4 says the host holds: the `CommitStore`, the
`LogSession`, the `RepoWatcher`, the `CatFileSession` and `GitDriver` (opened here because
`repo.open` runs the identity and capability probes), the ref snapshot, a `dictionaryCursor` for
W3's delta, and a `staleReason`.

**Streaming and cache, which are the same code path.** `streamGraph` walks a cursor from
`resumeThroughRow ?? 0`:

- rows already in the store are emitted as `source: "cache"` chunks with no git involvement —
  this is §5.4's whole promise, and it is what makes "hide/reveal rehydrates without re-running
  git" a property of the design rather than an optimisation someone remembers to add;
- when the cursor reaches `store.rowCount`, the first page is read from the `LogSession`
  (subsequent pages only on `loadMore`, per §5.1.1 — the host never loads a page the user did
  not ask for);
- within a page, rows are flushed as `source: "git"` chunks every `CHUNK_ROWS = 500` rows or
  every 16 ms, whichever comes first, so §5.1's "first commits painted" does not wait for a
  5,000-row page to finish;
- `onChunk` is **awaited**, so the credit-based backpressure in W2 reaches all the way back to
  P2's paused `git log`. This is the one place where the two backpressure mechanisms meet, and
  it is why `onChunk` returns a promise rather than void.

**Staleness and invalidation.** `refsChanged` marks the repo stale and emits the event; a
`stale` outcome from `logSession.readPage` (P2's spliced-page guard) drops the store, resets the
cursor and re-walks from row 0 — the caller sees a chunk sequence starting at `from: 0`, which
is exactly what the UI needs to know to discard what it had. P1's `driver.onInvalidated` is
wired to the same handler so a future phase's write invalidates the same way.

**Eviction** (§5.4, §5.5): `setUiVisible(false)` starts a timer; after `HIDDEN_EVICT_MS`
(5 minutes, an exported named constant, not a literal in a closure) the store is cleared, the
`LogSession` disposed and the watcher paused. Deliberately *not* a setting: nothing in P3 can
change it and a setting nobody tunes is surface with no consumer. Closing a repo evicts
immediately. What survives eviction is the repo identity, so a reveal after eviction re-walks
without re-probing.

**Done when:** integration tests (W16) cover open/stream/loadMore/close over generated repos;
the second `streamGraph` on the same repo spawns no git process; eviction then reveal spawns
exactly one; a `refsChanged` during a session emits once and marks stale; a cancelled stream
kills nothing that a subsequent stream needs.

## W12 — Electron palettes, and the theme layer's actual gap

whether that runs in `bun run check` depends on the file existing, so it is wired but skipped
with a message when the source is unavailable.

_Recorded during implementation. V1–V5 outcomes, and any decision made at the keyboard that
this plan did not anticipate — later phases read this section as part of the context they
inherit._

**W11's first pass missed the theme-kind body class; caught while starting W12.** `main/index.ts`
and `renderer/index.ts` were implemented and unit-tested against W11's bullet list, but the one
sentence saying the renderer itself "sets the theme-kind class on `<body>`" was read past the
first time — nothing else stamps `vscode-dark`/`vscode-light`/`vscode-high-contrast`/
`vscode-high-contrast-light` for Electron the way a real VS Code webview host does automatically,
so W12's generated palette would have had no selector to hang off of. Fixed in a follow-up commit
before starting W12's generator proper: `renderer/index.ts` now makes one extra `app.init` call
over the same transport `mount()` uses, resolves the kind from the `kiraVersion.theme.kind`
override (falling back to `prefers-color-scheme`/`prefers-contrast`/`forced-colors` media queries
when the override is `"system"`), applies the class before `mount()` to avoid a flash, and keeps
it live via `settings.changed` and `matchMedia`'s own `"change"` event — no new `contextBridge`
member or contract event needed, since none was available to spend.

**W12 — palette generation could not run in this sandbox; the generator is written and
committed, the palette is not.** Confirmed exhaustively: no `code`/VS Code install anywhere on
this machine, no `/Applications`, `$KIRA_VSCODE_APP` unset, and no `dark_modern.json` (or any VS
Code theme JSON) findable on the whole filesystem — none of `scripts/gen-theme-palettes.ts`'s
four source candidates resolve here. Per this plan's own instruction for exactly this case, the
generator was still written in full (`extractVscodeVarNames`, `varNameToColorId`,
`stripJsonComments`, the include-chain merge, and the CSS renderer are pure functions, smoke-
tested end to end against a hand-built fixture theme directory outside the repo — not committed,
per "do not hand-write a substitute file"), wired into `bun run check`/`bun run gen:theme-
palettes`, and `--check` skips with a message rather than failing when the output file is
absent, which it currently is: `packages/host-electron/src/theme/palettes.generated.css` does
not exist, `packages/host-electron/src/theme/.gitkeep` is still the only file in that directory,
and Electron therefore renders only the dark palette (every `--kv-*` token's literal fallback)
with no kind-switching, exactly as this plan's contingency describes. **To close the gap**, on a
macOS machine with VS Code installed: `bun run gen:theme-palettes` (resolves the default
`/Applications/Visual Studio Code.app` install with no flags needed), or `bun run scripts/gen-
theme-palettes.ts --source <dir>` pointing at any directory holding `dark_modern.json`,
`light_modern.json`, `hc_black.json` and `hc_light.json`. The harness's hand-written `PALETTES`
map in `themeSwitcher.ts` is therefore also left as P0 built it — there is no generated file yet
for it to move onto — so the visual-regression baselines are unchanged by W12 and W12's harness-
adoption clause is deferred to whoever runs the command above.

**W13 surfaced two real gaps in already-shipped W10 code, found empirically rather than by
inspection.** `html.ts`'s `WEBVIEW_ENTRY` and `main/index.ts`'s `RENDERER_HTML_PATH` were both
comments coordinating forward to "whatever W13 produces" rather than a value verified against a
real Vite build — W13 is where that build first actually ran, and it disagreed with both guesses:

1. *Vite's root can't be `host-vscode`.* The plan's UI target is one Vite build for both the
   webview and the Electron renderer entries; the renderer's HTML entry lives in a sibling
   package (`host-electron`), and Vite refuses to emit an HTML entry whose output path would
   fall outside the configured `root` (confirmed empirically: a `root: packages/host-vscode`
   config throws `RolldownError` the moment `host-electron/src/renderer/index.html` is added to
   the same build). `root` has to be `packages/`, the closest real common ancestor, which makes
   the webview's manifest key `host-vscode/src/webview/main.ts` rather than the shorter
   `src/webview/main.ts` `html.ts` had guessed, and puts the built renderer HTML at
   `dist/ui/host-electron/src/renderer/index.html` rather than `dist/ui/renderer/index.html`.
   Both files' hardcoded constants are updated to match what the build actually produces, with
   the reasoning now on the coordinating side rather than assumed.
2. *`extensionUri` is `packages/host-vscode`, not the repo root.* `panelView.ts` and `html.ts`
   both built `dist/ui`'s location as `Uri.joinPath(extensionUri, "dist", "ui")` — but
   `package.json`'s own `main: "../../dist/vscode/extension.js"` already commits this package to
   a *repo-root* `dist/`, two levels above `extensionUri`. Left as W10 wrote it, the extension
   would have looked for the UI bundle inside `packages/host-vscode/dist/ui`, which nothing ever
   builds. Fixed by joining `"..", "..", "dist", "ui"` in both places instead, matching the
   `main` field's own convention and `main/index.ts`'s sibling-of-`dist/electron` addressing.

A third bug was caught by inspecting the real manifest W13's build produced, not by re-reading
old code: `resolveUiAssets` only ever read an entry's *own* `manifest[key].css` array, but
because the webview and renderer entries share nearly all of `packages/ui`'s code, Vite puts
that shared code's CSS on the *imported chunk's* `css` array instead — the webview entry's own
`css` field is simply absent. Unfixed, the VS Code webview would have loaded with no theme
tokens, no density rules, and no codicon font at all, silently (no error, just an unstyled
page). Fixed with the standard Vite-manifest-consumer pattern: walk `imports` transitively and
concatenate every `css` array found along the way, not just the entry's own.

None of the three had a unit test to catch them — `packages/host-vscode` has no test files at
all (the `vscode` module isn't mockable without infrastructure this phase doesn't build, per
W10's own precedent), so this class of bug is exactly what `bun run build` actually running,
end to end, against its own real output was for. Verified: all four bundles build; the manifest
key match confirmed by inspecting the real `dist/ui/.vite/manifest.json`; the CSS fix confirmed
the same way (the webview entry's collected CSS list is non-empty and points at the shared
chunk's stylesheet); the two bundle-level checks confirmed to fail correctly (a deliberate
`Bun.version` added to `extension.ts` was caught and reverted; `renderer/index.ts`'s own
legitimate `host: "electron"` literal was confirmed *not* to trip the UI-bundle check once it
was scoped to the shared chunk via the manifest's `isEntry` flag instead of every `.js` file
under `dist/ui`). Not verified, for the same reason as V2/V3: the UI bundle actually rendering
correctly inside a real VS Code webview or a real `BrowserWindow` — no VS Code or Electron
binary exists in this sandbox (§ W12's finding above). `node --check` confirms all four bundles
are syntactically valid JS, and the renderer's relative asset URLs were confirmed by hand to
resolve correctly from the built HTML's actual on-disk nesting depth.

**W15 — the Electron binary is not actually blocked here, correcting W12/W13's assumption; the
VS Code binary genuinely is.** Re-probed directly rather than trusted forward: `bun install`
fetches the `electron` npm package's own binary from npm's registry (not a GitHub release), and
that registry is reachable through this sandbox's proxy — `node_modules/.bun/electron@…` holds a
real, runnable binary. What actually blocks a run here is narrower and different: no `$DISPLAY`
(fixed with `xvfb-run -a`) and no working setuid sandbox helper (`--no-sandbox`, already how
`main.ts` is launched). With both, `electron/shell.spec.ts`'s first test passes for real in this
sandbox against a real window, a real generated git repo, and the real RPC transport — not merely
written-and-unrunnable. `vscode/panel.spec.ts`, by contrast, needs `@vscode/test-electron`'s
`downloadAndUnzipVSCode()`, which really does fail here (`update.code.visualstudio.com` returns
an HTML error page where JSON is expected — the same proxy block as P0's V3, just surfaced as a
parse error rather than a bare 403 through this particular client). Exact commands are in each
spec file's own doc comment.

**A real, previously-undiscovered wiring gap in W12's palette delivery, found only because W15
actually ran a window end to end.** `gen-theme-palettes.ts` emits
`packages/host-electron/src/theme/palettes.generated.css`, but nothing in `host-electron` ever
loaded that file into a running app — no Vite import, no runtime read. Even with a real palette
file present (verified with a hand-built fixture, not committed — same "do not hand-write a
substitute" rule as W12's own finding), the app's background colour never changed. Fixed with two
changes: (1) `main/index.ts` now reads the file from disk (`existsSync` guard, since it
legitimately may not exist — W12's own contingency) and calls `webContents.insertCSS()` once per
window load, so a developer can regenerate the palette and relaunch with no rebuild; (2)
`gen-theme-palettes.ts`'s generated selectors changed from `body.vscode-dark` etc to
`:root:has(body.vscode-dark)` etc. The second change is the one that actually mattered: every
`--kv-*` consumer in `vscode-tokens.css` reads its `--vscode-*` source through a `var()` written
on `:root`, and a custom property's `var()` substitutes using the value visible at the
*declaring* element only — a `--vscode-editor-background` set on `body` is invisible to a
`var()` written on its ancestor `:root`, so `--kv-app-bg` froze to its literal fallback regardless
of which body class was active. `renderer/index.ts`'s `applyThemeClass` still stamps the class on
`<body>` (matching real VS Code, and `vscode-tokens.css`'s pre-existing high-contrast rule, which
was not affected since it declares a property fresh on `body` rather than reading one down from
`:root`); only where the *colour* declarations live moved. Verified against a real Electron
window with a hand-built two-theme fixture: `--kv-app-bg` read `#f5f5f5` under a real
`vscode-light` body class and the fallback `#1e1e1e` was gone.

**Driving the OS theme change from outside the app needed `app.evaluate`, not
`page.emulateMedia`.** The obvious tool for `electron/shell.spec.ts`'s theme test — Playwright's
`page.emulateMedia({colorScheme})` — never changed anything in a real run: Electron's own
`nativeTheme` resolves `prefers-color-scheme` for every renderer at the Chromium-embedder level,
underneath where CDP's media emulation attaches. `_electron`'s `ElectronApplication.evaluate`
runs in the real main process and can flip the real signal (`nativeTheme.themeSource`), which is
what `ports/theme.ts`'s `ElectronTheme` and `main/index.ts`'s own `theme.current()` read — this is
also more faithful to what the feature actually is (an OS-level signal, not a media query the
page happens to observe). That fix closed one gap and surfaced a narrower, third one specific to
this sandbox: `nativeTheme.themeSource` changing never propagates into the renderer's own
`matchMedia` here, because this container has no D-Bus session bus (confirmed in the same launch's
stderr: `Failed to connect to the bus: ... No such file or directory`), which is what `nativeTheme`
needs to learn about and broadcast an OS theme change at all. This is the one assertion in either
new spec that is genuinely environment-blocked rather than fixed — a real desktop session (macOS,
Windows, or Linux with a running D-Bus session bus) does not have this gap. Documented at the
test's own definition rather than only here, since it is narrower than "no VS Code/Electron
binary" and easy to conflate with it.

**`import.meta` cannot appear anywhere in a module Playwright's pinned test-file transform
loads — confirmed with a one-line repro, independent of any binary or network concern.**
`@playwright/test@1.62.1` failed to load `electron/shell.spec.ts` with `SyntaxError: Cannot use
'import.meta' outside a module` even though root `package.json` sets `"type": "module"` and Node
22 supports it natively; a bare `console.log(import.meta.url)` in an otherwise-empty spec file
reproduced the same failure. This ruled out importing `tests/fixtures/generateRepo.ts` at all
(it uses `import.meta.dir` for its `large()`/`largeBranchy()` disk cache, and the mere presence
of that token anywhere in an imported module's source breaks the load, even in code paths a spec
never reaches) — so both new specs use `resolve(process.cwd(), …)` for their own paths (safe:
`playwright.config.ts`'s `testDir` is root-relative, so Playwright always runs from the repo
root) and a new `tests/e2e/support/generateRepo.ts`, a deliberate, minimal duplicate of just

**`kiraVersion.theme.kind` is Electron-only** (`packages/core/src/settings/schema.ts`'s
`hosts: ["electron"]`) **— `panel.spec.ts`'s theme test exercises VS Code's own built-in colour
theme instead**, via the same quick-pick a person would use (`Preferences: Color Theme`, then
typing a theme name), which is the real, working half of
§3.4's theme story on this host today; `kiraVersion.theme.kind` has no VS Code configuration
property to change in the first place (confirmed: `host-vscode/package.json`'s generated
`contributes.configuration.properties` has exactly `git.path`/`graph.pageSize`/`graph.scope`/
`log.level`, no `theme.kind` — `toVsCodeConfiguration()` filters it out by design).

**VS Code has no repo-picker UI either, and `App.vue`'s `bootstrap()` only auto-opens a
persisted `repoId`, which a first-ever webview load never has** (`acquireVsCodeApi().getState()`
starts undefined) — so `KIRA_REPO` was extended to this host too, carried through `html.ts`'s
bootstrap JSON island (rebuilt fresh on every `resolveWebviewView`, unlike Electron's static
HTML) rather than `loadFile`'s `query` option. `webview/main.ts` only seeds the view-state store
from `bootstrap.repo` when `viewState.read()` is still null — a later resolve (the webview is
destroyed and recreated on every hide/reveal, §2.1, no `retainContextWhenHidden`) must never
clobber real persisted state, since that persisted state surviving is the entire mechanism
`panel.spec.ts`'s second test asserts.

**`playwright.config.ts`'s `webServer` stays at the config root, not moved under `harness`.**
Read directly from the pinned `@playwright/test@1.62.1`'s own shipped `types/test.d.ts`:
`webServer` exists only on the top-level `TestConfig` interface, not on `TestProject`/`Project`/
`FullProject` — there is no per-project form to move it to in this version. It only ever starts a
server the `electron`/`vscode` projects never reach, so this is the closest correct equivalent to
the plan's instruction until a Playwright version that supports per-project `webServer` is
pinned; documented in place with a comment rather than silently left as found.
