# P2 — History pipeline

Plan for the P2 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** the path from `git log` bytes to a laid-out graph, built to the memory and paging
discipline of §5.1.1, §5.2 and §5.5 — a paged, resumable history walk that never re-walks; a
column-wise typed-array store that holds 100k commits in single-digit megabytes; and a pure
lane-layout pass that emits packed buffers ready to be transferred, not cloned, to whatever
thread P4 puts it on.

**Platform and runtime constraints.** The git half (`logSession.ts`) inherits P1's macOS-only
scope (D27) unchanged — it spawns the system git through P1's resolved binary and adds no new
platform-conditional branch. The `core` half is deliberately the opposite: `store/` and
`graph/` are pure TypeScript over typed arrays with no `node:*`, no DOM, no `vscode`, no
framework, so they run identically in the extension host, in Electron main, in a browser
worker, and under `bun test`. There is no macOS dependency in the layout algorithm and this
plan does not invent one.

There is, however, a **runtime** constraint that is new in this phase and is load-bearing:
§5.1.1's pause is not something our code does, it is something the *runtime's stream
implementation* does on our behalf. Measured while writing this plan, against the cached
`large(100_000)` fixture (see W11): under Node 22 a consumer that stops pulling from
`child.stdout` leaves `git log` alive and blocked on `write()` — the mechanism §5.1.1 assumes.
Under this repository's Bun test runtime the same code drains the pipe eagerly and git runs to
completion while we are "paused". Production is Node (§8.1), so the design is sound; but it
means **`bun test` cannot assert the pause**, and any exit criterion that depends on it is run
under Node. This is called out again in W11 and V1 rather than discovered at the keyboard.

No CI (D28) — every check here is a command someone runs, and running them is an exit
criterion.

**Not a goal:** anything that renders. No canvas, no Vue, no virtualized list, no Load more
*button*, no `postMessage`, no `Worker` instantiation, no `packages/ipc` change. P2 produces a
library with tests and a perf harness as its only callers, exactly as P1 did; P3's RepoService
and P4's graph view are its first production consumers. Also not a goal: search (P10), the
watcher (P3), `ops/` (P6–P9), and writing a commit-graph file — D21's rule is inherited from
P1's W8 verbatim and the string `commit-graph write` must not appear in this phase's diff
outside `tests/fixtures/` (W13, and only against repositories we generate ourselves).

The one thing P2 must get right that no later phase can fix cheaply: **the store's shape and
the layout's incrementality.** A row-wise `CommitRecord[]` works perfectly at 5,000 commits and
is the whole of §5.5's stated problem at 100k, and by then it is threaded through the
renderer, the hit test, the detail pane and the search matcher. The same is true of layout: a
`layout(allRows)` that recomputes from row 0 on every Load more is simpler, plausibly fast
enough, and quietly incompatible with §5.5's "transferred, not cloned" — a transfer detaches
its source, so re-laying out everything each page means re-*copying* the whole parent structure
into the worker every page, forever. Both are cheap to get right now and expensive to retrofit.

### Where the worker line falls

The phasing row says "lane layout **in a worker**", and §3.1 puts `layout.worker.ts` under
`packages/ui/src/graph/`. Those two facts pull in opposite directions and the resolution is
that they are describing different things.

The *algorithm* is P2's, entirely, and it is written to be worker-ready in a way that is
testable today:

- it is a pure function of typed arrays to typed arrays, with no `self`, no `postMessage`, no
  DOM and no `node:*`;
- its input and output are structured-clone-safe plain data, and it declares its own transfer
  list (`layout.ts`'s `transfer` field), so "transferred, not cloned" is a property of the
  return value rather than a convention at a call site;
- W10 proves that property mechanically, with `structuredClone(result, { transfer })` and a
  real worker round trip.

The *file* `packages/ui/src/graph/layout.worker.ts` is P4's, and is deferred for three
reasons. First, its entire content once the algorithm is pure is a `self.onmessage` handler
that calls `layoutAppend` and posts the result with its transfer list — under ~30 lines of
wiring. Second, that wiring is against a message shape the IPC contract has not settled: P3
owns `graph.stream`'s chunking and backpressure, and writing the worker now means writing it
twice. Third, and decisively, `packages/ui` has no bundle yet — no Vite worker build config,
no entry point, no test that can load it — so the file would ship as the one thing
`AGENTS.md` forbids: scope that is present but not exercised. `packages/ui` may import
`@kira-version/core` (the boundary rule in `biome.json` permits core + ipc), so P4 wrapping
a pure function loses nothing that building it now would gain.

A reasonable person could disagree and put the ~30-line worker file in P2. The reason not to
is that it cannot be run, and a worker that cannot be run is a claim, not a deliverable.

## W1 — `tests/fixtures/topology.ts`

The exit bar says "layout unit tests over **hand-built** topologies incl. octopus merges", and
that word is doing work. `generateRepo.ts` builds real repositories with real git, which is
right for the pipeline's integration tests (W14) and wrong for layout unit tests: it costs a
process per commit, it cannot express the shapes that break lane assignment (a twelve-parent
octopus, a repository with three unrelated roots, fifty concurrent branches, a merge whose
parents are 40,000 rows apart), and a layout test that needs a temp directory is a layout test
nobody runs in a tight loop.

So: a tiny in-memory topology builder, living beside `generateRepo.ts` because it is the same
kind of thing (a fixture source) and added to §3.1's tree in the same commit.

```ts
/** "A", "B:A", "C:A", "D:B,C" — one entry per commit, newest last, parents by name. */
export function topology(spec: readonly string[]): CommitRecord[]
```

It emits `CommitRecord`s in **reverse topological order** — newest first, exactly as
`git log --topo-order` does — from a spec written oldest-first, because writing a topology
oldest-first is how a human thinks about one and reading a walk newest-first is how the
pipeline consumes it. Shas are synthesised deterministically from the name (`name` hashed to
40 hex chars) so a test can assert on identity without pinning a real sha. It validates the
spec: an unknown parent name, a cycle, or a child listed before its parent is a thrown error
in the fixture, not a mysterious layout result.

Two helpers alongside it, since three of W6's cases need them and hand-writing 50 entries is
how a test stops being read:

```ts
export function fan(branches: number, depthPerBranch: number): CommitRecord[]
export function octopusOf(parents: number): CommitRecord[]
```

The named shapes W6–W9 test against, all expressed through this builder: linear; a single
fork and merge; a fork that is never merged (a lane that stays open to the end of the loaded
range); octopus with 3 and with 12 parents; criss-cross (two merges with two lowest common
ancestors); multiple disconnected roots; a merge whose second parent is far above it; fifty
concurrent open lanes; a commit with two children in the *same* lane's expectation set; and a
page boundary where a parent is not yet loaded.

**Done when:** the builder round-trips every named shape, rejects a malformed spec, and
`topology(["A","B:A"])` yields `B` before `A`.

## W2 — `core/store/intern.ts`

§5.5's third rule, both halves of it, in one file because they solve the same problem with two
different shapes.

```ts
export class StringInterner {
  intern(value: string): number      // stable id, first-seen order
  get(id: number): string
  readonly size: number
  readonly byteLength: number        // estimated retained bytes, for W15's accounting
}

export class SubjectBuffer {
  /** Appends in strict row order; the returned index must equal the caller's row index. */
  append(subject: string): number
  at(index: number): string
  readonly count: number
  readonly byteLength: number
}
```

The interner is a `Map<string, number>` plus a `string[]`, and it is the easy half: author
names, emails and ref names repeat, so a 100k-commit repo with 20 authors retains 20 strings.

`SubjectBuffer` is the interesting half. Subjects are the one genuinely large and genuinely
non-repeating set (§5.5), so they go into a single growing `Uint8Array` of UTF-8 bytes with a
`Uint32Array` of start offsets — subject `i` is `bytes[offsets[i] .. offsets[i+1])`, which is
why appends must be strictly row-ordered and why `append` asserts it rather than trusting it.
Growth is by doubling with a `set()` copy; at 100k × ~40 bytes that is ~4 MB in one allocation
instead of 100k separate string objects. `at()` decodes on demand through a shared
`TextDecoder`, which is what §5.5 means by materializing only the rows on screen.

One decision worth stating because it looks like an oversight otherwise: **the store consumes
P1's `CommitRecord`, whose fields are already decoded strings**, so `SubjectBuffer.append`
re-encodes a string P1's parser just decoded. The alternative — pushing byte ranges from
`parse/log.ts` straight into the buffer — saves that round trip but duplicates the parser's
field splitting inside `core`, and P1's W10 explicitly promised that "the record-yielding
interface it exposes is the one P2 keeps". The round trip is transient garbage, not retained
heap, and W15 measures whether it matters. Do not pre-optimise it; if the first-page budget is
tight, the finding belongs in Findings with a number attached.

**Done when:** interning is stable and order-independent across insert orders; a subject
containing astral-plane characters, a lone surrogate, and an empty string all round-trip;
`append` throws when called out of row order; `byteLength` tracks actual allocation.

## W3 — `core/store/shaTable.ts`

§5.5's second rule — "shas are stored as 20-byte binary in a single flat `Uint8Array`, not as
40-char hex strings (which cost ~120 bytes each in V8)" — plus the lookup that rule quietly
makes hard.

```ts
export class ShaTable {
  constructor(opts?: { widthBytes?: 20 | 32; initialCapacity?: number })
  append(hex: string): number          // row index
  hexAt(row: number): string
  shortHexAt(row: number, chars: number): string
  bytesAt(row: number): Uint8Array     // a subarray view, never a copy
  rowOfHex(hex: string): number        // -1 when not present
  rowOfBytes(sha: Uint8Array): number
  readonly count: number
  readonly widthBytes: number
  readonly byteLength: number
}
```

**The lookup is the whole design problem.** Parents arrive as hex shas and must become row
indices; refs arrive as object ids and must become row indices. The obvious implementation, a
`Map<string, number>` keyed on the 40-char hex, costs roughly 100k × (a ~120-byte string + a
~50-byte map entry) ≈ 17 MB — which is more than everything else in the store put together and
is precisely the representation §5.5 exists to forbid. Storing shas as bytes and then indexing
them by string would be a rule followed in the letter only.

So the index is an **open-addressed hash table over the binary shas**: an `Int32Array` of
row-index slots (−1 = empty) sized to the next power of two above `2 × capacity`, hashed on
the first four bytes of the sha read little-endian (git object ids are uniformly distributed,
so the leading bytes are as good a hash as anything we could compute and cost nothing),
linear probing, collisions resolved by comparing the full `widthBytes` in the flat array.
At 100k commits that is a 2^18 × 4 B ≈ 1 MB table plus 2 MB of shas — against 17 MB, and it
is the single most memory-significant decision in the store. Growth rehashes at a 0.5 load
factor.

**`widthBytes` is a constructor parameter, not the constant 20**, detected from the length of
the first hex string appended. `git init --object-format=sha256` produces 32-byte object ids
and 64-character hex, and a store that hardcodes 20 would silently truncate every sha in such
a repository — the class of bug that reproduces on one user's machine and nowhere else. This
costs one field and one multiplication now; §5.5's "20-byte" is the common case, not the only
one. The same reasoning P1 applied to unborn HEAD.

`append` validates: wrong length for the established width, or a non-hex character, is an
`assert` failure — a malformed sha means the parser broke, and hiding it as a lookup miss
turns a loud bug into a wrong graph.

**Done when:** 100k random shas insert and look up correctly with no false positives (a
deliberate first-four-bytes collision, constructed by hand, resolves to the right row); a
sha-256 repository's 64-hex ids round-trip through a `widthBytes: 32` table; `bytesAt` returns
a view that reflects nothing but its own row; `rowOfHex` on an absent sha returns −1 without
allocating; the table survives a growth rehash with every prior entry still findable.

## W4 — `core/store/commitStore.ts`

§5.5's first rule: "commits are stored column-wise in typed arrays, not row-wise as objects …
a commit 'object' is materialized on demand for the ≤ 60 rows on screen and the one selected
commit, then discarded."

```ts
export class CommitStore {
  append(record: CommitRecord): number
  appendPage(records: Iterable<CommitRecord>): AppendResult
  readonly rowCount: number

  rowOfSha(hex: string): number
  shaAt(row: number): string
  shortShaAt(row: number, chars?: number): string
  subjectAt(row: number): string
  authorAt(row: number): CommitIdentity
  committerAt(row: number): CommitIdentity
  /** A view into the parent column: row indices, or -1 for a parent not (yet) loaded. */
  parentsOf(row: number): Int32Array
  decorationAt(row: number): readonly DecorationRef[]
  /** The ≤60-rows-on-screen path (§5.5): allocates one object, retains nothing. */
  commitAt(row: number): CommitRecord

  layoutInput(from: number, to: number): LayoutInput
  stats(): CommitStoreStats
  clear(): void
}

export interface AppendResult {
  readonly from: number
  readonly to: number
  /** Slots in the parent column that changed from -1 to a real row because this page
   *  supplied the parent. Feeds `layoutAppend`'s patch pass (W9). */
  readonly resolvedParentSlots: Uint32Array
}
```

**Columns.** Six `Uint32Array`s of table ids and timestamps (author name, author email, author
time, committer name, committer email, committer time), one `Uint32Array` of subject indices,
and the parents in CSR form: `parentOffsets: Uint32Array` of length `rowCount + 1` and
`parentRows: Int32Array` of total parent slots. CSR is what makes an octopus merge free — a
commit with twelve parents is twelve consecutive slots, not a special case — and it is exactly
the shape `lanes.ts` wants to read. Capacity grows by doubling; at 100k rows the whole column
set is under 4 MB.

**Timestamps are `Uint32Array`**, which is a real ceiling (2106) and a real floor (1970) rather
than an oversight. Clock-skewed and imported histories do produce commit dates outside that
range; the store clamps, asserts in development, and records the clamp count in `stats()`, so a
repository with a bogus date renders with a slightly wrong sort key on those rows instead of
costing 800 KB of `Float64Array` for everyone. If W15 or a later phase shows this to be wrong,
it is one type change in one file.

**Decorations are sparse and stay sparse.** `%D` is empty for all but a few hundred rows in any
real repository, so decorations live in a `Map<number, readonly DecorationRef[]>` rather than a
column. §5.5's rule is about the 100k-element columns, and turning a 200-entry map into a
column would be following it into a place it does not apply.

**Late parent resolution is the correctness centre of this file.** `--topo-order` guarantees a
parent is never emitted before its children, so when page 1 ends, some rows have parents that
are simply not loaded yet; those slots hold −1. When page 2 supplies them, those earlier rows'
parent slots must be filled in — otherwise every edge crossing a page boundary dangles forever
and the graph is wrong in a way that only appears after a Load more. Implementation: the store
keeps a pending list of (parent slot index, parent sha bytes) for unresolved slots; after each
page's shas are inserted into the `ShaTable`, the pending list is re-resolved and the resolved
slots are returned in `AppendResult.resolvedParentSlots` for the layout to patch. The list is
bounded by the walk's open frontier — the number of branches alive at the page boundary,
typically well under a hundred — not by the number of rows. Slots that never resolve (a shallow
clone's boundary, a graft) stay −1 permanently and are a legitimate terminal state, not an
error.

**Done when:** a store built from `topology()` reports the right parents for a root, a
two-parent merge and a twelve-parent octopus; `commitAt(row)` reconstructs a `CommitRecord`
byte-identical to the one appended, for every row of every W1 shape; appending in two pages
produces exactly the same columns as appending in one, including `parentRows` (this is the
page-boundary test and it gets its own name); `resolvedParentSlots` lists precisely the slots
that changed; `stats()` reports per-structure byte counts that sum to within a few percent of
the process's own retained delta.

## W5 — `core/graph/types.ts`

The contract between the store, the layout, and the thread the layout eventually runs on.
Written before the algorithm because the buffer layout is the part P4 and the IPC contract have
to agree with, and because the decisions in it are the ones that are expensive to change later.

```ts
export interface LayoutInput {
  readonly from: number;              // first row of this chunk
  readonly to: number;                // exclusive
  readonly parentOffsets: Uint32Array; // absolute, length rowCount + 1
  readonly parentRows: Int32Array;     // -1 = not loaded
  /** From `AppendResult` — slots that just became resolvable (W4). */
  readonly resolvedParentSlots: Uint32Array;
}

export const EDGE_STRIDE = 6;
export const EDGE_FROM_ROW = 0;
export const EDGE_TO_ROW = 1;
export const EDGE_FROM_LANE = 2;
export const EDGE_TO_LANE = 3;
export const EDGE_COLOR = 4;
export const EDGE_KIND = 5;
export const UNRESOLVED_ROW = 0xffffffff;

export type EdgeKind = 0 | 1 | 2;   // 0 straight, 1 branch-out, 2 merge-in

export interface LayoutChunk {
  readonly from: number;
  readonly to: number;
  readonly laneOf: Uint32Array;      // one entry per row in [from, to)
  readonly colorOf: Uint32Array;
  readonly edges: Uint32Array;       // EDGE_STRIDE-wide records, sorted by fromRow
  readonly edgeIndex: Uint32Array;   // CSR: row - from → first edge, length (to - from) + 1
  /** (edgeIndex, toRow) pairs correcting edges emitted in *earlier* chunks. */
  readonly patches: Uint32Array;
  readonly laneCount: number;
  readonly maxEdgeSpan: number;
  readonly transfer: readonly ArrayBuffer[];
}

export interface LayoutFrontier { /* opaque; plain data only */ }
```

Four decisions embedded there, each with a reason:

- **Edges are interleaved at a fixed stride in one `Uint32Array`**, not six parallel arrays.
  One buffer, one transfer, and the renderer's per-frame scan reads six adjacent words instead
  of touching six pages. `EDGE_*` are named offsets so nothing indexes by a bare literal.
- **`laneOf` and `colorOf` are both `Uint32Array`**, per §5.2's literal wording. A colour index
  fits in a byte and a `Uint8Array` would save ~300 KB at 100k, which is not worth diverging
  from the spec's own words for; it is an obvious later win if it ever shows up in a
  measurement.
- **`edgeIndex` and `maxEdgeSpan` exist for the renderer's benefit and cost the layout
  nothing.** P4 draws only the visible row window (§5.3) and therefore needs to find the edges
  intersecting it. `edgeIndex` gives it the edges starting at each row in O(1), and
  `maxEdgeSpan` — the largest `toRow − fromRow` in the chunk — tells it exactly how far above
  the window it must look back to catch a long edge passing through, instead of scanning from
  row 0 or guessing. Emitting per-row segments instead would have made the window query
  trivial and cost 100k × open-lanes × 24 bytes ≈ 24 MB; this is the same query for ~3 MB.
- **`UNRESOLVED_ROW` is a real terminal state**, not a placeholder. An edge to a parent outside
  the loaded range, or below a shallow boundary, keeps it, and P4 draws such an edge running
  off the bottom of the loaded history. Making it `0xffffffff` rather than −1 keeps the column
  unsigned.

The worker message shapes (`LayoutRequest`/`LayoutResponse`, carrying a sequence number so a
superseded request's result can be dropped) live here too, as types only. They are what P4's
`layout.worker.ts` will speak; declaring them in `core` is what stops P4 and P3 from inventing
two different ones.

**Done when:** the module contains no runtime logic beyond constants; every field of
`LayoutChunk` is structured-clone-safe (asserted by W10, not by inspection).

## W6 — `core/graph/lanes.ts`

§5.2's forward pass, and the reason `--topo-order` is non-negotiable in §4.4.

> "a single forward pass over the topologically ordered commit list maintaining an array of
> open lanes; for each commit, claim the leftmost lane whose expected child is this commit,
> route remaining parents into free or newly-allocated lanes, and emit edge segments"

The state is one `Int32Array` of open lanes, where `openLanes[i]` is the row index the lane is
waiting for (`EMPTY = -1`, `PENDING = -2` for a lane waiting on a parent that is not loaded
yet). Per row:

1. Find the **leftmost** lane expecting this row; if none, allocate the leftmost free lane.
   Leftmost is what makes the layout stable and deterministic: two runs over the same
   topology must produce byte-identical output, and "whichever lane we happen to find first"
   does not.
2. Every *other* lane also expecting this row closes here and contributes a merge-in edge —
   this is the multiple-children case and it is the one a naive implementation gets wrong,
   because it thinks a lane is claimed by exactly one commit.
3. Route parents. Parent 0 continues in the claimed lane unless a lane to the left is already
   expecting it, in which case the claimed lane closes into that one. Parents 1..n−1 take a
   lane already expecting them if there is one, else the leftmost free lane, else a newly
   allocated one at the right edge. An octopus merge is this loop running eleven more times;
   it needs no special case and W1's `octopusOf(12)` proves it.
4. A parent of −1 leaves its lane `PENDING`, records the (lane, edge index) pair in the
   frontier, and emits an edge to `UNRESOLVED_ROW`.
5. A root commit (no parents) closes its lane.

`laneCount` is the high-water mark of allocated lanes, so P4 can size the graph column without
scanning.

The frontier — the open-lane array, the pending map, the next colour counter, and the next row
— is everything needed to resume the pass at a page boundary, and it is returned rather than
kept in module state so the same function can lay out two repositories without them seeing each
other.

**Done when:** every W1 shape has an asserted lane assignment; the pass is deterministic (same
input → identical output, asserted by running it twice and comparing bytes); a fifty-branch fan
allocates fifty lanes and reuses them as they close; a merge whose parents are both already
expected by open lanes closes the right one; running the pass in two halves with the frontier
carried across produces the identical result to running it once (this invariant gets its own
test and is re-asserted at W9 over the packed buffers).

## W7 — `core/graph/edges.ts`

Edge emission is driven by W6's pass, but it lives in its own file because the packing, the
sort invariant and the CSR index are a separate concern from lane bookkeeping and because
§3.1's tree says so.

An edge is emitted per parent link: `(fromRow, toRow, fromLane, toLane, color, kind)`. At 100k
commits with the usual ~1.3 parents per commit that is ~130k edges ≈ 3.1 MB, which is the
budget this design is chosen against.

Responsibilities:

- **Append into the interleaved buffer** with doubling growth, returning the edge's index so
  W6 can record it in the frontier for a later patch.
- **Maintain the sort invariant**: edges are appended in increasing `fromRow` because the pass
  walks rows in order, so `edgeIndex` is built by a single sweep rather than a sort. Assert the
  invariant rather than assuming it — a future change that emits an edge out of order would
  otherwise corrupt every window query in P4 silently.
- **Classify `kind`**: straight (parent continues the same lane), branch-out (a parent routed
  into a different lane below), merge-in (a lane closing into another at this row). P4 draws
  these differently; deciding it here, where the lane transition is known, is free, and
  re-deriving it in the renderer from lane numbers is not.
- **Track `maxEdgeSpan`** as edges are appended.
- **Patch a dangling edge**: `patchTarget(edgeIndex, toRow)` sets a previously-`UNRESOLVED_ROW`
  target and records the (edgeIndex, toRow) pair in the chunk's `patches` array when the edge
  belongs to an earlier chunk — the mechanism that makes a Load more fix up the previous page's
  edges without re-laying it out.

**Done when:** edge counts and endpoints are asserted for every W1 shape; the sort invariant
holds and its assertion fires when deliberately violated; `edgeIndex` locates the right edge
range for the first, last and a middle row; `maxEdgeSpan` equals the true maximum over a shape
with one deliberately long edge; patching an edge in an earlier chunk produces exactly one
`patches` entry and leaves the current chunk's own edges out of it.

## W8 — `core/graph/colors.ts`

The only palette we invent (§3.4), reduced in `core` to an integer.

```ts
export const DEFAULT_PALETTE_SIZE = 8;
export function allocateColor(state: ColorState, neighbours: readonly number[]): number;
```

A colour is assigned when a lane is **opened** and held for that lane's lifetime, so a branch
keeps one colour from its tip to its merge point and a lane reused later gets a different one.
The assignment is a rotating counter modulo the palette size, skipping any colour currently in
use by an immediately adjacent open lane when a free one is available — enough to stop two
neighbouring lanes drawing in the same colour, cheap, and fully deterministic, which matters
because the visual regression suite in P4 will screenshot it.

`DEFAULT_PALETTE_SIZE` is 8 because P0 already seeded exactly eight lane tokens
(`--kv-graph-lane-0` … `-7`) in `packages/ui/src/theme/readTokens.ts`; it is a parameter so
that P4 can change the token count without touching `core`. Contrast checking, colour-vision
distinguishability and the high-contrast variants are §3.4's, done against real colours in
P3/P4 — `core` never sees a hex value (§6.1's token-only rule).

**Done when:** the same topology always produces the same colour column; adjacent open lanes
differ in colour whenever the palette has a free entry; a lane closing and reopening does not
inherit the old colour; palette size 1 degrades to "everything colour 0" without looping
forever.

## W9 — `core/graph/layout.ts`

The orchestrator: W6's pass plus W7's edges plus W8's colours, packed into `LayoutChunk` and
handed back with a transfer list.

```ts
export function layoutAppend(input: LayoutInput, frontier?: LayoutFrontier): LayoutAppendResult;
export interface LayoutAppendResult {
  readonly chunk: LayoutChunk;
  readonly frontier: LayoutFrontier;
}
export function layoutTransferList(chunk: LayoutChunk): ArrayBuffer[];
```

**Incremental by construction, and this is the decision the phase turns on.** The first call
lays out rows `[0, 5000)` and returns a frontier; the twentieth call lays out `[95000, 100000)`
given the nineteenth's frontier, patches whatever dangling edges the new page resolved, and
returns buffers covering only the new rows. The full-re-layout alternative — recompute rows
0..N on every Load more — is simpler and, at ~100k rows, probably fast enough on its own. It is
rejected anyway, for a reason that is not about speed: §5.5 requires worker transfers to be
transfers, and a transfer detaches its source. Re-laying out from row 0 each page means
re-copying the entire parent structure into the worker on every page and re-transferring the
entire output back, forever — the exact duplication across threads §5.5 exists to prevent.
Appending sends one page in and one page out.

The correctness obligation this creates is a single invariant, and it is the most important
test in the phase: **laying out a topology page by page produces byte-identical buffers to
laying it out in one pass**, once the patches are applied. It is stated as a property test over
every W1 shape at several page sizes (1, 2, 3, 5000 — small sizes force page boundaries in the
middle of merges, which is where this breaks).

`layoutTransferList` returns each buffer exactly once; a buffer listed twice throws at
`postMessage`, and a buffer omitted is silently cloned, which is the failure mode that would
show up as a memory regression in P4 with no obvious cause. W10 asserts both directions.

**Done when:** the page-by-page/one-pass invariant holds for every W1 shape at every page size
tested; the transfer list is exactly the chunk's distinct buffers; a chunk laid out from a
frontier belonging to a different topology is rejected rather than producing garbage; laying
out 100k rows of `largeBranchy` in one pass and in twenty pages produces identical output.

## W10 — Worker-readiness proof

The phasing row says the layout runs in a worker. P2 does not build the worker (see the scope
boundary), so it owes a mechanical proof that the algorithm *can* be moved to one — which is a
stronger statement than "it looks pure".

Two checks, one required and one best-effort:

1. **Transfer semantics, required.** `structuredClone(chunk, { transfer: layoutTransferList(chunk) })`
   round-trips the chunk, and every source buffer is detached afterwards (`byteLength === 0`).
   This is exactly the operation `postMessage` performs, it needs no worker, no DOM and no
   bundle, and it fails loudly on the two mistakes that matter: a non-cloneable field sneaking
   into `LayoutChunk` (a class instance, a function, a closure) and a transfer list that is
   wrong in either direction.
2. **A real worker, best-effort.** The same round trip through an actual off-main-thread worker
   (`node:worker_threads` under the runtime `bun test` provides), asserting the received chunk
   is identical and the sender's buffers are detached. This catches nothing the first check
   does not in principle, but it is the difference between believing the algorithm is
   thread-safe and having run it on another thread. If the test runtime's worker support proves
   flaky — P1's Findings record one Bun child-process divergence already, and V1 records a
   second — this check is recorded as environment-limited in Findings rather than deleted, and
   the first check stands as the gate.

`LayoutFrontier` is deliberately plain data too, even though it never has to cross a thread in
the design P4 will build (the worker keeps it between pages). Keeping it cloneable costs
nothing and leaves the alternative arrangement — frontier held on the main thread, sent in with
each request — available without a rewrite.

**Done when:** check 1 passes for a chunk from every W1 shape; check 2 passes or is recorded
with the reason it could not.

## W11 — `git/logSession.ts`

§5.1.1's paused long-lived process. The phase-defining item.

> "a single long-lived `git log` process per repo that we read `pageSize` records from and then
> **pause** (stop reading; the OS pipe buffer applies backpressure and git blocks), resuming on
> Load more. The second form avoids re-walking and is what P2 implements, with `--skip` as the
> fallback if a repo's process was reclaimed."

**Spawned like `catFile`, not through `driver.read()`.** P1's `catFile.ts` spawns through the
`ProcessRunner` directly while reusing the driver's `buildGitArgv`/`buildGitEnv`, and
`logSession.ts` follows that precedent exactly — same signature shape, same env, same `-c`
overrides, same `--no-optional-locks`. The reason is not symmetry: `driver.read()` acquires a
slot in the bounded read pool (default 4) and releases it on process exit, so a session that is
paused by design would hold a quarter of the repository's read concurrency hostage for as long
as the panel is open. A long-lived, one-per-repo process is categorically not the burst of
reads that pool exists to throttle, which is exactly why P1 put `cat-file` outside it too.
Error classification still goes through `errors.ts`'s `classifyGitError`, so a failed walk
produces the same typed error as any other read.

```ts
export interface LogSessionOptions {
  readonly scope: "all" | "head";
  /** `kiraVersion.graph.pageSize` (§5.1.1); P3's settings schema feeds it, default 5000. */
  readonly pageSize?: number;
  /** Kill the paused process after this long idle; the next page falls back to --skip. */
  readonly idleReclaimMs?: number;
}

export type PageOutcome =
  | { readonly kind: "page"; readonly appended: number; readonly exhausted: boolean }
  | { readonly kind: "stale"; readonly reason: "refsChanged" };

export interface LogSession extends Disposable {
  readonly loadedCount: number;
  readonly exhausted: boolean;
  readPage(sink: (record: CommitRecord) => void, opts?: { signal?: AbortSignal }): Promise<PageOutcome>;
  remaining(): Promise<number>;
  dispose(): void;
}

export function openLogSession(
  git: ResolvedGit,
  runner: ProcessRunner,
  repoRoot: string,
  opts: LogSessionOptions,
): LogSession;
```

**A sink callback, not an async iterable**, which is a deliberate deviation from P1's
everything-is-an-iterable style. A page boundary is a *count*, and a caller that abandons an
iterator halfway leaves the session in a state where "how many records have I consumed" and
"where is git" disagree — the one thing this class exists to keep straight. A callback also
gives §3.5's partial-render behaviour for free: rows reach the store as they arrive, so a
consumer can flush a screenful long before the page completes. In practice the sink is
`store.append`.

**The pause.** The session holds the process's `stdout` async iterator and simply stops calling
`next()` once `pageSize` records have been handed to the sink. Measured while writing this plan
against `large(100_000)` under Node 22: the process is still alive 1.5 s later, blocked on
write, with the OS pipe (64 KiB) and the stream's own high-water mark (64 KiB) bounding what
has been read ahead — around 250 records of slack at this format's record size. Resuming
yielded the remaining 95,000 records in 159 ms with no re-walk. **Under this repository's Bun
test runtime the same code drains eagerly and git exits during the "pause"** — so the assertion
"git is still running" belongs in V1's Node probe, and the `bun test` suite asserts only the
runtime-independent properties: exact page boundaries, no duplicated or skipped records across
a resume, order preserved, `exhausted` set on the last page.

**The `--skip` fallback and what makes it safe.** If the process died or was reclaimed, the
next `readPage` restarts with `--skip=<loadedCount> --max-count=<pageSize>` over the same rev
set. That is only correct if the walk is reproducible, and it is not reproducible if refs moved
underneath us — a fetch during the session would splice new commits into the walk and the
`--skip` offset would then point at the wrong record, producing a page that silently duplicates
or omits history. So the session **snapshots the ref tips it started from** (from the same
`for-each-ref` the pipeline already runs) and, before any `--skip` restart, re-resolves and
compares them. A mismatch returns `{ kind: "stale", reason: "refsChanged" }` rather than a
page; the caller's correct response is to drop the store and re-walk from page 1, which is
precisely what P1's `driver.generation`/`onInvalidated` and §4.5's `refsChanged` already exist
to trigger. Serving a spliced page would be the kind of wrongness a user cannot see and cannot
report.

**The walk itself** is §4.4's, minus `--max-count` (there is no page limit; the pause is the
limit):

```
git --no-optional-locks log --topo-order -z \
    --format=%H%x1f%P%x1f%an%x1f%ae%x1f%at%x1f%cn%x1f%ce%x1f%ct%x1f%D%x1f%s \
    --all --glob=refs/stash
```

built by reusing `parse/log.ts`'s `LOG_FORMAT` and its args builder (W12 factors the rev-set
half out), so the session cannot drift from the format its parser expects — P1's rule that the
format and its parser live together, honoured rather than worked around.

**Lifecycle.** `dispose()` kills the process and waits for exit, like `catFile.ts`; a leaked
paused `git log` per repo open is a process a user finds in Activity Monitor. `idleReclaimMs`
exists because §5.5 requires caches to be bounded and evictable and a blocked git holds pack
files mapped; when it fires the process is killed, `loadedCount` is retained, and the next page
takes the `--skip` path. Ownership is the caller's — the session is deliberately **not** hung
off `GitDriver` the way `catFile` is, because doing so would change the driver's constructor
signature for a composition P3 owns.

**Done when:** page boundaries are exact across 1, 2 and 20 pages on generated repos;
`exhausted` is set precisely on the page that ends the walk and a further `readPage` is a
no-op; the `--skip` fallback after a forcibly killed process yields a byte-identical record
sequence to the uninterrupted one; a ref moved mid-session produces `stale` rather than a page;
an aborted `readPage` kills the process and leaves the session disposable; `dispose()` leaves
no child process; `scope: "head"` walks only the current branch (D10's toggle).

## W12 — Shared rev-set builder and the remaining-count query

§5.1.1: "The button shows what it will do — 'Load 5,000 more (127,400 remaining)' — with the
remaining count from a cheap `git rev-list --count --all` run once per refresh."

P1's `queries.ts` has `countCommits(driver, scope)` building `["rev-list", "--count", "--all"]`,
while `parse/log.ts`'s `logArgs` builds `["--all", "--glob=refs/stash"]`. Those are two
spellings of "the rev set" maintained in two places, and the moment they disagree the remaining
count is wrong by exactly the number of commits in the disagreement — a number the UI shows the
user as fact. Factor one builder:

```ts
// parse/log.ts, beside LOG_FORMAT and logArgs
export function revSetArgs(scope: "all" | "head"): string[];
```

used by `logArgs`, by `logSession.ts`'s spawn, and by `countCommits`. `remaining()` on the
session is then `count − loadedCount`, computed against the *same* rev set the walk uses, and
cached until the session is invalidated (§5.1.1's "once per refresh").

Measured while writing this plan on git 2.43: `--all` already includes `refs/stash`
(`for-each-ref` lists it, and `rev-list --count --all` and `--all --glob=refs/stash` agree on a
`withStash` fixture), which makes §4.4's parenthetical — "`--all` covers heads/tags/remotes but
**not** `refs/stash`" — at best redundant on current git. **Do not remove the flag.** It is
harmless, it is what the spec says to run, and a flag that guards against a git version behaving
differently costs nothing. V3 re-confirms this on the target platform's git and records the
answer; a spec correction, if one is warranted, is a separate change to §4.4 and not something
this phase does silently.

**Done when:** one builder is the only place a rev set is spelled; the count and the walk agree
exactly on `withStash`, `withRemote` and `octopus`; `remaining()` after each of twenty pages
equals the number of records the next pages actually yield, ending at zero.

## W13 — Fixture extensions

Two gaps in P0's fixtures that P2's exit criteria walk straight into.

**`largeBranchy(n, opts)` — because `large(n)` cannot exercise a lane.** The existing
`large(100_000)` is a single linear branch built by `git fast-import`. It is the right ceiling
fixture for parse throughput (P1's W12 used it correctly) and it is useless for measuring
layout: a linear history has one lane, one colour and one edge per row, so a layout time
measured against it says nothing about the algorithm P2 is being judged on. Add a fast-import
generator producing `n` commits across a configurable number of long-lived branches with
periodic merges back — branches and merges are one extra directive each in a fast-import
stream, so this is a variation on `buildFastImportStream`, not a second generator. Cached under
the same `.cache/` scheme with its own key. Defaults chosen to look like a real repository
rather than a stress test: on the order of 8–16 concurrent branches with merges every few
hundred commits, plus one deliberately long-lived branch that merges only near the tip, so
`maxEdgeSpan` is exercised.

**A commit-graph file, because the first-page budget depends on one and real repositories have
one.** Measured while writing this plan on the cached `large(100_000)`, git 2.43, this sandbox:

| Command | No commit-graph | With commit-graph |
|---|---|---|
| `git log --topo-order --all --max-count=5000` | **449 ms** | **12 ms** |
| `git log --topo-order --all` (full 100k) | 479 ms | 143 ms |
| `git rev-list --count --all` | 403 ms | 92 ms |

`--topo-order` without a commit-graph is **not incremental**: git computes the whole ordering
before emitting the first record, so the first page of a 100k repository costs a full-history
walk — 449 ms of git time before a single byte of ours runs, against a ≤400 ms budget for the
whole first page (§5.1). With a graph file, generation numbers make the same walk lazy and the
first page costs 12 ms. This is §4.4's "dramatically faster" stated far more sharply than the
spec implies, and it is the empirical justification for D21's one-time prompt.

The resolution is **not** to write a graph into a user's repository (D21 forbids it and this
phase does not touch that rule). It is that `git gc` has written commit-graphs by default since
2.24, so any 100k-commit repository on a developer's machine that has ever been gc'd already
has one — which makes "with commit-graph" the realistic configuration and "without" the
degraded one. So: `large()` and `largeBranchy()` write a commit-graph as part of generation,
because that is what a real repository of that size looks like, and because a fixture we
generate ourselves is not a user's `.git`. The budget in W15 is measured against that
configuration, and the no-graph number is measured and recorded alongside it, ungated, as the
number a later phase's prompt copy will quote.

**Done when:** `largeBranchy(100_000)` builds in comparable time to `large(100_000)`, caches,
and produces a history whose layout uses more than one lane (asserted, not assumed);
regenerating either fixture twice yields identical shas; the commit-graph is present after
generation and the generators remain deterministic with it.

## W14 — Pipeline integration tests

`tests/integration/historyPipeline.test.ts`: real git, P0's and W13's generated repositories,
the whole path from `openLogSession` through `CommitStore` to `layoutAppend`.

This is where the six-line composition P2 declines to ship as a class gets written down and
exercised:

```ts
const session = openLogSession(git, runner, repo.dir, { pageSize });
const store = new CommitStore();
let frontier: LayoutFrontier | undefined;
for (;;) {
  const before = store.rowCount;
  const outcome = await session.readPage((r) => store.append(r));
  if (outcome.kind === "stale") break;
  const result = layoutAppend(store.layoutInput(before, store.rowCount), frontier);
  frontier = result.frontier;
  if (outcome.exhausted) break;
}
```

Coverage: the walk over `linear`, `branchy`, `octopus`, `crissCross` and `withStash` produces a
store whose row count, shas, parents and decorations match `git log`'s own output for the same
command (compared against a plain `execFile` of the §4.4 invocation, so the test is checking us
against git rather than against ourselves); paging the same repository at page sizes 1, 2 and
`n` yields identical stores and identical layout buffers (the page-boundary invariant, now over
real git output rather than W1's hand-built shapes); a stash entry appears as rows in the walk
(§7.6 — "they are commits; `--glob=refs/stash` in the walk puts them there"); refs from
`refs()` resolve to store rows including an annotated tag resolving through its peeled target;
`remaining()` decreases correctly to zero; a repository with an unborn HEAD yields an empty
store rather than an error; a single-commit repository lays out one row in one lane.

Run in the default `bun test` for the same reason P1 gave: with no CI (D28), a suite outside
the default command is a suite that rots. Generated shapes stay small; `large*` stays perf-only.

**Done when:** all of the above pass against real git ≥2.38, and the store-versus-`git log`
comparison covers every field the store retains.

## W15 — Perf: first page and Load more to 100k

`tests/perf/historyPipeline.ts`, wired into `test:perf` beside P0's `run.ts` and P1's
`parserThroughput.ts`, following their conventions exactly: a committed baseline JSON, a 20%
regression tolerance, a `--update-baseline` flag, non-zero exit on regression.

Measured against `largeBranchy(100_000)`:

| Metric | What it is | Bar |
|---|---|---|
| `firstPageMs` | `openLogSession` → 5,000 records parsed, appended to the store, and laid out | ≤ 400 ms (§5.1), and reported broken down into git time / parse+store time / layout time |
| `loadMoreMs` | each subsequent page, same path, worst of the nineteen | ≤ 400 ms (§5.1) |
| `fullWalkMs` | all twenty pages | recorded, not gated |
| `storeBytes` | `store.stats()` after 100k | baseline + 20% |
| `layoutBytes` | retained layout buffers after 100k | baseline + 20% |
| `heapUsedMB` | process heap after 100k, sampled and medianed | baseline + 20% |
| `firstPageMsNoGraph` | `firstPageMs` with the commit-graph removed | recorded, not gated (W13) |

The breakdown matters more than the total. P1's W12 exists so that a first-page regression can
be attributed to the parser without re-deriving it; this item extends the same courtesy to the
store and the layout, so a future phase seeing 500 ms knows which of four things moved.

Two honest notes about what this measures:

- **It is a headless measurement, not the renderer budget.** §5.1's 80 MB / 250 MB are renderer
  figures covering Vue, the DOM row pool and canvas backing stores alongside the store; none of
  those exist yet. What P2 can measure, and therefore what it gates on, is the retained cost of
  the things P2 built. The expectation from §5.5's own arithmetic is single-digit megabytes for
  the columns plus ~4 MB of subjects plus ~3 MB of edges — call it under 25 MB for the store and
  layout together at 100k, which leaves P4 the whole rest of the 250 MB. If W15's number comes
  in far above that, §5.5's rules are not being followed somewhere and that is a finding, not a
  new baseline.
- **`heapUsedMB` needs a forced collection to mean anything**, and the obvious tool (`Bun.gc`)
  is banned outside `scripts/**` and `*.test.ts` by `biome.json`'s `noRestrictedGlobals`. Either
  sample-and-median as P0's `run.ts` already does for the browser heap, or widen that override
  to `tests/perf/**` in the same commit — a real, small config change, named here so it is a
  decision rather than a lint failure discovered at the end.

**Done when:** `bun run test:perf` reports every metric above against a committed baseline, and
an injected 30% slowdown in the layout fails it.

## Exit criteria

The phasing row's bar is *"First page within budget; repeated Load more to 100k within time
**and heap** budget; layout unit tests over hand-built topologies incl. octopus merges."*
Complete when all of the following hold, verified by running them:

- [ ] `bun install && bun run check && bun run test` is green, with the new integration suite in
      the default `bun test`.
- [ ] **First page within budget:** `bun run test:perf` reports `firstPageMs` ≤ 400 ms on
      `largeBranchy(100_000)` with a commit-graph present, broken down into git / parse+store /
      layout, against a committed baseline. `firstPageMsNoGraph` is reported alongside it and
      recorded in Findings.
- [ ] **Repeated Load more to 100k within time budget:** all twenty pages complete, the worst
      `loadMoreMs` ≤ 400 ms, and the walk is not repeated — asserted by the session spawning
      exactly one process across the whole run.
- [ ] **…and heap budget:** `storeBytes`, `layoutBytes` and `heapUsedMB` at 100k are within 20%
      of their committed baselines, and the store+layout total is in the single-to-low-double
      digit megabytes §5.5's arithmetic predicts. The §5.1 renderer figures (80 MB / 250 MB)
      are explicitly P4's and are not claimed here.
- [ ] **Layout unit tests over hand-built topologies incl. octopus merges:** every W1 shape has
      asserted lanes, edges and colours, including octopus at 3 and 12 parents, criss-cross,
      multiple roots, fifty concurrent lanes and an unmerged branch.
- [ ] Layout is deterministic: the same input produces byte-identical buffers across runs.
- [ ] Page-by-page layout equals one-pass layout, byte for byte, for every W1 shape at page
      sizes 1, 2, 3 and n, and for `largeBranchy(100_000)` at 5,000.
- [ ] Transfer, not clone: `structuredClone(chunk, { transfer })` round-trips and detaches every
      buffer in the transfer list, and the list contains each buffer exactly once.
- [ ] The store holds 100k commits with shas as binary (no 40-char hex retained anywhere), one
      interned entry per distinct author, one concatenated subject buffer, and no per-row
      object — asserted by `stats()` and by the absence of a `Map<string, …>` keyed on a sha.
- [ ] `commitAt(row)` reconstructs the appended `CommitRecord` exactly, for every row of every
