# P4 — Graph UI

Plan for the P4 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** the thing a user actually looks at. P3 finished the pipe — git → `RepoService` →
packed chunks → transport → a UI-side `CommitStore` — and rendered its output as a strip of
labelled numbers. P4 replaces that strip with the surface §6 describes: a virtualized commit
list with real columns and ref badges, a lane graph drawn from P2's layout buffers with the
layout pass finally running in the worker §3.2 puts it in, an explicit Load-more button carrying
its remaining count, selection and keyboard navigation, a working Refresh, and the responsive
behaviour a panel that is short, wide, and constantly resized demands (§6.3).

---

## The rendering decision, and how it was reached

This plan was written once against a hand-rolled virtualizer with the graph as a separate
`<canvas>` layered over it, and then **revised in place** after that design was challenged
directly: use a real grid library, and render the graph as a column *inside* it rather than as
a canvas on top of it, if that is genuinely achievable. It is. The result is a smaller design
than the one it replaces, and the reasoning is recorded here because several work items below
only make sense once it is understood.

**Decision: `slickgrid@5.20.0` owns every column, including the graph. The graph column's cell
formatter returns one small `<svg>` per row. There is no `<canvas>` anywhere in the phase.**

### What was actually checked

**SlickGrid — the library.** `slickgrid` on npm is the [6pac fork](https://github.com/6pac/SlickGrid),
the acknowledged successor to `mleibman/SlickGrid` (dormant since 2014). Verified against the
published package rather than the README:

| Question | Answer |
|---|---|

| Maintained? | `5.20.0` published **2026-09-02**, the day before this plan was written; `5.19.0` in August, `5.18.x` through May. This is a live project |

| Webview CSP | Clean. Grepped the published grid and core for `eval`, `new Function`, `document.write` and `insertAdjacentHTML`: **zero occurrences**. It is an ordinary ES module and needs no `unsafe-eval`, so `html.ts`'s nonce policy admits it as-is, with no directive added (unlike the worker in V1, which does need one) |
| ARIA | **The one genuine cost.** Roles are hardcoded and not configurable: the container gets `role="grid"`, rows `role="row"`, cells `role="gridcell"` + `tabindex="-1"` + `aria-describedby`. | Vue wrapper | `slickgrid-vue@10.10.0` exists and is MIT — but it is a wrapper over the whole `slickgrid-universal` stack and drags in `vanilla-calendar-pro`, `multiple-select-vanilla`, `autocompleter`, `@formkit/tempo` and excel-export types for editors, filters and date pickers we will never open, plus its own Bootstrap/Material theming that would fight §6.1's "no colour that is not a theme token". **Rejected in favour of a ~120-line local wrapper** over the bare package. `AGENTS.md`'s prefer-a-library rule is about non-trivial infrastructure — the virtualizer — not about a component's mount/unmount lifecycle |

**The prior art, and a correction.** The brief for this revision suggested that
`mhutchie.git-graph` draws its lanes as one small SVG per row, each row drawing only its own
vertical slice. **That is not what it does**, and checking was worth it. Reading `web/graph.ts`
and `web/main.ts` from the extension's own source: it builds **one `<svg>` sized to the entire
content height**, containing one `<path>` per *branch* (a whole multi-row polyline accumulated
in a single `d`) plus one `<circle>` per commit, and replaces that whole `<g>` on every render.
The commit table beside it is `tableElem.innerHTML = '<table>' + html + '</table>'` — every
loaded commit, in the DOM, at once. **It does not virtualize at all.** It gets away with this
because its defaults are `initialLoad: 300` and `loadMore: 100`; the design is sound at
hundreds of rows and would not survive one of our 5,000-commit pages, let alone 100,000. Its
last stable release is 1.30.0, April 2025.

So the useful lesson from the prior art is the opposite of the one expected: **the per-row-slice
idea is a good one that nobody in this niche has actually built**, and the reason to build it is
that it composes with virtualization, which is precisely what Git Graph's whole-content SVG
cannot do.

### Why per-row SVG, with the numbers

The slice model works because P2's edge decomposition already confines every transition to one
row: an edge `(fromRow, toRow, fromLane, toLane)` is an **arc** entirely inside the row below
the child, plus a **vertical run** in the parent's lane. A row therefore needs to know only what
crosses its own 22 px band, which `LayoutStore.segmentsInRow(row)` answers in bounded time (W3).
No row consults an edge as a whole; a merge spanning 40,000 rows contributes one vertical run to
each row it passes, and each of those rows draws it without knowing the edge exists.

The cost, concretely, since this is the question the decision turns on:

- **Elements per row.** Segments in a row are grouped by lane colour and emitted as one `<path>`
  per colour with several subpaths in its `d`, not one element per segment. A row is then
  `<svg>` + (colours present, 1–3 typical, ≤ 8) `<path>` + 1 node shape ≈ **4 elements typical,
  ≤ 10 worst case** — against up to 12 lanes plus arcs if each segment were its own element.
- **Elements on screen.** The panel is short: 250–400 px is ~11–18 rows; maximized on a tall
  display, ~55. At a 60-row worst case that is **~240 elements typical, ≤ 600 worst** for the
  whole graph column. The rest of the page adds five cells and a few badge spans per row. This
  is a small document by any measure.
- **Cost per frame while scrolling.** Only rows newly entering the viewport are built. A fast
  fling moves perhaps 40 rows in one frame: 40 × ~4 = **~160 element constructions**, each a
  `createElementNS` plus two or three `setAttribute` — order **0.2–0.4 ms**, against a 16.7 ms
  frame. Rows leaving are dropped by the grid.
- **GC pressure, stated honestly.** This is where SVG genuinely loses to a single reused canvas,
  which allocates nothing per frame. A scripted scroll across 20,000 rows constructs ~80,000
  short-lived elements. They are small, uniform, and die young, which is the allocation profile
  a generational collector handles best — but "it should be fine" is not a measurement, and
  §5.1's 32 ms worst-frame bar is exactly the instrument that would catch it being wrong. W15
  measures it at three scroll positions on the 100,000-row scenario, and W17's V4 establishes
  the noise band first so the number means something.

**Where this could have failed, and did not.** The failure mode worth taking seriously was not
element count — it was an edge that spans more rows than the DOM holds. That is fatal for a
whole-content SVG (Git Graph's shape) and irrelevant here, because the slice model never
represents an edge as an object; it represents each row's cross-section. The second was
per-frame construction cost, and the arithmetic above has an order of magnitude of headroom.
The third — a hairline seam where two rows' vertical runs meet at a fractional device pixel — is
real, cosmetic, and addressed in W8 by overdrawing each run half a pixel past the band with
`overflow: visible` on that one cell.

**What canvas would have bought, and why it is not worth it.** Zero per-row allocation, and one
element instead of hundreds. What it costs, all of which we now simply do not pay: a second
positioned surface whose scroll offset must be kept in sync with the grid's own (which the grid
paginates internally past the element-height cap, so "sync" is not just `scrollTop`); a
`devicePixelRatio` story with a resize and monitor-change path; resolved colour strings plus a
`MutationObserver` and a forced repaint on theme change, because a canvas cannot read a CSS
variable (§3.4 called that "the most visible possible bug" — it is now designed out rather than
defended against); a repaint-coalescing state machine over seven trigger sources; and a graph
that is invisible to screenshot diffing at the element level. **The canvas is eliminated
entirely** — not reduced to an overlay over one column, not kept as a fallback.

exactly as planned.

### The dependency to add

`packages/ui/package.json`: `"slickgrid": "5.20.0"` — pinned exactly, no caret, matching this
repo's convention. Nothing else. `sortablejs` arrives as a transitive entry in the lockfile and
is never imported (`enableColumnReorder: false`); do not add it, and do not add
`slickgrid-vue`, `@slickgrid-universal/*`, or any theme package. Styles are **not** imported
from `slickgrid/dist/styles/*` — those carry Bootstrap/Salesforce/Material palettes that
violate §6.1's token rule. W6 writes the ~80 lines of structural CSS the grid needs
(`.slick-viewport`, `.slick-row`, `.slick-cell` positioning) against the `--kv-*` layer instead,
and that file is the *only* place SlickGrid class names appear in a stylesheet.

**Platform and runtime constraints.** macOS only (D27), inherited unchanged; no CI (D28), so
every check here is a command someone runs and running it is an exit criterion. What is new in
this phase is that **the renderer is now the performance-critical process**. P1 and P2 measured
git and the store; P3 measured the wire. §5.1's four renderer-side budgets — 300 ms to first
commits painted, 400 ms to a first page, 60 fps sustained scroll with no frame over 32 ms, and
the 80 MB / 250 MB heap ceilings P2 explicitly declined to claim from a headless process — are
P4's to meet and P4's to measure. They are the reason §5.3's rules exist (a virtualized grid
whose DOM is bounded by the viewport rather than by history, per-row SVG for the graph column,
no Vue reactivity over the commit set), and every work item below that touches rendering is
written against them rather than against "it feels fast".

The second new constraint is the **worker**, which is the first time this project runs code off
the main thread in production. §3.2 puts lane layout there; P2 built `layoutAppend` as a pure
function with a declared transfer list precisely so P4 could wrap it in ~30 lines. Wrapping it
is cheap; getting the *data flow around it* right is not, and W4 spends its length on that
rather than on the wrapper.

**On verification in this sandbox, stated up front so the phase does not stall on it.** This is
a headless Linux container. P3's V2/V3 settled what runs here: Electron launches under
`xvfb-run -a --no-sandbox` and its Playwright project genuinely runs; a VS Code download does
not (`update.code.visualstudio.com` is blocked), so `tests/e2e/vscode/panel.spec.ts` remains
inherited-open. The posture is P3's, unchanged: **verify everything verifiable headlessly — the
harness e2e suite, the visual-regression baselines, the perf harness through CDP, the unit
tests over the renderer's pure halves — and record the display-, hardware- and VS-Code-dependent
halves as inherited-open in Findings with the exact command a macOS machine must run.** Two of
P4's exit criteria are of that kind and are named as such below: the 60 fps figure on real
hardware, and §6.1's side-by-side density review against the native workbench list, which
requires a real workbench beside a real panel.

**Not a goal.** The detail pane's *contents* (metadata, message, trailers, signature, file tree,
diff) are P5; P4 builds the pane's region, its open/close semantics and its breakpoint
behaviour, and leaves it empty. No context menu and no row actions — checkout, branch, tag,
revert, reset, cherry-pick, copy-message all belong to the phases that own their pre-flight
(P6–P9). No branch or tag list, no conflict banner (P6). No fetch/pull/push/stash toolbar
buttons (P7, P8). No search box, no toggles, no scope selector (P10). No status bar item, no
SCM title button, no packaging (P11). The clipboard is not wired: the sha column renders as a
button because that is what §6.4 says it is, but the copy action and the `Clipboard` port land
with P5's copy actions, and a button that looks live and does nothing is worse than a button
that is explicitly not there yet — so it is rendered `disabled` with a title saying so.

The one thing P4 must get right that no later phase can fix cheaply: **the commit set must never
become reactive, and the grid must never be handed materialized rows.** §5.3 and §5.5 state
both, and both are the kind of thing that works at 5,000 rows, is invisible in review, and is a
rewrite of every component by P10. Passing SlickGrid a plain array — the shape every tutorial
uses — means building 100,000 objects with eight fields each, which is the exact representation
§5.5 exists to forbid; the `CustomDataView` adapter is what prevents it, and it is three methods
long. A `ref()` where `shallowRef()` was meant hands Vue's proxy a 100k-row store to walk, and
`reactive()` around the grid instance itself would proxy every DOM node it holds. All of these
are cheap to get right in W6 and expensive to retrofit once the detail pane, the search
highlighter and five dialogs are reading the same state.

### What P3 left broken, and why P4 is where it surfaces

P3's exit criteria for rehydration were met by `tests/integration/repoService.test.ts` counting
spawns and by `panel.spec.ts`, which V3 left unrunnable. Between those two lies a real defect,
found while planning this phase by reading the code rather than by running it:

**A cache replay to a *fresh* receiver sends a dictionary the receiver does not have.**
`RepoSession.dictionaryCursor` is monotonic per host session (`repoService.ts`, `#emitRange`
advances it by `commits.dictionary.length` on every chunk). `CommitStore.packSlice(from, to,
dictionaryBase)` emits only the strings interned *after* `dictionaryBase`, and
`CommitStore.appendPacked` asserts `chunk.dictionaryBase === interner.size`. So the sequence
§2.1 guarantees will happen — webview shown, streamed, hidden, destroyed, re-shown with a brand
new `GraphViewState` whose store is empty — replays row 0 with `dictionaryBase` at whatever the
cursor had reached, and `appendPacked` throws before a single row lands. The identity columns of
that chunk reference dictionary ids that were never sent, so even without the assert the author
column would be wrong rather than absent.

**And the UI has no handler for a stream that restarts at row 0.** P3's own plan says a stale
re-walk produces "a chunk sequence starting at `from: 0`, which is exactly what the UI needs to
know to discard what it had". The host half was built (`#ensureFresh` drops the store and resets
`dictionaryCursor`); the UI half was not — `GraphViewState.#applyChunk` calls `appendPacked`
unconditionally, so the first post-invalidation chunk throws on the `chunk.from === rowCount`
assert instead of resetting.

Both are P4's to fix (W2, W5), for the same reason: P4 is the phase where a hidden-then-shown
panel has to come back with rows in it, and where a `refsChanged` during a session has to do
something a user can see. They are recorded here rather than in P3's Findings because the fix
ships in this phase's diff, and because a plan that inherits a defect silently is how the defect
survives another phase.

### What the mockup shows that P4 does not build

`docs/design/panel-mockup.html` is the approved visual reference (§6.7) and P4 is the phase that
finally implements most of it — the row geometry, the lane graph's own geometry, the badges, the
Load-more button and the toolbar shape all come from it. The mockup draws its lanes to a
`<canvas>` and we draw the same geometry as SVG (§5.3, §6.7); the numbers — row height, lane
pitch, node radii, stroke width, the arc's shape — transfer unchanged, and they are the reason
the mockup is a reference at all. It also shows a search box, Fetch/Pull/Push/Stash
buttons, a conflict banner, a populated detail pane, a context menu and a status bar item. None
of those is P4's. §6.7 settles the standing of the disagreement in advance: the mockup "is not a
P4 acceptance target; the acceptance criteria are in §10." The visual-regression baselines this
phase commits are of the panel P4 actually ships, not of the mockup.

### The contract entries P4 adds

Three changes, all in W2, all of which take `CONTRACT_VERSION` from `2` to `3` — which is
enforced: `wrapVersioned`/`validate.ts` reject a mismatched frame loudly, so the two hosts, the
harness mock and the UI move together in one commit or the app refuses to start.

```ts
"graph.refresh": { params: { repoId: string }; result: { restarted: boolean } }
"graph.loadMore": { params: { repoId: string; pages?: number }; result: { started: boolean } }
                   // unchanged shape; gains real cancellation (W2)
```

`graph.stream`'s chunk shape is unchanged. Nothing is added for layout: the layout buffers are
produced in the renderer's own worker from data the stream already carries (§3.2), and putting
them on the wire would mean the host doing work the renderer must redo on rehydration anyway.

## W1 — The lane palette, and the one colour we are allowed to invent

§3.4: "Graph lane colours are the only palette we invent, since no workbench colour id means
'branch lane 3'. They are generated per theme kind for contrast against
`--vscode-editor-background`, checked for WCAG contrast, and made distinguishable under the
common colour-vision deficiencies. High-contrast themes get their own set plus outlines." And:
"We also expose our colours as themable contribution points (`contributes.colors`)."

P0 seeded eight placeholder tokens in `vscode-tokens.css` and labelled them as placeholders in
the file ("These eight are a placeholder progression, not yet contrast-validated"). P2 emitted a
palette *index* and never a colour. P3 kept the placeholders and deferred the rest here. This
item closes it.

**`scripts/gen-lane-palette.ts`** (new; add to §3.1's tree beside `gen-theme-palettes.ts`)
produces, from one small source table of hues, four sets of eight colours — one per theme kind —
and writes two artifacts:

1. `contributes.colors` entries in `packages/host-vscode/package.json`, ids
   `kiraVersion.graphLane0` … `kiraVersion.graphLane7`, each with the four defaults VS Code's
   manifest schema takes (`dark`, `light`, `highContrast`, `highContrastLight`) and a
   description. Contributed colour ids are injected into every webview as `--vscode-*` variables
   under the same mechanical renaming as built-in ids (§3.4), so `kiraVersion.graphLane3`
   arrives as `--vscode-kiraVersion-graphLane3` with no code on our side — and a user or theme

2. The corresponding literal fallbacks in `packages/ui/src/theme/vscode-tokens.css`, so each
   token becomes `--kv-graph-lane-N: var(--vscode-kiraVersion-graphLaneN, <generated literal>)`,
   **plus the eight one-line rules that consume them** —
   `.kv-lane-N { stroke: var(--kv-graph-lane-N); }` and the matching `fill` rule for node
   shapes. This is where the SVG decision pays: the graph's colours are applied by the cascade,
   so a theme switch, a `workbench.colorCustomizations` override and a density change all reach

   string, and `palette.ts` (W8) exports class *names*, not colours.
   The literal is what Electron uses: `gen-theme-palettes.ts` extracts the `--vscode-*` names
   referenced by this file and looks them up in VS Code's theme JSON, where a *contributed* id
   does not exist — so it is omitted, the fallback chain takes over, and Electron gets the same
   colour without a second generator. That is worth a comment in both scripts, because it looks
   like an oversight and is the intended path.

**The checks, which are the substance of this item and not the colours:**
`scripts/check-lane-palette.ts` (or a `--check` mode on the generator, matching
`gen-settings.ts`'s convention) is wired into `bun run check` and fails on:

- **Contrast.** Every lane colour against its kind's `editor.background`, at the WCAG
  non-text-contrast bar of **3:1** — a 1.6 px stroke is a graphical object, not body text, so
  the 4.5:1 text bar is the wrong test and citing it would be cargo-culting. The two
  high-contrast kinds require 4.5:1, since that is the whole point of those themes.
- **Distinguishability, including under CVD.** Every pair of the eight, and separately every
  *adjacent* pair, must exceed a CIE ΔE threshold after simulating protanopia, deuteranopia and
  tritanopia (Brettel/Viénot matrices — twenty lines of arithmetic in the script, no
  dependency). Eight hues that are distinct to a trichromat and collapse to three under
  deuteranopia is the exact failure this check exists to prevent, and it is not detectable by
  looking at the palette.
- **Determinism.** The generator's output is committed; `--check` fails when the file on disk
  differs from what the source table produces, so a hand-edit to the manifest or the CSS is
  caught the way `gen-settings.ts`'s already is.

**High-contrast gets outlines, not just colours** (§6.1: "it requires explicit borders where
other themes use background fills alone"). This too is pure CSS now: `--kv-graph-node-outline`
and `--kv-graph-node-outline-width` are defined in `vscode-tokens.css` only under the two
high-contrast body selectors (which already exist in that file), and the node rule reads
`stroke: var(--kv-graph-node-outline, none)`. Every node gets the outline in the two
high-contrast kinds and nothing anywhere branches on theme kind at runtime.

**Not in this item:** badge colours (P6, see the scope table) and any change to `core/graph/
colors.ts`, which keeps emitting an index. `packages/core` never learns a hex value (§6.1's
token-only rule, B4's lint).

**Done when:** `bun run check` fails on a hand-edited manifest or CSS and on a deliberately

## W2 — `graph.refresh`, cancellable `loadMore`, and the dictionary-mark fix

Three host-side changes, one commit, `CONTRACT_VERSION` → `3`.

**1. `graph.refresh`.** §6.2 defines Refresh precisely enough to implement without inventing:
it "forces a full re-query — refs, status, and history walk — bypassing every cache", it is
"distinct from the automatic invalidation the watcher performs, which is incremental and does
not re-walk", it "is idempotent (a second press while running is a no-op, not a queued second
walk)", and it "preserves selection and scroll position across the refresh".

```ts
// packages/ipc/src/contract.ts
"graph.refresh": { params: { repoId: string }; result: { restarted: boolean } }

// packages/git/src/repoService.ts
refresh(repoId: string): void;   // marks the session stale; the next stream re-walks
```

The mechanism already exists and is the one thing not to duplicate: `#ensureFresh(session)`
drops the store, disposes the `LogSession`, opens a new one and resets `dictionaryCursor`, and
runs on the next `streamGraph`/`loadMore`. So `refresh()` is `session.staleReason = "refresh"`
and nothing else — the `staleReason` union widens from `"refsChanged" | undefined` to
`"refsChanged" | "refresh" | undefined` so a log line can say which it was. `restarted: false`
is returned when the repo id has no open session, which is the honest answer rather than a
throw. Idempotency falls out: two `refresh` calls before the next stream set the same flag once.
The re-query of refs is not a separate call — decorations ride the walk (`%D` in §4.4's format),
and the ref snapshot `logSession` takes for its `--skip` guard is retaken when the session is
replaced.

**2. `loadMore` becomes genuinely cancellable.** §5.1.1 says loading more "is cancellable", and
today it is not: `RepoService.loadMore` takes no signal, so an aborted RPC leaves the host
reading a full 5,000-row page. P2's `LogSession.readPage(sink, { signal })` already accepts one.
Thread it: `loadMore(repoId, pages, signal?)` → `#readPageIntoStore(session, signal)` →
`readPage(sink, { signal })`, and `rpcHandlers.ts` passes the server's per-request
`AbortSignal` (W2 of P3 already maps a `cancel` frame to one). Rows read before the abort stay
in the store — that is correct and is worth stating in the UI (W9): cancelling stops the load,
it does not unload.

**3. The dictionary mark, fixing the rehydration defect.** `packSlice`'s `dictionaryBase`
contract is "the caller is responsible for tracking what the receiver has already been sent" —
and the receiver is not the session, it is *this stream*. A receiver holding exactly rows
`[0, R)` has interned exactly the strings first seen in those rows, because interning happens in
row order; so the size is a pure function of `R` and the host can record it:

```ts
// RepoSession
dictionaryMarks: Map<number, number>;   // boundary row -> interner size after that row
```

A mark is written at every chunk boundary `#emitRange` emits (plus `0 → 0` at session start),
which is exactly the set of rows a client's `loadedRows` can ever equal, since the client only
ever advances by whole chunks. `streamGraph` then resolves its base from the mark for the
clamped resume row; **a resume row with no mark replays from row 0 with base 0** rather than
guessing. At 100k rows and `CHUNK_ROWS = 500` that is 200 entries — the memory argument against
it does not exist.

The rejected alternative was making the chunk self-describing: pack `[id, string]` pairs for
exactly the identities the slice references, and let the receiver plant them at those ids. It is
more robust in the same way W3-of-P3's parents-as-shas is more robust, and it was rejected
because it changes `StringInterner`'s id contract (ids currently mean first-seen order, and
sparse assignment makes `intern()` and `internAt()` two different things with an invariant
between them) for a problem the mark solves in six lines. If a later phase ever needs a chunk
that can be applied to a receiver in an unknown state — a second webview onto the same repo, say
— that is when the interner changes.

**Done when:** `tests/integration/repoService.test.ts` gains a test that streams a repo fully,
then streams it again into a **freshly constructed** `CommitStore` from `resumeThroughRow: 0`
and asserts every row matches the first store row for row (this is the test whose absence hid
the defect: the existing tests collect chunks without ever applying them to a second store);
a resume at a real chunk boundary appends onto a store holding exactly those rows; a resume row
that is not a boundary replays from 0; `graph.refresh` on a streamed repo makes the next stream
emit from `from: 0` with `source: "git"` and spawns exactly one new `git log`; a `loadMore`
aborted mid-page leaves the session usable and the partial rows readable; `bun run check` passes
with `CONTRACT_VERSION` at 3 in every consumer.

## W3 — `packages/ui/src/graph/layoutStore.ts`

New file, added to §3.1's tree. P2 produces one `LayoutChunk` per appended page, with a global
edge numbering and a `patches` array that corrects edges belonging to *earlier* chunks; its own
`types.ts` names the missing piece — "the reassembler (the consumer holding every chunk) maps a
global index back to (chunk, local offset)". This is that consumer. It is main-thread, UI-only,
and pure: no Vue, no DOM, no SlickGrid, so it is unit-testable in `bun test` without a browser.

```ts
export interface RowVisual { readonly lane: number; readonly color: number }

export interface EdgeSegment {
  readonly fromRow: number; readonly toRow: number;      // toRow may be UNRESOLVED_ROW
  readonly fromLane: number; readonly toLane: number;
  readonly color: number; readonly kind: EdgeKind;
}

export class LayoutStore {
  append(chunk: LayoutChunk): void;
  clear(): void;
  readonly rowCount: number;      // rows covered by appended chunks
  readonly laneCount: number;     // high-water mark across chunks — the gutter's width input
  laneOf(row: number): number;
  colorOf(row: number): number;
  /** Every segment that paints inside this one row's band — the vertical run of each lane
   *  crossing it and the arc of any edge that changes lane within it. Allocation-free: fills
   *  a caller-owned array and returns the count. This is what the graph column's formatter
   *  calls, once per row it renders. */
  segmentsInRow(row: number, out: EdgeSegment[]): number;
  /** The batch form, over [firstRow, lastRow]. Not on the render path — it exists as the
   *  test oracle W3's unit tests compare `segmentsInRow` against, and as the query a future
   *  prefetch would use. */
  segmentsInWindow(firstRow: number, lastRow: number, out: EdgeSegment[]): number;
}
```

**`segmentsInRow` is the primary query, and that is a change from the pre-SlickGrid design**,
which repainted a whole ~25-row window at once and so asked for the window. The grid renders
row by row and calls a formatter per cell, so the per-row form is what the render path needs.
The two share their indexes and one is the other's oracle; both are exact.

A segment is reported to a row in **band coordinates** — `enters` and `exits` booleans plus the
y-fractions where the arc starts and ends within the band — so `rowSvg.ts` (W8) can emit a path
without knowing the row's absolute position or the edge's full extent. That is the whole point:
a row's SVG is a function of the row's cross-section and nothing else.

**Chunk indexing.** Chunks are appended in order and are contiguous, so `laneOf`/`colorOf` are a
binary search over chunk starts (≤ 20 entries at 100k rows, ~200 at a million) plus one typed
array read. Not a per-row copy into one flat array: that would double the memory the transfer
was supposed to avoid.

**Applying patches.** A chunk's `patches` is `(globalEdgeIndex, toRow)` pairs naming edges in
earlier chunks whose `UNRESOLVED_ROW` target the new page resolved. `append` walks them, maps
each global index to `(chunk, local offset)` through each chunk's own edge-count range, and
writes `EDGE_TO_ROW` in place. Writing into an earlier chunk's `edges` buffer is legal — it is
ours, it was transferred to us, and nothing else holds a reference — and it is what keeps a
Load more from re-laying out the previous page (§5.5's whole argument in W9 of P2).

**The row query is the interesting half.** A row must report every edge crossing it out of a
history of 100,000, so "which edges touch this row" must not be O(all edges). `edgeIndex` gives
edges *starting* at a row in O(1), but an edge starting 40,000 rows above and ending below still
paints a vertical run *through* the row, and `maxEdgeSpan` — P2's answer — is the largest span in
the chunk, which one long-lived branch merge makes useless as a lookback bound.

So `append` builds one side index: **`longEdges`, every edge whose span exceeds
`LONG_EDGE_ROWS = 64`, in a flat array sorted by `fromRow`.** Real repositories have hundreds of
these, not thousands — they are exactly the merges of long-lived branches. `segmentsInRow(r)` is
then: a CSR scan over rows `[r − LONG_EDGE_ROWS, r]` (bounded, ~64 rows of edge starts), plus a
filtered pass over `longEdges` for those spanning `r` (binary search on `fromRow`, then a linear
filter on `toRow`). Exact, allocation-free, and bounded by the lookback window rather than by
history.

**Cost per rendered row, since the grid now calls this once per row rather than once per
window:** the CSR scan touches ~64 rows' worth of edge starts (a handful of edges each in any
real topology), and the `longEdges` filter is a binary search plus a scan of a few hundred
entries. Order a few microseconds, against the ~0.2 ms budget a row's whole construction has.
It is called only for rows *newly entering* the viewport — a fling of 40 rows costs 40 calls,
not 40 × the viewport. If `longEdges` ever grows into the thousands on a pathological
repository, the next step is bucketing it by row range — named here so it is a known move, not
built now for a repository nobody has shown us.

**Done when:** unit tests (`tests/unit/ui/layoutStore.test.ts`, under `tests/unit/` because it
needs `tests/fixtures/topology.ts` — P2's finding) assert that a store fed page-by-page reports
the same `laneOf`/`colorOf` for every row as one fed a single whole-history chunk, for every W1-
of-P2 shape; that a patch from a later page corrects an earlier page's edge target;
that `segmentsInRow` returns exactly the segments a brute-force scan over all edges returns, for
**every row** of every shape, including rows that start no edge and rows crossed only by an edge
whose endpoints are both far outside the lookback window; that concatenating `segmentsInRow`
over a range equals `segmentsInWindow` over that range; and that a row query allocates nothing
after the first call (asserted by reusing the `out` array and comparing counts, not by heap
inspection).

## W4 — `layout.worker.ts` and `layoutClient.ts`

§3.2 puts lane layout in a worker; P2 made `layoutAppend` a pure function with a declared
transfer list so that this file could be thin. It is thin. The data flow around it is not, and
that is what this item is about.

**`packages/ui/src/graph/layout.worker.ts`** — a module worker holding the `LayoutFrontier`
between calls (so a page's layout resumes rather than recomputes), receiving `LayoutRequest`
and posting `LayoutResponse`, both already declared in `core/graph/types.ts` for exactly this
reason. It calls `layoutAppend` and posts with `layoutTransferList(chunk)`. Under 40 lines.

**`packages/ui/src/graph/layoutClient.ts`** (new; add to §3.1's tree) — the main-thread side:
constructs the worker with Vite's own `new Worker(new URL("./layout.worker.ts", import.meta.url),
{ type: "module" })` form, keeps the request sequence, drops responses whose sequence is stale
(P2 put `sequence` in the message shape for precisely the double-Load-more race), and exposes:

```ts
export interface LayoutClient {
  submit(input: LayoutInput): Promise<LayoutChunk>;
  reset(): void;        // discards the frontier — a refresh or a repo switch
  dispose(): void;
}
```

**The direction of copying is the decision here.** `LayoutInput` carries `parentOffsets` and
`parentRows` — views over the *whole* `CommitStore`'s parent columns, absolute-indexed, because
the pass must see parents outside the new range to patch earlier edges. They must be **copied**
into the request, never transferred: transferring detaches the store's own columns and the store
is the thing the row renderer reads on every frame. The response *is* transferred, which is what
§5.5 asks for and where the size actually is.

Two consequences worth writing down before they are discovered:

- `structuredClone` of a typed array clones its whole backing `ArrayBuffer`, not just the view's
  window. `CommitStore`'s columns are capacity-doubled, so the buffer behind a 130k-slot
  `parentRows` view may be 256k slots. At 4 bytes that is ~1 MB copied per page — twenty times
  over a full 100k walk. That is acceptable (W15 measures it; the whole page budget is 400 ms
  and this is a memcpy), and it is *not* acceptable to fix it by transferring. If it ever
  matters, the fix is `submit` building tight `Int32Array` copies of the exact used range, which
  is three lines — named, not built, because the measurement comes first.
- The worker's own store-side view is stale by construction between pages, which is fine:
  `layoutAppend`'s contract is that the input carries everything the pass reads.

**The fallback, which V1 decides.** A module worker inside a VS Code webview must satisfy the
CSP in `packages/host-vscode/src/html.ts`, which today is `default-src 'none'; … script-src
'nonce-${nonce}'` and declares **no `worker-src`** — and `worker-src` falls back to `child-src`
and then to `default-src`, i.e. `'none'`. So the CSP must gain `worker-src ${cspSource} blob:;`
(and the nonce does not apply to worker scripts, which is the trap: a worker is fetched, not
inlined, so it is the *source* directive that governs it). V1 confirms this on a real webview.
If a module worker cannot be made to load there at all, `layoutClient.ts` keeps its interface and
runs `layoutAppend` on the main thread in an idle callback, chunked to `CHUNK_ROWS` so it never
holds the thread for a frame — a real degradation to record in Findings, not a reason to
restructure the renderer, because every consumer above `LayoutClient` is written against a
promise either way. Building the client interface first is what makes that fallback a
one-file change.

**Done when:** a unit test drives `layoutClient.ts` against a stubbed worker and asserts stale
responses are dropped and `reset()` discards the frontier; an integration-style test in the
harness lays out a real scenario through the real worker and asserts the resulting
`LayoutStore` matches a synchronous `layoutAppend` over the same input, row for row; the
worker bundles into `dist/ui` as its own chunk (W13's build check confirms it is emitted, since
a silently-inlined worker would defeat the whole item); and the source columns are **not**
detached after a submit (`parentRows.byteLength !== 0`), which is the assertion that catches
someone "optimising" the copy into a transfer.

## W5 — UI state: `graphView.ts` rebuilt, `selection.ts`, `viewState.ts` v2

P3's `state/graphView.ts` is 80 lines that append chunks and expose four scalars. P4 turns it
into the module every component reads, and it keeps §5.3's rule at its centre: **the
`CommitStore` and the `LayoutStore` are `markRaw`'d and never reactive; only scalars are.**

```ts
// state/graphView.ts
class GraphViewState {
  readonly store: CommitStore;          // markRaw
  readonly layout: LayoutStore;         // markRaw
  readonly loadedRows: ShallowRef<number>;
  readonly remaining: ShallowRef<number>;
  readonly exhausted: ShallowRef<boolean>;
  readonly laneCount: ShallowRef<number>;
  readonly loading: ShallowRef<"idle" | "streaming" | "loadingMore" | "refreshing">;
  readonly generation: ShallowRef<number>;   // bumped on every reset; components key off it
  openStream(repoId: string, resumeThroughRow?: number): Promise<void>;
  loadMore(pages?: number): Promise<void>;
  loadAll(): Promise<void>;
  refresh(): Promise<void>;
  cancelLoad(): void;
}
```

**`generation` is the mechanism that makes a reset visible to the grid.** Nothing else changes
when 100k rows are dropped and re-walked — `loadedRows` might land on the same number — and
SlickGrid's row cache holds rendered rows until it is told they are stale, so it would keep
showing the old history. Every consumer that caches anything derived from the store invalidates
on `generation`; for the grid that means `grid.invalidateAllRows()` followed by
`updateRowCount()` and `render()`, which is the library's own three-call idiom for "the data
underneath you changed completely" and is the only correct response to a reset.

**Reset on a restart-at-zero chunk**, the second half of the defect W2 fixes on the host side:

```ts
#applyChunk(chunk) {
  if (chunk.from === 0 && this.store.rowCount > 0) this.#reset();   // host re-walked
  this.store.appendPacked(chunk.commits);
  …
}
```

and `#reset()` clears the store, the `LayoutStore`, the `LayoutClient`'s frontier and bumps
`generation`. An `appendPacked` that throws anyway (a genuinely corrupted stream) is caught,
logged, and turned into a full re-open from row 0 rather than an unhandled rejection that leaves
a half-populated list on screen — the store's asserts are the right place for the check and the
wrong place for the recovery.

**Layout is driven from the append**, not from the render: after each chunk lands,
`layoutClient.submit(store.layoutInput(from, to))` runs and its `LayoutChunk` goes into the
`LayoutStore`; `laneCount` updates. When the promise resolves, the rows that chunk covers are
invalidated (`grid.invalidateRows(rows); grid.render()`) so their graph cells are rebuilt with
lanes they now have. This means rows can be *listed* before their lanes exist — which is correct
and is what makes the ≤ 300 ms first-paint budget reachable: text first, graph a frame later,
never a blank list waiting on a worker. The graph column's formatter must therefore handle
"this row has no layout yet" by returning an empty `<svg>`, not by throwing — the one case in
this phase where an absent value is a normal state rather than a bug.

**`state/selection.ts`** (§3.1's tree, deferred by P3 to here):

```ts
class SelectionState {
  readonly row: ShallowRef<number>;         // -1 for none
  readonly sha: ShallowRef<string | null>;  // survives a re-walk; the row index does not
  select(row: number): void;
  selectBySha(sha: string): boolean;        // used after a refresh/rehydrate
  clear(): void;
}
```

Selection is stored **by sha as well as row**, because §6.2 requires Refresh to preserve
selection and a re-walk renumbers every row. After a reset, `selectBySha` re-resolves against
`store.rowOfSha` once the sha is loaded again; when it is not (it fell below the loaded range,
or it is gone from history), selection clears and the list does not scroll — silently selecting
a *different* commit at the same row index would be the worst available behaviour in a tool
whose next phase attaches destructive actions to the selected row.

**`state/viewState.ts` → version 2.** §5.4's full list, finally:

```ts
export interface PersistedViewState {
  readonly version: 2;
  readonly repoId: string | null;
  readonly loadedRows: number;
  readonly detailOpen: boolean;
  readonly scrollRow: number;         // a row index, not a pixel: a row survives a re-walk
  readonly selectedSha: string | null;
  readonly columnWidths: { author: number; date: number; sha: number };
  readonly dateFormat: "relative" | "absolute";
  readonly detailWidth: number;
}
```

P3's rule holds unchanged and is why the bump is safe: **a state whose `version` is not the
current one is discarded whole, never partially applied.** Writes stay debounced (scroll fires
continuously; `setState` on every frame is a message per frame to the extension host).

**Done when:** unit tests over `GraphViewState` with a fake transport assert: chunks append in
order; a `from: 0` chunk after rows exist resets and bumps `generation`; a corrupted chunk
produces a re-open rather than a rejection; `loadMore` appends without disturbing
`selection.row`; `refresh` clears and re-populates with selection re-resolved by sha; a v1
persisted state is discarded and a v2 one round-trips every field.

## W6 — `CommitGrid.vue` and `columns.ts`

The phase's largest single item and the one contact point with the library. §5.3's rules live
here: one virtualized grid owns every column, its DOM is bounded by the viewport rather than by
history, and every column's content is a synchronous formatter returning a real element.

**`CommitGrid.vue` is a host, not a renderer.** Its template is a single `<div ref="host">`.
Everything else is `onMounted` construction, `onBeforeUnmount` teardown, and a handful of event
wires. The grid instance is `markRaw`'d and held in a plain (non-reactive) variable — wrapping it
in `ref()` would hand Vue's proxy every DOM node the grid owns, which is the same mistake as
making the commit set reactive and has the same fix.

```ts
grid = new SlickGrid(host.value, dataView, columns, {
  rowHeight,                       // from readTokens(); never a literal in this file
  enableCellNavigation: false,     // §6.6 navigates rows, not cells — see Interaction below
  enableColumnReorder: false,      // §6.2: resizable, not reorderable. Also: no SortableJS
  enableHtmlRendering: false,      // formatters return elements; no innerHTML, no escaping
  showColumnHeader: false,         // §6.1 — the workbench list has no header
  enableTextSelectionOnCells: true,
  explicitInitialization: false,
  minRowBuffer: 3,
  rowTopOffsetRenderType: "transform",
});
```

Each option above is load-bearing and each gets a one-line comment in the file saying why,
because every one of them is a plausible thing for a later reader to flip.

**The data view is the whole of §5.5's contract with the library:**

```ts
const dataView = {
  getLength: () => graphView.loadedRows.value,
  getItem: (row: number) => store.commitAt(row),   // materialized, used, discarded
  getItemMetadata: (row: number) => rowMetadata(row),  // cssClasses: selected / head / stash
};
```

Three methods. **This is what keeps a 100,000-commit repository from becoming 100,000 objects**
— `getItem` is called once per row the grid actually renders, which is the ≤ 60 on screen, and
the record it returns is dropped as soon as the formatters have read it. Handing SlickGrid a
plain array instead is the single most damaging thing that could be done in this phase and it
would pass every functional test.

**Columns (`columns.ts`), per §6.2's list** — graph, message with inline ref badges (W7),
author, date, sha:

| Column | Width | Notes |
|---|---|---|
| graph | `padLeft + min(laneCount, MAX_LANES) × laneWidth + gutterPad`, recomputed via `setColumns` when `laneCount` grows | not user-resizable (`resizable: false`); W8 owns its formatter and its geometry |
| message | remaining width, `text-overflow: ellipsis` | badges are inline-start of the subject, per the mockup |
| author | persisted, default 74 px | |
| date | persisted, default 52 px, `font-variant-numeric: tabular-nums` | clicking toggles relative/absolute for every row and persists (§6.2) |
| sha | persisted, default 60 px, `--kv-mono-font-family` | a `<button>`, `disabled` in P4 with a title naming P5 (see the scope boundary) |

Every formatter returns an `HTMLElement`; none returns a string. With
`enableHtmlRendering: false` that is enforced by the library rather than by discipline, and it
means a commit subject containing `<script>` is text by construction, with no sanitizer in the
loop and nothing to get wrong.

**Styling.** SlickGrid's shipped stylesheets are **not** imported — they carry Bootstrap /
Salesforce / Material palettes that would violate §6.1's token rule on sight. `CommitGrid.vue`'s
own `<style>` block supplies the ~80 lines of structural CSS the grid requires (viewport, row
and cell positioning, and the `.grid-canvas` panes — the library's own name for the `div` that
holds the rows; there is no `<canvas>` element behind it) and maps every colour to the `--kv-*`
layer:
`--kv-row-hover-bg`, `--kv-row-selected-bg`, `--kv-focus-border`, which come from
`--vscode-list-*` (§6.1: "VS Code's own components are the reference for ours"). This file is
the only place in the repository where a `.slick-*` class name appears, which is what keeps the
library swappable and the token lint meaningful.

**Metrics come from the token layer, not from constants in this file** — `--kv-row-height`
(22 px at default density, §6.1) is read through `readTokens.ts` and passed as the `rowHeight`
option; a density change re-reads it and calls `grid.setOptions({ rowHeight })` plus
`invalidateAllRows()`. The graph column's geometry reads the same number, so the rows and the
lanes cannot drift.

**Resizing without a header row.** The workbench list has none and §6.1 says copy it rather than
design a second answer, so `showColumnHeader: false` stands — which costs SlickGrid's own resize
handles, since those live in the header. We keep the design the pre-SlickGrid plan had: a 5 px
drag handle at each of the three boundaries, absolutely positioned over the list, spanning its
height, `role="separator"` with `aria-orientation="vertical"`, arrow keys resizing by 8 px so it
is reachable without a mouse (§6.6 makes full keyboard reachability a v1 requirement, not
polish). The difference is where the width *lives*: the handle writes through
`grid.setColumns(...)`, so the grid's column model stays the single source of truth and the
cells re-lay out through the library rather than through a second CSS path. Widths clamp to sane
minimums and persist through `viewState`.

**Interaction (§6.4, §6.6).** `enableCellNavigation: false`, because §6.6 specifies row
navigation and SlickGrid's built-in keyboard model moves a *cell* cursor — adopting it would put
an active-cell outline on a list that has no cell-level concept. So: `onClick` selects the row
(and a second click on the selected row toggles the detail pane closed); a `keydown` handler on
the viewport implements `↑`/`↓` (select and `scrollRowIntoView`), `Home`/`End` (first and last
loaded row), `PageUp`/`PageDown` (by a viewport), `Enter` (open the pane, again to close), `Esc`
(close). `F5` and `Ctrl/Cmd+R` trigger Refresh when the panel has focus (W10 owns the action).
`onContextMenu` **selects the row and does nothing else in P4** — the menu is P6's, and selecting
on right-click now means P6 adds a menu to a row that is already correctly selected (§6.4:
"Right-clicking a row also selects it, so the menu never acts on a commit the user cannot see").

Selection is *ours*, not the library's `RowSelectionModel`: the model exists to support
multi-select and cell ranges we do not want, and W5's `SelectionState` already holds selection by
sha for Refresh survival. Selected-row styling rides `getItemMetadata`'s `cssClasses`, and
changing selection invalidates exactly the two affected rows, never all of them.

**Scroll position** is `grid.getViewport().top` / `grid.scrollRowIntoView(row)` — row indices,
not pixels — which is both what `viewState` should persist (a row survives a re-walk; a pixel
offset does not) and what makes the library's internal page/offset compensation invisible to us.

**Done when:** the rendered `.slick-row` count stays bounded (viewport + buffer, not row count)
across a scroll from row 0 to row 99,999 and back (asserted in W13); `getItem` is called at most
once per rendered row per render, asserted by a counting wrapper in a unit test over the data
view; scrolling to the end of a 100k list and back leaves selection and column widths unchanged;
keyboard selection moves, scrolls into view, and does not scroll when the row is already
visible; a container resize re-lays out exactly once (`grid.resizeCanvas()` on a debounced
`ResizeObserver`); no `.slick-*` selector appears outside `CommitGrid.vue`; the grid instance is
not reactive (asserted by `isReactive(grid) === false`).

## W7 — `refBadges.ts`

§6.2 puts ref badges inline in the message column; §7.9 requires tags to be "visually distinct
from branch badges (different shape and colour)" and annotated/lightweight to be
distinguishable; §7.6 requires stash entries, which are rows in the walk, to be "visually
distinguished".

**Not a Vue SFC, and the reason matters.** A SlickGrid formatter is synchronous and returns a
DOM element; mounting a Vue component per badge per row would mean an app instance and a
lifecycle per badge, created and torn down as rows scroll — orders of magnitude more expensive
than the badges themselves, for nothing. So this is `refBadges.ts`: pure functions returning
elements, no framework, unit-testable without a DOM harness beyond `happy-dom`. §3.1's tree is
updated accordingly (`RefBadge.vue` → `refBadges.ts`). The same reasoning applies to the graph
column (W8) and to the message, author, date and sha formatters (W6): **nothing inside a grid
row is a Vue component**, which is also why §8.5's framework argument comes out stronger than
when it was written.

The data is already on the wire: `DecorationRef` (`{kind: "branch", name, isHead} | {kind:
"remoteBranch", name} | {kind: "tag", name} | {kind: "head"}`) rides every packed chunk and
`store.decorationAt(row)` returns it. P4 renders it and adds nothing to the model.

| Kind | Shape | Token | Glyph |
|---|---|---|---|
| local branch | pill (9 px radius) | `--kv-badge-local-bg` | `codicon-git-branch` |
| remote branch | pill | `--kv-badge-remote-fg` | `codicon-cloud` |
| tag | square (3 px radius) | `--kv-badge-tag-fg` | `codicon-tag` |
| stash | square, dashed border | `--kv-badge-stash-*` (new tokens) | `codicon-archive` |
| HEAD | the local-branch badge gains a filled dot and `aria-label` "current branch" | `--kv-focus-border` | — |

Codicons only (§3.4/§6.1) — the mockup's `⎇`/`🏷` are placeholders in a static file, not a
licence to introduce a second icon set. Badge text truncates at ~190 px with the full name in
`title`; a row with more than three badges collapses the overflow into a `+N` badge whose title
lists them, because a commit with twelve remote branches on it would otherwise eat the message
column on a panel that is short and wide to begin with.

A stash row's *badge* is here; the stash **node** shape in the graph column is W8's, and the two
must agree on which rows are stashes — the single source is `decorationAt`, not a second
heuristic.

**Done when:** every decoration kind renders with the right shape, token and codicon in all four
theme kinds (W13's visual baselines cover it); HEAD is announced by a screen reader as part of
the row, not as a separate control; a row with six decorations renders three plus `+3` and its
title names all six; badge colours come only from `--kv-*` tokens (B4's lint enforces it).

## W8 — `graphColumn.ts`, `rowSvg.ts`, `palette.ts`, `hitTest.ts`

§5.3: "The graph column is a column, not an overlay. Its formatter returns one small `<svg>`
holding only the slice of the graph that passes through *that row's* height."

This is the phase-defining item and, after the revision, the smallest it has ever been. There is
no component, no lifecycle, no `devicePixelRatio` handling, no resize path, no repaint
coalescing and no theme subscription — all of which existed only to keep a second drawing
surface aligned with rows it was not part of. What remains is a pure function from a row to an
element.

**`palette.ts`** — now trivial, because SVG reads CSS. It exports `laneClass(colorIndex): string`
(`"kv-lane-0"` … `"kv-lane-7"`, modulo the palette size) and the node-shape class names, and it
holds **no colour values at all**. W1's generated CSS is what turns a class into a colour, so a
theme switch, a high-contrast kind and a user's `workbench.colorCustomizations` override all
reach the graph through the cascade with nothing running. The bug §3.4 called "the most visible
possible bug" — the graph keeping its old colours after a theme switch — is not defended against
here; it cannot be expressed.

**`rowSvg.ts`** — pure, no Vue, no library, no DOM query. Given a row's segments, the row's node
kind, and the geometry, it builds the element:

```ts
export const GEOMETRY = { laneWidth: 13, padLeft: 11, gutterPad: 6,
                          nodeRadius: 3.4, mergeRadius: 4.2, strokeWidth: 1.6,
                          maxLanes: 12, overdraw: 0.5 } as const;
export function gutterWidth(laneCount: number): number;
export function buildRowSvg(row: RowSlice, rowHeight: number): SVGSVGElement;
```

The numbers are the mockup's (`ROW_H 22`, `LANE_W 13`, `PAD_L 11`, node radii, the 1.6 px
stroke), which is what makes §6.7's "approved visual reference" mean something — they are
geometry, and geometry does not care whether it is drawn to a canvas or a path. `rowHeight` is
not among them: it comes from `--kv-row-height`, the same value the grid takes as its
`rowHeight` option, so the lanes and the rows cannot drift.

Five decisions inside it:

- **One `<path>` per lane colour present in the row, not one per segment.** All of a colour's
  segments — vertical runs and arcs alike — are concatenated into a single `d` (`M…V…` for each
  run, `M…C…` for each arc) and emitted as `<path class="kv-lane-3">`. This is what holds a row
  to ~4 elements typical and ≤ 10 worst, and it is the difference between a comfortable frame
  budget and an argument about one.
- **Edges are decomposed into an arc and a run**, unchanged from the pre-SlickGrid design and
  now doing more work than it was designed for. For an edge `(fromRow, toRow, fromLane, toLane)`
  the transition happens entirely within the row below the child — a bezier from the child's
  centre to the bottom of its own row in the parent's lane, exactly as the mockup draws it — and
  the rest is a vertical run in `toLane`. Because the arc is confined to one row, **every
  segment a row must draw is expressible in that row's own coordinates**, and a row never needs
  to know an edge's extent. That property is what makes a per-row SVG possible at all, and it
  was already in the plan before there was a reason to need it.
- **Vertical runs overdraw the band by `overdraw = 0.5` px at each end**, with
  `overflow: visible` on the graph cell only. Two adjacent rows' runs meet at a row boundary
  that, at a fractional `devicePixelRatio` (1.25 and 1.5 are common), does not land on a device
  pixel; without the overdraw that seam can show as a hairline gap down an otherwise continuous
  line. This is the one cosmetic risk the SVG path carries that the canvas path did not, it
  costs one constant, and W13's visual baselines at a fractional DPR are where it is confirmed.
- **An edge to `UNRESOLVED_ROW` runs to the bottom of its row and stops** (P2's `types.ts`
  states this is a real terminal state, not a placeholder) — which, on the last loaded row, is
  exactly the right affordance above a Load-more button, and needs no special case: the row
  simply has a run that enters and does not exit.
- **Node shapes:** filled `<circle>` for an ordinary commit; `<circle>` with a 2 px ring for a
  merge (more than one parent, from `store.parentsOf(row).length`); a dashed ring for a stash (a
  `stash` decoration on the row). The high-contrast outline is a CSS rule (W1), not a branch
  here.

**`graphColumn.ts`** — the SlickGrid column definition and the formatter that binds `rowSvg` to
it:

```ts
export function graphColumn(layout: LayoutStore, store: CommitStore, rowHeight: () => number): Column {
  const slice: EdgeSegment[] = [];        // reused across every call; never reallocated
  return {
    id: "graph", field: "graph", resizable: false, focusable: false, sortable: false,
    formatter: (row) => buildRowSvg(readSlice(layout, store, row, slice), rowHeight()),
  };
}
```

The `slice` array is allocated once and refilled by `segmentsInRow` on every call — W3 made that
query allocation-free precisely so this line could be written. A row with no layout yet (W5: text
lands before lanes do) returns an empty `<svg>` of the right width, never a throw.

Lanes beyond `maxLanes = 12` are clamped to the twelfth column rather than widening the gutter
without bound. A fifty-lane repository does exist (P2's `fan(50, …)` fixture is one) and letting
the graph eat a panel that is short and wide is the worse failure: the message column is what
the user reads. The clamp is stated in the file and is a candidate Finding if the density review
(W16) disagrees.

**`hitTest.ts`** — reduced to `laneAt(offsetX)`, pure arithmetic over the *cell-relative* x.
Which **row** was clicked is no longer ours to compute: SlickGrid's `onClick` carries `row` and
`cell` directly, and rederiving it from `scrollTop` would be a second answer to a question the
library already answers correctly through its own page/offset compensation — the classic way two
sources of truth drift. What the library cannot know is which *lane* within the gutter the
pointer landed on, and that stays here. P4's only consumer is a click on the graph cell selecting
the row, but it is written and tested now because P5's parent-navigation and P6's context menu
both need it.

**There are no repaint triggers**, and that is the clearest single sign the revision was the
right one. The pre-SlickGrid design coalesced seven of them — scroll, resize, DPR change, a new
`LayoutChunk`, a `generation` bump, selection change, theme change — into one
`requestAnimationFrame`, and each was a chance to miss a repaint or to do a redundant one.
Now: scroll and resize are the grid's business; DPR is the browser's; theme and selection are
the cascade's; and the two that genuinely change *content* — a new `LayoutChunk` and a
`generation` bump — are already handled in W5 as `invalidateRows` / `invalidateAllRows`, which
is one call each and the library's own vocabulary.

**Done when:** the graph column draws the `clean` scenario identically to the mockup's own
rendering of the same topology (compared by eye once and then frozen as a W13 baseline);
scrolling a 100k list builds rows in bounded time independent of scroll position (asserted in
W15 by frame timing at row 0 and at row 90,000); switching theme kind recolours the graph with
**no JavaScript executed** (asserted by screenshotting after only a `data-vscode-theme-kind`
change, with no grid method called); a merge, a stash and an unresolved edge each render their
distinct form; a row's SVG contains one `<path>` per lane colour present rather than one per
segment (asserted in a unit test over `buildRowSvg`); no vertical seam is visible at a
fractional `devicePixelRatio` (W13 baseline at `deviceScaleFactor: 1.5`); `laneAt` unit tests
cover the gutter's left edge, the clamped twelfth lane, and an x past the gutter.

## W9 — `LoadMoreButton.vue` and the load-more flow

§5.1.1 is unusually specific and every clause is testable: pages of 5,000
(`kiraVersion.graph.pageSize`), an explicit button pinned at the bottom of the list, **not**
infinite scroll; the label "shows what it will do — *Load 5,000 more (127,400 remaining)*"; "a
modifier-click loads everything, for the user who knows what they are asking for and accepts the
memory"; and "loading more never moves the viewport, never disturbs selection, and is
cancellable".

**The flow, given the host P3 built.** `graph.loadMore` reads pages into the host's store and
returns; it does not push rows. The rows arrive by **re-opening `graph.stream` from
`loadedRows`**, which the host answers entirely from cache (`source: "cache"`, zero spawns).
That is two round trips per press and it is the right shape: the alternative — keeping one
stream open for the session and pushing into it — makes the host hold a stream across a webview
disposal it cannot observe, and P3's supersede-on-reopen rule already makes re-opening safe.
Stated here because a reader will otherwise assume the stream stays open.

```
press → loading = "loadingMore"
     → graph.loadMore({repoId, pages: 1}, signal)
     → openStream(repoId, resumeThroughRow = loadedRows)   // cache-only chunks
     → each chunk: appendPacked → updateRowCount → layoutClient.submit → invalidateRows
```

**Viewport preservation** falls out of the structure — rows are appended *below*, so growing the
row count moves nothing above it — but it is asserted rather than assumed, because the one-line
accident is real and now has a specific shape: `updateRowCount()` is the correct call after an
append and `setData(..., scrollToTop)` / `invalidateAllRows()` are not. The first tells the grid
the list got longer; the others throw away rendered rows the user is looking at, and one of them
takes the scroll position with it.

**The remaining count** is `chunk.remaining` (kept live by the host through `logSession.
remaining()`), formatted with `Intl.NumberFormat` for the thousands separator. The button reads
`Load {pageSize} more ({remaining} remaining)`; when `remaining < pageSize` it says
`Load the last {n}`; when `exhausted` it is not rendered at all, and the list's end is the end.

**Modifier-click** (Alt/Option, matching the workbench's own "do the bigger thing" modifier)
calls `loadAll()`, which loops `loadMore` until `exhausted`, keeps the button in its loading
state with a cancel affordance, and appends progressively so the list stays live throughout.
Its tooltip says what it will do and names the memory cost, per §5.1.1's "accepts the memory".

**Cancellation** aborts the in-flight request (W2 threaded the signal to git) and says plainly
what happened: rows already read are kept, the button returns to its normal label with the
updated remaining count. A cancel that silently discarded a page the user already paid for
would be worse than no cancel.

**Done when:** the harness's `hugeRepo` scenario shows the right label, loads exactly one page
per press, leaves `scrollTop` and selection byte-identical across the press, disables the button
while in flight (a second press is a no-op, not a queued second page), removes the button on
exhaustion, and an Alt-click loads every remaining page with a working cancel.

## W10 — `Toolbar.vue`, `RepoPicker.vue`, `RefreshButton.vue`, and the states with no graph

§6.2's toolbar is `[repo ▾] [branch ▾] │ ⟳ │ Fetch Pull Push │ Stash ▾ │ Search […] ⚙`.

**`RepoPicker.vue`** closes a real gap rather than adding chrome: P3's UI could only open a repo
that was already in persisted state, which is why both host e2e specs had to smuggle a
`KIRA_REPO` environment variable in. The picker calls `repo.list` (already on the contract) for
candidates, renders them in a quick-input-styled dropdown borrowed from the workbench's own
surface (§6.1: "Dialogs borrow the quick-input surface"), and offers **Open Folder…** at the
bottom, which is `repo.pick` → `repo.open`. Switching repos resets `GraphViewState`, clears
selection, and writes the new `repoId` to `viewState`.

**`RefreshButton.vue`** — the leftmost action, `codicon-refresh`, `F5` and `Ctrl/Cmd+R` when the
panel has focus (§6.2). Calls `graph.refresh` then re-opens the stream from row 0; spins while
in flight; a second press while running is a no-op. It carries the one piece of watcher UI P4
owns: when a `repo.changed` event with `kind: "refsChanged"` arrives, the button shows a small
unobtrusive dot and its tooltip says the history changed on disk. **P4 does not auto-refresh** —
§6.2 draws the line explicitly ("distinct from the automatic invalidation the watcher performs,
which is incremental and does not re-walk"), and pulling 100k rows out from under a user who is
mid-scroll because a background `git fetch` finished is the behaviour that line exists to
prevent. Selection and scroll survive a refresh: selection by sha (W5), scroll by row index,
both re-applied once the row is loaded again.

**The states with no graph**, each a real surface rather than an empty box:

- **Git too old / not found / unusable** (`GitStatus`, §4.2's block state). A centred panel
  naming the detected and required versions, the platform's upgrade command
  (`brew upgrade git` on macOS — this is the platform copy P3's W1 deliberately left as a UI
  string rather than putting in `core`), and the `kiraVersion.git.path` setting id the wire
  already carries in `GitStatus.tooOld.settingId`. Nothing else in the UI renders while this
  holds: §4.2 says "the app does not start into a degraded mode".
- **No repository open** — the repo picker, prompted, and nothing else.
- **Repository with no commits** (unborn HEAD, which P1 handles and P2's store renders as zero
  rows) — a one-line explanation, not an empty list with a scrollbar.
- **Loading** — the list renders its rows as they stream; there is no spinner over an empty
  panel, because the first chunk arrives in tens of milliseconds and a spinner that flashes is
  worse than nothing.

**Done when:** the picker lists candidates and opens both a listed one and a picked folder; a
scenario whose `app.init` reports `tooOld` renders the block state and no list; Refresh re-walks
(`chunk-source` goes back to `git`), preserves selection and scroll, and is a no-op while
running; a `repo.changed` event marks the button without re-walking.

## W14 — The accessibility pass

"Accessibility pass on the virtualized list" is an exit criterion and §6.6 makes it a v1
requirement rather than polish: "Full keyboard reachability and ARIA roles on the virtualized
list are v1 requirements, not polish."

**This item changed shape with the library, and the change is the honest cost of adopting it.**
The pre-SlickGrid plan specified `role="listbox"` with `role="option"` rows and
`aria-posinset`/`aria-setsize`. SlickGrid hardcodes its roles — verified in the published source,
not assumed: the container gets `role="grid"`, rows `role="row"`, cells `role="gridcell"` with
`tabindex="-1"` and an `aria-describedby`. There is exactly one other `aria-*` attribute in the
entire grid. None of it is configurable.

Two routes, and the choice is deliberate:

1. **Overwrite it** — set `role="listbox"` on the container after construction and rewrite every
   rendered row's role in the `onRendered` handler. It would work; the container role is set
   once and never re-set, and rows pass through `onRendered`. But it means fighting the library
   on every render, forever, and it means cells inside options — which is invalid ARIA unless
   they are also demoted to `presentation`.
2. **Complete it** — keep `role="grid"` and add the attributes SlickGrid omits.

**We take (2), and not only because it is less work.** A commit list with message, author, date
and sha columns, resizable column boundaries and per-cell content genuinely is a grid; the
workbench list this design copies visually is single-column, and `listbox` was the right answer
for the single-column list the pre-SlickGrid plan was building. `aria-rowcount` / `aria-rowindex`
are the grid pattern's exact equivalent of `aria-setsize` / `aria-posinset` and exist for
precisely this case — a grid whose rendered rows are a window onto a much larger set.

What the pass adds, in one `onRendered` handler:

- **Counts.** `aria-rowcount` on the container (the *total* loaded rows, not the rendered ones —
  without it a screen reader announces "row 3 of 30" for a repository with 100,000 commits), and
  `aria-rowindex` on each rendered row, one-based per the ARIA spec. `aria-colcount` on the
  container and `aria-colindex` on each cell come from the column model.
- **Selection.** `aria-selected` on every rendered row, driven from the same
  `getItemMetadata` state that drives the selected-row class, so the visual and the announced
  state cannot disagree.
- **Focus.** Roving `tabindex` on the selected row — not `aria-activedescendant`, because rows
  are created and destroyed as the viewport moves and an `activedescendant` id pointing at a
  node the grid has since removed is exactly the pattern that breaks in practice. The focused
  row is always a real, rendered node: selection scrolls it into view first, focuses second.
  SlickGrid's own `_focusSink` elements (two `tabindex="0"` divs it places at the container's
  edges) must not become tab stops in front of it — **V2 verifies this**, and the remedy if they
  do is to set them `tabindex="-1"` after construction.
- **Announcements.** Each row's accessible name is a composed string — subject, author, relative
  date, refs — set on the row element, not assembled by the reader from the visual column soup;
  the sha button and the resize separators have their own labels. The graph cell is
  `aria-hidden="true"`: it carries no information the row text does not.
- **Live regions.** The Load-more result ("5,000 more loaded, 122,400 remaining") and Refresh
  completion are announced through one polite live region, which is how a keyboard user learns
  the button did something.
- **No colour-only meaning.** Lane colour is decorative; every distinction a user must perceive
  (selection, HEAD, tag vs branch, stash) has a shape or text carrying it too (W7, W8).

The whole of the above is one function called from `onRendered({startRow, endRow})`, applied to
the rows in that range. It runs on rows the grid just built, so it costs a handful of
`setAttribute` calls per newly rendered row — the same order as the row's own construction.

Tooling: `@axe-core/playwright` against the harness in all four theme kinds — a pinned
devDependency. It is worth it: hand-written ARIA assertions catch what the author thought of,
and the four theme kinds are where contrast violations actually appear.

**Done when:** axe reports no violations at the `serious` or `critical` level in any of the four
theme kinds; a keyboard-only pass (tab into the panel, pick a repo, move selection, open and
close the pane, resize a column, load more, refresh) is possible without a mouse and is scripted
in the interaction suite; `aria-rowcount` reports 20,000 and `aria-rowindex` reports the true
one-based position in a 20,000-row scenario, including after a scroll to the end; tabbing into
the panel lands on the selected row and not on a focus sink.

## W15 — Perf: the renderer's own budgets

`tests/perf/graphUi.ts`, wired into `test:perf` after `streamRoundTrip.ts`, following the
established conventions exactly (committed baseline JSON, 20% tolerance, `--update-baseline`,
non-zero exit on regression). It drives the harness through CDP the way P0's `run.ts` does, and
it is the first time §5.1's renderer rows are measured at all — P2 explicitly declined to claim
them from a headless process, and P3 measured only the wire hop.

| Metric | Scenario | Bar |
|---|---|---|
| `firstPaintMs` | `clean` | ≤ 300 ms, from navigation to `kira:first-paint` (§5.1's "panel open → first commits painted") |
| `firstPageMs` | `ceiling` | ≤ 400 ms to the first 5,000 rows listed and laid out |
| `loadMoreMs` | `ceiling` | ≤ 400 ms per press, worst of five, scroll position unchanged |
| `worstFrameMs` | `ceiling` | ≤ 32 ms, over a scripted scroll of 2,000 frames at rows 0, 50k and 90k |
| `medianFrameMs` | `ceiling` | ≤ 16.7 ms (the 60 fps clause), recorded and gated |
| `heapFirstPageMB` | `ceiling`, one page | ≤ 80 MB (§5.1) |
| `heapFullMB` | `ceiling`, all 100k | ≤ 250 MB (§5.1) |
| `layoutSubmitMs` | `ceiling` | the worker round trip per page — recorded, not gated, so a first-page miss is attributable in one line rather than re-derived |
| `rowBuildMs` | `ceiling` | median and p99 time to build one row's cells, sampled inside the graph column's formatter — recorded, not gated. This is the number the rendering decision rests on (the estimate was ~0.2 ms for a 40-row fling, i.e. a few µs per row); recording it is what turns that estimate into a fact, and it is what makes a `worstFrameMs` miss attributable to the graph column or not, in one line |
| `svgNodesPerRow` | `badges` | mean SVG elements per rendered graph cell — recorded, not gated. Guards the one-path-per-colour grouping, which is what keeps the element count flat |
| `bundleKB` | build | the gzipped delta `slickgrid` adds to `dist/ui` — recorded, not gated. §8.5 already settled that bundle size is close to irrelevant for a locally-loaded webview, so this exists to make the cost visible rather than to gate on it |

`kira:first-paint` and `kira:layout-complete` already exist as marks in `App.vue` (P0 put them
there); `kira:layout-complete` changes meaning in this phase from "the placeholder mounted" to
"the first `LayoutChunk` has been applied and the rows it covers have been re-rendered with
their lanes", which is what it was always a placeholder for, and the change is noted at the mark
rather than silently.

Frame timing uses `requestAnimationFrame` deltas collected in-page during a scripted
`mouse.wheel` scroll, not CDP's tracing: the numbers are cruder and they are reproducible, which
is what a 20% gate needs. Heap follows `run.ts`'s existing collect-sample-median discipline —
a single `JSHeapUsedSize` reading is noise.

**Honest note, carried forward from P2's and P3's:** these are headless-Linux numbers on
container hardware. The 60 fps clause in particular is a *hardware* claim, and this sandbox is
not the mid-range laptop §5.1 names. The gate here catches regressions; the absolute claim is
closed on macOS with `bun run test:perf`, recorded as inherited-open the way P1's V2 and P2's V1
were.

**The one measurement this phase genuinely owes.** `AGENTS.md` says to measure when a real,
concrete question is at stake and not as a ritual. The concrete question here is the one the
rendering decision turned on: **does building a few SVG elements per newly-visible row hold the
frame budget at 100k rows, where a reused canvas would allocate nothing?** The estimate above
says yes with an order of magnitude to spare, and the estimate is not the answer.
`worstFrameMs` on the `ceiling` scenario is, with `rowBuildMs` and `svgNodesPerRow` beside it so
that a miss is attributable rather than mysterious. If it misses, the escalation ladder is
named and ordered so it is not invented under pressure: (1) raise `minRowBuffer` so fewer rows
are built per fling frame; (2) cache built `<svg>` elements for recently-evicted rows in a small
LRU and `cloneNode` them; (3) move the graph column to `asyncPostRender`, accepting that the
graph lags the text by `asyncPostRenderDelay` during a fast scroll. Only if all three fail does
the canvas question reopen, and that would be a Finding with numbers in it, not a reversal.

**Done when:** every metric reports against a committed baseline; an injected 30% slowdown in
`buildRowSvg` fails the frame metrics and an injected retained-array leak fails the heap
metrics; the heap numbers are within §5.1's ceilings or the miss is a Finding with the
attribution (store, layout buffers, grid row cache, SVG elements) broken out.

## W16 — The density review against the native workbench list

## W17 — Verification tasks

Five assumptions this plan makes. V1 blocks nothing but should be run **before** W4 commits to a
worker; the others run alongside. Each gets a recorded answer under Findings.

**V1 — does a module worker load inside a VS Code webview, and under what CSP?**
`html.ts`'s current policy is `default-src 'none'; … script-src 'nonce-${nonce}';` and declares
no `worker-src`, which falls back through `child-src` to `default-src 'none'` — so as written,
`new Worker(...)` is blocked. Confirm the directive that admits it (`worker-src ${cspSource}` for
a bundled worker file, plus `blob:` if Vite inlines a small worker), confirm that a *module*
worker (`type: "module"`) loads from a `vscode-webview://` origin at all, and confirm the nonce
does not need to reach it. If module workers turn out to be unusable there, record it and take
W4's named fallback (chunked main-thread layout behind the same `LayoutClient` interface). This
is the one verification whose answer changes a work item's shape.

**V2 — SlickGrid's focus and keyboard model against ours, in a real browser.** This replaces the
pre-SlickGrid V2 ("does a 2.2-million-pixel spacer scroll correctly?"), which the library
retires: it maintains its own page/offset compensation behind `maxSupportedCssHeight` precisely
so a caller never meets the browser's element-height limit. What is *not* settled is how its
focus machinery interacts with the roving `tabindex` W14 needs. Confirm, on the `ceiling`
scenario: that the two `tabindex="0"` `_focusSink` divs the grid places at the container's edges
do not become tab stops before the selected row (and that setting them `tabindex="-1"` after
construction does not break the grid's own scroll-into-view); that with
`enableCellNavigation: false` no active-cell outline appears and our own `keydown` handler sees
every key §6.6 needs; that `scrollRowIntoView` lands the row fully visible at both ends of a
100,000-row range rather than half-clipped; and that `getViewport().top` round-trips through
`viewState` exactly. Each has a small, named remedy; none changes a work item's shape, which is
why this runs alongside rather than first.

**V3 — `vue-tsc` and TypeScript 7, the check §8.3 schedules for this phase by name.** "Re-confirm
the `vue-tsc`/TS-7 state at P0 and again at P4 — this area is moving month to month, and it may
well already be resolved by P4." P0's V1 found `vue-tsc@3.3.11` hard-crashing on TS 7 and left
the repository with two TypeScript versions (root `7.0.2`, `packages/ui` `6.0.3` for `vue-tsc`).
Re-check whether a `vue-tsc` supporting TS 7 has shipped; if it has, the switch is a dependency
bump and the deletion of the second version, and doing it in this phase — the one that adds the
most `.vue` code — is worth more than doing it in any later one. If it has not, record the
version checked so P5 does not re-derive it.

**V4 — frame timing and heap in this sandbox, and what they are worth.** Establish what
`requestAnimationFrame` deltas and `JSHeapUsedSize` actually report on headless Chromium here
(a headless compositor may report a synthetic vsync), so W15's gate is calibrated against real
variance rather than against an assumed 16.7 ms cadence. Record the run-to-run spread the way
P3's W17 did for its timings — a baseline whose noise band is unknown is a baseline that fails
randomly.

**V5 — does the packed-chunk path survive the fix, end to end, on the real webview transport?**
W2 fixes the dictionary mark and W5 fixes the restart-at-zero handling, both asserted headlessly.
The half that only a real VS Code can show is the one §2.1 actually promises: hide the panel,
let the webview be destroyed, re-show it, and see rows — with authors — repaint from cache with
no `git log` spawn. `panel.spec.ts`'s second test already exists to watch it and is blocked by
the same download gap; note in Findings that this specific defect is why that test matters more
than its "chunk-source is cache" assertion suggests.
