# P4 — Graph UI

Plan for the P4 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** the thing a user actually looks at. P3 finished the pipe — git → `RepoService` →
packed chunks → transport → a UI-side `CommitStore` — and rendered its output as a strip of
labelled numbers. P4 replaces that strip with the surface §6 describes: a virtualized commit
list with real columns and ref badges, a canvas lane graph drawn from P2's layout buffers with
the layout pass finally running in the worker §3.2 puts it in, an explicit Load-more button
carrying its remaining count, selection and keyboard navigation, a working Refresh, and the
responsive behaviour a panel that is short, wide, and constantly resized demands (§6.3).

**Platform and runtime constraints.** macOS only (D27), inherited unchanged; no CI (D28), so
every check here is a command someone runs and running it is an exit criterion. What is new in
this phase is that **the renderer is now the performance-critical process**. P1 and P2 measured
git and the store; P3 measured the wire. §5.1's four renderer-side budgets — 300 ms to first
commits painted, 400 ms to a first page, 60 fps sustained scroll with no frame over 32 ms, and
the 80 MB / 250 MB heap ceilings P2 explicitly declined to claim from a headless process — are
P4's to meet and P4's to measure. They are the reason §5.3's three rules exist (canvas for the
graph, a recycled DOM pool for text, no Vue reactivity over the commit set), and every work
item below that touches rendering is written against them rather than against "it feels fast".

The second new constraint is the **worker**, which is the first time this project runs code off
the main thread in production. §3.2 puts lane layout there; P2 built `layoutAppend` as a pure
function with a declared transfer list precisely so P4 could wrap it in ~30 lines. Wrapping it
is cheap; getting the *data flow around it* right is not, and W4 spends its length on that
rather than on the wrapper.

**On verification in this sandbox, stated up front so the phase does not stall on it.** This is
a headless Linux container. P3's V2/V3 settled what runs here: Electron launches under
`xvfb-run -a --no-sandbox` and its Playwright project genuinely runs; a VS Code download does
not (`update.code.visualstudio.com` is blocked), so `tests/e2e/vscode/panel.spec.ts` remains
inherited-open. The posture is P3's, unchanged: **verify everything verifiable headlessly — the
harness e2e suite, the visual-regression baselines, the perf harness through CDP, the unit
tests over the renderer's pure halves — and record the display-, hardware- and VS-Code-dependent
halves as inherited-open in Findings with the exact command a macOS machine must run.** Two of
P4's exit criteria are of that kind and are named as such below: the 60 fps figure on real
hardware, and §6.1's side-by-side density review against the native workbench list, which
requires a real workbench beside a real panel.

**Not a goal.** The detail pane's *contents* (metadata, message, trailers, signature, file tree,
diff) are P5; P4 builds the pane's region, its open/close semantics and its breakpoint
behaviour, and leaves it empty. No context menu and no row actions — checkout, branch, tag,
revert, reset, cherry-pick, copy-message all belong to the phases that own their pre-flight
(P6–P9). No branch or tag list, no conflict banner (P6). No fetch/pull/push/stash toolbar
buttons (P7, P8). No search box, no toggles, no scope selector (P10). No status bar item, no
SCM title button, no packaging (P11). The clipboard is not wired: the sha column renders as a
button because that is what §6.4 says it is, but the copy action and the `Clipboard` port land
with P5's copy actions, and a button that looks live and does nothing is worse than a button
that is explicitly not there yet — so it is rendered `disabled` with a title saying so.

The one thing P4 must get right that no later phase can fix cheaply: **the commit set must
never become reactive, and the row pool must never be rebuilt.** §5.3 states both; both are the
kind of thing that works at 5,000 rows, is invisible in review, and is a rewrite of every
component by P10. A `v-for` keyed on row index re-creates DOM on every scroll tick and is
indistinguishable from a correct implementation until the repository is large. A `ref()` where
`shallowRef()` was meant hands Vue's proxy a 100k-row store to walk. Both are cheap to get right
in W6 and expensive to retrofit once the detail pane, the search highlighter and five dialogs
are reading the same state.

### What P3 left broken, and why P4 is where it surfaces

P3's exit criteria for rehydration were met by `tests/integration/repoService.test.ts` counting
spawns and by `panel.spec.ts`, which V3 left unrunnable. Between those two lies a real defect,
found while planning this phase by reading the code rather than by running it:

**A cache replay to a *fresh* receiver sends a dictionary the receiver does not have.**
`RepoSession.dictionaryCursor` is monotonic per host session (`repoService.ts`, `#emitRange`
advances it by `commits.dictionary.length` on every chunk). `CommitStore.packSlice(from, to,
dictionaryBase)` emits only the strings interned *after* `dictionaryBase`, and
`CommitStore.appendPacked` asserts `chunk.dictionaryBase === interner.size`. So the sequence
§2.1 guarantees will happen — webview shown, streamed, hidden, destroyed, re-shown with a brand
new `GraphViewState` whose store is empty — replays row 0 with `dictionaryBase` at whatever the
cursor had reached, and `appendPacked` throws before a single row lands. The identity columns of
that chunk reference dictionary ids that were never sent, so even without the assert the author
column would be wrong rather than absent.

**And the UI has no handler for a stream that restarts at row 0.** P3's own plan says a stale
re-walk produces "a chunk sequence starting at `from: 0`, which is exactly what the UI needs to
know to discard what it had". The host half was built (`#ensureFresh` drops the store and resets
`dictionaryCursor`); the UI half was not — `GraphViewState.#applyChunk` calls `appendPacked`
unconditionally, so the first post-invalidation chunk throws on the `chunk.from === rowCount`
assert instead of resetting.

Both are P4's to fix (W2, W5), for the same reason: P4 is the phase where a hidden-then-shown
panel has to come back with rows in it, and where a `refsChanged` during a session has to do
something a user can see. They are recorded here rather than in P3's Findings because the fix
ships in this phase's diff, and because a plan that inherits a defect silently is how the defect
survives another phase.

### What the mockup shows that P4 does not build

`docs/design/panel-mockup.html` is the approved visual reference (§6.7) and P4 is the phase that
finally implements most of it — the row geometry, the lane canvas, the badges, the Load-more
button and the toolbar shape all come from it. It also shows a search box, Fetch/Pull/Push/Stash
buttons, a conflict banner, a populated detail pane, a context menu and a status bar item. None
of those is P4's. §6.7 settles the standing of the disagreement in advance: the mockup "is not a
P4 acceptance target; the acceptance criteria are in §10." The visual-regression baselines this
phase commits are of the panel P4 actually ships, not of the mockup.

### The contract entries P4 adds

Three changes, all in W2, all of which take `CONTRACT_VERSION` from `2` to `3` — which is
enforced: `wrapVersioned`/`validate.ts` reject a mismatched frame loudly, so the two hosts, the
harness mock and the UI move together in one commit or the app refuses to start.

```ts
"graph.refresh": { params: { repoId: string }; result: { restarted: boolean } }
"graph.loadMore": { params: { repoId: string; pages?: number }; result: { started: boolean } }
                   // unchanged shape; gains real cancellation (W2)
```

`graph.stream`'s chunk shape is unchanged. Nothing is added for layout: the layout buffers are
produced in the renderer's own worker from data the stream already carries (§3.2), and putting
them on the wire would mean the host doing work the renderer must redo on rehydration anyway.

## W1 — The lane palette, and the one colour we are allowed to invent

§3.4: "Graph lane colours are the only palette we invent, since no workbench colour id means
'branch lane 3'. They are generated per theme kind for contrast against
`--vscode-editor-background`, checked for WCAG contrast, and made distinguishable under the
common colour-vision deficiencies. High-contrast themes get their own set plus outlines." And:
"We also expose our colours as themable contribution points (`contributes.colors`)."

P0 seeded eight placeholder tokens in `vscode-tokens.css` and labelled them as placeholders in
the file ("These eight are a placeholder progression, not yet contrast-validated"). P2 emitted a
palette *index* and never a colour. P3 kept the placeholders and deferred the rest here. This
item closes it.

**`scripts/gen-lane-palette.ts`** (new; add to §3.1's tree beside `gen-theme-palettes.ts`)
produces, from one small source table of hues, four sets of eight colours — one per theme kind —
and writes two artifacts:

1. `contributes.colors` entries in `packages/host-vscode/package.json`, ids
   `kiraVersion.graphLane0` … `kiraVersion.graphLane7`, each with the four defaults VS Code's
   manifest schema takes (`dark`, `light`, `highContrast`, `highContrastLight`) and a
   description. Contributed colour ids are injected into every webview as `--vscode-*` variables
   under the same mechanical renaming as built-in ids (§3.4), so `kiraVersion.graphLane3`
   arrives as `--vscode-kiraVersion-graphLane3` with no code on our side — and a user or theme
   author can override it from `workbench.colorCustomizations`, which is the courtesy §3.4 asks
   for, delivered by the platform rather than by us.
2. The corresponding literal fallbacks in `packages/ui/src/theme/vscode-tokens.css`, so each
   token becomes `--kv-graph-lane-N: var(--vscode-kiraVersion-graphLaneN, <generated literal>)`.
   The literal is what Electron uses: `gen-theme-palettes.ts` extracts the `--vscode-*` names
   referenced by this file and looks them up in VS Code's theme JSON, where a *contributed* id
   does not exist — so it is omitted, the fallback chain takes over, and Electron gets the same
   colour without a second generator. That is worth a comment in both scripts, because it looks
   like an oversight and is the intended path.

**The checks, which are the substance of this item and not the colours:**
`scripts/check-lane-palette.ts` (or a `--check` mode on the generator, matching
`gen-settings.ts`'s convention) is wired into `bun run check` and fails on:

- **Contrast.** Every lane colour against its kind's `editor.background`, at the WCAG
  non-text-contrast bar of **3:1** — a 1.6 px stroke is a graphical object, not body text, so
  the 4.5:1 text bar is the wrong test and citing it would be cargo-culting. The two
  high-contrast kinds require 4.5:1, since that is the whole point of those themes.
- **Distinguishability, including under CVD.** Every pair of the eight, and separately every
  *adjacent* pair, must exceed a CIE ΔE threshold after simulating protanopia, deuteranopia and
  tritanopia (Brettel/Viénot matrices — twenty lines of arithmetic in the script, no
  dependency). Eight hues that are distinct to a trichromat and collapse to three under
  deuteranopia is the exact failure this check exists to prevent, and it is not detectable by
  looking at the palette.
- **Determinism.** The generator's output is committed; `--check` fails when the file on disk
  differs from what the source table produces, so a hand-edit to the manifest or the CSS is
  caught the way `gen-settings.ts`'s already is.

**High-contrast gets outlines, not just colours** (§6.1: "it requires explicit borders where
other themes use background fills alone"). The palette module exports, alongside the eight
colours, a per-kind `nodeOutline: string | null` and `nodeOutlineWidth` that W8's renderer
applies to every node and reads through the same token layer
(`--kv-graph-node-outline`, defined in `vscode-tokens.css` only under the two high-contrast body
selectors, which already exist in that file).

**Not in this item:** badge colours (P6, see the scope table) and any change to `core/graph/
colors.ts`, which keeps emitting an index. `packages/core` never learns a hex value (§6.1's
token-only rule, B4's lint).

**Done when:** `bun run check` fails on a hand-edited manifest or CSS and on a deliberately
low-contrast hue; the eight ids appear in `contributes.colors` with four defaults each; setting
`workbench.colorCustomizations: {"kiraVersion.graphLane0": "#ff00ff"}` changes the canvas after
a theme re-read with no reload (asserted in W13's harness equivalent by writing the
`--vscode-kiraVersion-graphLane0` variable directly, and in `panel.spec.ts` for real, per V3's
inherited-open status); `readTokens.ts`'s `TOKEN_NAMES` covers every token the renderer reads.

## W2 — `graph.refresh`, cancellable `loadMore`, and the dictionary-mark fix

Three host-side changes, one commit, `CONTRACT_VERSION` → `3`.

**1. `graph.refresh`.** §6.2 defines Refresh precisely enough to implement without inventing:
it "forces a full re-query — refs, status, and history walk — bypassing every cache", it is
"distinct from the automatic invalidation the watcher performs, which is incremental and does
not re-walk", it "is idempotent (a second press while running is a no-op, not a queued second
walk)", and it "preserves selection and scroll position across the refresh".

```ts
// packages/ipc/src/contract.ts
"graph.refresh": { params: { repoId: string }; result: { restarted: boolean } }

// packages/git/src/repoService.ts
refresh(repoId: string): void;   // marks the session stale; the next stream re-walks
```

The mechanism already exists and is the one thing not to duplicate: `#ensureFresh(session)`
drops the store, disposes the `LogSession`, opens a new one and resets `dictionaryCursor`, and
runs on the next `streamGraph`/`loadMore`. So `refresh()` is `session.staleReason = "refresh"`
and nothing else — the `staleReason` union widens from `"refsChanged" | undefined` to
`"refsChanged" | "refresh" | undefined` so a log line can say which it was. `restarted: false`
is returned when the repo id has no open session, which is the honest answer rather than a
throw. Idempotency falls out: two `refresh` calls before the next stream set the same flag once.
The re-query of refs is not a separate call — decorations ride the walk (`%D` in §4.4's format),
and the ref snapshot `logSession` takes for its `--skip` guard is retaken when the session is
replaced.

**2. `loadMore` becomes genuinely cancellable.** §5.1.1 says loading more "is cancellable", and
today it is not: `RepoService.loadMore` takes no signal, so an aborted RPC leaves the host
reading a full 5,000-row page. P2's `LogSession.readPage(sink, { signal })` already accepts one.
Thread it: `loadMore(repoId, pages, signal?)` → `#readPageIntoStore(session, signal)` →
`readPage(sink, { signal })`, and `rpcHandlers.ts` passes the server's per-request
`AbortSignal` (W2 of P3 already maps a `cancel` frame to one). Rows read before the abort stay
in the store — that is correct and is worth stating in the UI (W9): cancelling stops the load,
it does not unload.

**3. The dictionary mark, fixing the rehydration defect.** `packSlice`'s `dictionaryBase`
contract is "the caller is responsible for tracking what the receiver has already been sent" —
and the receiver is not the session, it is *this stream*. A receiver holding exactly rows
`[0, R)` has interned exactly the strings first seen in those rows, because interning happens in
row order; so the size is a pure function of `R` and the host can record it:

```ts
// RepoSession
dictionaryMarks: Map<number, number>;   // boundary row -> interner size after that row
```

A mark is written at every chunk boundary `#emitRange` emits (plus `0 → 0` at session start),
which is exactly the set of rows a client's `loadedRows` can ever equal, since the client only
ever advances by whole chunks. `streamGraph` then resolves its base from the mark for the
clamped resume row; **a resume row with no mark replays from row 0 with base 0** rather than
guessing. At 100k rows and `CHUNK_ROWS = 500` that is 200 entries — the memory argument against
it does not exist.

The rejected alternative was making the chunk self-describing: pack `[id, string]` pairs for
exactly the identities the slice references, and let the receiver plant them at those ids. It is
more robust in the same way W3-of-P3's parents-as-shas is more robust, and it was rejected
because it changes `StringInterner`'s id contract (ids currently mean first-seen order, and
sparse assignment makes `intern()` and `internAt()` two different things with an invariant
between them) for a problem the mark solves in six lines. If a later phase ever needs a chunk
that can be applied to a receiver in an unknown state — a second webview onto the same repo, say
— that is when the interner changes.

**Done when:** `tests/integration/repoService.test.ts` gains a test that streams a repo fully,
then streams it again into a **freshly constructed** `CommitStore` from `resumeThroughRow: 0`
and asserts every row matches the first store row for row (this is the test whose absence hid
the defect: the existing tests collect chunks without ever applying them to a second store);
a resume at a real chunk boundary appends onto a store holding exactly those rows; a resume row
that is not a boundary replays from 0; `graph.refresh` on a streamed repo makes the next stream
emit from `from: 0` with `source: "git"` and spawns exactly one new `git log`; a `loadMore`
aborted mid-page leaves the session usable and the partial rows readable; `bun run check` passes
with `CONTRACT_VERSION` at 3 in every consumer.

## W3 — `packages/ui/src/graph/layoutStore.ts`

New file, added to §3.1's tree. P2 produces one `LayoutChunk` per appended page, with a global
edge numbering and a `patches` array that corrects edges belonging to *earlier* chunks; its own
`types.ts` names the missing piece — "the reassembler (the consumer holding every chunk) maps a
global index back to (chunk, local offset)". This is that consumer. It is main-thread, UI-only,
and pure: no Vue, no DOM, no canvas, so it is unit-testable in `bun test` without a browser.

```ts
export interface RowVisual { readonly lane: number; readonly color: number }

export interface EdgeSegment {
  readonly fromRow: number; readonly toRow: number;      // toRow may be UNRESOLVED_ROW
  readonly fromLane: number; readonly toLane: number;
  readonly color: number; readonly kind: EdgeKind;
}

export class LayoutStore {
  append(chunk: LayoutChunk): void;
  clear(): void;
  readonly rowCount: number;      // rows covered by appended chunks
  readonly laneCount: number;     // high-water mark across chunks — the gutter's width input
  laneOf(row: number): number;
  colorOf(row: number): number;
  /** Every segment that can paint inside [firstRow, lastRow]. Allocation-free: fills a
   *  caller-owned array and returns the count, so a 60 fps repaint allocates nothing. */
  segmentsInWindow(firstRow: number, lastRow: number, out: EdgeSegment[]): number;
}
```

**Chunk indexing.** Chunks are appended in order and are contiguous, so `laneOf`/`colorOf` are a
binary search over chunk starts (≤ 20 entries at 100k rows, ~200 at a million) plus one typed
array read. Not a per-row copy into one flat array: that would double the memory the transfer
was supposed to avoid.

**Applying patches.** A chunk's `patches` is `(globalEdgeIndex, toRow)` pairs naming edges in
earlier chunks whose `UNRESOLVED_ROW` target the new page resolved. `append` walks them, maps
each global index to `(chunk, local offset)` through each chunk's own edge-count range, and
writes `EDGE_TO_ROW` in place. Writing into an earlier chunk's `edges` buffer is legal — it is
ours, it was transferred to us, and nothing else holds a reference — and it is what keeps a
Load more from re-laying out the previous page (§5.5's whole argument in W9 of P2).

**The window query is the interesting half.** The renderer paints ~25 visible rows out of
100,000 at 60 fps, so "which edges touch this window" must not be O(all edges). `edgeIndex` gives
edges *starting* at a row in O(1), but an edge starting 40,000 rows above and ending below the
window still paints a vertical run *through* it, and `maxEdgeSpan` — P2's answer — is the
largest span in the chunk, which one long-lived branch merge makes useless as a lookback bound.

So `append` builds one side index: **`longEdges`, every edge whose span exceeds
`LONG_EDGE_ROWS = 64`, in a flat array sorted by `fromRow`.** Real repositories have hundreds of
these, not thousands — they are exactly the merges of long-lived branches. `segmentsInWindow` is
then: a CSR scan over rows `[firstRow − LONG_EDGE_ROWS, lastRow]` (bounded, ~90 rows of edges),
plus a filtered pass over `longEdges` for those intersecting the window (found by binary search
on `fromRow` then a linear filter on `toRow`). Exact, allocation-free, and bounded by the window
rather than by history. If `longEdges` ever grows into the thousands on a pathological
repository, the next step is bucketing it by row range — named here so it is a known move, not
built now for a repository nobody has shown us.

**Done when:** unit tests (`tests/unit/ui/layoutStore.test.ts`, under `tests/unit/` because it
needs `tests/fixtures/topology.ts` — P2's finding) assert that a store fed page-by-page reports
the same `laneOf`/`colorOf` for every row as one fed a single whole-history chunk, for every W1-
of-P2 shape; that a patch from a later page corrects an earlier page's edge target;
that `segmentsInWindow` returns exactly the segments a brute-force scan over all edges returns,
for every window position on every shape, including windows containing no row that starts an
edge; and that a window query allocates nothing after the first call (asserted by reusing the
`out` array and comparing counts, not by heap inspection).

## W4 — `layout.worker.ts` and `layoutClient.ts`

§3.2 puts lane layout in a worker; P2 made `layoutAppend` a pure function with a declared
transfer list so that this file could be thin. It is thin. The data flow around it is not, and
that is what this item is about.

**`packages/ui/src/graph/layout.worker.ts`** — a module worker holding the `LayoutFrontier`
between calls (so a page's layout resumes rather than recomputes), receiving `LayoutRequest`
and posting `LayoutResponse`, both already declared in `core/graph/types.ts` for exactly this
reason. It calls `layoutAppend` and posts with `layoutTransferList(chunk)`. Under 40 lines.

**`packages/ui/src/graph/layoutClient.ts`** (new; add to §3.1's tree) — the main-thread side:
constructs the worker with Vite's own `new Worker(new URL("./layout.worker.ts", import.meta.url),
{ type: "module" })` form, keeps the request sequence, drops responses whose sequence is stale
(P2 put `sequence` in the message shape for precisely the double-Load-more race), and exposes:

```ts
export interface LayoutClient {
  submit(input: LayoutInput): Promise<LayoutChunk>;
  reset(): void;        // discards the frontier — a refresh or a repo switch
  dispose(): void;
}
```

**The direction of copying is the decision here.** `LayoutInput` carries `parentOffsets` and
`parentRows` — views over the *whole* `CommitStore`'s parent columns, absolute-indexed, because
the pass must see parents outside the new range to patch earlier edges. They must be **copied**
into the request, never transferred: transferring detaches the store's own columns and the store
is the thing the row renderer reads on every frame. The response *is* transferred, which is what
§5.5 asks for and where the size actually is.

Two consequences worth writing down before they are discovered:

- `structuredClone` of a typed array clones its whole backing `ArrayBuffer`, not just the view's
  window. `CommitStore`'s columns are capacity-doubled, so the buffer behind a 130k-slot
  `parentRows` view may be 256k slots. At 4 bytes that is ~1 MB copied per page — twenty times
  over a full 100k walk. That is acceptable (W15 measures it; the whole page budget is 400 ms
  and this is a memcpy), and it is *not* acceptable to fix it by transferring. If it ever
  matters, the fix is `submit` building tight `Int32Array` copies of the exact used range, which
  is three lines — named, not built, because the measurement comes first.
- The worker's own store-side view is stale by construction between pages, which is fine:
  `layoutAppend`'s contract is that the input carries everything the pass reads.

**The fallback, which V1 decides.** A module worker inside a VS Code webview must satisfy the
CSP in `packages/host-vscode/src/html.ts`, which today is `default-src 'none'; … script-src
'nonce-${nonce}'` and declares **no `worker-src`** — and `worker-src` falls back to `child-src`
and then to `default-src`, i.e. `'none'`. So the CSP must gain `worker-src ${cspSource} blob:;`
(and the nonce does not apply to worker scripts, which is the trap: a worker is fetched, not
inlined, so it is the *source* directive that governs it). V1 confirms this on a real webview.
If a module worker cannot be made to load there at all, `layoutClient.ts` keeps its interface and
runs `layoutAppend` on the main thread in an idle callback, chunked to `CHUNK_ROWS` so it never
holds the thread for a frame — a real degradation to record in Findings, not a reason to
restructure the renderer, because every consumer above `LayoutClient` is written against a
promise either way. Building the client interface first is what makes that fallback a
one-file change.

**Done when:** a unit test drives `layoutClient.ts` against a stubbed worker and asserts stale
responses are dropped and `reset()` discards the frontier; an integration-style test in the
harness lays out a real scenario through the real worker and asserts the resulting
`LayoutStore` matches a synchronous `layoutAppend` over the same input, row for row; the
worker bundles into `dist/ui` as its own chunk (W13's build check confirms it is emitted, since
a silently-inlined worker would defeat the whole item); and the source columns are **not**
detached after a submit (`parentRows.byteLength !== 0`), which is the assertion that catches
someone "optimising" the copy into a transfer.

## W5 — UI state: `graphView.ts` rebuilt, `selection.ts`, `viewState.ts` v2

P3's `state/graphView.ts` is 80 lines that append chunks and expose four scalars. P4 turns it
into the module every component reads, and it keeps §5.3's rule at its centre: **the
`CommitStore` and the `LayoutStore` are `markRaw`'d and never reactive; only scalars are.**

```ts
// state/graphView.ts
class GraphViewState {
  readonly store: CommitStore;          // markRaw
  readonly layout: LayoutStore;         // markRaw
  readonly loadedRows: ShallowRef<number>;
  readonly remaining: ShallowRef<number>;
  readonly exhausted: ShallowRef<boolean>;
  readonly laneCount: ShallowRef<number>;
  readonly loading: ShallowRef<"idle" | "streaming" | "loadingMore" | "refreshing">;
  readonly generation: ShallowRef<number>;   // bumped on every reset; components key off it
  openStream(repoId: string, resumeThroughRow?: number): Promise<void>;
  loadMore(pages?: number): Promise<void>;
  loadAll(): Promise<void>;
  refresh(): Promise<void>;
  cancelLoad(): void;
}
```

**`generation` is the mechanism that makes a reset visible to the renderer.** Nothing else
changes when 100k rows are dropped and re-walked — `loadedRows` might land on the same number —
and a canvas that repaints only on scroll would keep showing the old graph. Every consumer that
caches anything derived from the store (the canvas's last-painted window, the row pool's text)
invalidates on `generation`.

**Reset on a restart-at-zero chunk**, the second half of the defect W2 fixes on the host side:

```ts
#applyChunk(chunk) {
  if (chunk.from === 0 && this.store.rowCount > 0) this.#reset();   // host re-walked
  this.store.appendPacked(chunk.commits);
  …
}
```

and `#reset()` clears the store, the `LayoutStore`, the `LayoutClient`'s frontier and bumps
`generation`. An `appendPacked` that throws anyway (a genuinely corrupted stream) is caught,
logged, and turned into a full re-open from row 0 rather than an unhandled rejection that leaves
a half-populated list on screen — the store's asserts are the right place for the check and the
wrong place for the recovery.

**Layout is driven from the append**, not from the render: after each chunk lands,
`layoutClient.submit(store.layoutInput(from, to))` runs and its `LayoutChunk` goes into the
`LayoutStore`; `laneCount` updates. The canvas repaints when the promise resolves. This means
rows can be *listed* before their lanes exist — which is correct and is what makes the ≤ 300 ms
first-paint budget reachable: text first, graph a frame later, never a blank list waiting on a
worker.

**`state/selection.ts`** (§3.1's tree, deferred by P3 to here):

```ts
class SelectionState {
  readonly row: ShallowRef<number>;         // -1 for none
  readonly sha: ShallowRef<string | null>;  // survives a re-walk; the row index does not
  select(row: number): void;
  selectBySha(sha: string): boolean;        // used after a refresh/rehydrate
  clear(): void;
}
```

Selection is stored **by sha as well as row**, because §6.2 requires Refresh to preserve
selection and a re-walk renumbers every row. After a reset, `selectBySha` re-resolves against
`store.rowOfSha` once the sha is loaded again; when it is not (it fell below the loaded range,
or it is gone from history), selection clears and the list does not scroll — silently selecting
a *different* commit at the same row index would be the worst available behaviour in a tool
whose next phase attaches destructive actions to the selected row.

**`state/viewState.ts` → version 2.** §5.4's full list, finally:

```ts
export interface PersistedViewState {
  readonly version: 2;
  readonly repoId: string | null;
  readonly loadedRows: number;
  readonly detailOpen: boolean;
  readonly scrollTop: number;
  readonly selectedSha: string | null;
  readonly columnWidths: { author: number; date: number; sha: number };
  readonly dateFormat: "relative" | "absolute";
  readonly detailWidth: number;
}
```

P3's rule holds unchanged and is why the bump is safe: **a state whose `version` is not the
current one is discarded whole, never partially applied.** Writes stay debounced (scroll fires
continuously; `setState` on every frame is a message per frame to the extension host).

**Done when:** unit tests over `GraphViewState` with a fake transport assert: chunks append in
order; a `from: 0` chunk after rows exist resets and bumps `generation`; a corrupted chunk
produces a re-open rather than a rejection; `loadMore` appends without disturbing
`selection.row`; `refresh` clears and re-populates with selection re-resolved by sha; a v1
persisted state is discarded and a v2 one round-trips every field.

## W6 — `CommitList.vue` and `CommitRow.vue`

The phase's largest single item and where §5.3's second and third rules live: "Text columns
(message, author, date, ref badges) are virtualized DOM rows — real text for accessibility,
selection, and theming — with a recycled row pool" and "the DOM row pool is fixed-size (visible
rows + small overrun). No row is created during scrolling; nodes are recycled and their text
updated."

**Structure.** A scroll container (`overflow-y: auto`) holding a spacer of
`rowCount × rowHeight` px, with `poolSize = ceil(clientHeight / rowHeight) + OVERSCAN` row
components absolutely positioned and moved by `transform: translateY(...)`. The pool is
`v-for`-ed over **pool slot indices**, never over rows:

```html
<CommitRow v-for="slot in poolSize" :key="slot" … />
```

Keying on the slot is the entire recycling mechanism; keying on the row index — the natural
thing to write — makes Vue create and destroy a component per scroll tick and produces a list
that is correct, passes every functional test, and misses the frame budget on a large
repository. It gets a comment in the file saying so, because it is the one line in this phase
most likely to be "cleaned up" later.

`OVERSCAN = 4` rows above and below. The pool resizes only on a container resize
(`ResizeObserver`), never on scroll.

**Row content per §6.2's column list** — graph gutter (left padding equal to the canvas gutter
width, W8), then message with inline ref badges (W7), author, date, sha:

| Column | Width | Notes |
|---|---|---|
| graph gutter | `padLeft + min(laneCount, MAX_LANES) × laneWidth + 6` | not a column the user can resize; owned by W8's geometry so DOM and canvas cannot disagree |
| message | flex, `text-overflow: ellipsis` | badges are inline-start of the subject, per the mockup |
| author | persisted, default 74 px | |
| date | persisted, default 52 px, `font-variant-numeric: tabular-nums` | clicking it toggles relative/absolute for every row and persists (§6.2) |
| sha | persisted, default 60 px, `--kv-mono-font-family` | a `<button>`, `disabled` in P4 with a title naming P5 (see the scope boundary) |

**Resizing** without a header row (the workbench list has none, and §6.1 says copy it rather
than design a second answer): a 5 px drag handle at each of the three boundaries, absolutely
positioned, spanning the list's height, `role="separator"` with `aria-orientation="vertical"`,
arrow keys resizing by 8 px so it is reachable without a mouse (§6.6 makes full keyboard
reachability a v1 requirement, not polish). Widths clamp to sane minimums and persist through
`viewState`.

**Metrics come from the token layer, not from constants in this file** — `--kv-row-height` (22
px at default density, §6.1) is read once through `readTokens.ts` and re-read on the same change
event the canvas uses, so a density change moves both. Hover, focus and selection backgrounds
are `--kv-row-hover-bg` / `--kv-row-selected-bg` / `--kv-focus-border`, which map to
`--vscode-list-*` (§6.1's "VS Code's own components are the reference for ours").

**Interaction (§6.4, §6.6).** Click selects, and clicking the selected row again toggles the
detail pane closed; `↑`/`↓` move selection and scroll it into view; `Home`/`End` jump to the
first and last loaded row; `PageUp`/`PageDown` move by a viewport; `Enter` opens the detail pane
(again on the same row closes it, matching the click); `Esc` closes the pane. `F5` and
`Ctrl/Cmd+R` trigger Refresh when the panel has focus (W10 owns the action). Right-click
**selects the row and does nothing else in P4** — the menu is P6's, and selecting on right-click
now means P6 adds a menu to a row that is already correctly selected (§6.4: "Right-clicking a row
also selects it, so the menu never acts on a commit the user cannot see").

**Materializing rows.** Each visible row calls `store.commitAt(row)` — §5.5's "materialized on
demand for the ≤ 60 rows on screen … then discarded". Nothing caches a `CommitRecord` beyond the
frame, and nothing puts one in a reactive object.

**Done when:** the pool's DOM node count is constant across a scroll from row 0 to row 99,999
(asserted in W13 by counting `.kv-row` elements before and after); scrolling to the end of a
100k list and back leaves selection and column widths unchanged; keyboard selection moves,
scrolls into view and never scrolls the container when the row is already visible; a resize of
the container changes the pool size exactly once per resize; `commitAt` is called at most
`poolSize` times per frame (asserted with a counting wrapper in a unit test over the
windowing function, which is extracted as a pure `visibleWindow(scrollTop, height, rowHeight,
rowCount)` for exactly that reason).

## W8 — `GraphCanvas.vue`, `renderer.ts`, `palette.ts`, `hitTest.ts`

§5.3: "The graph column is a single `<canvas>`, redrawn per frame for the visible row window
only, `devicePixelRatio`-aware. Hit testing is arithmetic (`row = floor(y / rowHeight)`), not
DOM."

**`palette.ts`** — the canvas cannot read CSS variables, so this resolves the eight lane tokens
plus the node-outline tokens through P0's `TokenReader` (already built, already watching
`<body>`'s class and style attributes), caches the resolved strings, and re-exposes them as
`laneColor(index): string`. It subscribes to `TokenReader.onChange` and triggers a full repaint —
this is the bug §3.4 calls "the most visible possible bug" (the graph keeping its old colours
after a theme switch while everything around it re-cascades for free) and it is prevented by
three lines here rather than by remembering.

**`renderer.ts`** — pure drawing, no Vue, taking a context, a `LayoutStore`, a `CommitStore`
(for stash/merge node shape), a window and a palette:

```ts
export const GEOMETRY = { laneWidth: 13, padLeft: 11, gutterPad: 6,
                          nodeRadius: 3.4, mergeRadius: 4.2, strokeWidth: 1.6,
                          maxLanes: 12 } as const;
export function gutterWidth(laneCount: number): number;
export function paint(ctx: CanvasRenderingContext2D, view: RenderView): void;
```

The numbers are the mockup's (`ROW_H 22`, `LANE_W 13`, `PAD_L 11`, node radii, the 1.6 px
stroke), which is what makes §6.7's "approved visual reference" mean something. `rowHeight` is
not among them: it comes from `--kv-row-height` so the canvas and the DOM rows cannot drift.

Four decisions inside it:

- **The canvas is viewport-sized, not content-sized.** The mockup sizes its canvas to the whole
  list because its list is fifteen rows; 100,000 rows × 22 px is 2.2 million pixels, an order of
  magnitude past what browsers will allocate. So the canvas covers the scroll container's client
  box, sits over it (`position: absolute; pointer-events: none`), and paints with
  `y = row × rowHeight − scrollTop`. It is `devicePixelRatio`-scaled with `setTransform` and
  re-sized on `ResizeObserver` and on a DPR change (`matchMedia("(resolution: …)")`), because a
  window dragged to a second monitor is a real thing that happens and a stale backing store is
  visibly blurry.
- **Edges are decomposed into an arc and a run.** For an edge `(fromRow, toRow, fromLane,
  toLane)`, the transition happens entirely within the row below the child — a bezier from the
  child's centre to the bottom of its own row in the parent's lane, exactly as the mockup draws
  it — and the rest is a vertical run in `toLane` from there to the parent's centre. That
  decomposition is what makes windowed painting exact: the arc paints only when `fromRow` is in
  or just above the window; the run is clipped to the window and is drawn for a long edge that
  starts 40,000 rows above without knowing anything about the rows in between. `W3`'s
  `segmentsInWindow` is what supplies them.
- **An edge to `UNRESOLVED_ROW` runs off the bottom** of the loaded range and stops there
  (P2's `types.ts` states this is a real terminal state, not a placeholder) — which is exactly
  the right affordance above a Load-more button.
- **Node shapes:** filled circle for an ordinary commit; hollow with a 2 px ring for a merge
  (more than one parent, read from `store.parentsOf(row).length`); hollow with a dashed ring for
  a stash (a `stash` decoration on the row); plus the high-contrast outline W1 supplies. In the
  two high-contrast kinds every node also gets its outline unconditionally (§6.1).

Lanes beyond `maxLanes = 12` are clamped to the twelfth column rather than widening the gutter
without bound. A fifty-lane repository does exist (P2's `fan(50, …)` fixture is one) and letting
the graph eat a panel that is short and wide is the worse failure: the message column is what
the user reads. The clamp is stated in the file and is a candidate Finding if the density review
(W16) disagrees.

**`hitTest.ts`** — `rowAt(y, scrollTop, rowHeight)` and `laneAt(x)`, pure arithmetic, no DOM
(§5.3). P4's only consumer is a click on the gutter selecting the row, but it is written and
tested now because P5's parent-navigation and P6's context menu both need it and because it is
four lines of arithmetic that are easy to get wrong at the `devicePixelRatio` boundary.

**Repaint triggers**, all coalesced into one `requestAnimationFrame`: scroll, resize, DPR
change, a new `LayoutChunk`, `generation` bump, selection change, theme change. Never a repaint
per event.

**Done when:** the canvas draws the `clean` scenario identically to the mockup's own rendering
of the same topology (compared by eye once and then frozen as a W13 baseline); scrolling a 100k
list repaints in bounded time independent of scroll position (asserted in W15 by frame timing at
row 0 and at row 90,000); switching theme kind repaints with the new palette and no reload;
a merge, a stash and an unresolved edge each render their distinct form; `hitTest` unit tests
cover the row boundary, the last row, an out-of-range `y`, and a fractional DPR.

## W9 — `LoadMoreButton.vue` and the load-more flow

§5.1.1 is unusually specific and every clause is testable: pages of 5,000
(`kiraVersion.graph.pageSize`), an explicit button pinned at the bottom of the list, **not**
infinite scroll; the label "shows what it will do — *Load 5,000 more (127,400 remaining)*"; "a
modifier-click loads everything, for the user who knows what they are asking for and accepts the
memory"; and "loading more never moves the viewport, never disturbs selection, and is
cancellable".

**The flow, given the host P3 built.** `graph.loadMore` reads pages into the host's store and
returns; it does not push rows. The rows arrive by **re-opening `graph.stream` from
`loadedRows`**, which the host answers entirely from cache (`source: "cache"`, zero spawns).
That is two round trips per press and it is the right shape: the alternative — keeping one
stream open for the session and pushing into it — makes the host hold a stream across a webview
disposal it cannot observe, and P3's supersede-on-reopen rule already makes re-opening safe.
Stated here because a reader will otherwise assume the stream stays open.

```
press → loading = "loadingMore"
     → graph.loadMore({repoId, pages: 1}, signal)
     → openStream(repoId, resumeThroughRow = loadedRows)   // cache-only chunks
     → each chunk: appendPacked → layoutClient.submit → repaint
```

**Viewport preservation** falls out of the structure — rows are appended *below*, the spacer
grows downward, and `scrollTop` is untouched — but it is asserted rather than assumed, because
a naive re-render that resets `scrollTop` is a one-line accident.

**The remaining count** is `chunk.remaining` (kept live by the host through `logSession.
remaining()`), formatted with `Intl.NumberFormat` for the thousands separator. The button reads
`Load {pageSize} more ({remaining} remaining)`; when `remaining < pageSize` it says
`Load the last {n}`; when `exhausted` it is not rendered at all, and the list's end is the end.

**Modifier-click** (Alt/Option, matching the workbench's own "do the bigger thing" modifier)
calls `loadAll()`, which loops `loadMore` until `exhausted`, keeps the button in its loading
state with a cancel affordance, and appends progressively so the list stays live throughout.
Its tooltip says what it will do and names the memory cost, per §5.1.1's "accepts the memory".

**Cancellation** aborts the in-flight request (W2 threaded the signal to git) and says plainly
what happened: rows already read are kept, the button returns to its normal label with the
updated remaining count. A cancel that silently discarded a page the user already paid for
would be worse than no cancel.

**Done when:** the harness's `hugeRepo` scenario shows the right label, loads exactly one page
per press, leaves `scrollTop` and selection byte-identical across the press, disables the button
while in flight (a second press is a no-op, not a queued second page), removes the button on
exhaustion, and an Alt-click loads every remaining page with a working cancel.

| Width | Detail pane |

## W14 — The accessibility pass

"Accessibility pass on the virtualized list" is an exit criterion and §6.6 makes it a v1
requirement rather than polish: "Full keyboard reachability and ARIA roles on the virtualized
list are v1 requirements, not polish."

What a virtualized list has to get right, and what the pass asserts:

- **Roles and counts.** The scroll container is `role="listbox"` (single-select) with
  `aria-label="Commits"`; each row is `role="option"` with `aria-selected`. Because only ~30 of
  100,000 rows exist in the DOM, every row carries **`aria-posinset` and `aria-setsize`** — the
  attributes that exist precisely for this case; without them a screen reader announces "row 3
  of 30" for a repository with 100,000 commits.
- **Focus.** Roving `tabindex` on the selected row with the container focusable when nothing is
  selected — not `aria-activedescendant`, because the pool recycles DOM nodes and an
  `activedescendant` id that moves between physical nodes is exactly the pattern that breaks in
  practice. The focused row is always a real, rendered node: selection moves the window first,
  focus second.
- **Announcements.** Each row's accessible name is a composed string — subject, author, relative
  date, refs — not the visual column soup; the sha button and the resize separators have their
  own labels. The graph canvas is `aria-hidden="true"` with `role="presentation"`: it carries no
  information the row text does not, and announcing a canvas is noise.
- **Live regions.** The Load-more result ("5,000 more loaded, 122,400 remaining") and Refresh
  completion are announced through one polite live region, which is how a keyboard user learns
  the button did something.
- **No colour-only meaning.** Lane colour is decorative; every distinction a user must perceive
  (selection, HEAD, tag vs branch, stash) has a shape or text carrying it too (W7, W8).

Tooling: `@axe-core/playwright` against the harness in all four theme kinds — a new pinned
devDependency, and the one place in this phase where a dependency is added. It is worth it:
hand-written ARIA assertions catch what the author thought of, and the four theme kinds are
where contrast violations actually appear.

**Done when:** axe reports no violations at the `serious` or `critical` level in any of the four
theme kinds; a keyboard-only pass (tab into the panel, pick a repo, move selection, open and
close the pane, resize a column, load more, refresh) is possible without a mouse and is scripted
in the interaction suite; `aria-posinset`/`aria-setsize` report the true position in a 20,000-row
scenario.

## W15 — Perf: the renderer's own budgets

`tests/perf/graphUi.ts`, wired into `test:perf` after `streamRoundTrip.ts`, following the
established conventions exactly (committed baseline JSON, 20% tolerance, `--update-baseline`,
non-zero exit on regression). It drives the harness through CDP the way P0's `run.ts` does, and
it is the first time §5.1's renderer rows are measured at all — P2 explicitly declined to claim
them from a headless process, and P3 measured only the wire hop.

| Metric | Scenario | Bar |
|---|---|---|
| `firstPaintMs` | `clean` | ≤ 300 ms, from navigation to `kira:first-paint` (§5.1's "panel open → first commits painted") |
| `firstPageMs` | `ceiling` | ≤ 400 ms to the first 5,000 rows listed and laid out |
| `loadMoreMs` | `ceiling` | ≤ 400 ms per press, worst of five, scroll position unchanged |
| `worstFrameMs` | `ceiling` | ≤ 32 ms, over a scripted scroll of 2,000 frames at rows 0, 50k and 90k |
| `medianFrameMs` | `ceiling` | ≤ 16.7 ms (the 60 fps clause), recorded and gated |
| `heapFirstPageMB` | `ceiling`, one page | ≤ 80 MB (§5.1) |
| `heapFullMB` | `ceiling`, all 100k | ≤ 250 MB (§5.1) |
| `layoutSubmitMs` | `ceiling` | the worker round trip per page — recorded, not gated, so a first-page miss is attributable in one line rather than re-derived |

`kira:first-paint` and `kira:layout-complete` already exist as marks in `App.vue` (P0 put them
there); `kira:layout-complete` changes meaning in this phase from "the placeholder mounted" to
"the first `LayoutChunk` has been applied and the canvas has painted", which is what it was
always a placeholder for, and the change is noted at the mark rather than silently.

Frame timing uses `requestAnimationFrame` deltas collected in-page during a scripted
`mouse.wheel` scroll, not CDP's tracing: the numbers are cruder and they are reproducible, which
is what a 20% gate needs. Heap follows `run.ts`'s existing collect-sample-median discipline —
a single `JSHeapUsedSize` reading is noise.

**Honest note, carried forward from P2's and P3's:** these are headless-Linux numbers on
container hardware. The 60 fps clause in particular is a *hardware* claim, and this sandbox is
not the mid-range laptop §5.1 names. The gate here catches regressions; the absolute claim is
closed on macOS with `bun run test:perf`, recorded as inherited-open the way P1's V2 and P2's V1
were.

**Done when:** every metric reports against a committed baseline; an injected 30% slowdown in
`renderer.paint` fails the frame metrics and an injected retained-array leak fails the heap
metrics; the heap numbers are within §5.1's ceilings or the miss is a Finding with the
attribution (store, layout buffers, DOM pool, canvas backing store) broken out.

## W16 — The density review against the native workbench list

§6.1's last paragraph makes this an explicit P4 obligation: "This is verified, not asserted: the
Playwright suite screenshots every surface in all four theme kinds … and **P4's review includes
a side-by-side against the native workbench list at the same density**."

It is a human review, and it is the one exit criterion no test can stand in for. The procedure,
so it is repeatable rather than a vibe:

1. Open a real VS Code with the extension loaded (`--extensionDevelopmentPath`), the panel
   showing our list and the Explorer or a Search result list visible in the sidebar.
2. Compare, at the same zoom and theme: row height, the vertical centring of text within a row,
   left padding, the hover and selection backgrounds and their inset, the focus outline's width
   and offset, font size and weight of primary versus secondary text, and icon size.
3. Record each mismatch with the token or metric that produces it, fix it in `density.css` or
   `vscode-tokens.css`, and re-check.
4. Capture the side-by-side screenshot and record the outcome in Findings.

**In this sandbox this cannot be run** — V3's VS Code download block is unchanged — so it is
carried forward as inherited-open with the command that closes it, exactly as P3 carried
`panel.spec.ts`. What *can* be done here and is: the same comparison against VS Code's published
list metrics (22 px rows, 20/26 px at the other density settings, the `list.*` colour ids we
already consume) as a static check, and a note that the eyeball half remains open.

## W17 — Verification tasks

Five assumptions this plan makes. V1 blocks nothing but should be run **before** W4 commits to a
worker; the others run alongside. Each gets a recorded answer under Findings.

**V1 — does a module worker load inside a VS Code webview, and under what CSP?**
`html.ts`'s current policy is `default-src 'none'; … script-src 'nonce-${nonce}';` and declares
no `worker-src`, which falls back through `child-src` to `default-src 'none'` — so as written,
`new Worker(...)` is blocked. Confirm the directive that admits it (`worker-src ${cspSource}` for
a bundled worker file, plus `blob:` if Vite inlines a small worker), confirm that a *module*
worker (`type: "module"`) loads from a `vscode-webview://` origin at all, and confirm the nonce
does not need to reach it. If module workers turn out to be unusable there, record it and take
W4's named fallback (chunked main-thread layout behind the same `LayoutClient` interface). This
is the one verification whose answer changes a work item's shape.

**V2 — the canvas and the scroll container at 100k rows.** Confirm in a real browser that a
spacer of 2.2 million pixels scrolls correctly (Chromium's own limits on element height and on
`scrollTop` precision), that `scrollTop` stays integral enough that `floor(scrollTop /
rowHeight)` does not drift at the bottom of the range, and that the viewport-sized canvas
approach has no visible seam during fast scrolling. Record the numbers: if a spacer that large is
unreliable, the fallback is a scaled scrollbar and it is much better to know now.

**V3 — `vue-tsc` and TypeScript 7, the check §8.3 schedules for this phase by name.** "Re-confirm
the `vue-tsc`/TS-7 state at P0 and again at P4 — this area is moving month to month, and it may
well already be resolved by P4." P0's V1 found `vue-tsc@3.3.11` hard-crashing on TS 7 and left
the repository with two TypeScript versions (root `7.0.2`, `packages/ui` `6.0.3` for `vue-tsc`).
Re-check whether a `vue-tsc` supporting TS 7 has shipped; if it has, the switch is a dependency
bump and the deletion of the second version, and doing it in this phase — the one that adds the
most `.vue` code — is worth more than doing it in any later one. If it has not, record the
version checked so P5 does not re-derive it.

**V4 — frame timing and heap in this sandbox, and what they are worth.** Establish what
`requestAnimationFrame` deltas and `JSHeapUsedSize` actually report on headless Chromium here
(a headless compositor may report a synthetic vsync), so W15's gate is calibrated against real
variance rather than against an assumed 16.7 ms cadence. Record the run-to-run spread the way
P3's W17 did for its timings — a baseline whose noise band is unknown is a baseline that fails
randomly.

**V5 — does the packed-chunk path survive the fix, end to end, on the real webview transport?**
W2 fixes the dictionary mark and W5 fixes the restart-at-zero handling, both asserted headlessly.
The half that only a real VS Code can show is the one §2.1 actually promises: hide the panel,
let the webview be destroyed, re-show it, and see rows — with authors — repaint from cache with
no `git log` spawn. `panel.spec.ts`'s second test already exists to watch it and is blocked by
the same download gap; note in Findings that this specific defect is why that test matters more
than its "chunk-source is cache" assertion suggests.
