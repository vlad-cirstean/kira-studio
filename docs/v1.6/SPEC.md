# Kira Studio — v1.6

v1.5 shipped the code intelligence subsystem as one cohesive chapter (`docs/v1.5/SPEC.md`, C1-C14).
This chapter returns to v1.1/v1.2/v1.4's own shape: six independent, unrelated phases across
existing modules, so it continues `P` numbering rather than taking a fresh letter — the same reason
v1.4's own opening paragraph gives for reusing `P` instead of picking a new one.

**Nineteen rows today**, up from the original six. P63's own planning pass (committed, not yet
implemented) found its implementation depends on two prerequisites, so this table now inserts them
ahead of it in landing order (P64, P65) rather than implementing P63 straight off its own plan. The
two code-review rounds `CLAUDE.md`'s process always closes a chapter with are now explicit rows

**Sequencing.** P60 (CodeMirror removal) goes first because two later rows plausibly touch editing
surfaces it will have already moved onto Monaco (P67's cell editor). P61 (dependency/runtime
upgrade) goes second, deliberately right after P60 rather than first or last: P60 already touches
`package.json` removing a whole dependency family, so doing the broader version bump immediately
after — on the tree P60 leaves, not before it — avoids two independent large dependency churns
landing at once. P62 is independent of every other row.

P63's plan is done and approved but its implementation is deliberately not next: P64 and P65 sit
between the plan and the build. P64 closes the one non-trivial repo-map MCP dogfooding entry P63's
planning pass logged (`docs/v1.6/mcp-repo-map-issues.md`) — `CLAUDE.md`'s own rule that a

else the server's existing tree-sitter graph could usefully answer, where "useful" means measurably

found during P64's own implementation, not part of its plan, so it gets its own row rather than

scratch fast — target is seconds, not minutes, on a repository this size — since that cost lands on

then implements P63's
already-approved plan twice, from the same starting commit, in isolated worktrees — once using the
