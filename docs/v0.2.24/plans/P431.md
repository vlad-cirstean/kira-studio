## Claude Code mechanism (verified, not guessed)

Checked against the installed CLI, Claude Code 2.1.316 (`claude --help` and the bundle at `/opt/claude-code/bin/claude`):

- Flag `--autocompact <auto|tokens>`, in `claude --help`: "Auto-compact window size (auto, or 100k–1M tokens)".
  Parser accepts `auto`, `500k`, `200000`, or `200` as shorthand; else "It must be 'auto', or between 100k and 1M".
  Bounds in the bundle: `Kx=1e5`, `d0=1e6`.
- Same knob as settings key `autoCompactWindow` (this repo's `.claude/settings.json` sets `350000`) and env
  `CLAUDE_CODE_AUTO_COMPACT_WINDOW`. Effective window is `min(model context window, configured)`.
- Resolver (`BS()` in the bundle) reads `CLAUDE_CODE_AUTO_COMPACT_WINDOW` first, then settings. The CLI's own
  `/autocompact` dialog says the env var "is set and takes precedence".
- `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` also exists (lowers the threshold by a percentage). Not used: the row asks for a
  limit, and the window is what `/autocompact`, the flag and the setting all name.

Decision: Claude maps stage setting `auto_compact_window` (whole tokens, 100000 to 1000000) onto `--autocompact <n>`.
Reasons: public flag in `--help`; scoped to the one process (not inherited by tools the agent runs); works for
`claude -p` and the TUI alike; lands in argv, so the op log command and the fake `claude`'s recorded `.args` show it.
An old CLI without the flag fails the launch loudly ("unknown option"), never silently.
Precedence vs a user-exported `CLAUDE_CODE_AUTO_COMPACT_WINDOW`: Claude Code's own rule applies; Kira does not strip
it. The implementer confirms the flag-vs-env order once by hand (step 7) and records the fact in ARCHITECTURE.

## Design

### Provider-keyed catalog (`internal/harness`)

New `internal/harness/stagesettings.go`:

```go
// StageSettingKind is a stage setting's value type. Only int exists today.
type StageSettingKind string

const StageSettingInt StageSettingKind = "int"

// StageSetting is one setting a provider takes per workflow stage. Key is the YAML and wire key.
type StageSetting struct {
	Key      string
	Kind     StageSettingKind
	Min, Max int
	// LabelKey and HintKey are i18n message keys; HintKey takes {min} and {max}.
	LabelKey, HintKey string
}

// StageValues are one provider's validated values, key to canonical text; nil or empty is provider default.
type StageValues map[string]string

// Parse returns the canonical value of v, false when v is not valid for s.
func (s StageSetting) Parse(v string) (string, bool)
```

- `Parse` for `int`: `strconv.Atoi(strings.TrimSpace(v))`, inside `[Min, Max]`, returns `strconv.Itoa(n)`.
- `harness.Provider` gains `StageSettings() []StageSetting` (every provider declares; empty means none). Only two
  implementers exist: `claude.Provider` and `fakeprovider.Provider` (embeds claude).
- `HeadlessSpec` gains `Stage StageValues` ("the step's values for this provider; nil = defaults").
  `InteractiveSpec` gains the same field. The provider alone maps keys onto its CLI, so flag knowledge stays in
  `internal/harness/claude` ("the only package that knows the claude CLI's flags").
- `internal/harness/providers/providers.go` gains a static catalog, same reason as `ConfigDirs` (validation runs
  without a registry):

```go
// StageSet is one provider's stage settings.
type StageSet struct {
	ID, Label string
	Settings  []harness.StageSetting
}

// StageCatalog lists every registered provider's stage settings in registration order; providers with none are left out.
func StageCatalog() []StageSet
```

### Workflow YAML (`adeflow`)

Shape, provider-keyed:

```yaml
  - id: implement
    name: Implement
    kind: agent
    ...
    settings:
      claude:
        auto_compact_window: 200000
```

Parse rules (`parse.go`), first error wins as today:

- `stepKeys`: add `"settings"` to agent, review and manual. Add `"settings"` to the not-allowed loop list in `step`.
- Manual: allowed only with `session: true`; else `settings is not allowed on manual steps without a session`
  (same shape as the prompt rule). Script steps: refused by the existing loop (`settings is not allowed on script steps`).
- New `func (v *validator) settings(n *yaml.Node, sp string) map[string]map[string]string`, with
  `var stageCatalog = providers.StageCatalog()` next to `agentConfigDirs`:
  - `n` must be a mapping: `settings must be a mapping`.
  - Each key must be a catalog provider id: `settings: unknown agent "x" (known: claude)`.
  - Each provider value must be a mapping: `settings.claude must be a mapping`.
  - Each inner key must be in that provider's settings: `settings.claude: unknown setting "x"`.
  - Each value: `Parse`; on false: `settings.claude.auto_compact_window must be a whole number from 100000 to 1000000`.
  - Empty provider mapping and empty `settings` mapping parse to no entry (dropped on save).
- `step()` initializes `Settings: map[string]map[string]string{}` and reads the block after `sandbox`, on every kind
  that allows it (manual: inside the `KindManual` branch, after `session`).

Writer (`writer.go`):

- `stepOrder`: insert `"settings"` after `"sandbox"`.
- New `applySettings(m *yaml.Node, s map[string]map[string]string)`: no non-empty provider block, `dropKeys(m, "settings")`
  (a file without the block stays byte-identical, `applySandbox` precedent). Else find or create the mapping
  (`put(m, "settings", ..., stepOrder)`), per provider in `StageCatalog()` order find or create its mapping, per key in
  catalog order `setScalar(pn, key, kInt, value, true, order)`, drop keys and providers no longer present.
- `applyStep`: call it for agent and review next to `applySandbox`; manual branch: when `s.Session`, else
  `dropKeys(m, "settings")`. `dropOthers` already removes it on a script step (not in `stepKeys`).

### Wire (`adewire`, frozen `wire.ts`, additive only per P143 rule 1)

`adewire/wire.go`:

```go
// WorkflowStep:
	// Settings are the stage settings per agent provider id, key to value; empty means every provider's defaults.
	Settings map[string]map[string]string `json:"settings"`

// StageSettingSpec is one setting the editor offers, from the provider catalog.
type StageSettingSpec struct {
	Provider      string `json:"provider"`
	ProviderLabel string `json:"providerLabel"`
	Key           string `json:"key"`
	Kind          string `json:"kind"` // "int"
	Min           int    `json:"min"`
	Max           int    `json:"max"`
	Label         string `json:"label"`
	Hint          string `json:"hint"`
}

// WorkflowsResult:
	// StageSettings is every stage setting the registered providers take, in provider then catalog order.
	StageSettings []StageSettingSpec `json:"stageSettings"`
```

`wire.ts`: `WorkflowStep.settings: Record<string, Record<string, string>>` (doc: "Per provider id, setting key to
value; `{}` = provider defaults."), `export interface StageSettingSpec { provider; providerLabel; key; kind: 'int';
min; max; label; hint }`, `WorkflowsResult.stageSettings: StageSettingSpec[]`.

No bridge method is added: the catalog rides on `WorkflowsResult` (`useWorkflows()`), as `sandbox` does. No change
to `bridge/index.ts`, `appwire.go`, `ipcChannels.ts`, `mockRuntime.ts`.

Nil safety: a task's workflow snapshot from before P431 unmarshals `Settings` as nil. Launch code reads nil as
none. Implementer greps every path that serializes a stored snapshot's `WorkflowStep` to the wire (`snapshotWorkflow`
readers); where one exists, fill `{}` before returning, so `wire.ts` stays non-null.

### Applied at launch (`ade`)

New `apps/kira-space/internal/ade/stagesettings.go`:

- `func stageValues(settings map[string]map[string]string, agent harness.Provider) harness.StageValues`: the block
  for `agent.ID()`, keeping only keys in `agent.StageSettings()` whose value passes `Parse` (an old snapshot never
  sends a removed key). Nil when none. A block for another provider is ignored, never an error (a workflow can be
  shared across providers; the parser already refused unknown ids).
- `func stepSettingsOf(tc *taskCtx, stepID string) map[string]map[string]string`: the step's settings in the task's
  workflow, nil when none (sibling of `stepResultsOf` in `launches.go`).
- `func (b *TaskBoard) stageCatalog() []adewire.StageSettingSpec`: from `providers.StageCatalog()`, label and hint
  through `i18n.T` (hint params `min`, `max` formatted with thousands separators via the existing number helper if
  one exists in `internal/i18n`, else plain digits).

Launch paths, all of them stage agent sessions:

1. Headless agent, smart-script and review-round runs: `stepDef` gains `Settings map[string]map[string]string`, set
   in `workflowSteps` (zeroed for script steps like `Sandbox`). `superviseAgent` sets `spec.Stage =
   stageValues(def.Settings, agent)` right after building `spec`. Rebase runs use a synthetic def without settings.
2. Manual step session (`LaunchStep`): `PrepareArgs` gains `Settings map[string]map[string]string`; set
   `pa.Settings = step.Settings`. `Tracker.Prepare` sets `InteractiveSpec.Stage = stageValues(args.Settings, agent)`
   after it resolved `agent` (active, `args.Provider`, or the resumed record's provider).
3. Review agent with a step (`launchReviewAgent`): both `PrepareArgs` literals get `Settings` from `step` when
   non-nil (resume and new).
4. Take over and restart of a step session (`takeOverLocked`, `RestartSession`): when the record has a `StepID`, set
   `Settings: stepSettingsOf(tc, rec.StepID)` on their `PrepareArgs` (load `tc` the way each already does; read both
   functions first).
5. Ad hoc sessions (`StartBranch`, no step): none.

`Compose` needs no change: `Prepare` builds the command, `Compose` checks it verbatim.

`Workflows()` (`board_writes.go`): `res.StageSettings = b.stageCatalog()` next to `res.Sandbox`.
