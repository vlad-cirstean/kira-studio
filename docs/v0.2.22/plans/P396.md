# P396 plan: three-finger swipe up moves focus to another Space

Spec row: Mission Control (three-finger swipe up) moves focus to another Space. Find cause, fix.

## Verdict on cause

Code alone does not determine the cause. Discovery (CodeGraph traces of every raise path, plus a
read of Wails `v3.0.0-beta.28` darwin sources) finds no app or Wails code that reacts to Mission
Control. Plan therefore lands permanent activation tracing plus a Mac protocol, then a fix chosen
by what the trace shows. Do not ship a speculative behaviour change without that trace.

### What can switch Spaces

macOS switches Space when the app activates or a window becomes key on another Space (default
Mission Control setting "When switching to an application, switch to a Space with open windows").
Only these calls activate or order a window front:

- Wails `windowFocus` (`$GOMODCACHE/github.com/wailsapp/wails/v3@v3.0.0-beta.28/pkg/application/webview_window_darwin.go:1098-1111`):
  `activateIgnoringOtherApps:` when inactive, then `makeKeyAndOrderFront:`.
- Wails `windowShow` (same file `:945-953`): `makeKeyAndOrderFront:`.
- Wails launch activate (`application_darwin.go:323-338`): once, at `ApplicationDidFinishLaunching`.
- Wails default reopen handler (`events_common_darwin.go:30-39`): shows hidden windows on
  `applicationShouldHandleReopen` (Dock click, relaunch). Not sent by Mission Control.

Window delegate callbacks (`webview_window_darwin.m:575-760`) and app delegate callbacks
(`application_darwin_delegate.m:90,150`) only forward events, and only when a listener exists. No
`collectionBehavior` override: `internal/shell/window.go:84-91` leaves `MacWindow.CollectionBehavior`
zero, so Wails sets `FullScreenPrimary` (normal).

### App paths that call Show/Focus

All go through `shell.WindowRegistry.Focus` (`internal/shell/registry.go:147-160`: `App.Show`
unhide, `win.Show`, `UnMinimise`, `Focus`). Grep confirms no other `.Show()`/`.Focus()` in Go and
no `@wailsio/runtime` window call in any frontend. Callers:

1. `prompts.Router.Open` auto-raise (`internal/prompts/router.go:198-226`): when the target window
   is not key and `RaiseOnOpen(kind)`; spawns `RevealKind` (`:273-297`). Studio only, kind `dbmcp`,
   gated by `dbMcp.focusOnApproval` (default true) — `apps/kira-studio/internal/appwire/wire.go:281-287`.
   Space passes no `RaiseOnOpen`.
2. Prompt notification click: `RevealKind` (both apps).
3. Space agent notification click: `Wired.revealNote` (`apps/kira-space/internal/appwire/wire.go:453-479`).
4. Space `AdeTaskService.FocusSession` (`apps/kira-space/internal/bridge/adetask.go:1015-1044`),
   called only from button clicks (`AdeTuiPane.vue:38`, `AdeReviewAgentPanel.vue:134`,
   `useNeedsAction.ts:28`).

Frontend focus listeners (`useWindowFocus` in `promptsQueries.ts:43`, `agentNotify.ts:23`,
`useReviewWorking.ts:57`, `AdeReviewFiles.vue:29`, `git-ui/src/App.vue:1661`) only refetch or
report focus; none reaches path 1-4.

### Ranked hypotheses

- H1 (only app-side candidate): path 1. Mission Control makes the Studio window non-key, so
  `Focused(target)` reads false; a DB MCP approval opening then raises the target window, and macOS
  switches to its Space. Fits when an agent is driving DB MCP with prompt-mode connections.
  `Focused` checks only the target window, so the raise also fires while the user works in another
  Studio window — same symptom outside Mission Control.
- H2: OS behaviour, no app call. On Mission Control exit macOS reactivates the app and picks its
  main window, which sits on another Space. Nothing in the app triggers it.
- H3: unknown activation from Wails internals not found above. The trace below exposes it.

## Steps

Stage A runs in this sandbox. Stage B needs the user on a Mac. Stage C picks the fix.

### Stage A — activation trace (implement now)

1. New `internal/shell/activation.go`: `AttachActivationTrace(app *application.App) (detach func())`.
   Register `events.Mac.ApplicationDidBecomeActive`, `ApplicationDidResignActive`,
   `ApplicationDidHide`, `ApplicationDidUnhide`. Each logs
   `slog.Debug("app event", "scope", "window", "event", <name>)`. Copy `wake.go`'s doc-comment
   point: registering is what makes the delegate post the event at all. Return one detach that
   calls every off func.
2. `internal/shell/window.go` `Attach` (`:149-182`): add per-window listeners for
   `events.Mac.WindowDidBecomeKey`, `WindowDidResignKey`, `WindowDidChangeOcclusionState`,
   `WindowDidChangeScreen`, `WindowDidChangeSpace` (may never fire: AppKit has no such window
   notification; keep it, cheap). Each logs `slog.Debug("window event", "scope", "window", "key",
   key, "event", <name>)`. Add each off func to the returned detach.
3. `internal/shell/registry.go` `Focus` (`:147-160`): after the `!ok` guard, log
   `slog.Info("window raise", "scope", "window", "key", key)`. Info, not Debug: raises are rare and
   are the one app action that switches Space.
4. `internal/prompts/router.go` `Open` (`:222-225`): inside `if raise`, log
   `slog.Info("prompt raise", "scope", "prompt", "kind", p.Kind, "target", <target key>)`. Compute
   the target once under the lock (it is already computed at `:210`; keep it in a local).
5. Wire step 1 in both mains next to `shell.AttachReopen`: `apps/kira-studio/main.go:194`,
   `apps/kira-space/main.go:177`. Discard detach like the neighbouring calls do, or add it to the
   same teardown they use if one exists.
6. `docs/ARCHITECTURE.md` "Known open items": add entry "Mission Control Space switch (P396)
   unconfirmed on macOS" with the Stage B protocol in two lines; delete once Stage C lands.
   Also add one line to the window-shell section: activation events trace at Debug (`scope=window`),
   raises at Info.

Commit: `fix(shell): trace app activation and window raises (P396)`.

No unit test: logging only (CLAUDE.md test bar). No flow test: no behaviour change.

### Stage B — confirm on a Mac (user, signed or `wails3 dev` build)

1. Settings → Advanced → log level `debug`. Logs live under `config.LogsDir()`
   (`<KIRA_HOME>/logs`, Studio; `<KiraSpaceHome>/logs`, Space).
2. Two Spaces. Space 1: one Kira window, focused. Space 2: another Kira window (same app).
3. Swipe up three fingers, wait 2 s, swipe down. Repeat 5 times. Then once with no window on
   Space 2. Then with Studio DB MCP running an agent against a prompt-mode connection.
4. Note the clock time of each jump. Send the log lines within ±2 s of each jump, plus the macOS
   version and whether "switch to a Space with open windows" is on.

### Stage C — fix by outcome

- `window raise` line at the jump, preceded by `prompt raise kind=dbmcp` (H1): change raise gating
  in `Router.Open`. Skip the raise when any app window is key; instead `Claim` the prompt to the
  key window so the popup shows where the user is. Add `FocusedKey() (string, bool)` to
  `prompts.Windows` (`router.go:17-22`), implemented on `shell.WindowRegistry` beside `AnyFocused`
  (`registry.go:209`), on `focusWindows` (`apps/kira-studio/internal/appwire/wire.go:296-302`) and
  on the flow fakes (`apps/kira-studio/internal/flowharness/shellfakes.go:215`,
  `internal/prompts/router_test.go` `fakeWindows`). During Mission Control no window is key, so
  also hold the raise while the app is active: track `ApplicationDidBecomeActive`/`ResignActive`
  from step A1 in an atomic bool, pass it as `Deps.AppActive func() bool`, and skip the raise when
  true. Feature test pair per CLAUDE.md: Studio `flows/promptflow` (or `dbmcpflow`
  `TestDbMcpApprovalFocus`) asserts no `Focus` and a claim to the focused key; UI half in
  `tests/ui/prompts.spec.ts` asserts the popup renders in the focused window. Update
  `docs/ARCHITECTURE.md:2309-2312` raise rules.
- `window raise` line from another caller (paths 2-4): fix that caller the same way; name it in
  the result.
- No `window raise` line, only `app event`/`window event` lines (H2): OS behaviour. No code fix is
  honest. Record in `docs/ARCHITECTURE.md` "Known open items" the OS setting that causes it and the
  user-side switch (System Settings → Desktop & Dock → Mission Control → "When switching to an
  application, switch to a Space with open windows for the application"). Ask the user before
  closing the row: they own any re-scope.
- An activation line with no app caller (H3): trace the Wails call; consider a Wails issue or
  option (e.g. `MacWindow.CollectionBehavior`). New plan iteration `P396-iter2.md`.

Stage C is a separate pass against this plan's outcome table; it needs Stage B data first.
