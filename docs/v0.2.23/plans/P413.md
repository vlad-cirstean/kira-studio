# P413 Review comment dialog: fix overflow and editing, compact gutter

Plan for `docs/v0.2.23/SPEC.md` row P413. Base: `b6c57df`. Discovery ran through `codegraph_explore`.

One sequential Sonnet implementer. No stream split: the overflow fix, the edit flow and the gutter all rewrite
`apps/kira-space/frontend/src/views/repo/reviewDecorations.ts` and `ReviewThread.vue`.

## User ask

"the comment dialog is very broken. It s longer than what i can see. I can t edit the messages. Also if making
changes there those gutter column eat a lot of space. What if the plus icon is replacing the line number, and the
hunk checkmark to be an actual empty row like line 1 then add the checkmark and the empty line and then line 2. If
it s not possible report back"

## Feasibility report

Relay this section to the user verbatim in the phase result (orchestrator: quote it in the hand-off).

**Plus replaces the line number: feasible.** Monaco 0.56 decorations carry `lineNumberClassName` and
`lineNumberHoverMessage` (public API, `monaco.d.ts`). The hovered line's number gets a class that hides the digits
and draws the `add` codicon in their place; a click on `GUTTER_LINE_NUMBERS` of that line opens the composer. A
commented line keeps its number, tinted with the comment colour; a click opens its thread. Tradeoffs:

- Clicking a line number in the review diff no longer selects the line (`selectOnLineNumbers: false`, right pane
  only). Dragging in the text still selects; "Mark selection reviewed" still works from the context menu.
- The hovered line's number is hidden while the pointer is on that line.
- Keyboard route unchanged: context menu "Add review comment".

**Hunk checkmark as its own row: feasible.** Each hunk gets a one-line Monaco view zone placed above its first
changed line (line 1, checkmark row, line 2). The checkmark sits in the zone's margin node, in the line-number
column; the rest of the row stays empty. A view zone is not a model line: line numbers, comment anchors
(`range.start`), mark ranges, next/previous change (`getLineChanges`) and `revealCommentLines` keep their
coordinates. The git-core `DiffRow`/`flattenDiffRows` row index belongs to the pure diff model, not to the Monaco
review diff, so nothing re-indexes. The diff editor already aligns the left pane to foreign view zones
(`diffEditorViewZones.js` `getAdditionalLineHeights`), so side by side stays aligned. Monaco virtualizes zones
itself; no row bookkeeping on our side. Tradeoffs:

- One extra line of height per hunk: vertical space traded for width.
- With both ideas the glyph margin goes away entirely, on both panes (`glyphMargin: false`). The gutter is then
  line numbers plus Monaco's +/- indicator column (and folding, unchanged). The implementer records the measured
  `layoutInfo.contentLeft` before and after in the phase result.
- A pure deletion hunk still has no checkmark (no new-side line; same as today).

Verdict: both proposals ship in this phase. Nothing is declined.

## Findings (current tree)

### Where the "dialog" lives

- Review window centre tabs open `views/repo/RepoDiffView.vue` (also the git module's review diff tabs). For a
  review tab it calls `attachReviewDecorations(mod, editor, deps)` (`views/repo/reviewDecorations.ts`) on the
  modified pane of a read-only Monaco diff editor built by `useDiffEditor.ts`.
- The comment "dialog" is `ReviewThread.vue`, mounted with `createApp` into an `IViewZone` domNode by `openZone`
  (`openCompose` for a new comment, `toggleThread` for an existing one). Modes: `view`, `compose`.
- Gutter: `paint()` puts hunk state in `GlyphMarginLane.Right` (`kira-review-glyph-actionable`/`-reviewed`),
  comments and the hover "add" glyph in `GlyphMarginLane.Left` (`kira-review-glyph-comment`/`-add`), and a
  placeholder `kira-review-lane` on line 1 reserves the Left lane. `useDiffEditor` passes `glyphMargin: true` to
  the diff editor (both panes get the margin; the left pane never uses it). CSS:
  `packages/theme/src/review-decorations.css`.

### Overflow root causes

1. Height uncapped: `openZone` measures `firstElementChild.scrollHeight` once and sets `heightInPx` to it. A long
   body or reply makes the zone taller than the editor viewport. The root's `overflow-auto` never scrolls because
   the box is exactly as tall as its content.
2. Width: a view zone's domNode spans `.lines-content`, which is the scroll width (longest line). In a file with a
   long line the box runs past the pane; its `justify-end` buttons sit off screen and the box scrolls sideways with
   the code.
3. Wheel: the zone lives inside Monaco's scrollable element, whose wheel handler calls `preventDefault`. Even a
   capped inner box could not scroll by wheel.
4. Measured once: typing, `resize-y` on the Textarea, or switching mode never re-lays the zone out; content
   clips or overlaps the next lines.

VS Code's `ZoneWidget` (`monaco-editor/esm/vs/editor/contrib/zoneWidget/browser/zoneWidget.js`) solves all four:
an empty view zone reserves the vertical space; the content lives in an overlay widget (outside the scrollable
element and outside `.lines-content`), positioned by the zone's `onDomNodeTop`/`onComputedHeight` callbacks, width
`layoutInfo.width - minimap - verticalScrollbarWidth`, height capped at `max(12 lines, 80% of editor height)`.

`ZoneWidget` itself is not public API (absent from `monaco.d.ts`, constructor takes the internal `ICodeEditor`
and its subclasses need internal services). Declined as an import for that reason; port its mechanics through the
public `IViewZone` + `IOverlayWidget` pair, about 60 lines.

### Editing root causes

1. No edit exists. Wire has `review.comment.add/list/remove/setState/clear/export`; `ReviewThread` view mode offers
   only state, close, delete. Store has `updateComment` (used by `SetCommentState`, `ReplyComment`, `MarkSent`).
2. Suspected: keystrokes in the compose Textarea bubble to Monaco's keybinding listener on the editor container
   (arrows, Home/End, select all, find). Not proven. The implementer reproduces it first with a keyboard-driven UI
   test (below); the fix ships only if the test fails without it. Report which in the result.
3. Every thread action swallows its failure (`logError` only). A refused add looks like "nothing happens".
4. Composer never takes focus on open.

## Design

### 1. Wire: `review.comment.edit` (contract 55 → 56, additive)

- `packages/git-ipc/src/contract.ts`: `'review.comment.edit': { params: { repoId; branch; id: number; body:
  string; kind: ReviewCommentKind }; result: { readonly changed: boolean } }`. Doc: replaces body and kind; keeps
  range, anchor, state and reply; clears `sentAt` (the edited text was never sent). `changed` false when the id
  matches nothing.
- `validate.ts`: method set entry, `CONTRACT_VERSION = 56` with a dated comment like P392's. Go
  `gitrpc/contract.go`: `ContractVersion = 56`, same comment. `TestContractVersion_Is55` → `_Is56`. Grep both
  sides for other version or method-count asserts and update them.
- `gitrpc/wire.go`: `ReviewCommentEditParams{RepoID, Branch, ID int64, Body, Kind}`, `ReviewCommentEditResult{Changed}`.
- `gitrpc/comments.go` `handleReviewCommentEdit`: same validation as add/setState: `requireNonEmpty repoId`,
  `validRefArg branch`, `id > 0`, kind `change|question` (required), `normalizeCommentBody`, empty →
  `backend.space.gitrpc.commentEmpty.body`, `> MaxCommentBytes` → `commentTooLong`. Register in `handlers.go`.
- `gitsession/comments.go` `RepoEntry.EditComment(ctx, branch, id, body, kind) (bool, error)`: store call plus
  `Touch`, like `SetCommentState`.
- `gitreview/comments.go` `Store.EditComment`: `updateComment(ctx, repoID, branch, "body = ?, kind = ?, sent_at =
  NULL", []any{body, kind}, id)`.
- `frontend/src/repo/git/transport.ts` `COMMENT_MUTATION_METHODS` gains `review.comment.edit`, so every open review
  surface repaints.

### 2. Thread as a zone widget (overflow fix)

`reviewDecorations.ts` replaces `openZone`/`closeZone` with one `ThreadWidget` built on public API:

- Spacer `IViewZone`: empty `domNode`, `afterLineNumber`, `ordinal: 0`, `heightInPx`, `onDomNodeTop: top =>
  overlay.style.top = top + 'px'`, `onComputedHeight: h => overlay.style.height = h + 'px'`.
- `IOverlayWidget` (`getId`, `getDomNode`, `getPosition: () => null`): the Vue app mounts here. Width and left
  from `modifiedEditor.getLayoutInfo()` (`width - minimap.minimapWidth - verticalScrollbarWidth`, left 0), updated
  on `modifiedEditor.onDidLayoutChange`. Before the first `onDomNodeTop` call, `top = -1000px` (ZoneWidget does the
  same). Check in the pinned `viewZones.js` whether `onDomNodeTop` fires when the zone leaves the viewport; if not,
  hide the overlay on `onDidScrollChange` when the zone's top is outside `[0, layoutInfo.height]`.
- Height: `min(contentHeight, maxHeight)` where `maxHeight = max(12 * lineHeight, 0.8 * layoutInfo.height)`;
  recomputed on layout change. Floor: content height (never below it while under the cap).
- `ReviewThread.vue` root becomes a scroll box (`h-full overflow-auto`) around an inner content element. VueUse
  `useResizeObserver` on the inner element emits `resize(height)`; the widget sets `heightInPx` and calls
  `layoutZone`. No one-shot `nextTick` measurement. Wheel scrolls the box natively (overlay is outside Monaco's
  scrollable element).
- Keep the z-index 10 only if hit tests still need it on the overlay; drop `VIEW_ZONE_Z_INDEX` for the thread if
  not (overlay widgets sit above view lines).
- Textarea: VueUse `useTextareaAutosize` (grows with content; the box scrolls past the cap); drop `resize-y`.
  Focus the Textarea when compose or edit opens (`useFocus` or `nextTick` focus).
- Keys: if the keyboard test (section Tests) fails, stop `keydown` propagation at the thread root after the
  component's own handlers (`form.submit` stays bound on the Textarea via `useShortcut`). Escape cancels compose or
  edit, closes view mode.
- Errors: thread actions become async callback props returning `Promise<string>` (`''` on success, else
  `errorText(err)`), not fire-and-forget emits. The thread shows a non-empty result in an `Alert variant="error"`
  and stays open; success closes or returns to view as below. `logError` stays.

### 3. Edit a comment from its thread

- `ReviewThread.vue` modes: `view | compose | edit`. View mode gains an Edit button (`common.action.edit.label`,
  `pencil` codicon, `data-testid="review-thread-edit"`). Edit mode reuses the compose form (kind
  `SecondaryTabs` + Textarea) prefilled from the comment; Save (`common.action.save.label`,
  `review-thread-save`) and Cancel. Empty body disables Save.
- `reviewDecorations.ts`: the open thread's comment lives in a `shallowRef<ReviewComment>`; the app renders
  `h(ReviewThread, { comment: openComment.value, … })`. `loadComments` replaces it with the fresh object of the same
  id, so after the repaint the thread shows the saved text in view mode. Gone id → close (existing rule).
- `handleEdit(comment, body, kind)` → `review.comment.edit`; success returns `''` and the component switches back
  to view; the repaint fan-out reloads.
- Agent reply and state stay. Any comment is editable (all local comments are the user's own; the reply is
  read-only).
- Panel lists (git-ui Review pane, `AdeWorkflowReviewPanel`) stay read-only; their path link opens the diff where
  the thread edits.

### 4. Compact gutter

- `useDiffEditor.ts`: review variant passes `glyphMargin: false` (explicit, per the existing 0.56 default note).
  `attachReviewDecorations`: `modifiedEditor.updateOptions({ glyphMargin: false, selectOnLineNumbers: false })`.
- Drop `laneCollection`, every `glyphMargin*` option and the `GlyphMarginLane` click branch.
- Add mark: `addGlyphCollection` on `hoverLine` sets `lineNumberClassName: 'kira-review-ln kira-review-ln-add'` and
  `lineNumberHoverMessage: addComment.tooltip`. Comment: `commentCollection` sets
  `lineNumberClassName: 'kira-review-ln kira-review-ln-comment'` and `lineNumberHoverMessage:
  commentHoverMessage(c)`.
- Click: `onMouseDown` on `GUTTER_LINE_NUMBERS`: comment on that line → `toggleThread`; else `hoverLine === line`
  → `openCompose`.
- CSS (`review-decorations.css`, Monaco class names need global CSS, not Tailwind): `.kira-review-ln` pointer;
  `.kira-review-ln-add` hides digits (`color: transparent`) and draws the codicon `add` glyph centred via
  `::before` (`font-family: codicon`, content of `codicon-add`), muted, `--kira-fg` on hover; `.kira-review-ln-comment`
  keeps digits, `--kira-info` colour with a subtle tinted background. No width change on hover.
- Hunk rows: per hunk with a `hunkChangeBlock`, one view zone `{ afterLineNumber: block.start - 1, heightInLines: 1,
  ordinal: 1, domNode: empty div, marginDomNode }`. The thread's `ordinal: 0` keeps a thread directly under its line
  when both follow the same line; Monaco's inline deleted-lines zones (default ordinal) come after. `marginDomNode`
  hosts a `createApp` of new `ReviewHunkMark.vue` (`<script setup lang="ts">`): theme `TooltipIconButton`, icon
  `pass-filled` (reviewed, `--kira-ok`) or `circle-large-outline` (actionable, `--kira-accent`), label
  `common.markUnreviewed.tooltip`/`common.markReviewed.tooltip`, `data-testid="review-hunk-mark"`,
  `data-state="reviewed|actionable"`, click → `mark(block, !reviewed)`. Margin node gets z-index 10 if the click
  does not land otherwise (verify in the UI spec).
- `paint()` diffs hunk rows by `block.start`: remove all and re-add inside one `changeViewZones` call, unmount the
  old apps. `dispose()` removes the zones and unmounts the apps. `hunkByLine` stays for the context menu path only
  if still used; delete if not.
- `app.use(i18n)` at both new `createApp` sites (ARCHITECTURE rule).

Libraries: shadcn-vue (`Button`, `Textarea`, `Alert`, `TooltipIconButton` from theme), VueUse
(`useResizeObserver`, `useTextareaAutosize`, `useFocus`), Tailwind classes in Vue templates, global CSS only for
Monaco decoration class names. No Pinia store: no shared client state (thread state is per editor). No TanStack
Query: the review layer talks to the git transport directly with its own sequence guards; unchanged.
