# P411 Task statuses: move to Workflow page, fully customizable

Plan for `docs/v0.2.23/SPEC.md` row P411. Base: `669de96`. Discovery ran through `codegraph_explore`.

One sequential Sonnet implementer. No stream split: migration, model, engine, wire, frontend editor and
tests form one chain (the editor reads the new wire; the UI spec reads the flow test's contract).

## User ask

"The task statuses should be in the workflow page not settings and I don't understand the mapping and
the hardcoding of it. App comes with some defaults sure but they should be totally customisable, have
more color options, and of course if I change them for an existing work item it is what it is."

## Findings (current tree)

### What the "mapping" is today

Three hidden layers decide a task's status. None is visible in one place.

1. **Categories.** Each status row carries `category` (`todo | active | review | done`), shown in
   Settings as "Counts as". Every category needs at least one status, so the last status of a
   category cannot be deleted (`lastOfCategory` disables the button; `normalizeSet` refuses the save).
   The user never sees what a category does.
2. **"First status of a category" picks.** Automation never names a status. It asks for "the
   lowest-position status of category X":
   - new task: first `todo`; new review task: first `review` (`repos/adetask.go` `insertTask` via
     `firstStatusOf`);
   - review task turned into a task: first `todo` (`UpdateTask`);
   - task back at its first step with nothing run: first `todo`; workflow finished: first `done`
     (`ade/status.go` `syncStatus`);
   - step whose own status left the set: first `review` (review step) or first `active`
     (`resolveStepStatus`);
   - deleted status without a reassign entry: first kept status of its category (`reassignRemoved`).
   So reordering statuses or flipping "Counts as" silently changes what automation does.
3. **Per-step status in workflow files, with hardcoded seed ids.** A step has `status` (inspector
   select in `AdeStepAdvanced.vue`, with an "Edit statuses" link that jumps to Settings). A step that
   omits it gets `in-progress`, or `in-review` on a review step: `adewire.DefaultStatus`,
   `StatusInProgress`, `StatusInReview` (`bridge/adewire/results.go`), mirrored in the frontend
   (`board/workflowForm.ts` `kindDefaults`, `withKind`). The writer drops `status` when it equals that
   default (`adeflow/writer.go` `applyStep`). If the user renames or deletes the seed `in-progress`,
   the "default" keeps pointing at an id that may not exist and falls through to layer 2.
   `adeflow/parse.go` `legacyStatuses` maps pre-P379 names ("In progress") to seed ids.

Frontend repeats layer 2: `board/status.ts` `statusOf` (unknown id → first of `todo`/`review`),
`board/panelFacts.ts` `statusWhy` (`category === 'todo'` means "not started"), `AdeStepAdvanced.vue`
`missingLabel` (fallback by category).

### Colours

Six tones (`amber red green blue purple grey`), shared with action/state tones (`board/actions.ts`
`Tone`, `tones.ts`, literal values in `tones.css` pinned by `scripts/check-ade-colours.sh`). The status
colour feeds the task tag (`actions.ts` `tag.tone = i.status.tone`), `AdeTaskPanel.vue` `tone`, the
Settings swatch, mobile `PlanTaskCard.vue` chip. Coupling status colour to state tones is why there are
only six.

### Not coupled to status (checked, no change)

Board lanes and P405 shelves (Plan/Later/Backlog: `ade_task_plan`, no status read), Needs-you
(`needs/*`: own tones, no status), P407 handover/stage dialogs (workflow steps, not statuses), P408/P409
MCP tools (`agentmcp.TaskInfo` has no status), prompts (no status text). Mobile only displays status
(`useAgentsModel.ts` `statusOf`, `PlanTaskCard.vue` chip); mobile has no status write.

## Design

### Model: status = label; automation names statuses explicitly

- A **status** is `id` (stable slug, never shown), `name`, `color`, `position`. No category, no flags.
  Kira reads no meaning into a name, colour or position.
- **Automatic changes** ("status defaults") are four explicit slots stored beside the set. Each names
  one status or is empty = "Keep current status".

  | slot | when it applies | empty means |
  |---|---|---|
  | `new` | task created; review task turned into a task; task back at its first step with nothing run | not allowed: required |
  | `step` | a non-review step starts and the step sets no status of its own (or its status was deleted) | keep current |
  | `review` | a review step starts with no own status; a review task is created | keep current (review task created: `new`) |
  | `finished` | the workflow finishes | keep current |

- A workflow step's `status`: `""` = use the slot of its kind (`step` or `review`); an id = that
  status. Id no longer in the set → slot of its kind.
- Why slots and not open/active/done flags: the app logic reads status at exactly these four moments
  and nowhere else. Flags would recreate the hidden "first status that has flag X" rule. Slots make
  each automatic move a visible select the user sets directly. No invented semantics (no cancelled).
- Migration preserves behaviour exactly: each slot is seeded with the status today's rule picks
  (first by position of the matching category), so no task changes on first launch and
  `syncLiveStatuses` finds nothing to move.

### "It is what it is"

- Tasks store `status_id`. Rename or recolour a status: only display changes. Reorder: only picker
  order and Back/Next order change.
- Changing a slot or a step's status never touches existing tasks. A slot applies at the next
  automatic moment only (sync already fires only when the position key changes, `syncStatus`).
- Tasks already started keep their frozen `workflow_json`; a step there that resolved to `in-progress`
  at parse time stays explicit. Accepted, same rule.
- Manual move holds until the next step change (unchanged).

### Deleting a status (decision)

A task must always show a real status (no SQL FK; an orphan id renders as a broken chip). So delete
**requires an explicit target**: every removed id needs a `reassign` entry, for live and archived tasks
alike (the server cannot know the frontend's archived count, so the rule is unconditional). No silent
category fallback. Blocking delete until the user moves tasks by hand was rejected: same outcome, many
more clicks.

- Delete always opens a confirm dialog: "Move its tasks to: [select]". Body lists what uses it: live
  task count, default slots naming it, workflow steps naming it (counted from `useWorkflows` data).
- Slots naming the removed status move to the chosen target in the same save. Workflow files are not
  rewritten; their steps fall back to the slot of their kind, and the step inspector flags them.
- Last remaining status cannot be deleted (min 1, max 20 unchanged).

### Storage: migration `0059_p411_ade_task_status_defaults.sql`

- Rebuild `ade_task_statuses` (SQLite cannot alter a CHECK): new table `(id TEXT PRIMARY KEY, name
  TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 40), color TEXT NOT NULL CHECK (color IN (<16>)),
  position INTEGER NOT NULL)`; `INSERT ... SELECT id, name, tone, position`; drop old; rename.
- `CREATE TABLE ade_task_status_defaults (slot TEXT PRIMARY KEY CHECK (slot IN
  ('new','step','review','finished')), status_id TEXT NOT NULL)`. Absent row = keep current.
- Seed in the same file, before the drop (needs `category`): for each (slot, category) pair
  (`new/todo`, `step/active`, `review/review`, `finished/done`) insert the lowest-position id of that
  category (`ORDER BY position, id LIMIT 1`, same tie-break as `listStatuses`).
- Register version 59 in `internal/storage/migrations/embed.go`.
- Migration test `internal/storage/migrations/migrate_ade_task_status_defaults_test.go` (pattern of
  `migrate_ade_task_statuses_test.go`): a customised 0058 set (reordered, renamed, two `active`
  statuses, a status with `tone=purple`) migrates to colours by name and slots by first-by-position.
  Earns its keep: data derivation with a tie-break rule.
