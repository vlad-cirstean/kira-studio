# Kira Studio — v1.4

v1.3 shipped **git** as a third top-level subsystem, headless: a Go backend inside Kira Studio and
a separately-installed VS Code extension as its frontend (`docs/v1.3/SPEC.md`, G1-G34).

This chapter has no equivalent headline. It is six independent phases across modules that already
exist — test-suite cost, an Api import path, two SQL-editor gaps, one git-extension feature, and a
visual-regression tier. Nothing here is a port of one subsystem, and no row depends on another
row's code.

**Numbering: P1-P6, restarting at P1.** v1.1 and v1.2 each restarted the same way, since neither
continued the previous spec's list. v1.3 broke from that and used `G1…` for one reason it stated
itself — the whole chapter *was* the git subsystem, so the phase list and the subsystem were the
same thing. That reason does not hold here, so the `P` prefix default returns.

**Six rows is where this chapter opens, not where it ends.** The table accrues rows as phases land,
the same convention `docs/v1.1/`, `docs/v1.2/` and `docs/v1.3/` each state for their own. A later
row may also re-scope an earlier one's edges once that phase's plan reads the current tree.

`docs/ARCHITECTURE.md` is authoritative for how the app actually works today; this file records
only this chapter's phases, one row each. Every row gets its own Opus-authored plan under `plans/`
before implementation starts, per `CLAUDE.md`. None is written as part of this spec.

## Phasing

| Phase | Deliverable | Why here |
|---|---|---|
| **P1 Test-suite speed** | Measure, then cut, the wall-clock cost of every suite this repo runs, and merge genuine duplication. No baseline exists to cut against: `docs/PERF.md` tracks app-level budgets and has never recorded suite duration, so establishing one is step one. What the tree shows going in. **Go** (`bun run test:go` = `go test ./...`): 1596 `Test*` functions across 259 `_test.go` files, and **not one `t.Parallel()` anywhere** — packages run concurrently, every test inside a package runs serially. Container fixtures are already well handled (`internal/adapters/testsupport`: one container per test binary, memoized by `fixture.go`, started concurrently by `Prewarm`), but a test *binary* is a process — `internal/ipcfixture` starts mariadb, mysql, clickhouse, redis, sqs and kafka a second time beside `internal/adapters/*`'s own six, in the same `./...` run. `-race` over the full tree takes real minutes (`docs/v1.3/SPEC.md`'s own "Full verification scope" note). **`tests/ui/`**: 248 tests, 47 spec files, real WebKit against the real built bundle, `fullyParallel` — but `ui-timing` (4 wall-clock tests, `workers: 1`) declares `dependencies: ['ui']`, so it waits for all 248 before its own ~4 start, and `slick-grid.spec.ts` alone is ~110s (`playwright.config.ts`'s own comment). **Bun**: 73 specs in `tests/unit/` plus 45 in-source `*.test.ts` under `packages/`/`apps/kira-studio-vscode/`. **`tests/ipc/`** 6 frontend specs, **`tests/e2e-real/`** 4 specs/6 tests, **`apps/kira-studio-vscode/tests/`** 2 Playwright projects. **CI** (`.github/workflows/ci.yml`): four jobs, three of them `needs: checks`, so nothing starts until lint, typecheck, build, `test:go` and `verify:packaging` all finish; `bun run test:go` then runs twice (macOS `checks` with no Docker, ubuntu `container-tests` with it), and only the `darwin && cgo` files make the macOS run more than a subset; `scripts/setup.sh` regenerates bindings in three separate jobs; `test:ipc:fe`, `test:webview`, `test:e2e-real` and `test:matrix` run in no CI job at all. Merging coverage is in scope but bounded: `CLAUDE.md` exempts `internal/adapters/*/*_test.go` from the sparse-unit-test bar and keeps them per-capability, and the P25 general/complete split stays — prune genuine duplication there, nothing more; the 73 + 45 TypeScript specs against `tests/ui/`'s 248 are the likelier overlap | Every later phase pays this cost on every loop, so it earns the most by landing first. `CLAUDE.md`'s "implement the whole plan, then test once and fix what's found" rule exists *because* the expensive suites are expensive — that rule is a workaround for exactly what this phase attacks |
| **P2 Api: import collections from Postman's own local storage** | Import Postman collections with no export step, from Postman desktop's own on-disk LevelDB store, behind a new menubar entry beside today's. Today's import is file-based end to end: `internal/shell/menutemplate.go`'s *Import Postman Collection…* emits `ChannelImportPostman`, `App.vue` switches to Api mode and opens a file chooser, `CollectionsService.Import` receives **only a path** (never the bytes), `postman.Parse` reads the chosen `.json`, and `CollectionsRepo.ImportTree` writes it to `kira.db` with `origin_json` preserved for round-trip fidelity (v1.2 P4). This phase replaces the *source*, not the pipeline: locate Postman's local store, decode it into the same `postman.Tree`, hand it to the same `ImportTree`, so storage, Postman-format fidelity and the existing warning report are untouched. Prior art for reading another tool's own state directly is already in the tree and should be followed: `internal/datagrip` (v1.2 P25) locates a JetBrains config directory under the user's home (`configdir.go`), parses it (`Scan`), and sends only a path across the bridge. **The LevelDB key and record layout is real reverse-engineering, not specified here** — the legacy Postman desktop app kept local Scratchpad collection/environment records in LevelDB, but the exact key shape, record encoding and version skew must be established against a real Postman installation at this phase's own Opus planning pass, which also picks the Go LevelDB reader (there is no LevelDB dependency in `go.mod` today) and decides the behaviour when the store is absent, locked by a running Postman, or a version this app has not seen. **Dropped after planning, before completion.** A real plan (`docs/v1.4/plans/P2-postman-leveldb-import.md`, reverted with the rest of this row's work) and a partial implementation (`internal/postmanstore`, also reverted) established what the LevelDB reverse-engineering above actually requires: Postman's local records are not JSON but Chromium `SerializedScriptValue`-encoded JS objects, so reading them means decoding both the IndexedDB-over-LevelDB key/value coding scheme *and* a working subset of Blink/V8's own value serializer, on top of a Postman Collection Format v1→v2.1 conversion — real, scoped, buildable work (an estimated few hundred lines once narrowed to the plain-data tags a collection actually needs), but judged too much complexity for the value one menubar import action adds. `go.mod` gained and then lost `github.com/syndtr/goleveldb` and `github.com/cions/leveldb-cli` across this row's commits and its revert; see git history for the full researched plan and the reverted code | Independent of every other row. The expensive half — faithful Postman-format modelling, storage, the tree UI — already exists and is unchanged, so the phase is locate, decode, map. Removing the export step removes the one manual act between a user's existing collections and this app |
| **P3 SQL formatting for the remaining SQL editors** | **Library decision, made here rather than deferred: keep `sql-formatter`.** It is already a dependency (`15.8.2`) and already the formatter behind the query console's Format button (v1.1 P13, revised P19 D13 and P22b D12) — `views/console/format.ts` splits with the same splitter *Run all* uses and calls `formatDialect` per statement, through `views/console/sqlFormatterEntry.ts`'s lazy chunk (~37 KB gzip, tree-shaken to the five dialects this app speaks). Two alternatives compared and declined. CodeMirror's own `@codemirror/language` `indentService`/`indentOnInput` over `@codemirror/lang-sql`'s Lezer tree would integrate more natively, but it re-indents lines and never re-wraps or normalizes a statement — indentation is not formatting. Prettier with `prettier-plugin-sql` adds a second formatter runtime whose own default backend is `sql-formatter`, so it buys nothing this app does not already have. The deliverable is therefore coverage, not a swap: bring formatting to the SQL editing surfaces that still have none. The concrete one found in the tree is `project/SchemaDialog.vue` — the per-connection DDL document (v1.1 P18 D3) — which mounts `CodeMirrorHost` with `:autocomplete="false"`, registers no `view.format` command and has no Format affordance, even though the console, gRPC beautify, the menubar *Format* entry and the global Shift+Alt+F chord all already exist. Audit for any other SQL-bearing editor in the same state while there. **This session's P3 slot went to a real bug hunt in the query console instead** — reported as Format producing unusable output (sql-formatter's clause-per-line style even for a trivial `select * from products`) and, separately, a confirmed real bug (Format immediately after typing, then Cmd+Z, wiped the whole query — CodeMirrorHost's external-sync dispatch had no `isolateHistory` annotation, so `history()`'s own `newGroupDelay` merged it into the adjacent typing's undo group; fixed). The style complaint's own fix was implemented, then reverted at the user's explicit request (made without sign-off) — see git history around that revert for what it would have done. **The `SchemaDialog.vue` coverage gap this row originally scoped stays open**, unstarted, a candidate for a later phase | Small, self-contained, and the one decision it carried (which library) the tree already answers. Pairs with P4: both close gaps on the same editors, so one pass over `SchemaDialog.vue` serves both |
| **P4 SQL editor autocomplete from cached table/column metadata** | Close the cases the console's schema-aware completion does not reach, and converge it with the data view's. **The data-view filter autocomplete** is `views/grid/filterCompletion.ts` (v1.1 P18 D7/D8): `FilterToolbar.vue`'s WHERE/ORDER BY boxes read `runtime[tabId].meta.columns` — the L1-cached `kira:tree:describe` result for the relation the tab is open on, authoritative because it includes columns the current projection hides — fall back to the loaded page's own columns when `describe()` errored, quote each identifier dialect-correctly only when it needs it, and render through `theme/primitives/completion`, not CodeMirror. **The SQL editor's own autocomplete** lives in `views/console/completion.ts` and `views/console/sqlLanguageService.ts`: layered, DDL document first, then cached columns (P22c D4), then bare tree relation names, over `@codemirror/lang-sql`'s `schemaCompletionSource`/`keywordCompletionSource`; `state/schemaColumns.ts` holds the cache, filled from `control.treeSchemaColumns` on the view's own lifecycle hook (never from a `CompletionSource`, never on a keystroke) and dropped on reconnect and on an explicit tree Refresh (P24 D10). **The real gap is the key.** That cache is keyed by `containerPathFor` — the console tab's path walked back to its last `database:`/`schema:` segment. A console opened at the connection root has `path === ''` (`OperationsPanel.vue`'s new-console action passes exactly that, and `openConsoleTab` substitutes a real path only for a Postgres connection with a session-remembered *Set as default*), so `containerPathFor` returns `null`, `ensureSchemaColumns` never fires, `cachedRelationsFor` returns `[]`, and that console falls all the way through to lang-sql's keyword source with no table or column name in it. Give a root-opened console the same cached completion a container-scoped one gets, give `SchemaDialog.vue`'s DDL editor completion at all (P3 touches the same component), and fold the two candidate builders over the same cached column metadata together wherever they genuinely overlap rather than leaving two implementations | The mechanism exists and is well-designed; what it lacks is reach. Closing a gap inside it costs far less than the second completion path a fresh implementation would leave behind, and the root-opened console is a normal way to open one, not an edge case |
| **P5 Git extension: status-bar blame widget** | A status-bar item showing the commit that last touched the active editor's current line — author, age, summary — click-through to the commit it names. **Reused, all shipped in v1.3**: the extension already creates and owns one `vscode.StatusBarItem` (G10 D16, `apps/kira-studio-vscode/src/extension.ts`), today carrying connection state and G12 D10's debounced in-flight indicator, so status-bar lifecycle, theming and disposal are solved; `commit.detail` (G4) already renders a commit and is the natural click target; `commit.resolvePr` (G24) already answers "which PR does this commit belong to", per-commit rather than per-branch-tip, which is exactly the shape a blame line needs; `packages/git-ipc`'s contract plus `internal/gitrpc`'s handler table is the surface a new method lands in. **New, and checked: no blame path exists anywhere.** A tree-wide search for `blame` across `apps/`, `packages/` and `docs/ARCHITECTURE.md` returns one unrelated hit. So this phase adds a real `git blame` run through `internal/gitclient`'s streaming runner, a porcelain parser beside `gitclient/porcelain`'s existing ones and guarded the same way theirs are (the committed golden-byte corpus — a blame porcelain parser is squarely the "several interacting rules" case `CLAUDE.md`'s testing bar exists for), a new contract method with the `CONTRACT_VERSION` bump it implies (33 today), and the extension-side line tracking — active editor, cursor line, invalidation on edit, on save and on `repo.changed` — which has no analogue in the extension today. Whether blame is computed per-line on demand or per-file incrementally, and how a dirty buffer's line numbers map back to committed lines, are design questions for this phase's own planning pass | Builds only on infrastructure v1.3 already shipped and proved, and adds the first git capability that needs a genuinely new `git` command rather than another view over the existing log/graph pipeline — which is what keeps it a standalone phase instead of a follow-up inside another |
| **P6 Visual regression testing across pages and modules** | Fast, reliable pixel-level regression coverage for every page and module. **Nothing does pixel comparison today.** `tests/ui/` (248 tests, real WebKit, the real built bundle, both wire planes mocked) asserts DOM, geometry and computed styles; its single screenshot is `mode-switch.spec.ts`'s ink measurement (P22 D5 — decode a PNG, count ink, no baseline image). `apps/kira-studio-vscode/tests/layout` asserts real `getBoundingClientRect()` box heights, which is the answer G16 landed after a shipped build rendered a graph panel visually collapsed to ~75px while its `aria-rowcount` stayed correct and every check passed. So the exact failure class a visual tier catches has already bitten this repo once, and is currently guarded by hand-written geometry assertions per surface. **The risk is real and specific here, not generic.** `--kira-font-ui` is a system-font stack (`-apple-system`, `Segoe UI`, `Ubuntu`, …) that resolves to a different real face on a macOS dev machine than on the Linux CI runner; `--kira-font-data` is user-customizable by design (P26 D3); `tests/ui/` runs WebKit (WKWebView on macOS, WebKitGTK on Linux) while the extension tier runs Chromium, so two rasterizers are already in play; and `theme/primitives.css` carries at least one `infinite` animation. A baseline captured on one machine is not assertable on another until fonts are pinned, animation is frozen and the renderer is fixed — and "fast" and "reliable" pull against each other precisely there. **Tool and approach are not decided here.** Playwright's own `toHaveScreenshot` costs no new dependency, keeps baselines in-repo and supports per-platform snapshot suffixes, but makes every developer machine a baseline authority; a dedicated visual-diff service normalizes across platforms and brings a review UI, but is a hosted tier that `CLAUDE.md`'s fully-open-source rule constrains hard. This phase's own Opus planning pass picks one, together with the containment measures above and which surfaces get baselines at all | Last, so it baselines a tree P1-P5 have already changed rather than one they would immediately invalidate. P1 is also its real precondition: a pixel tier's affordable size is a function of what the suites already cost, and P1 is the phase that measures that |
| **P7 Git graph polish: row/bullet geometry, uncommitted-work click-through, file-tree icon colors** | Three independent, hands-on-use findings against the shipped git graph (`packages/git-ui`), none touching the same file for the same reason. **(1) Row height and bullet alignment.** Every commit row is a fixed 36px today (`theme/density.css`'s `--kv-row-height`, a single SlickGrid-wide option) with `.kv-cell-message`'s CSS grid unconditionally reserving both the 16px ref/PR-badge track and the 18px subject track (`CommitGrid.vue`) — so an undecorated commit (the common case) pays the same height as a heavily-decorated one, and the graph node's own y-coordinate (`rowSvg.ts`'s `planNode`/`edgeCommand`, `cy = rowHeight / 2`) centers on that fixed total rather than on the subject line itself. Only a row that actually has a ref/PR badge should be two lines tall; every row's bullet should align to its own commit-message line, not the row's midpoint. The installed SlickGrid fork (5.20.0) already ships `enableVariableRowHeight`/`ItemMetadata.height` unused in this repo (`getItemMetadata` returns only `cssClasses` today), and `density.css` already carries an unused `--kv-row-height-compact: 20px` token from an earlier, never-finished density pass — both real, already-there seams this phase uses rather than invents. **(2) Uncommitted work has no click-through.** `UncommittedChangesStrip.vue` is a pinned, deliberately non-interactive strip above the grid (`role="status"`, no click handler) — its own doc comment names the reason: a GitLens-style pseudo-row inside the graph was rejected in v1 as a ~25-site grid-row-index-to-store-row-index remapping project, and a click action was separately deferred for needing a `sha`-shaped IPC method that "uncommitted" does not have. Both constraints still hold and are not reopened here: this phase keeps the strip, makes it focusable and clickable, and adds the one new IPC method actually missing — `working.detail`, composing `git status`'s untracked entries with a plain `git diff --numstat/--name-status HEAD` (never `diff-tree`, which cannot reach the working tree at all) into the same `FileChange[]` shape `commit.detail` already produces, so the existing `FileTree.vue`/`DetailPane`-adjacent rendering needs no new component logic, only a new pane variant and a third selection state alongside the existing commit/stash one. **(3) File-tree icon colors disagree with VS Code's own.** `FileTree.vue`'s `setiIconFor` (`icons/setiFileIcon.ts`) is a thin wrapper over the `seti-icons@0.0.4` npm package, whose bundled `definitions.json` is a stale upstream snapshot: `.test.ts`/`.spec.ts`/`.test.tsx`/`.spec.tsx` render yellow (`#cbcb41`) where VS Code's own real seti icon theme (`extensions/theme-seti/icons/vs-seti-icon-theme.json` in microsoft/vscode, fetched and diffed against this repo's palette in this phase's own research pass) renders orange (`#e37933`) — confirmed by executing both resolvers side by side. Every other mapping this repo has already matches VS Code's exactly; this is a narrow, already-root-caused color fix, plus the handful of extensions (`.spec.cjs`/`.test.cjs`/`.spec.mjs`/`.test.mjs`) VS Code maps that the stale package has no entry for at all | Three real defects found by using the shipped feature, not speculative polish — (1) and (2) both revisit `UncommittedChangesStrip.vue`/`CommitGrid.vue`'s own v1 decisions with infrastructure (variable row height, a real working-tree `FileChange[]` source) that did not exist or was not wired when those decisions were made; (3) is a one-file, already-diagnosed correctness bug against an authoritative external reference. Bundled together as one phase because all three are graph-surface UX findings from the same review pass, not because any depends on another |
