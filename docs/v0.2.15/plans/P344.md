# P344 plan: dev traffic lights match released app

Spec row: `docs/v0.2.15/SPEC.md` P344. Bug: macOS traffic-light buttons differ between dev server
and released bundled app. User: "In the released app the buttons are different. Smaller."
Source of truth: released app. Dev must render identical to it.

## Root cause

Not window config. One code path builds every window in both builds:
`internal/shell/window.go:65` `Options`, called from `internal/shell/openwindow.go:78`. Its
`Mac.TitleBar` (`window.go:84-91`) is `AppearsTransparent`, `HideTitle`, `FullSizeContent`, no
toolbar. Nothing reads dev vs production there.

Wails' `production` build tag changes no window chrome. `application_production.go` and
`application_dev.go` (wails v3.0.0-beta.28) differ only in dev-server wait, logging and debug
mode. `webview_window_darwin.go` titlebar code has no build-tag branch.

Build env is identical too. `apps/kira-studio/build/darwin/Taskfile.yml` `build:native` sets the
same `MACOSX_DEPLOYMENT_TARGET`/`CGO_CFLAGS`/`CGO_LDFLAGS` (`14.0`) for `DEV=true` and packaged
builds. `Info.dev.plist` differs from `Info.plist` only by `NSAppTransportSecurity`
(`NSAllowsLocalNetworking`). Same for Kira Space.

What differs: SDK the binary links against.

- Release: `.github/workflows/release.yml:75` `runs-on: macos-15`. v0.2.14 release run
  40163357707 log: `Image: macos-15-arm64`, `Version: 20260907.0337.1`. That image's readme:
  `16.4 (default)` Xcode, `Xcode Command Line Tools 16.4`, default SDK `macosx15.5`. Nothing in
  `.github/` or `scripts/` runs `xcode-select` or sets `DEVELOPER_DIR`. Release binary links
  macOS 15.5 SDK.
- Dev: `bun run dev:studio` runs `wails3 task dev`, whose primary command `wails3 task run`
  (`build/config.yml:63`) runs `darwin:run` (`build/darwin/Taskfile.yml` `run:`). It builds with
  whatever toolchain the user's Mac has. `docs/PACKAGING.md` records real-Mac work on macOS 26.5.2.
  Xcode / CLT 26 links macOS 26 SDK.

macOS 26 (Tahoe) AppKit picks window chrome by linked SDK. Binary linked against 26 SDK gets new
design: larger traffic lights, new titlebar metrics. Binary linked against pre-26 SDK runs in
compatibility mode: old, smaller traffic lights. That matches report exactly: release (15.5 SDK)
smaller, dev (26 SDK) larger.

v0.2.14 already dropped `UseToolbar`/`MacToolbarStyleUnifiedCompact` (`git log -L84,91` on
`window.go`, commit `b407b4e`) as suspected cause. It changed both builds equally, so it could not
close dev/release gap.

## Fix

Opt dev build into same compatibility mode release already gets. Apple's Info.plist key
`UIDesignRequiresCompatibility` (Boolean, macOS 26+) makes 26-SDK-linked app render pre-26 design.
Pre-26 SDK builds ignore it.

Add to all four plists, so dev and release stay identical even after release runner's default
Xcode moves to 26:

```xml
		<key>UIDesignRequiresCompatibility</key>
		<true/>
```

Insert right after each `LSMinimumSystemVersion` `<string>` line, outside Space's
`kira:doctypes` markers:

- `apps/kira-studio/build/darwin/Info.plist` after line 22
- `apps/kira-studio/build/darwin/Info.dev.plist` after line 22
- `apps/kira-space/build/darwin/Info.plist` after line 528
- `apps/kira-space/build/darwin/Info.dev.plist` after line 528

Both `create:app:bundle` and `run` copy these plists into bundle unchanged (PlistBuddy only stamps
version), so key reaches both `.app` and `.dev.app`.

No change to `window.go` options or `tokens.css` `--kira-titlebar-inset-left: 78px`. Release is
truth and already uses those values. Once dev renders compat chrome, user re-checks inset on
dev; it should already match release.

Declined:

- Pin dev to 15 SDK (`SDKROOT`/`DEVELOPER_DIR` in `darwin:run`). Needs Xcode 16 on user's Mac,
  breaks on CLT-only machines, and drifts again when release runner changes.
- Move release to Xcode 26. Makes release larger, contradicts source of truth.
- Custom-drawn traffic lights (`Frameless`). Loses native behaviour; `window.go:82` already
  declines it.

## Guard against regeneration

`docs/PACKAGING.md:102` already notes `wails3 task common:update:build-assets` reverts both plists
(`LSMinimumSystemVersion`). It would drop new key too, silently re-opening bug.

Add `S14` to `scripts/verify-packaging.sh`, after S13 (line 161 block), same style as S12/S13:
for each of four plists, `grep -A1 '<key>UIDesignRequiresCompatibility</key>' | grep -q '<true/>'`,
else `fail "design compatibility key missing" "<plist> lacks UIDesignRequiresCompatibility=true — dev and release traffic lights would differ (P344); re-add after regenerating build assets"`.
Source-level, runs on Linux in `pr.yml:73` (`bun run verify:packaging`). Also assert it on built
bundles: in Studio and Space artifact blocks (next to A3/A5), PlistBuddy
`Print :UIDesignRequiresCompatibility` equals `true`, call it A6.
