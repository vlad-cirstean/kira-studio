## Library

Reuse, add nothing. Repo already ships `vue-draggable-plus` 0.6.1 (MIT; wraps SortableJS, MIT) behind `behaviour/sortableReorder.ts` + `components/SortableList.vue`, and `behaviour/treePointerDrag.ts` (VueUse) for virtualized trees. ## Decisions

- **One phase, no Part split.** Both shared primitives already exist; the work is per-surface adoption on two disjoint surfaces (API tree; automations module). One sequential implementer: total size is moderate, and both halves regenerate Wails bindings and contracts, where a parallel split buys little and risks binding-file collisions.
- **Sibling order: folders and requests interleave** by `sort_order` (Postman order is data; import/export round-trips it). No folders-first rule. Automations keep ungrouped scripts above the collections block (unchanged layout); a script moves between sets, a collection never nests.
- **API collections reorder via new `CollectionsService.ReorderCollections({ ids })`** (connections/scripts precedent: whole-list order, `sqlitex.ReorderSortOrder`, ids not listed keep relative order after). No migration: column exists, dense or not.
- **Collection drag in the API tree.** Press on a collection row starts a collection drag when every selected row is a collection (mixed selection refused, as today for collections). Refused while a search is active (partial order). Drop resolution during a collection drag: hit row belongs to collection C; C's header top half -> `before C` (line at header top); C's header bottom half or any row inside C's visible block -> `after C` (line at the bottom of the block's last visible row). No `into`. No-op drops resolve to null (no line, no call).
- **Item drag unchanged.** `MoveItems` already covers reorder within a parent and re-parent across folders/collections.
- **Keyboard alternative = menu `Move up`/`Move down`** (ids `move-up`/`move-down`, `common.moveUp.tooltip`/`common.moveDown.tooltip`, icons `arrow-up`/`arrow-down`, `shortcut: 'list.moveUp'|'list.moveDown'`) plus Alt+Up/Down through the same menu (`viaMenu`, connections precedent). Disabled at the ends of the row's own sibling set and while searching.
  - API collection row: swap with neighbor collection -> `ReorderCollections`.
  - API request/folder row: within its parent only, never hops out of a folder. Up: `MoveItems([id], collectionId, parentId, beforeId = previous sibling)`. Down: `beforeId = sibling two after, or null`. Single-row menu only; multi-select menu gets none (Alt+arrow on a multi-selection does nothing).
  - Automations script row and collection header: same items; run `scripts.reorder` / `scripts.reorderCollections` with the swapped order. Alt+arrows stay on `SortableList` keyboard (already bound); the menu items only show the chord and run the move. Do not also bind `list.move*` in `useTreeShortcuts` (double move).
- **Automations cross-set drag.** Scripts drag between ungrouped and any expanded collection, landing at the drop index. Backend: `Move` gains optional `beforeId` (null = append, current behavior), one transaction. Collapsed collection header is not a drop target (menu `Move to collection` covers it). Empty expanded collection accepts a drop (Sortable `emptyInsertThreshold`; give the list a min height if the spec shows it cannot).
- **Persistence after a drop**: no optimistic local reorder. API: mutation then `afterTreeListChange` (existing). Automations: store action, broadcast snapshot (existing). A rejected call shows the panel error and leaves the persisted order.
