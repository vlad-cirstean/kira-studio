# P379 ADE tasks: customizable statuses, manual moves both ways

Base: `9d77d66` (P378 closed). Discovery by Grep/Read: CodeGraph MCP failed to connect (`codegraph` not in `$PATH`); `ToolSearch "codegraph"` found nothing.

## Ask

`SPEC.md` row plus user: "Ade tasks have customisable statuses and i can go back and forth manually."

1. User defines the status set: name, order, colour.
2. User moves any task to any status, forward or back.
3. Automatic transitions keep working on top of that.

This reverses decision D10 ("status derived, never typed", `docs/ARCHITECTURE.md` ADE Model). The user asked for it; D10 goes.

## Decisions

- **Scope: global, one table.** Statuses live in new table `ade_task_statuses`, not a settings leaf. Tasks and workflow files reference status ids; delete must reassign tasks in the same transaction as the set rewrite. A settings JSON row cannot give that. Not per repo: a task spans repos.
- **Status shape:** `id` (slug, `^[a-z0-9][a-z0-9_-]*$`, max 40), `name` (trimmed, 1-40 chars, unique case-insensitive), `tone` (one of the 6 ADE tones), `category` (`todo | active | review | done`), `position`. 1-20 statuses. Each category keeps at least one status. No icons: ADE chips have none.
- **Category** drives automation defaults: new task -> first `todo`; review task -> first `review`; finished workflow -> first `done`; step with no or unknown status -> first `review` for a review step, else first `active`. "First" = lowest position in that category. UI label: "Counts as".
- **Default set** (migration seed) reproduces today: `todo` To do grey todo; `in-progress` In progress amber active; `in-review` In review blue review; `done` Done green done. Names seeded in English; they are user data after that.
- **Ids are stable; names are free.** Rename never touches tasks or workflow files. A new status gets a server slug from its name (`qa`, collision -> `qa-2`).
- **Workflow step `status:` holds a status id.** The parser maps the four legacy names (`To do`, `In progress`, `In review`, `Done`) to the default ids, so existing files load unchanged; the writer emits ids. Parse checks syntax only (id pattern), not membership: workflow files load without the DB. An id not in the set resolves at runtime to the kind default above. `DefaultStatus(kind)` returns `in-review` / `in-progress`.
- **Stored per task:** `ade_tasks.status_id`, `status_by` (`auto | user`), `status_step` (engine-internal: the step key whose status was last applied; not on the wire). No SQL FK: SQLite refuses `ADD COLUMN ... REFERENCES` with a non-NULL default, and rebuilding `ade_tasks` (many FKs point at it) is not worth it. The repo keeps integrity: writes validate against the set; set rewrites reassign in the same tx. A read of an unknown id falls back like a missing step status (defensive only).
- **Automation vs manual: last event wins.** Engine re-applies status only when the task's current step changes, never on refresh or read. `syncStatus(tc)` computes key = `currentStepID(tc)` (`done` when finished, `""` while not started); when key != `status_step`: write the step's resolved status (or first `done` for `done`, first `todo` for `""`), `status_by = auto`, `status_step = key`, notify board. A manual move writes `status_id`, `status_by = user` and leaves `status_step`, so it sticks until the next step change. Examples: agent finishes, next step is a review step -> its status (In review); user drags back to In progress -> stays until the task moves on.
  - "Not started" mirrors today's To do rule: at the first non-skipped step, entry at first step, no runs since watermark, no sessions.
  - Call sites, task mutex held: end of `advanceLocked`; after `startStep`; `queueRun` (loops/retries); `StepDone`; `SetTaskStep`; `SetTaskWorkflow` (resets to `""` -> first todo); `LaunchStep` and session start of a manual step; once per live task in `Recover` (heals the coarse migration backfill). Implementer confirms coverage with the flow test, not by inspection alone.
  - Only kind `task` syncs. Review and parked tasks keep whatever status they have. Review -> task conversion (P377) sets first `todo`, `status_by = auto`, `status_step = ""`.
- **Blocked is not a status.** It is a stuck/failed alert, derived as today (`progress.bad` or failed setup). Plan card cell: Blocked tag still wins (alert priority, as today). Task panel and phone card: status chip plus a separate red `Blocked` chip, so a manual move is always visible. Merged and Not merging cell tags stay as today.
- **Manual move surfaces:** task menu `Status` submenu (all kinds, checked current); task panel Status row becomes a picker with back/next buttons (pattern of `AdeStepMover`). Status moves are allowed while runs are live: status no longer drives the engine. Step moves stay separate and unchanged. No drag: the board has no status columns, and adding a status-column board is a new view nobody asked for.
- **IPC:** `TaskPatch.statusId` on existing `UpdateTask` (P377 precedent). New method `SaveStatuses` (dense rewrite plus reassign map) returns the set. Statuses ride on `Board.statuses`, so plan model reads tasks and statuses atomically, the phone gets them free, and a save emits the board push. Task wire gains `statusId`, `statusBy`.
- **Delete in use:** client sends `reassign: {removedId: targetId}`. A removed id without an entry goes to the first kept status of its category. Applies to live and archived tasks. UI asks for the target only when live tasks use it.
- **Settings UI:** new Settings dialog section `Task statuses`, self-saving like `FileTypesPane` (each edit sends `SaveStatuses`). Workflow inspector status select lists the set and links to that section via the existing `settingsSection` deep link. No new Pinia store: the set is server state (TanStack Query via `useBoard` plus a `useSaveStatuses` mutation); pane edit state is component-local, shared with nothing. Rejected: settings `ade` leaf (no transactional reassign).
- **Phone:** shows stored status and Blocked chip. No phone status write: the ask names no phone surface, and a phone write needs a new `mobileweb` route plus permission row. Left out entirely, not half-built.
- **No split.** The wire change (step status ids, stored status) breaks the frontend's derived display in the same commit, so backend and UI cannot land as separately coherent parts. One sequential implementer, granular commits.
