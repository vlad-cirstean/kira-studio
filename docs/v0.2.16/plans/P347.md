# P347 plan: date-ordered git graph, sibling branches grouped only where they overlap

Spec row: `docs/v0.2.16/SPEC.md` P347. Branches forking from main render as starting from nowhere.
Wanted: time order for the whole graph. Only where two or more branches forking from the same
commit interleave, show each one contiguously (topologically) at that spot. Every branch draws a
real edge down to its fork commit.

## Root cause

Not pagination and not a dropped edge in `lanes.ts`. P93 (v1.8, `docs/HISTORY.md` "v1.8 P93")
made the display order branch-major for the whole graph, on purpose:

1. Backend walks `git log --topo-order` (`apps/kira-space/internal/gitclient/porcelain/log.go:36-41`,
   `logBaseArgs`). Store rows arrive in that order.
2. `buildRowPlan` (`packages/git-core/src/graph/rowPlan.ts:396`) buckets every row by tip priority
   (`assignRowRanks`, `:270`). Bucket 0 is everything reachable from HEAD, i.e. nearly the whole
   history. `collapseBuckets` (`:326`) emits bucket 0 in full, then bucket 1, and so on.
3. So every non-HEAD branch's own commits land *below every loaded row of main*. The fork commit
   (on main) sits far above them.
4. `projectLayoutInput` (`:453`) drops each upward parent link from the lane input and records only
   `forkParentOf` (`:477-479`, `:503-505`). `lanes.ts` never sees the fork edge.
5. `planForkStub` (`packages/git-ui/src/graph/rowSvg.ts:182`) draws that link as a dashed run
   from the row's own top edge to its node, inside one row. Visually: a branch starting from
   nowhere. Each new page pushes the branch groups further down.

Repro in this repo: HEAD `chapter/v0.2.15` forks from `b407b4eef`; `origin/main` tip `c57ca83d9`
also forks from `b407b4eef`. Under P93 `c57ca83d9` renders after all loaded main history with a
dashed stub. `git log --all --date-order --graph` shows it between `8bf6223b9` and `1822ff967`
with a real line to `b407b4eef`.

`--topo-order` itself is the "topological for the entirety" the user rejects. Scratch repo
(m0, m1 on main; `feat` f1 f2 f3, `fix` x1 x2 off m1; main m2..m6 after; f3 newest):

```
topo-order: f3 f2 f1 m6 m5 m4 m3 m2 x2 x1 m1 m0     (m2..m6 pushed below old f1)
date-order: f3 m6 m5 m4 m3 m2 x2 f2 x1 f1 m1 m0     (fix/feat interleave)
wanted:     f3 m6 m5 m4 m3 m2 x2 x1 f2 f1 m1 m0     (date order; fix and feat each contiguous)
```

## Decisions

- **Backend walks `--date-order`.** One token in `logBaseArgs`. Keeps the invariant every client
  module relies on (a parent's row is strictly after all its children: `assignRowRanks`' assert
  `rowPlan.ts:306`, `lanes.ts` header). The loaded prefix becomes the newest commits, so later
  pages append below instead of inserting above visible rows. Paging (`--skip` respawn), the tail
  scan (`LogScanArgs`, same base args, prefix property kept) and `rev-list --count` are
  order-agnostic or share the base. Applies to the ranged review walk too (same base args); a
  `base..topic` range reads fine in date order. Cost: git uses the same incremental generation-
  number walk for both flags; check with the perf test below, not assumed.
- **Local grouping lives client-side, in the display projection.** `RowPlan` already maps store
  rows to display rows and is rebuilt over the whole store on every page (`GraphViewState
  .#rebuildLayout`, `graphView.ts:533-538`). Reordering in Go would break the `--skip` resume and
  the scan-prefix property. Priority is the store row index, not a timestamp: with no
  interleaving siblings the display order equals store order exactly, and fixtures need no dates.
- **Drop branch-major grouping entirely.** Group assignment (`assignRowRanks`) stays: collapse
  labels and keys still need it. Ordering no longer uses it.
- **Collapse keeps working, per run.** A collapsed group used to be one contiguous bucket. Now a
  group's rows can form several runs in display order. Contract each maximal run of consecutive
  rows of one non-zero group, same rules as today per run (`MIN_COLLAPSIBLE` = 3, expanded keys,
  toggle). Expanding a key expands all its runs. Default stays on. Group 0 never collapses.
- **No upward links remain, so the fork stub goes.** The new order is a topological order of the
  loaded rows; every parent is below its child, and a placeholder holds one contiguous run. Delete
  `forkParentOf`, the stub draw and the stub click (dead code otherwise; knip in pre-push).
  Fork edges become ordinary `lanes.ts` lanes. An unloaded fork parent keeps today's pending lane
  running off the bottom until its page lands.

## Algorithm: `localTopoOrder(input: LayoutInput): Int32Array`

New file `packages/git-core/src/graph/displayOrder.ts`. Input is `store.layoutInput(0, rowCount)`
(CSR: `parentOffsets`, `parentRows`, `-1` = parent not loaded). Output: store rows in display
order. Needs the unresolved first-parent sha for boundary chains; pass a `firstParentSha(row)`
callback backed by `store.commitAt(row).parents[0]`, called only for chains whose bottom's first
parent is `-1`.

1. **Child counts.** `childCount[p]` = number of parent links to `p` among loaded rows. Date order
   guarantees a loaded row's children are all loaded.
2. **Chains** (one pass, store order). Row `r` with no chain yet starts chain `c` (`chainTop[c] =
   r`). Let `p` = first parent of `r`. If `p >= 0` and `childCount[p] === 1`, `p` joins `c`.
   `chainBottom[c]` = last row assigned. A merge's second-parent link never continues a chain, and
   a commit with two or more children always starts a new chain.
3. **Fork key** of chain `c` = first parent of `chainBottom[c]`: its row when loaded (then it has
   two or more children), else its sha. A root bottom has no key and never blocks. Chains with
   equal keys are siblings.
4. **Walk.** Min-heap of ready rows keyed by store row (ready = all loaded children emitted;
   start with rows of `childCount === 0`). Per fork key, a stack of started, unfinished chains.
   Pop the smallest row `r` in chain `c`:
   - `r` is not `chainTop[c]` and `c` is not on top of its key's stack: park `r` as `c`'s next
     row (at most one per chain) and continue.
   - Otherwise emit `r`. If `r` is the chain top and `c` has a key, push `c` on that stack. If `r`
     is the chain bottom, pop `c` (always the top: a lower chain cannot progress while a later
     sibling is open); if the new top has a parked row, push it back into the heap.
   - Decrement each loaded parent's remaining-children count; push it at 0.

   Rule in words: a sibling that starts while another is open finishes before the other resumes.
   Starting a new chain is never blocked, so a recent tip still shows at its date. Progress is
   guaranteed: a chain's non-top row has exactly one child (its predecessor), so the top chain of
   every stack is always continuable. Each row enters the heap at most twice: O(n log w), w =
   ready-set width.

Prototype (scratch, not committed) results:

- Scratch fork repo: exactly the "wanted" line above.
- Merged branch (`fa` merged into main, interleaved with m2/m3): `m4 merge-fa fa3 fa2 fa1 m3 m2
  m1 m0`, so the merged branch sits contiguous below its merge.
- This repo (7672 commits): valid topological order, all rows emitted, 0.2s including `git log`.
- Prefix stability on this repo: plans built from the first 250/1000/2500/4000/6000 rows agree
  exactly with the full plan's order restricted to those rows.

Not final on arrival in theory: when a page loads a chain's unloaded bottom parent with a single
child, two chains merge and can become siblings of a different key. Only rows next to the loaded
boundary can move. Document this in the module header; do not claim finality. Grid already
repaints wholesale on every plan publish (`CommitGrid.vue:697`).

Heap: use `flatqueue` (ISC, zero dependencies, typed-array backed, `push(id, priority)`/`pop()`).
Pin an exact version at least two weeks old (3.1.0 is current; confirm date and license on the
package page) in `packages/git-core/package.json` `dependencies`. Use typed arrays for
`childCount`, chain ids, tops, bottoms, parked rows, and a per-chain `stackBelow` link with
per-key top heads (`Int32Array` for row keys, `Map<string, number>` for the few sha keys). No
per-row object allocation; this runs on every relayout over the whole store.
