## 1. P203 Git graph: rows vanish after a refs change; clicking a commit leaves the graph blank

### Reproduction (done during planning)

- Mock UI specs (`repo-graph-pr-badge.spec.ts`, `repo-workspace.spec.ts` "Open all changes") click a commit and stay
  green, before and after v2.1: they never re-walk the graph. The mock opens `graph.stream` once and answers every
  open with the same chunk list, so a restart at row 0 with a shorter first page never happens.
- Real backend (server-tag recipe in `docs/DEV_ENVIRONMENT.md`, git `Locate` patched by `-overlay`, fake `gh` on
  `PATH`, synthetic repo: 2300 commits, 60 branches via `git fast-import`, 60 open PRs). Steps: open the repo, click
  rows 5, 8, 12, then `git commit --allow-empty` in the repo (refs change, auto refresh re-walks from row 0), wait 3 s,
  click again. Result on v2.1 head, every run:

  ```
  AssertionError: ShaTable: row 2302 out of range (500 entries)
    hexAt <- rowHasBadges <- rowMetadata <- rowHeightProvider <- ensureRowPositionIndexer <- updateRowCount
    (CommitGrid graphView.generation watcher); a second one from appendRowHtml <- renderRows <- render
  ```

  Screen: the top rows render blank, the newest commits are missing, the list keeps stale rows below. A click then
  re-renders against the broken grid (selection watcher `invalidateRows` + `render`). Same driver against the
  `ba8419e` frontend (v2.0, before v2.1): same assertion, newest commits missing (stale list, no blank rows).

### Root cause

`PackedStreamState.applyChunk` (`packages/git-ui/src/state/packedStream.ts`), on a chunk with `from === 0` while the
store holds rows: calls `hooks.onReset()`, then `#clear()` (store emptied, `generation++`), then appends the new first
page (500 rows). `GraphViewState.#applyChunk`'s `onReset` only resets the layout client
(`packages/git-ui/src/state/graphView.ts:570`). `plan` keeps describing the old 2300-row store until the async
`#drainLayoutRebuilds` -> `#rebuildLayout` runs. In between, Vue flushes `CommitGrid.vue`'s `graphView.generation`
watcher (`invalidateAllRows`/`updateRowCount`/`render`): SlickGrid's length is the stale plan's, `rowMetadata` maps a
display row to store row 2302, `rowHasBadges` calls `store.shaAt(2302)`, which asserts. The throw aborts SlickGrid
mid-`updateRowCount`, leaving its row cache and position index half rebuilt.

Pre-existing (present at `ba8419e`), exposed far more often by v2.1: P191 (`e32003a`) makes Plan refresh fetch every
board repo, and P189 (`ee150dd`) re-requests PR facts on every `refsChanged`, so every fetch now drives an extra
`scheduleAncestryRebuild` (`invalidateRowHeights`) render into the same stale-plan window.

### Fix (minimal, verified during planning)

`graphView.ts` `#applyChunk`: the restart-at-zero `onReset` hook drops the old layout and plan in the same synchronous
step as the store clear:

```ts
onReset: () => {
  this.#pendingLayoutRange = undefined;
  this.#resetLayout();
},
```

`#resetLayout()` sets `plan` to `identityRowPlan(0)`, clears `layout` and `#layoutPlan`, resets `laneCount` and the
layout client. The watcher flush then sees a 0-row plan; the drain that `#applyChunk` starts right after sets the new
plan synchronously at `#rebuildLayout`'s top, all inside the same task, so no empty frame paints. Planning ran this
change on the real backend three times: no assertion, rows correct after the re-walk and after clicks (scroll position
kept by the existing auto-refresh capture). Do not add try/catch around SlickGrid calls or guards in `rowMetadata`: the
invariant is "plan never references a store row the store lacks", fixed at its source.

Check the review stream (`review.ts` uses its own `PackedStreamState` with no plan) for the same shape; it has no plan,
so expect nothing to change there; say so in the notes.

### Tests
