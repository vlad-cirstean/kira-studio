## 1. P197 Skip a workflow stage

### Decision: skip is a stage-level workflow flag, plus a one-off per-task skip

"Right click a stage in a workflow, skip it" reads as the workflow editor, so the persistent meaning
lives in the file: `skip: true` on a stage. A skipped stage stays defined (id, steps, history keep
their keys) but no task enters it by moving forward. Rejected alternative, per-task skip flags
stored at run time: a new table plus engine rules for one task, while P192's `SetTaskStage` already
moves one task past a stage. So the task view gets the one-off form through that existing call:
right-click a stage block in the task's Workflow block, "Skip this stage" moves the task to the next
runnable stage. Both forms share one traversal helper.

Versioning (P196): the flag is part of the workflow JSON, so a started task runs its snapshot and
ignores a later skip toggle; `workflowOutdated` already flags the drift. A not-started task follows
the live file. A not-started task already sitting on a stage that becomes skipped stays there (skip
only governs entry); its mover and menus offer Next.

## 3. P199 Kira Space tools for agents (MCP)

### Decisions

- **D1 Same loopback server, scoped grants.** `adeagent.Server` already serves `finish_step` over
  loopback Streamable HTTP with a bearer token per run and a `0600` config file. Extend it rather
  than add a second server: one `--mcp-config` file per launch (the flag is variadic and the TUI
  take-over path already passes one). Server name stays `kira-ade`.
- **D2 Grant per launch.** `type Grant struct { RunID, TaskID string; Space bool }`.
  `Register(g Grant) (configPath string, release func(), err error)` replaces
  `Register(runID)`. A registration's token maps to its grant; `verify` sets
  `TokenInfo.UserID = "g<seq>"` and handlers resolve the grant with `s.grant(req)` under `s.mu`
  (a released grant fails at once). `finish_step` requires `RunID != ""`; Space tools require
  `Space && TaskID != ""`. Every Space tool acts on `grant.TaskID` only; there is no task argument.
- **D3 Tool visibility by grant.** `mcp.NewStreamableHTTPHandler`'s `getServer(req)` reads
  `auth.TokenInfoFromContext(req.Context())` and returns one of three prebuilt `*mcp.Server`s:
  finish only, Space only, both. An agent never sees a tool it cannot call.
- **D4 Workflow flag.** Top-level `kira_space_mcp: true` (YAML), `Workflow.KiraSpaceMcp bool
  \`json:"kiraSpaceMcp"\``. Read from `taskWorkflow(task)`, so a started task keeps the flag of its
  snapshot (P196). Off by default.
- **D5 Where grants go.** Headless runs (`superviseAgent`): `Register(Grant{RunID, TaskID, Space})`;
  `allowedTools` adds the four Space tool names when on (headless `-p` denies unlisted tools).
  TUI launches `LaunchStage`, `StartBranch`, `TakeOver`: when on, register a Space grant (merged
  with `finishBinding`'s run grant into one registration on take-over) and append
  `--mcp-config <file> --allowedTools <names...>` to `PrepareArgs.ExtraArgs`. The review agent gets
  none (its job is review).
- **D6 Release.** Headless: at process exit (as today). TUI: `TaskBoard.tuiGrants
  map[recordID]tuiBinding` replaces `tuiRuns` keyed by run (`tuiBound(runID)` scans);
  `OnTUIStopped(recordID)` releases. Fix the existing leak too: `Tracker.pruneExpiredPendingLocked`
  returns the expired intents' `RecordID`s and `Prepare` calls `OnStopped` for each after unlock, so
  an abandoned launch's token and file go (today a never-composed take-over binding leaks until
  restart). `Recover` already deletes stale `*.mcp.json`.
- **D7 Repos only from the registered list.** The agent names a repo by nickname, name or code repo
  id (exact, case-sensitive; nickname first). Unknown: error listing registered repos and telling
  the agent to ask the user to import it from the Git module ("Manage repositories…"). Ambiguous
  name: error listing the matches with ids. No path import from an agent.
- **D8 Additive only.** `declare_repos` adds missing repos (as `AddTaskRepo`, `origin = 'agent'`);
  it never removes a repo the task has.
- **D9 Branch request semantics.** `request_branch(repo, name)`, under the task mutex:
  1. Task live, not archiving (`checkNotArchiving`), kind `task` or `parked`; review refused.
  2. Resolve repo (D7); add it to the task when missing.
  3. Task branch in that repo already named `name`: idempotent; ensure its worktree
     (`ensureWorktree`, `startSetup` when fresh) and return its state.
  4. Already created under another name: refuse `"the task already has branch X in <repo>; work
     there"`. No renames of created branches.
  5. Not created: validate `name` with `git check-ref-format --branch` (gitclient runner, the
     board's `GitPath`), refuse the repo's main and its integration branches, refuse over 255 bytes
     (bridge's `adeMaxBranchBytes`; `ade` cannot import `bridge`, so a twin `maxBranchNameBytes` in
     `ade`). Then `ensureWorktree(ctx, title, rec, sb, name)`: `claimBranchName`
     already refuses an existing ref (`branch X already exists`) and a name another live task holds
     (`ErrBranchNameTaken`). Fresh worktree: `startSetup(..., b.onSetupReady)`, so P202's
     indicators and held runs behave as for any other trigger. Mark `origin = 'agent'`.
  6. Return `{repo, branch, worktree, setup: {state, note}}`. `ensureWorktree` failure records a
     failed setup with its reason (P202 `recordSetupFailure`) and returns the error.
- **D10 Waiting.** `request_branch` never waits for the prepare script. `branch_status(repo,
  waitSeconds 0-600)` polls `GetSetup` each second until the state leaves `running` or the wait
  ends (ctx cancel ends it). Tool results tell the agent to call it before working in the worktree.
- **D11 Headless scope.** `StartRun` still creates every unnamed mine branch before step 1
  (derived names or Run dialog names), as today. Agent-chosen names therefore come from a task's
  interactive stage (TUI) or a `once` step adding repos for later steps. A TUI agent working in a
  requested worktree outside its cwd gets Claude Code's normal directory permission prompt. Record
  in the notes; this is the honest boundary, not a gap to paper over.

### Tools (`adeagent/space.go`)

`adeagent` cannot import `ade` (cycle). Interface in `adeagent`, implemented by `*ade.TaskBoard`:

```go
type SpaceTools interface {
	TaskInfo(ctx context.Context, taskID string) (TaskInfo, error)
	DeclareRepos(ctx context.Context, taskID string, repos []string) (TaskInfo, error)
	RequestBranch(ctx context.Context, taskID, repo, name string) (BranchInfo, error)
	BranchStatus(ctx context.Context, taskID, repo string, wait time.Duration) (BranchInfo, error)
}
```

- `task_info` (no args): task title, Jira key, workflow name, current stage; `repos` on the task
  (`repo` nickname-or-name, `codeRepoId`, `branch` or null, `worktree`, `setup`); `registered`
  repos (`name`, `nickname`, `codeRepoId`, `path`).
- `declare_repos {repos: string[]}` (1-20 entries): D8; returns `task_info`.
- `request_branch {repo: string, name: string}`: D9.
- `branch_status {repo: string, waitSeconds?: int}`: D10.
- Server `Instructions`: one paragraph: call `task_info` first; declare repos before branching;
  create branches only with `request_branch`, never `git branch`/`git worktree`; wait with
  `branch_status` before editing a new worktree.
- `adeagent/suffix.go`: `SpaceToolNames` (the four `mcp__kira-ade__*` names); headless prompt suffix
  gains one line naming the tools when Space is on.
- `NewServer(dir, onFinish, space SpaceTools)`; `NewTaskBoard` passes the board itself.
- Errors are tool results with `IsError: true` and a sentence the agent can act on, never a Go
  error string leak.
