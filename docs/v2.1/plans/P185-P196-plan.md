## 3. Stream A

### P185 Panel resize stays attached to the cursor

Facts (read on base):
- reka-ui `SplitterResizeHandle` does not use pointer capture. Its module registry
  (`node_modules/.bun/reka-ui@2.10.5*/.../dist/utils/registry.js`) listens `mousedown` on
  `document.body` and, while a drag is down, `mouseup` on `window`. A drag ends only when that
  `mouseup` reaches it **and** the handle's `data` object is still in `intersectingHandles`; only
  then does `setResizeHandlerState('up')` call the group's `stopDragging()`. While the group's
  `dragState` is non-null, every `SplitterPanel` gets `pointer-events: none`
  (`utils/style.js`), and a later hover over the handle keeps resizing — the reported symptom.
- The Wails runtime (`@wailsio/runtime` 3.0.0-beta.21, `dist/drag.js`) installs capture-phase
  `mousedown`/`mousemove`/`mouseup` listeners on `window` and calls `stopImmediatePropagation()`
  on `mouseup` while its own `dragging`/`resizing` flag is set (native title-bar drag or window-edge
  resize). A `mouseup` swallowed there never reaches reka's bubble listener.
- WKWebView does not deliver `mouseup` for a release outside the window.
- `DockResizeHandle.vue`/`AdePanelResizeHandle.vue` use VueUse `useDraggable` (pointer events on
  `window`); it ends on `pointerup` only, not `pointercancel`/`lostpointercapture`.
- `KuiColumnResizeHandle.vue` already ends on `pointerup`/`pointercancel`/`lostpointercapture`.

Steps:
1. Reproduce before fixing. New `apps/kira-studio/tests/ui/panel-resize.spec.ts` and
   `apps/kira-space/tests/ui/panel-resize.spec.ts`: press the project-panel handle
   (`[data-slot="resizable-handle"]` inside `.workbench-shell`), (a) release without moving,
   (b) drag and release, (c) drag, release outside the viewport (`page.mouse.up()` after moving
   past the edge), (d) the Operations dock handle and (Space) the `ade` panel handle the same way.
   After release assert: handle `data-state` is not `drag`; `[data-testid="main-panel"]` computed
   `pointer-events` is not `none`; moving the mouse over the handle afterwards does not change the
   panel width. Run on WebKit as well as Chromium if the Playwright config allows a project
   override (WKWebView is the shipping engine); record which cases fail where.
2. Confirm the cause with a probe, never assumed: log reka's `dragging` emit and a capture-phase
   `window` `mouseup`/`pointerup` listener during a real `bun run dev:studio`/`dev:space` run if
   the sandbox allows it (`docs/DEV_ENVIRONMENT.md`); otherwise the Playwright probe. Candidates,
   in the order to check: (H1) `mouseup` never reaches reka (released outside the window, or
   swallowed by Wails' capture listener); (H2) the handle re-registers mid-drag (a new
   `hitAreaMargins` object identity re-runs reka's `watchEffect`, dropping the old `data` from the
   registry while `intersectingHandles` still holds it, so `'up'` reaches no active handle and
   `stopDragging()` never runs) — the Vue compiler emits `:hit-area-margins="{ coarse: 8, fine: 4 }"`
   as a new object on every slot render; (H3) a handle unmounts mid-drag (`v-if`), unregistering
   without `stopDragging()`.
3. Fix once, in `packages/theme/src/components/ui/resizable/ResizableHandle.vue`, whatever the probe
   shows. Requirements the fix must meet regardless of cause: (a) `hitAreaMargins` reaches reka
   with a stable identity — rebuild it only when `coarse`/`fine` change (`watch` on the two
   primitives, `shallowRef` holder); (b) a drag ends even when reka never sees `mouseup`: while
   reka reports `dragging`, VueUse `useEventListener(window, ['pointerup', 'pointercancel'],
   ..., { capture: true })`, `useEventListener(window, 'blur', ...)` and a `pointermove` with
   `buttons === 0` dispatch one synthetic `MouseEvent('mouseup', { bubbles: true, clientX,
   clientY })` on `window`, which is reka's own end path (`handlePointerUp`). Name this in a
   one-line comment: reka 2.10.5 ends a drag only on `window` `mouseup`. No library fork, no
   replacement splitter (reka is the shadcn-vue resizable primitive; the gap is one event).
   Keep `WorkbenchShell.vue`'s handle markup as is unless the probe shows H2 needs the constant
   there too (then hoist `HIT_AREA_MARGINS` to a module constant).
4. `DockResizeHandle.vue`, `AdePanelResizeHandle.vue`: end the drag on `pointercancel` and
   `lostpointercapture` too (VueUse `useDraggable` has no such option in 15.0.0: check its source;
   if absent, add `useEventListener` on the handle for both and reset the gesture, emitting the
   same `dragging false`/`commit` the normal end emits). `KuiColumnResizeHandle.vue`: edit only if
   the probe shows it fails.
5. Verify: both new specs pass; `bun run test:ui:studio` and `test:ui:space` relevant projects;
   `test:visual:*` for the workbench shell (no handle look change expected).

Commits: `test(ui): reproduce stuck panel resize`, `fix(theme): end splitter drag on every
release path`, `fix(workbench): end dock and ade resize on pointer cancel`.

### P189 Git: cached GitHub PRs; graph badge only at the branch tip

Facts: `gitsession/gh.go` keeps per-repo TTL caches (snapshot 5 min, branch 5 min, commit 10 min)
but `ghState.drop()` clears all of them on every `refsChanged` (any fetch, commit, checkout).
`packages/git-ui/src/state/pr.ts` `PrState` clears everything on `refsChanged` and `setRepoId`, so
every refs change or tab switch refetches. `CommitGrid.vue` `prsFor: (sha) =>
props.pr?.prForCommit(sha)` returns `bySha` plus `prByAncestry`, which badges every commit on a PR
branch.

Cache decision: server-side in Go plus last-known data in `PrState`, not TanStack Query. Reason:
git-ui runs in two hosts (Kira Space and the VS Code webview), neither mounts a `QueryClient` for
git-ui, and the Go session is the one cache both hosts share; TanStack Query would add a second,
per-webview cache in front of it.

1. `gh.go`: on `refsChanged`, keep entries and mark them stale (`staleAt` timestamp) instead of
   `drop()`; a stale or TTL-expired entry is returned immediately and a single-flight refresh runs
   in the background (reuse `claimSnapshotFetch`'s pattern for branch/commit lookups), pushing the
   existing PR-changed notification when the result differs. Keep the breaker and the per-commit LRU
   bound. Remote change (`remoteChecked`) still drops the GitHub-remote detection. Extend the
   existing `gh` tests (they cover concurrency and TTL arithmetic: real complexity).
2. `pr.ts`: on `refsChanged` keep current maps and re-request in the background; swap when
   answered (generation guard already exists, `#clearGeneration`). Keep a per-repo map of
   last-known state so `setRepoId` back to a repo shows its facts at once. Update `pr.test.ts`.
3. `CommitGrid.vue`: `prsFor` badges a commit only when it is a PR head: `bySha` entries whose
   `headSha === sha`, plus `byBranch` records whose `headSha === sha`. Never `prByAncestry`.
   `DetailPane.vue`/`CommitMeta.vue` keep `prForCommit` (ancestry included). If ancestry is then
   used only by details, compute it lazily for the selected commit instead of on every layout
   chunk (`scheduleAncestryRebuild`), only if that is simpler; otherwise leave it.
4. Verify: `bun test packages/git-ui`, `go test -race ./apps/kira-space/internal/gitsession/...`,
   `test:ui:space` repo-graph specs; a graph UI assertion that a PR branch's non-tip commit has no
   badge and the tip has one (extend a repo-graph spec B owns).

Commits: `perf(git): keep PR facts across refs changes`, `fix(git-ui): PR badge only at the branch
tip in the graph`.

### P196 Agents: explicit workflow save; edits apply only to work not started

Facts: `AdeWorkflowForm.vue` autosaves (500 ms debounce, flush on unmount) through
`useSaveWorkflow` (`workflowSaveScope`); `AdeWorkflowYaml.vue` the same at 800 ms through
`useSaveWorkflowYaml`. `SaveWorkflow` (`internal/ade/workflows.go`) rewrites the file via
`adeflow.Reader.Save` → `encodeWorkflow`/`applyWorkflow`. A task stores only `workflow_id` and the
current stage snapshot (`ade_tasks.current_stage_json`, migration 0008); `StageDone` reads the next
stage from `b.deps.Workflows.Get(id)`, the live file. So a started task mixes versions today.

Design:
1. Migration `0017_p196_ade_task_workflow_snapshot.sql`: `ade_tasks.workflow_json TEXT` (NULL =
   not started, follows the live file) and `workflow_hash TEXT NOT NULL DEFAULT ''`. Register in
   `embed.go`; guard test pattern as `0016`.
2. "Started" = the task's first run, first session, or first stage move (`StageDone`,
   `SetTaskStage`). At that moment `snapshotWorkflow(taskID)` stores the effective workflow JSON
   and its hash (sha256 of the canonical JSON, the same encoding `Reader.record` uses). `SetTaskWorkflow`
   on a started task is refused, as today's rules for a running task already are (check
   `taskworkflow.go`); on a not-started task it clears any snapshot.
3. Every reader of a task's workflow goes through `b.taskWorkflow(task)`: snapshot when present,
   else live `Workflows.Get`. Callers: `StageDone`, P192's `SetTaskStage`, `loadTaskCtx` users,
   board assembly (stage list per task), `sessionView`'s lookup source on the wire if it reads the
   workflow (P193). `current_stage_json` stays the current stage.
4. Wire: `Task.workflowOutdated bool` (snapshot hash differs from the live file's hash; false when
   not started or the live file is missing/invalid) and `Task.workflow *Workflow` only if the
   frontend needs the snapshot's stages (P192's stage picker does: send the snapshot's stages).
5. Editors: no autosave. Each editor holds a draft, shows Save (`dialog-primary`) and Discard,
   disabled when clean; Save runs the existing mutation; ⌘S saves. Leaving with unsaved changes
   (switching workflow or page) asks via `packages/workbench/src/components/ConfirmDialog.vue`.
   Remove `scheduleSave`, flush-on-unmount and the debounce; keep YAML validation debounce. The
   editor header states "Saved edits apply to work not yet started."
6. Workflow selector (`ade/v2/panel/AdeWorkflowBlock.vue`): lists live versions as now; for a
   started task with `workflowOutdated`, a small `Badge` beside the select: "updated — applies to
   new work only", tooltip naming that this task runs the version it started with.
7. Verify: Go tests for snapshot-on-start, stage moves reading the snapshot after an edit, and
   `workflowOutdated` (versioning rules interact: real logic); `ade-v2-workflows.spec.ts` (no
   autosave, Save/Discard, leave-confirm) and `ade-v2-panel.spec.ts` (indicator).

Commits: `feat(ade): snapshot a task's workflow when work starts`, `feat(ade): explicit workflow

## 6. Verification per stream, then landing

Per commit: the pre-commit hook (`bun run lint`, `bun run typecheck`) passes, plus
`go build ./... && go vet ./...` for Go changes. Once at stream end: `bun run lint:all`,
`go test -race` for touched packages, the stream's UI projects (`test:ui:studio`, `test:ui:space`,
visual where markup changed), `bun test` for touched packages. Fix every failure in the same stream,
pre-existing or not (`CLAUDE.md`). The orchestrator verifies each stream against its rows before
landing (grep for real callers, run the suites), not from the notes file alone.

Landing, after all three streams are verified:
1. In each worktree: `git rebase v2.0` (any order). A real conflict means the ownership table was
   wrong: stop and report, do not resolve by editing the other stream's file.
2. Fast-forward `v2.0` to each rebased branch in turn; rerun `bun run lint:all`, `bun run typecheck`,
   `go test ./...` and both UI suites on the combined tree.
3. `git worktree remove ../kira-v21-{a,b,c}`, delete the stream branches, push `v2.0`.
4. Orchestrator writes the result sections into `SPEC.md` from the three notes files and deletes
   the notes files in the same commit.

Then the code-review step (`CLAUDE.md` "Code review", on request): one Opus reviewer scoped to
`ba8419e..<landed head>`, findings to `docs/v2.1/plans/P185-P196-review.md` committed before one
Sonnet fixer starts; findings file deleted once fixed.
