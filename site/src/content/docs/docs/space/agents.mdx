Agents needs an authenticated `claude` CLI. Hooks ride each session's own `--settings` file. Your Claude Code settings files are never touched.

## Tasks and branches

A task owns branches across repositories. A branch is one of:

- `mine`: created here, with a name.
- `review`: another author's branch.
- `parked`: kept out of the merge order. The plan shows it as Not merging.

Task status derives from the workflow and its runs. You never type it.

Backlog items stay off the plan until you promote them.

## Base branch and stacking

A task picks its base branch per repository: the repository's main, any branch, or another planner branch to stack on. A headless run rebases the branch when the base changes. **Change base…** and **Rebase onto** start that run.

No rebase starts on its own when a base moves.

## Workflows

A workflow is a YAML file in the `workflows` folder of the Space home, `~/.kira-space/workflows`. No workflow ships preinstalled. Sample files live in `apps/kira-space/internal/adeflow/testdata`.

The app watches the folder. A broken edit keeps the last valid version and reports the line.

A workflow holds stages. A stage has a kind:

- `user`: you do the work.
- `agent`: Claude Code runs each step headless.
- `script`: one shell command, no steps.

An agent step or a script stage runs `once`, for `each repo`, or `only <repo>`.

### Results and routes

An agent step can declare 1 to 12 results. Each result has an `id`, an `ok` flag and a `next` route:

- `next`: the next step.
- A step id: that step. A later step skips the steps between. An earlier step makes a loop.
- `end`: the end of the stage.
- `stop`: stop the task. Only a result that is not ok can use it.

A route to the step itself or an earlier step is a return. The step's `max_returns` limits them per task, stage, step and branch. The count survives restart and Resume.

- Agent step: 1 to 10, default 3.
- Review step: 0 to 10, default 0. `0` means no limit.

At the limit the run stops with `Stopped: <step> reached its limit of <n> returns.` Retry the step to continue.

Older files still load. `retry N` becomes `max_returns: N`. A result `max` on a loop route becomes the largest value. `max_returns` with `on_failure`, or with a result `max`, is refused. Saving never writes a result `max`.

A run that ends with no report takes the step's `failed` result. A step without declared results stops on failure, or follows its `on_failure` rule: `stop`, `retry 1`, `retry 2` or `back:<step id>`.

### Graph editor

The Workflows page edits a workflow as a graph or as YAML. Save with `Cmd+S`. Nothing saves automatically. Leaving with unsaved edits asks first.

Edit on the canvas. `+ Step` in a stage adds a step. `+ Add stage` under the graph adds a stage. The `⋯` menu on a stage has Add step, Add stage after, Move up, Move down, Skip and Remove. The `⋯` menu on a step, or a right click, has Add step after, Make start and Remove. Select a step to edit its fields, including **Max returns**, in the inspector.

A task follows the live file until its first run, session or stage move. After that it keeps a snapshot, and an updated file applies to new work only.

### Review steps

A step with a `review` block waits for you instead of running an agent. Put it after the step that wrote the code.

```yaml
- id: review
  name: Review
  runs_on: each repo
  timeout: 1h
  review:
    send_to: implementer
  results:
    - id: approved
      ok: true
    - id: rejected
      ok: false
      next: stop
```

`send_to` is `implementer` or `new`. `implementer` resumes the Claude session of an earlier agent step. `new` starts a review agent that keeps its own session across rounds. The optional `implementer` key names that step. Empty means the nearest earlier agent step. A review step takes no `prompt`, `allowed_tools` or smart script. `timeout` stays required.

The run enters the `review` state and the board shows **Waiting for review** and a **Review** item in Needs you. Open **Review code**, comment on the diff, then pick **Send to agent** in the **Workflow review** tab. The tab also holds the route and the finish buttons.

A comment is a **Change** or a **Question**. One send is one headless round. The agent answers each open comment with `reply_review_comment` and may commit. An answered comment turns **Addressed**. Reopen one and send again for another round. A round runs one at a time. A round resumed on the `implementer` runs with that step's `allowed_tools` plus `reply_review_comment`, so list `Edit` there if answers may change files. A `new` agent gets no `allowed_tools` list.

Finish with one of the step's results. The note you type (up to 2000 characters) reaches the step the result routes to. Open comments ask for a confirmation first.

If the implementer session is gone, the round moves to a new review agent and the tab says so. A round that a quit interrupted shows **Resume**. The review run itself stays in `review` across a restart.

### Sandbox

On macOS every agent step runs under a Seatbelt sandbox. A step without a `sandbox` block gets the default: write the branch worktree, network on.

```yaml
sandbox:
  access: write        # write | read | off
  read: [~/notes]      # extra read-only folders
  allow: [~/go]        # extra read-write paths
  network: true        # false: Claude API only
```

- `write`: writes the worktree and the scratch folder. Reads the worktree, tools and the `read` list. A home file outside them fails.
- `read`: same reads, no worktree writes.
- `off`: no sandbox, no other keys. The step badge shows `No sandbox`.
- Paths are absolute or start with `~/`. Keychain paths are refused.

Git inside the sandbox can stage, commit, amend and rebase in place. It cannot create branches, worktrees or tags, change config or hooks, write other branches, or delete objects. Use `request_branch` for a branch. Use `fetch_remote` and `push_branch` for the network; both run in the app. `push_branch` pushes the task branch only, never a protected branch, and a read step cannot push.

The SSH agent is blocked. With `network: false` only the Claude API is reachable. The macOS keychain is blocked unless you turn on **Keychain access for sandboxed agents** in Settings, Claude Code. Without it Claude must sign in from the environment: run `claude setup-token` and export the token from your shell profile.

The run line shows a lock badge: `Write worktree`, `Read only`, `No sandbox`, or `N blocked` after denials. Click it for the policy, the first 50 blocked actions and the profile. A run that fails after a block says `Sandbox blocked <op> <path>.` Take over opens an unsandboxed session.

Linux and Windows write the profile but do not enforce it. The badge says `Not enforced`. Claude permission rules still apply; they do not stop shell commands.

## Runs

A headless run starts `claude -p` in the branch worktree. The agent reports through the `finish_step` tool. A run that ends without calling it fails with `no report: Claude ended without calling finish_step`.

A step starts automatically or waits for your approval.

A run that came back shows `↩ n/N`: returns used of the limit. A step with no limit shows `↩ n`. The chip turns red when the limit stops the run.

Each run line shows its sandbox badge. See [Sandbox](#sandbox).

### Agent tools

A workflow with `kira_space_mcp: true` gives its runs extra tools on the `kira-ade` MCP server. See [MCP tools](../../reference/mcp-tools/).

Branches and repositories an agent adds carry an `agent` chip.

## Interactive sessions

Start Claude Code in a branch worktree from the board. **Take over** turns a headless run into an interactive session. A taken-over run can still call `finish_step`.

A branch holds one session at a time.

## Review code

**Review code** opens the per-branch review in one step: `Cmd+Shift+R`.

The right pane has two tabs when the branch has a review step: **Workflow review** and **Ask agent**. Without a review step it shows the review agent only.

## Notifications

A desktop notification fires when a session finishes, a session needs input, or a background run ends. Click it to open that session or task.

Configure each kind in `Settings > Claude Code`. The same pane has **Keep this Mac awake while a Claude Code session is running**.

The status bar shows Claude Code's five-hour and weekly usage for sessions that Kira starts. Turn it off in `Settings > Claude Code`.
